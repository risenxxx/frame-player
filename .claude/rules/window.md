# window — the short form

The short form of [`docs/rules/window.md`](../../docs/rules/window.md): the modules this area is made of,
its rules one paragraph each, and the commands that exercise it. Claude Code loads this file
by itself when a file it covers is opened with Read/Edit/Write — not when one is read through
Bash, which is why `CLAUDE.md` says to read it before changing the area.

Each line is the rule; the chapter it links to is the whole of it.

## Modules

| Path | What lives there |
|---|---|
| `src/lib/chrome.svelte.ts`, `endscreen.svelte.ts`, `step-engine.svelte.ts`, `updater.svelte.ts` | What came out of the page's script. `chrome` is the window shell — fullscreen and its veil, the title bar, the window buttons, the resize edges and the idle rules; it is one module rather than two because the chrome's visibility *is* the idle state. `endscreen` is the end of a file and the skip offer, which belong together because on the last chapter one becomes the other and `Enter` answers either. Each of them takes its inputs (`chrome.overlayOpen`, `chrome.sheetOpen`) rather than importing a dialog, and each exposes an `initX()` for its standing effects — see the `$effect` rule in [rules/frontend.md](../../docs/rules/frontend.md) |
| `src/lib/window-prefs.svelte.ts`, `window-fit.ts` | Geometry persistence, the window's shape ("match video aspect ratio": the fit, the minimum and the resize constraint, in `adoptShape`), always-on-top, macOS menu check marks, and what a trackpad pinch does right now (`windowPrefs.pinch` and the effect that tells the native side). `window-fit.ts` is the arithmetic, pure and tested — `pinchResizes` included |
| `src/lib/curtain.svelte.ts` | The dark between two files: when it comes down (before mpv is handed the next file), what lifts it (the window reporting the picture settled, and three ways back besides), and who draws it — the video view's own opacity on macOS, `Curtain.svelte` elsewhere. A leaf: it imports `player` and nothing above it |
| `src/routes/veil/+page.svelte` | Black shutter window content (fullscreen transition masking). Windows only: the window is built in `create_veil` (lib.rs), not declared in tauri.conf.json, because a declared window is a web view on macOS too, which never shows it |
| `src-tauri/src/lib.rs` | Plugin registration, window/app lifecycle, commands: `initial_files`/`open_file_ready` (see "Opening files" below), `zoom_pan`, `user_mpv_conf`, `mpv_conf_set`, `double_click_time` (Win: `GetDoubleClickTime`; mac: `NSEvent.doubleClickInterval`, default 0.5 s), `hdr_status` (Win: per-monitor HDR, 24H2 ACM-aware; mac: `macos_chrome::edr_headroom` — there is no HDR on/off switch on macOS, only a *dynamic* EDR headroom that collapses to ~1.0 when SDR brightness is maxed, so `enabled` legitimately fluctuates) |
| `src-tauri/src/window_guard.rs` | Clamp window into visible monitor area at startup |
| `src-tauri/src/window_shape.rs` | The window's shape, natively. Holding it during a resize: the `window_shape_lock` command, the `WM_SIZING` subclass Windows needs for it, and the rectangle arithmetic (`hold_shape`, pure and unit-tested); the macOS half is one AppKit property, in `macos_chrome::set_shape_lock`. Which corner a live resize keeps (`keep_corner`, `held_axes`) and the report that one is under way (`say_resizing`). And getting to a new shape: `window_frame_glide`, position and size as one frame, stepped over time, with `window_video_fade` for the picture going dark around it; `pinch_frame` is where a trackpad pinch takes the window (pure, unit-tested), and `macos_chrome::watch_pinch` is the monitor that feeds it. And, on Windows, keeping mpv's child window over the whole client area while the window resizes (`cover_video`), which mpv itself does a frame late and asynchronously |

## Critical gotchas

(Numbered as in `CLAUDE.md`, which keeps the headline of each.)

6. **Fullscreen transitions**: order matters — set veil state → wait double-rAF + ~30 ms (frame must be presented) → show shutter window → `setFullscreen`. Do not "simplify" this sequence; each step masks a distinct Windows artifact.
7. **Hidden `veil` window keeps the app alive** (on Windows, the one platform that creates it) — main-window `Destroyed` explicitly calls `app.exit(0)` in lib.rs. Removing that resurrects zombie processes that swallow Explorer "open with" requests via single-instance.
10. **The window is transparent, so "nothing painted" means "desktop visible"** — mpv renders *behind* the webview, so any moment when neither party paints is a hole through the window. `videoReady`/`.player.backdrop` keeps a dark fill until mpv's VO comes up, and on macOS the NSWindow carries an opaque `#101016` `backgroundColor` for the frames before the webview's first composite — never paired with `setOpaque(true)`. On Windows the same hole opens at every live resize one layer lower: mpv draws into a child window there and moves it a frame late, so `window_shape::cover_video` keeps the picture over the client area itself. → [window](../../docs/rules/window.md)
15. **Never move the macOS traffic lights by hand — grow the title bar instead.** There is no positioning API, and setting the buttons' frames is a measured dead end. An empty `NSToolbar` + `NSWindowToolbarStyle::Unified` grows the title bar 28 → 66 pt and AppKit places the buttons itself, tracking rects included. It is removed *before* the fullscreen transition starts (`window_enter_fullscreen`; removing it inside `WillEnterFullScreen` aborted the process on macOS 26, so every `setToolbar` is also exception-guarded) and restored on `DidExitFullScreen` (**not** `Will`), visibility comes from the frontend's recorded intent rather than the buttons' own `isHidden`, and the window is forced to `darkAqua`. → [window](../../docs/rules/window.md)

## Rules

- **A fullscreen transition on macOS goes through black.** AppKit animates snapshots of the window, which catch mpv's view and the web view mid-change (a stretched picture, the title bar twice), so the content view goes to alpha 0 *before* the transition — `window_fullscreen_mask` from the frontend, an overridden `toggleFullScreen:` for every other way in — and fades back after `Did{Enter,Exit}FullScreen`, with `MASK_CEILING` as the way back. The title bar (its container's alpha) and the rim (the shadow) go with it. → [window](../../docs/rules/window.md)
- **The mini player is a window mode, and every other size mode has to know about it.** With `wid` embedding there is no true picture-in-picture to reach for — the video is a child view of our own window — so it is a small … → [window](../../docs/rules/window.md)
- **"Match video aspect ratio" is a standing constraint, not one resize, and it is on by default.** The window is fitted once per new shape — around its own center, position and size as one native frame, over `MORPH_MS` — its minimum becomes the smallest size *of that shape*, and the platform holds the shape while an edge is dragged (`contentAspectRatio` on macOS, where the ratio outranks the minimum; a `WM_SIZING` subclass on Windows). The shape is the **decoder's** — `video-params/{dw,dh,rotate}` with `video-crop` applied (`decodedShape`) — never the VO's `dwidth`/`dheight`, which keep reporting `force-window`'s 960×540 field while a file resumed mid-way decodes up to its position. It is one choice of three (`WindowFit`: off / aspect / size, stored as `fitToVideo` + `videoSize`); `size` changes only which size that fit aims for — the picture's own, 100 % and shrunk into the screen, once per size — never the hold; 100 % is a point on macOS and a device pixel on Windows (`videoPixel`). → [window](../../docs/rules/window.md)
- **The web content is a frame or two behind the window and pinned to its top-left corner**, so a live resize keeps that corner wherever the grip allows — a resize the pointer is doing, never a fullscreen transition, which AppKit reports as one too (`keep_corner`, through a `setFrame:display:` added to tao's window class — under a ratio AppKit grows the following axis around its center), and everything drawn over the picture is away for as long as the window's frame is changing (`chrome.unsteady`: the two bars through `idle`, every other surface through the `.afloat` class in `app.css`), whatever the "hide the controls" setting says; letting go of the edge counts as a mouse move. → [window](../../docs/rules/window.md)
- **A trackpad pinch is the window's size, and the decision is native.** WebKit hands the page a `gesturechange` *and* a Ctrl+wheel (`deltaY = −100·magnification`) per magnify event and drops the modifiers on the way, so a local `NSEvent` monitor (`macos_chrome::watch_pinch`) is the only place ⌥+pinch and a pinch can be told apart; it decides once per gesture from what the frontend last said (`pinchResizes`: the setting, not fullscreen/mini/start screen/covered — **not** maximized, which on macOS is any window at the zoomed frame, via `window_pinch_mode`) and ⌥ off the event, and sets `pinch_frame` of the start frame × the running scale in the same main-thread turn, a 24 pt margin short of the screen: at the visible frame itself the window *is* zoomed, the next pinch went to the zoom and the shell refused to drag it. **Whole points, and never a frame the window already has**: a fractional frame at the current height went through AppKit's own `_setFrameCommon:` and came out NaN (macOS 26.5.2, three crashes). Windows unchanged. → [window](../../docs/rules/window.md)
- **A file change goes through black**: dark before mpv is handed the next file (`raiseCurtain`), lifted over the window's morph once the window reports the picture settled, with three more ways back. On macOS it is the video view's own opacity — a fill in the web view is late at the window's growing edge. → [window](../../docs/rules/window.md)
- **Floating over another app's fullscreen is decided by the window's class, not by its level — and every plausible guess about it is wrong.** "Always on top" only lifts a window above the others *on its own space*, and a … → [window](../../docs/rules/window.md)
- **Leaving fullscreen on macOS hands the keyboard to the wrong view, and the player takes it back.** tao's exit path makes its own content view first responder; `refocus_web_view` gives it to the web view `MASK_SETTLE` after `Did…`, never from the notification (tao's reset lands after it). → [window](../../docs/rules/window.md)
- **The HTML resize edges are Windows-only, and on macOS they were actively harmful.** `startResizeDragging` reaches `drag_resize_window`, which on macOS is a stub returning `NotSupported` — and Tauri discards the error (`let _ = … → [window](../../docs/rules/window.md)
- **Window prefs & the macOS menu bar**: settings live in `localStorage` (`frameplayer.window`: remember geometry / fit to video / always-on-top), restored **before** `show()` — restoring a visible window reads as a jump. → [window](../../docs/rules/window.md)
- **Hiding the cursor must trail the native button hide, never race it — and a timer is not a way to trail anything.** `set_buttons_visible` asks AppKit for a title-bar relayout, which resets the window's cursor rectangles and puts the arrow back; the flat margin that used to cover the IPC, the main-thread hop and the relayout is now a … → [window](../../docs/rules/window.md)
- **Hiding the cursor on idle has exactly one exception, and it is a corner, not a band.** `.player.nocursor` applies in windowed mode too — there is no fullscreen condition. The corner is a latch on the last mousemove, and only the native side can … → [window](../../docs/rules/window.md)
- **The chrome's hover flags are edge-triggered, so each one needs a way back.** `oscHover`, `barHover` and `chipHover` hold the bars up under a resting pointer, and one lost `mouseleave` pins the interface on screen for the rest of the session — which is why `pokeUi` … → [window](../../docs/rules/window.md)
- **Coming back to the window counts as a mouse move.** A space switch or an activation makes AppKit put the arrow back without sending a mousemove, and nothing re-applies `cursor: none` until the mouse is touched — so `wakeEffect` … → [window](../../docs/rules/window.md)
- **The click that brings the window forward is not a command, and the window takes it anyway.** `acceptFirstMouse: true`, or an inactive window cannot be dragged (every drag goes through the webview) and a double click on it lands as a pause; `ActivationGate` then swallows the picture's click for the system's double-click interval after activation, so that click pauses nothing and the double click still reaches fullscreen. macOS only. What the click does at all is the `videoClick` pill (both / fullscreen only / pause only). → [window](../../docs/rules/window.md)
- **Whether the chrome hides is the viewer's setting (`always`/`fullscreen`/`never`), and it is a term of `chrome.idle`, not a gate in front of the bars** — so the traffic lights follow it for free; the mini player counts as fullscreen. The cursor is a second setting reading `pointerIdle` (the idle *before* that setting), so it can go while a pinned bar stays — but never from over a bar, a dialog or a held seekbar. → [window](../../docs/rules/window.md)
