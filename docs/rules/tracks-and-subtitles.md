# Audio tracks, subtitles and content languages

Choosing a track and remembering the choice, subtitle search and placement, and the languages of the film as opposed to the languages of the interface.

Part of the rule book: [`CLAUDE.md`](../../CLAUDE.md) carries the one-line
version of each rule here, this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.

- **A subtitle found by the file's hash and one found by its title are different results, and the panel says which.** The hash (size + every 64-bit word of the first and last 64 KiB) identifies a *release*, so what comes back is already in sync; a title match is a guess about which rip you have and may be off by seconds. Conflating the two is what makes subtitle search disappointing elsewhere, so which one produced the list is reported and shown as a sentence. **The two searches must therefore be separate requests, and the verdict must come from the results rather than from the request** — this is the bug the first version shipped with. Sent together, the API answers with the **union**: measured, a hash alone returned 11 subtitles all flagged `moviehash_match`, the same hash plus an unrelated query returned 50 with still only those 11 flagged. The panel then announced "matched by the file itself" over a list of unrelated films — a file called `master.mkv` (an episode of a series) was offered *Master and Commander* under that heading. So: hash first, alone, with `moviehash_match=only`; the typed title only if that came back empty; and `match_kind` derived by looking at what arrived. The empty hash result is itself worth saying — "OpenSubtitles has nothing for this exact file" is a fact about the file, and it is what the viewer needs in order to stop trusting the list below it. Measured against the live API on 2026-08-03, and three of the four facts contradict what our own research assumed: **the rate limit is 5 requests per second**, not 1; **searching is not quota'd at all** while downloading is; **downloading works with no user account** (5/day per IP, and 100/day for a consumer marked *Under Development* — an anonymous `POST /download` returned `remaining: 99`), so signing in raises the ceiling rather than unlocking the feature. **Which bucket is being charged is in the response**: `uk` reads `app_ud_<consumer>` for a key in development — one allowance shared by everyone using that build — and `app_<consumer>_<ip>` for a released one, which is the per-IP allowance. Running a production key dry confirmed both the model and the refusal: five downloads answer 200 with `remaining` counting down, the sixth returns **HTTP 406** with `remaining: -1`, a human-readable `message` and `reset_time`. 406 is the daily quota and 429 is the rate limit — collapsing the two into "request failed" throws away the only thing worth telling the viewer, which is when it comes back and that signing in moves the ceiling; and the API's own relevance sort is not usable — searching "interstellar" put a documentary *about* the film first, hence the client-side sort of hash matches before download count. Two consequences in the code. A hash that matches nothing is the normal case for anything but a well-known release, so an empty hash search silently retries by title — free against a 5/s limit, and the difference between an empty panel and a usable list. And the key is the *application's*: OpenSubtitles bans apps that make their users register their own, so it ships with the binary, cannot be a secret, and is looked up in an order (`app_data` file → dev file → compiled-in) whose only purpose is that a revoked key can be replaced through the signed R2 channel without a release — the real cost of a leak is availability, not privacy. **There is no duration anywhere in the API** — verified by dumping a whole result and walking every key of the subtitle, its `files[]`, its `feature_details` and the `/features` record — so "will this one fit" is answered by `fps` instead, flagged when it differs from `container-fps` by more than 0.1: a 25 fps subtitle on a 23.976 fps file does not start late, it drifts further out the longer you watch, which is the failure viewers hit and cannot diagnose. An episode's own `title` is usually the literal "Episode 3", so episodes are labeled from `parent_title` + `season_number`/`episode_number` or a list of them says nothing. **Those two numbers are also what reaches a series at all**, and without them the feature simply misses: measured, `query=the day of the jackal` returns the **1973 film**, the same query with `season_number=1&episode_number=3` returns **122 subtitles for the 2024 series**, and `year=2024` is not a substitute — it answered with 10 000 results of "Empty Movie (SubScene)". They come from the file name (`parseEpisode` in format.ts), which also yields a far better query than the whole name. Only unambiguous markers are read — `S01E03` and its spacings, the spelled-out forms in both languages, and `1x03` bounded by non-digits so `1920x1080` cannot become "season 20, episode 10" — because a bare number in a release name is never an episode: `1080p`, `2024`, `x264` and `5.1` all sit exactly where a naive parser would read one. The panel says which season and episode it took, or a list of episodes appearing for a two-word query reads as the search guessing. **Removing a subtitle is two different actions, and which one applies is not a preference.** An embedded track cannot be removed at all — it lives in the container, taking it out would mean rewriting the video, and mpv's `sub-remove` refuses it anyway — so the × appears for external tracks only (`track-list/N/external`, with `external-filename` beside it). For an external one, detaching is the queue's gesture and would be enough, except for a consequence of our own naming: a subtitle we downloaded is called `<video>.<lang>.srt` *so that* `sub-auto=fuzzy` finds it next time, so detaching without deleting means it is back at the next launch and the removal reads as broken. Hence the file is deleted too — **but only for files we created**, recorded in `frameplayer.subs` (privacy-gated like the positions, since the path is named after the video). A subtitle the viewer made, corrected or dragged in is only ever detached; an unrecorded path is treated as theirs, which is the safe direction to be wrong in. `subs_delete_file` checks the extension as a second lock: a delete-by-path command that accepts any path is one wrong argument away from removing the video. **Signing in is an upgrade, never a gate**, and the code is shaped that way: downloading works signed out, so nothing checks for an account before trying, and what an account buys is the ceiling (5 a day per IP → 10–1000). What is stored follows from what losing it costs — the **token** goes into the OS keychain by default (it expires by itself, is revocable from the site, and lasts 24 h with no refresh endpoint, so without keeping it the viewer signs in again for practically every film), while the **password** is stored only behind an explicit opt-in, because it is the most sensitive thing this app will ever hold and is probably reused elsewhere; what it buys is silent renewal. Neither ever touches localStorage. Three details that are easy to get wrong: `/login` has its own rate limit of **1 request per second** where search allows 5, so nothing may retry in a loop; a **VIP account is answered by a different host**, handed over as `base_url` at login and used for everything afterwards, or a 1000-download account quietly behaves like a 20-download one; and a keychain refusal is **reported rather than swallowed** (`keychain_failed`) — on macOS the ACL is bound to the code signature, so dev builds re-prompt whenever the signature changes, and a session that silently lasts only until quit is worse than one that says so. The downloaded file goes beside the video as `<name>.<lang>.srt` so mpv's `sub-auto=fuzzy` finds it by itself next time, with nothing remembered on our side; a read-only folder falls back to the cache directory, and an existing file is never overwritten.
- **Closed captions are a subtitle track that isn't in the container.** `eia_608`/`eia_708` captions ride inside the video stream (SEI), so `ffprobe -select_streams s` shows nothing while mpv lists `--sid=1 (eia_608)` — do not conclude from ffprobe that a file has no subtitles. Two consequences the player has to live with, both inherent to the format rather than bugs in our code: captions are positioned on a 15×32 character grid, so the text is indented and off-center by design (the decoder literally emits leading spaces); and the decoder is stateful — roll-up/paint-on modes build the screen over many packets — so seeking into the middle of a caption leaves residue. This player seeks harder than stock mpv, which compounds that residue into captions from several scenes stacked on top of each other, hence `sub-clear-on-seek=yes` in `initialOptions`. IINA shows the same smear on the same file, so do not go looking for the cause in our render path. Such a track carries no title and no language, so `loadTracks()` names it from the codec — otherwise the menu offers a bare "Track 1" with no hint of what it is.
- **The subtitles get out of the control bar's way, and `sub-pos` is the only lever measured to work.** While the chrome is up the last line of dialogue sits behind the seekbar — exactly while it is being read, since what raised the bar was the viewer's own hand. `sub-shift.svelte.ts` lifts it by the bar's measured height, as a percentage of the *window* (which is what `sub-pos` speaks, so the device scale cancels out), and the height is `offsetHeight` on the `.osc` element rather than a constant: the mini player gives it less padding, and the bar is translated 10px down while hidden, which a bounding rect would report and a border-box height does not. `sub-margin-y` would be additive and need no base at all, but nothing here has established that it survives ASS override, while `sub-pos` reaching ASS subtitles is already measured (`sub-ass-override` defaults to `scale`) — and being wrong about it is silent, since the subtitles simply do not move. **The lift is the bar's height minus where the subtitle already sits**, and leaving that term out is the mistake this shipped with first: mpv holds subtitles `sub-margin-y` above the bottom edge, in "scaled pixels" of 1/720 of the window, so the two clearances added and left a whole scrim's height of empty picture between the text and the controls. It is read from mpv rather than assumed to be 22 (it is an option somebody's mpv.conf may set) and it cannot be a constant in pixels at all, since it scales with the window — 33px at 1080p, 66px at 4K; it is fetched once on `player.ready` rather than lazily beside the base, or the first appearance of the bar would be a two-step move. It is only an estimate for ASS, which takes its margin from its own style, but both live in the same 10–30 range against the same 720 reference. What is left is an 8px gap, which deliberately does **not** clear the scrim: `.osc::before` is drawn in the webview and therefore lies *over* mpv's picture, reaching 44px above the controls, so a subtitle there carries about 0.18 of black — a slight dimming against its own outline, where clearing it would cost 44px more. Two rules follow from `sub-pos` being the viewer's setting as well as ours. The base is **re-read from mpv on every apply**, never remembered across a session: the settings slider writes `sub-pos` live and directly, so whatever it last wrote is the truth. And the shift **stands down while a dialog is up** (`chrome.sheetOpen`), which is what guarantees that slider can only ever be dragged against an unshifted value — otherwise a position dialled in there would be measured from ours and shifted again on top of itself when the sheet closed. Writes are serialized through one promise chain, because restoring the base and reading it back are the same property and a restore in flight would be read as the base by the apply behind it. The move is instant against the bar's 0.25s fade: mpv has no animation for a property, driving one from here would be ~15 writes on its core thread per fade, and going first reads as the subtitles getting out of the way, which is what they are doing.
- **A remembered track is a description, not an id, and its scope is the folder.** Track ids are positions inside one file — the Russian dub that is #2 in episode 1 is routinely #3 in episode 2 — so a choice is stored as `{lang, title, codec, forced, index}` and resolved against whatever the next file turns out to have. Resolution is **scored, not compared for equality**, because not one of those fields is guaranteed: releases exist with languages and no titles, with titles and no languages ("Rus"/"Jap" as names), and with two same-language tracks separated only by codec. Language +100, title +60, codec +12, a forced/full mismatch −50 (a forced track carries alien dialogue, not the script — never a silent substitute), position +5 as a tiebreak only; below a floor of 60 nothing is applied at all and mpv's own `alang`/`slang` stands, which is the right answer for an episode that simply has no Russian dub. Language codes are normalized through a 639-2→639-1 table rather than compared by prefix, because `jpn` and `ja` share one letter. The choice is written to **two** scopes: the file (what was playing here) and its **folder** (what to look for next door) — a folder is what a season is and what the play queue is already built from, where a global memory would carry an anime's Japanese track onto an unrelated film. **A torrent's folder is its info hash**, and reading it as a stream instead cost the feature exactly where it is wanted most: an episode plays from a loopback URL, so `isNetworkSource` was true and both halves of the folder scope were skipped — every episode of a season an island, a dub picked on the first forgotten by the second, with mpv's `alang` then taking the first track of the right language, which on a release carrying seven Russian dubs is reliably the wrong one. `folderScopeKey` is that question asked once for both call sites (it had been spelled out at each, so the pair could disagree, and a scope guarded on two sides is only as good as the looser one); it answers `torrent:<hash>/` for a torrent, the directory for a local file, and null for a site, which is the case the original guard was right about. A better match may still arrive after the first one is applied (external subtitles land a beat after `file-loaded`), so the pending restore keeps the score it acted on and re-applies only on a strictly better candidate, until its deadline or a manual pick clears it. Entries written before this carried plain ids; they are still read, exact in the one file they came from.
- **Restoring on resume has two traps.** The chosen tracks live in `frameplayer.tracks`, separate from `frameplayer.positions` because those entries are *deleted* past 97 % and a dub choice should outlive finishing an episode; only explicit picks are recorded, since mirroring mpv's own auto-selection would freeze it against later `alang`/`slang` changes. Applying the choice cannot be a one-shot on `file-loaded`: external subtitles found by `sub-auto` appear a beat later and setting `sid` to an id that does not exist yet silently selects nothing — hence the `$effect` that waits for the track to show up, with a deadline so it cannot hijack a manual pick made in the meantime. **But it must also run once immediately, and for two separate reasons.** The race: the pending restore is a plain `let`, so arming it triggers no effect — the effect next runs when a track list *changes*, and if this file's list finished loading before `file-loaded` reached us, no further change is coming and the restore silently never applies. The delay: mpv has already selected a track by its own `alang` and is decoding it, so every millisecond before the switch is a moment of the wrong dub, and there is nothing to wait for when the list is already there. Both halves call one `applyPending(audioList, subList)`, which takes the lists as **arguments rather than reading them inside** — a bare `void player.audioTracks` to register the dependency is the shape that has caught this project before, since an expression statement is what a compiler or minifier is entitled to drop. Separately, a resume seek must carry the knob with it, and that takes **both** halves of the fraction. `seekOnResume` sets `seekValue` optimistically and holds it with `seekSettling` (exactly as a drag release does), because otherwise it stays at zero until mpv reports the new position — a second on a 4K file — and then jumps across the bar in full view. But the knob is drawn as `seekValue / duration`, and `duration` only arrives once mpv has opened the file, which is *after* the OSC is on screen — so fixing only the numerator still leaves a visible frame at the far left. `primeResume` therefore fills both from the history record (the same numbers the "resuming" popup prints) at `beforeLoad` time, and `barDuration` hands over to mpv's own the moment it has one. Display only: seek maths must keep using `player.duration`, since you cannot seek in a file whose length is still a guess.
- **The language of the interface and the language of the film are different questions, and conflating them was a bug with a name.** Every language choice in the player used to offer exactly two — `alang`/`slang` in the settings, and the subtitle-search filter — which was never a decision about languages: it was the *translation set* leaking into content preferences. There are two translations because there are two; what is being watched has nothing to do with that, and anyone with Japanese audio and Polish subtitles was simply not served. `languages.ts` is the fix and is **one table**: 639-1 code, the language named in itself, and the 639-2 spellings. Everything else is derived from it — `LANG_ALIASES` (which the remembered-track scoring uses to know `jpn` and `ja` are one language), `mpvLangValue`, `parseLangList`, `searchLanguages` — rather than kept as a second copy that drifts, which is exactly what the old alias map beside it had become. Four rules the code depends on. **Each language is named in itself**: someone hunting for Polish subtitles is looking for "Polski", and that also keeps 60-odd languages out of the `t()` dictionary, where they would be 120 strings saying the same thing and where the one entry a viewer needs is the one nobody translated. **A chosen language expands to all of its spellings, adjacent** — `--alang` is an ordered priority list, so `ja,jpn,en,eng` means "Japanese however it is tagged, else English", while grouping by spelling would let an `eng` track beat a `jpn` one. **The list is derived from the mpv.conf line, never stored beside it**, which is what makes a value someone typed by hand show up correctly and why nothing needed migrating: the two values this dialog used to write, `rus,ru` and `eng,en`, parse back to exactly `[ru]` and `[en]` (tested, along with the round trip, the B/T collapse `ger,deu,fre` → `[de, fr]`, and unknown tags being *kept* — the line is theirs and silently dropping an entry would change what mpv selects). And **search is ranked, not filtered in table order**: prefix-matching codes puts near-misses first — measured, typing `ru` matched Romanian ahead of Russian through its own `rum`. The control is a new `SettingDef` kind (`langs`) rather than a pill row, because `.segmented` picks one of a few *named* values and this is an ordered list drawn from sixty; chips carry the order, clicking one promotes it to preferred (order is priority, and without that the only way to change it is to remove everything above and re-add, which appends and therefore does not even work). The subtitle-search filter is those same preferences plus "любые", and it reads them from **mpv**, not from `settingsValues` — that map is filled when the settings dialog opens and is empty until then, so the filter would have depended on whether the viewer had been into settings this session.
- **"No subtitles in a language I am already hearing" is mpv's option, not ours, and its rule is not the obvious one.** `subs-with-matching-audio` — choices `no`/`forced`/`yes`, default **`yes`** on mpv 0.41 (read out of `options.c`, not assumed, which is why `null` is the "показывать" pill). Building this ourselves would mean reimplementing `select_default_track` and then fighting it *and* the remembered-track restore. Two things about the semantics, both from the source and both different from what one would design by hand. It gates on `mp_match_lang(langs, audio_lang)` — **the whole `slang` list against the selected audio track**, not the candidate subtitle's language — so with Russian audio and `slang=[ru,en]` the answer is *no subtitles at all*, not "skip Russian and fall through to English". That is the better rule: someone watching a Russian dub does not want English subtitles, they want none. And the consequence that follows from the same line, which the hint has to say out loud: because it tests the whole list, having `en` in your **subtitle** languages means an English-audio film gets no automatic subtitles either. That is what makes `forced` the sane middle rather than a curiosity — a forced track is alien dialogue and signage, exactly what you still want in a film you understand, and it matches what the track scoring already believes (`-50` for a forced/full mismatch). One more consequence worth knowing before it is reported as a bug: an external subtitle found by `sub-auto` is gated too, so with `no` a `.srt` sitting beside the video is not auto-selected when the audio matches. A subtitle downloaded through the OpenSubtitles panel is unaffected *that* session — `attachTrack` uses `sub-add … select`, which is an explicit pick — and only meets this rule on the next playthrough.
