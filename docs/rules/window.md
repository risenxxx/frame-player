# The window: chrome, fullscreen, the mini player and the cursor

The transparent window and what must always be painted into it, the macOS title bar, the mini player mode, geometry persistence and the idle rules.

Part of the rule book: [`CLAUDE.md`](../../CLAUDE.md) carries the one-line
version of each rule here, this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.
The *why* behind it — what was tried, what was measured — is in
[`../macos.md`](../macos.md).

- **The window is transparent, so "nothing painted" means "desktop visible"** — `.player` is transparent on purpose (mpv renders *behind* the webview), which makes any moment when neither party paints a hole through the window. Hiding the start screen (`showEmpty = false`) must therefore never be conflated with dropping the background: at launch with a file that flag flips before `init(mpvConfig)`, so the window was shown see-through until mpv's VO came up. `videoReady`/`.player.backdrop` keeps a dark fill until mpv paints. Erring long is free (mpv's own field is black underneath); erring short shows the desktop. The same hole exists one layer lower and *before* any of our code runs: on macOS the frame view draws the traffic lights the instant the window is ordered in, while the webview's first composite is a frame or two behind — so the buttons appear over bare desktop. Fixed natively in `macos_chrome::apply` by giving the NSWindow an opaque `#101016` `backgroundColor` (it sits below both the mpv view and the webview, so it only shows where nobody painted). Do **not** pair it with `setOpaque(true)` — that costs the system's rounded corners and edge shadow. Related: the window-appear animation is disabled via `setAnimationBehavior(None)`, which dates from when traffic-light placement lagged AppKit by a frame; that is fixed (see the traffic-lights rule below), so the line is now a taste choice rather than a workaround.
- **Never move the macOS traffic lights by hand — grow the title bar instead.** There is no positioning API (the buttons belong to the private frame view), so the obvious approach is to set their frames and re-set them whenever AppKit puts them back. That was built, in full, and it is a dead end. Three measured reasons, worth keeping because each one costs a day to rediscover: AppKit resets the buttons on every title-bar relayout and the causes cannot be enumerated (`setTitle` alone does it every time, and a container view of our own does not stop it); **position is only half of moving a button** — the ×/−/+ glyphs come from `NSTrackingArea`s AppKit lays out from its own model of where the traffic light is, never from the buttons' frames, so moved buttons keep the hover region of unmoved ones (glyphs lighting up 7.2 pt above and left, and the zoom button, past the stale rect's right edge, not responding at all); and **that cannot be repaired** — replacing the tracking area with a correctly positioned copy of itself (rect/options/owner/userInfo are all public) fixes the geometry and kills hover completely, because AppKit keys on the identity of the area *it* created, leaving glyphs that appear only while a button is held. What works instead is to change the title bar and let AppKit do the rest: an empty `NSToolbar` + `NSWindowToolbarStyle::Unified` grows it 28 → 66 pt, and AppKit itself places the buttons at (19, 33) with tracking rects to match — measured stable in the window, across resizes, after `setTitle`, and in fullscreen, where they keep the system's own placement and hover (which is exactly how Spotify behaves). It needs no per-relayout maintenance at all: `macos_chrome.rs` lost ~185 lines, a `CFRunLoopObserver`, a custom `NSView` subclass and a Tauri command to it. **The one thing the toolbar costs is fullscreen**: a window that has one shows it there *permanently*, as a tall opaque band whose buttons only appear once the system menu bar is revealed — instead of the thin strip that slides down on hover. So the toolbar comes off for fullscreen and is put back on `DidExitFullScreen` (measured: title-bar host 66 pt → 32 pt, buttons to the standard (9, 9) with their tracking rect). **It comes off before the transition starts, not in `WillEnterFullScreen`, and every `setToolbar` is wrapped in `objc2::exception::catch`.** Removing it from the notification crashed the player on macOS 26: AppKit posts that notification from inside `NSPerformVisuallyAtomicChange`, tearing the title bar down there made one of AppKit's own views remove a key-value observer from the NSWindow that was not registered, and the Objective-C exception unwound into tao's Rust dispatch closure, which cannot unwind it — `abort()`. The observer is AppKit's, so there is nothing of ours to balance; what can be controlled is where the swap happens and that an exception from it is caught. So `toggleFullscreen` on macOS calls `window_enter_fullscreen`, and `macos_chrome::enter_fullscreen` hides the traffic lights, removes the toolbar and calls `toggleFullScreen:` itself, **all in one main-thread turn**; `WillEnterFullScreen` gives back only the buttons it hid. Both halves of that order are measured by screen recording. Removing the toolbar without hiding the buttons first put them at the system position for three frames before the zoom began. Starting the transition with a second IPC call instead of in the same turn would let the hidden buttons and the short title bar reach the screen; in one turn they never do, and the frames match the old path exactly. The notification keeps removing the toolbar when it is still on — the green button, ⌃⌘F, and the fallback to `setFullscreen` when `enter_fullscreen` declines (no `FullScreenPrimary`, i.e. the mini player) — where the catch is what stands between an AppKit exception and a crash. Restoring must wait for **Did**, not `WillExitFullScreen` — measured, a toolbar set there has no effect at all: AppKit ignores it while the transition is in flight, and the window animates back and sits for several frames with the short title bar. That gap is visible as the buttons sitting at the system position and then jumping to ours, and there is no earlier hook to close it — so it is masked instead: hide the buttons on `WillExitFullScreen`, unhide right after the toolbar is back, and they appear already in the right place. What comes back must be the frontend's last instruction (`BUTTONS_VISIBLE`, recorded by `set_buttons_visible`), **not** the button's own `isHidden`: AppKit shows the buttons itself in the fullscreen strip, so reading them back returned an idle-faded UI with its traffic lights on, which the next idle pass then blinked away. **Recording that intent and acting on it are two different things**, and both halves are load-bearing. The frontend reports the idle state in fullscreen as well — excluding it (the rule once read `idle && !fullscreen`) left the record saying "visible" the whole time, so leaving fullscreen while idle flashed the traffic lights on and the idle effect hid them a frame later. But `set_buttons_visible` then declines to *apply* a hide while the window is fullscreen: there the buttons belong to the strip that slides down from the top edge, and the idle timer emptied a strip the user had just pulled down — including while the pointer rested on a control they were about to click. Separately: **force `darkAqua` on the window**. The frame view draws itself to match the appearance, not the background color, so under the light system theme it put a bright highlight along the window's **top edge** — far stronger than the shadow on the other three sides and obvious against the dark fill. Screenshots settled the cause: the line is identical with and without the toolbar (so not the toolbar's doing), `titlebarSeparatorStyle = .none` changes it by not one pixel, and it all but disappears under the dark appearance. Two properties it quietly depends on, both verified, both worth re-checking if the chrome changes: the 66 pt system title bar **does not swallow clicks** (anything below 10 pt from the top hit-tests to the content view, so `data-tauri-drag-region` and the HTML top bar keep working) — that follows from `FullSizeContentView` plus a transparent, item-less toolbar, and giving the toolbar items would end it; and **window geometry is unchanged** (frame == content == `contentRectForFrameRect`), so size persistence and fit-to-video do not drift by the title-bar height.
- **A fullscreen transition on macOS goes through black, because AppKit animates pictures of the window and not the window.** It stretches a snapshot of the window as it was towards the screen and cross-fades one of the window as it will be over it; mpv's view and the web view each paint on their own schedule, a frame or two behind the frame, and the snapshots catch them mid-change. Reported, intermittently and depending on where the window stood: the picture stretched tall for a moment, and the title bar twice — once at the top of the screen and once in the middle of it (the "before" picture at the window's old place). The old comment in `maskFullscreenTransition` said there was nothing to hide on macOS; that was wrong. The content view (picture and web view together) goes to alpha 0 over a black window fill *before* the transition and fades back `MASK_SETTLE` after `Did{Enter,Exit}FullScreen` (`macos_chrome.rs`, "Masking the fullscreen transition"). **Before** is the load-bearing word: the "before" picture is taken from what is on screen, and a change made in the same main-thread turn as `toggleFullScreen:` is not on screen yet — so the frontend masks first through `window_fullscreen_mask`, which returns only after `MASK_LEAD`, and every other way in (⌃⌘F, the menu, tao's `setFullscreen`) hits `toggleFullScreen:`, overridden on tao's window class to mask and send the toggle `MASK_LEAD` later; `Will{Enter,Exit}` masks whatever still got past both, late. It must not stay on: a failed transition is reported only to tao's delegate, so `MASK_CEILING` is the way back when no `Did…` comes. The deferred toggle and the lifts are timers in Rust that come back through `run_on_main_thread` (`on_main_after`), **not** selectors sent to the window with `performSelector:afterDelay:`: that was the first version, and neither the deferred toggle nor the lift ever arrived — the first request went black and did not change, the second one went fullscreen and stayed black for good, ceiling included. A dev build traces every step of the mask to stderr (`mask_trace`). The mask also takes what AppKit draws itself, since the snapshots carry it and the content view's alpha does not reach it: the title bar goes by its container's alpha (`frame_chrome_shown` — `NSTitlebarContainerView`, found above the close button and checked by name), never by the buttons' `isHidden`, which three other paths already own; and the light rim goes with the window's shadow (`setHasShadow(false)`), which is what draws it. Measured on recordings: before, the zoom carried the traffic lights on the black and the title bar as a strip wider than the window; after, a plain black shape with a clean edge. Both come back when the mask lifts. What the mask cannot change is the transition itself — its shape, the space switch, its length; that would take a custom animation, which was built and dropped: AppKit sets the window's frame itself during the transition, an `animator` animation was cut short by it (the window left full-size at a half-way position), and a hand-stepped one flickered the desktop through at the edges near the end. The custom-animation alternative (`window:startCustomAnimationToEnterFullScreenWithDuration:`, which is what IINA does) was not tried yet; it would still need the mask around the edge the web content lags at.
- **The mini player is a window mode, and every other size mode has to know about it.** With `wid` embedding there is no true picture-in-picture to reach for — the video is a child view of our own window — so it is a small always-on-top window with the chrome out of the way, which is 80 % of the value out of parts that already existed. What it cost was the interactions, and each one is a trap someone would otherwise find later: **the minimum window size has to be lifted first** (`minWidth`/`minHeight` are 480×320 in tauri.conf and a smaller request is silently clamped — the window simply would not shrink, with nothing to say why), and put back on the way out; **geometry must not be captured while mini**, exactly as it is not while fullscreen or maximized, or the next launch opens a thumbnail in the corner; **fit-to-video stands down**, or the next file's aspect undoes a size the viewer chose — the fit, that is: the shape is still held while the mini window is resized, and its minimum stays the mode's own rather than the floor of a shape (see the shape rule below); **always-on-top is owned by the mode** and the pref restored on exit; **fullscreen and mini each leave the other** on the way in; on macOS the mode also **floats over other applications' fullscreen spaces** (see below); on macOS the **traffic lights are hidden outright**, since in a 420 px window they sit on the picture; and going back to the start screen leaves mini, because the button that leaves it is drawn over the video. Dragging still works without the title bar: dragging the video area moves the window, which it already did — and the window is **magnetic** there (`snapMini`, on by default, in the window submenu): dragged within `SNAP_DIST` of a resting place it goes the rest of the way, to the same padded corner it opened in. Snapping and clamping answer different questions and both are needed — snapping owns the band near an edge, clamping owns everything outside the work area, since a mini window hanging off the screen has no title bar to grab it back by. The constraint that shapes it: **a native drag runs its own event loop and never says when it ends** — it swallows the pointerup, and the move events simply stop, which is also what a hand pausing mid-drag looks like. "Stopped moving for 300 ms" was the signal once, and it pulled the window to an edge from under a hand that was still holding it. So the snap waits for **the button**, asked of the system (`primary_button_down`: `NSEvent.pressedMouseButtons` on macOS, `GetAsyncKeyState` of the primary — swap-aware — button on Windows), every `SNAP_POLL_MS` from the moment the moves stop until it is up. A move with no button behind it (the system placing the window, the glide's own steps) finds it up on the first ask and settles as before; a failed ask counts as released. The move itself is **animated from the frontend** — one `setPosition` per frame over `GLIDE_MS`, eased out, driven by elapsed time rather than a frame count so a slow round trip stretches the steps and not the animation. There is no animated `setPosition` to call instead, and a window that teleports reads as a glitch: the eye has nothing to attribute the new position to. Its exit button is **round**, and that is not a style choice — a rounded rectangle inset from the window's own rounded corner has to obey the concentric rule (inner radius = outer minus the gap), and the outer radius is not ours to know: macOS picks one, Windows 11 another, and either can change with the OS. A circle has no corner to disagree with, which is why the system's own corner controls are circles. Two things this cost that are worth stating on their own, because neither announces itself: **a window API the frontend has never called before needs its capability added** — `setMinSize` was not in `capabilities/default.json`, so the call *rejected*, and with the geometry work sitting behind a bare `catch {}` the feature entered mini chrome on a window that had not moved or resized at all. Hence the mode flag now flips **after** the geometry lands, and failures are logged: "P does nothing" is a far better bug than a mode that half-applied. And **hiding a grid item does not re-center the rest** — `.controls` is `1fr auto 1fr`, so dropping the two side clusters left the remaining one auto-placed in the first column, i.e. the mini controls sat against the left edge; `justify-content` on a grid whose columns are `1fr` changes nothing.
- **Floating over another app's fullscreen is decided by the window's class, not by its level — and every plausible guess about it is wrong.** "Always on top" only lifts a window above the others *on its own space*, and a fullscreen app is a space of its own, so the mini player vanished exactly when a small player on top is wanted; it is the one thing a system PiP panel does that an always-on-top window does not. Everything below was measured with a probe app that put labeled windows in each configuration and screenshotted them over a fullscreen TextEdit, because three rounds of reasoning got it wrong first. **The level is irrelevant**: a plain `NSWindow` does not reach the space at floating (3), modal (8), main-menu (24), status (25), pop-up (101) *or* `CGShieldingWindowLevel`, which is above everything the system itself draws. **`CanJoinAllSpaces | FullScreenAuxiliary` is necessary but not sufficient** — every probe window had it. What decides it is **an `NSPanel` whose style mask carries `NonactivatingPanel`**, and it then works at level 3; either half alone fails (a plain window with the bit does not float, a panel without it does not float). Since the window is tao's `TaoWindow` and we never get to ask for a panel, it is **promoted in place with `object_setClass`** and put back on exit — verified in both directions over a fullscreen app. That is only sound because **`NSPanel` adds nothing to `NSWindow`** (measured: `class_getInstanceSize` 520 for both, zero own ivars), so only the method table changes; the size is re-checked at runtime anyway, and a future macOS that grew NSPanel would get a no-op rather than a corrupted window. Three consequences. `TaoWindow`'s overrides are gone while promoted — `canBecomeKeyWindow`/`canBecomeMainWindow` fall back to NSPanel's defaults (**key yes, main no**) and `sendEvent:` (tao's `movableByWindowBackground` drag) is not in use here anyway. **Nothing may call `set_focusable` while mini is on**: tao looks its `focusable` ivar up by name and NSPanel does not have it, so that panics inside tao rather than failing quietly. And `hidesOnDeactivate` must be forced off, because panels hide themselves when the app deactivates and switching to the fullscreen app *is* a deactivation. The restore has its own trap: **`FullScreenPrimary`, the flag that makes a window fullscreen-capable at all, shares an exclusivity group with `FullScreenAuxiliary`** (AppKit takes at most one from each group), so it comes off while mini is on and forgetting to put it back leaves `setFullscreen` silently doing nothing — hence the whole previous state is saved and written back verbatim rather than recomputed, and restored **first** on the way out, where the awaited window calls after it travel the same main-thread queue and act as a barrier for `toggleFullscreen`, which leaves mini on its way in. What this does *not* buy is corner tucking and pinch resize; those need the private `PIPViewController` route IINA takes, which would additionally mean reparenting mpv's `wid` view into a system panel — leaving the transparency hole above open in our own window — and giving up the HTML overlay with it.
- **Leaving fullscreen on macOS hands the keyboard to the wrong view, and the player takes it back.** tao's `windowDidExitFullScreen:` puts the saved style mask back through a helper that ends on `makeFirstResponder` with *tao's* content view — winit's "if we don't do this, key handling will break", true where the content view is the one that wants the keys. Here it is not: the web view is a child of it, and from that moment every key goes to a view that forwards none, until a click on the picture makes the web view first responder again. Reported as Space doing nothing after a double click out of fullscreen. `refocus_web_view` (macos_chrome.rs) runs `MASK_SETTLE` after `Did{Enter,Exit}FullScreen`, and only when the responder is where tao's reset leaves it (the content view, or nothing) and the window is still key — a responder chosen on purpose, or a window that lost the keyboard to another, is left alone. **Not from the notification handler**: tao's reset is dispatched asynchronously out of its delegate method, so a refocus made in the handler is undone a moment later. Same shape as the toolbar's return: the fix has to land after AppKit and tao are done, not when they say they are starting.
- **The HTML resize edges are Windows-only, and on macOS they were actively harmful.** `startResizeDragging` reaches `drag_resize_window`, which on macOS is a stub returning `NotSupported` — and Tauri discards the error (`let _ = ...`), so nothing anywhere reports that the call did nothing. The eight `.rz` strips are 5px wide, sit *inside* the window at `z-index: 50` and set their own `n-resize`/`e-resize` cursors, so on macOS they took the band AppKit uses for edge resizing and turned it into a dead zone that still looked live: the arrows appeared, the press was swallowed, and the window only resized when the pointer happened to land in the system's band **outside** the frame — which reads as "resizing works sometimes". They are needed on Windows, where the window is `decorations: false` and there are no system edges at all; on macOS the window is `Titled | Resizable` and AppKit handles edges and corners, including the outside band no DOM element can reach. General shape of the trap: a platform-stubbed API plus a discarded error means a control that is present, styled and inert.
- **Window prefs & the macOS menu bar**: settings live in `localStorage` (`frameplayer.window`: remember geometry / fit to video / always-on-top), restored **before** `show()` — restoring a visible window reads as a jump. And **nothing before `show()` may wait on an animation frame**: a hidden window renders none, so `requestAnimationFrame` there simply does not call back. `settleLayout` (waiting for the webview to take the restored size) polled with a double rAF, never returned, and held the whole launch until Rust's three-second safety net showed the window — which is why "remember size and position" made the player start seconds slower, with nothing in any log. It waits on the `resize` event with a 400 ms cap now. `window_guard::clamp_to_visible_area` was written for this and was inert until now (the window was always `center: true`). Geometry is never captured while fullscreen or maximized, or it would restore as a monitor-sized window with no maximized flag. A fit (`fitToShape`) must fix the **position** too, not just the size: a window told only a size grows from its top-left corner, so one near the right/bottom edge grows off-screen. Bounds come from `Monitor.workArea` (already excludes Dock and taskbar — the old `size * 0.95` guesswork was wrong in both directions), inset by `SCREEN_PADDING`. Where the window goes inside them is the shape rule's (`placeAround`, below). The macOS menu (`macos_menu.rs`) owns no state: items emit their id to the frontend, which runs the *same* functions as the context menu, and `sync_window_menu` pushes checkmarks back. **Accelerator rule**: only Cmd-combinations may be used. A menu accelerator makes the OS swallow the key before the webview sees it, so any single-key accelerator would silently replace the `e.code` hotkey rather than complement it. **The menu bar is also load-bearing for text editing**: replacing Tauri's default menu removed its Edit submenu, and without those items AppKit never delivers ⌘V, ⌘X or ⌘A to a focused field — the link dialog simply could not be pasted into. The Edit menu is back, deliberately **without Copy**, because ⌘C is this player's "copy the current frame" and a menu item would swallow it; copying text works through the right-click menu instead, which is why `onContextMenu` and the dialog backdrops leave editable elements to the system rather than calling `preventDefault` on everything.
- **"Match video aspect ratio" is a standing constraint, not one resize, and it is on by default.** It used to be a single `setSize` when a file opened, after which any edge could be dragged into a shape the picture does not have — the setting still ticked over a window showing black bars. Three things keep it true and `adoptShape` does them in an order that is load-bearing: the window is **fitted** once per new shape, its **minimum** becomes the smallest size *of that shape* (`floorForShape`), and the platform is told to **hold** the shape while an edge is dragged (`window_shape_lock`). Maximizing, fullscreen and the system's snap layouts are left alone: each is a shape asked for by name, and none of them goes through a live resize. **What the platform does with a ratio is measured, not assumed** (a probe window and then the player itself, both driven by mouse events posted from inside the process, since nothing outside it may synthesize input here). On macOS `contentAspectRatio` binds the live resize and the zoom button and nothing else: `setContentSize` with another shape is accepted as given, so setting a ratio reshapes nothing and the fit is still ours; fullscreen fills the screen as before; and a window leaving fullscreen under a ratio it did not have going in is reshaped by AppKit itself, height kept (1137×640 came back as 853×640 for a 4:3 file opened meanwhile). **The ratio outranks the minimum size** — under a minimum of 480×320 a 16:9 window was dragged down to 480×270, because AppKit clamps the proposed size per axis and applies the ratio afterwards — which is why the minimum has to be a size of the shape before the ratio goes on (569×320 for 16:9, 480×853 for an upright clip). It goes through tao's `setMinSize` like every other minimum, so that it keeps **one owner**: written natively, `contentMinSize` outranks the `minSize` tao writes, and the mini player's own minimum would be silently ignored. (tao adds the difference between the frame and `contentRectForFrameRect` to what it is given, 34 pt of height on this window, so the system reads 569×354; the ratio still takes the window to 569×320.) There is no "none" for a ratio: it and the resize increments are one constraint, and writing the increments as a single point is how it comes off. **Windows has no such property**, so `window_shape.rs` subclasses the window and rewrites the rectangle `WM_SIZING` offers — tao does not answer that message — and both resize paths end there, since the HTML edge strips and Tauri's border helper each post `WM_NCLBUTTONDOWN` to the main window. The rewrite (`hold_shape`, pure and unit-tested): an edge drives its own axis, a corner takes whichever axis asks for the larger window so that it stays under the pointer, what is not dragged does not move, and the minimum is the floor of the shape rather than a clamp per axis. It is type-checked against the msvc target and **has not yet been run on a Windows machine**, and neither has the Windows half of the glide. **The window changes shape around its own center, as one frame, over time.** The picture is in the middle of the window and that is where the eye is; resized from the top-left corner, which is what a bare `setSize` does, a 2:1 film giving way to a square clip throws the picture sideways by half of what the width changed by. `placeAround` keeps the center and then keeps the result inside the work area, one axis at a time, so a window the screen had to shrink in height still keeps its center across. **Position and size are one native call** (`window_frame_glide`): through the window API they are two, each queued to the main thread on its own, and nothing makes them land in one frame — so there is a `setFrame:display:` on macOS and a `SetWindowPos` on Windows behind one command, stepped natively over `MORPH_MS` by elapsed time, eased in and out (the mini player's glide eases out only, because that window is being caught by an edge; nothing is holding this one). The coordinates are tao's own, undone to the letter — `CGDisplayPixelsHigh` of the main display and the window's scale factor — or the window lands a menu bar away. Measured in the player on macOS, a 2:1 film to a square clip and back: some twenty steps over 210 ms, 10 ms apart at the median and 21 at the worst, the center within a point of where it started, and in a screen recording the picture centered in the window at every step with nothing uncovered at the edges. A newer glide supersedes one in flight and starts from where that one got to; `fittedFor` and `lastFit` are therefore written **before** the window moves, since whatever looks again while it is in the air would otherwise start a second fit from the middle of the first, aiming for an area that was nobody's choice. `prefers-reduced-motion` makes it one step. What the viewer sees before it starts is the new picture standing in the old one's window, so the wait is kept short: `SHAPE_SETTLE_MS` is 40 and the five reads of the window go out together. **Where the shape cannot be had, the window is let go**: a 9:16 clip needs 480×853 before the controls fit and a 13-inch laptop has some 757 pt between the menu bar and the Dock, so `shapeFits` refuses, the fit falls back to the old clamp and nothing is held — bars beside a picture are better than a window held to a size that does not fit its screen. **The five things that had the setting turned off** (`PREFS_VERSION` 2), each one a way to be on over a window that does not match. *An upright clip got a landscape window*: `dwidth`/`dheight` are the size **before** the VO turns the picture (mpv 0.41, `vo=gpu`: a clip with a 90° display matrix reads 1280×720 with `video-out-params/rotate` at 270), so the shape is `pictureShape` of the three, and rotating from the picture menu reshapes the window for the same reason. *The window shrank for good*: a fit keeps the window's area, and read from the window each time, one upright clip the screen had to shrink became the area of every film after it — `lastFit` remembers what the fit was aiming for and uses it again while the window is still the size it was left at. *A file that changed in fullscreen was never fitted*: `fittedFor` was written when a fit was asked for, not when one landed, so a fit that stood down still marked the shape as done; it is written on landing now, and a fit that finds the window still fullscreen on its way out — the mirror flips before the transition, the system's answer after it — asks again every `FIT_RETRY_MS`. *The minimum bent the shape*: clamped per axis, a fitted size reaching 480 or 320 lost its ratio exactly where there is no room to see it. *A shape was fitted that never existed*: `dwidth`, `dheight` and the rotation are three events, hence `SHAPE_SETTLE_MS`; mpv sends them together and they land within milliseconds of each other. Two more came out of running it. **A size is not yet a picture**: `force-window` gives the VO a 960×540 field of its own — before the first frame of every file, and for the whole of a file with no picture — and `dwidth`/`dheight` report it as readily as a film, so the window was reshaped twice on opening anything that is not 16:9; what says a picture exists is the decoder (`video-params/gamma`, already mirrored as `sourceTransfer`). And **the minimum of the previous shape is in the way of the next one's size** — 480×853 after an upright clip, which no 16:9 size at that area is over. macOS takes a size under the minimum as given (measured: `setContentSize` does not answer to `minSize`), while a Win32 window answers `SetWindowPos` with its tracking minimum, the silent clamp the mini player was written around — so a fit lowers the minimum to the window's own first and `holdShape` raises it to the new floor once the size has landed; raised first, tao grows the window to meet it and the fit then shrinks it, two jumps for one. The shape only ever moves to a real value **while the file is the same** (`dwidth` goes unavailable whenever the VO reconfigures, which on a torrent is every stall), the start screen lets the window go and empties `fittedFor`, and the next episode at the same shape is *not* refitted, so a size chosen during one episode survives into the next. It is a standing `$effect` rather than a call on the `dwidth` event because the 1 s sweep repairs a mirror without calling the `property` hook. **The default reaches existing installs**: every payload carries every field, so an "off" written under v2 was the default of its day rather than a choice and is not read; one written under v3 is.
- **The web content is a frame or two behind the window, and it is pinned to the window's top-left corner — three rules follow from that one measurement.** Measured on a bare `WKWebView` in a transparent window of its own, with nothing of the player in it, during a live resize driven by posted mouse events and read off a screen recording one row of pixels per frame: a square anchored 80 px from the **left** edge is 80 px from it in every frame, whichever edge is being dragged, and one anchored 80 px from the **right** edge is anywhere from 80 to 124 px from it — the layout of up to two frames ago, drawn from the view's top-left corner. WebKit does not resize in step with the window and cannot be told to pin its stale content to another corner; making a layer larger than the window does not help either, since the content is clipped to the size it was last laid out at. So what a resize looks like depends on whether the top-left corner moves: by the bottom-right corner the bars trail the edges they belong to, which reads as nothing; by any grip that moves the corner, everything that should be standing still on the screen is drawn in two places in turn, which reads as the interface doubled. **First: a live resize keeps the top-left corner whenever the grip allows it** (`window_shape::keep_corner`). With a ratio in force AppKit grows the axis that merely follows *around its center* — by the right edge, +120 across came with +34 at the top and −34 at the bottom — and it does so whether the ratio is `contentAspectRatio` or comes out of `windowWillResize:toSize:`, so holding the ratio had given the doubling to every grip but one, where a free window only ever had it by the left and top edges. AppKit sets every frame of a live resize through the window's own `setFrame:display:`, proposed afresh each time from the frame the resize began with, so a frame rewritten there is the frame the window takes and the next proposal does not argue with it (measured in the player: by the right edge the corner stays at one position for all 63 frames of the drag; by the left or top edge only the edge in hand moves). The method is **added to tao's window class** (`class_addMethod`; `TaoWindow` overrides three methods and this is not one of them) rather than the window moved to a subclass, which would be a second user of the class swap the mini player depends on; it follows that the corner is not kept while the mini player is on, where the window is an NSPanel. Which axis follows is read from **where the pointer went down** (`held_axes`, off the event being handled when `WillStartLiveResize` is sent), not from the proposal: the first frame of a resize has been seen proposed with the following axis on its bottom edge, which from the proposal alone is the top edge being dragged, and cost a two-point jump at the start of the drag. The band in which a press counts as a corner is wider than the system's on purpose — an edge taken for a corner leaves the axis where AppKit puts it, a corner taken for an edge pins an axis the viewer is dragging. On Windows the rectangle is ours already (`hold_shape`), and the axis that follows grows from the top-left there too. **Second: the bars are away for as long as the window's frame is changing** (`chrome.unsteady`: a resize by hand, or a fit on its way) — for every grip alike, one behavior rather than one per edge, since the left and top edges cannot be had without the corner moving. The native side says when (`frameplayer://window-resizing`, **from the press on the edge**, before the window has changed — the first frames of a drag are the ones the bars trail worst. On macOS that is a local `mouseDown` monitor judging the point by geometry (`say_resizing_on_press`: 3 pt either side of an edge, a 10 pt corner — measured with posted events on macOS 26, a drag resized from 2 pt inside to 2 pt outside an edge and from an 8 pt corner inset, not from 4 or 12), because `WillStartLiveResize` is posted with the event *after* the press, the first drag or the release, so a press held still said nothing; it ends at `DidEndLiveResize`, or at a mouse-up reaching the monitor, which a real resize swallows — a press taken for one that was not costs a blink. On Windows it is `WM_NCLBUTTONDOWN` with a sizing hit-test (both the HTML strips and the border helper send it), and the default handler runs the whole sizing loop inside it, so its return is the end; not `WM_ENTERSIZEMOVE`, which a move sends too): a live resize runs in the system's own loop and the web view hears of sizes, never of a drag. They go on `--chrome-fade` (50 ms) rather than the quarter of a second idling takes, and like `tuning` this hides what floats **and nothing else** — the cursor is what is doing the dragging. **"The bars" is every surface drawn over the picture, and the first attempt at this rule was only the two that read `chrome.idle`**: the top bar and the control bar left, and the end screen stayed in the middle of the resize with its three cards, which is how it was found. The rest have nothing in common to be hidden through, so they carry a class, `.afloat`, and `app.css` has the one rule about it (`.player.unsteady .afloat`): the end screen, the loading plate, the OSD, the skip button, a tooltip, the context menu and the two chips of the top bar. A surface added later needs the class and nothing else. What does not carry it is what fills the window — the start screen, the casting screen, a dialog with its backdrop — since there is nothing under those to show instead. They come back **at the pace of the bars** (`chrome.settling`, `SETTLE_MS`): most of them have no transition of their own and were whole again in the frame the edge was let go, a quarter of a second ahead of the bars they had left with. Checked by reading the computed opacity of each during a drag rather than by eye: the end screen and both bars at zero within two samples of the first frame, and back through the same values together. It holds under every value of the "hide the controls" setting, `never` included: that setting is about a pointer at rest, and this is the opposite of one. **Letting go of the edge counts as a mouse move** (`pokeUi`), which the web view saw none of for the whole drag, so the bars come back and the setting's own timer runs from there. What this does not reach is the rest of the HTML — the start screen, an open dialog — which still doubles under a grip that moves the corner, as it does in any window drawn by a web view. **Third: the dark between two files is the video view's own opacity on macOS, not a fill in the web view** — below. **Only a resize the pointer is doing keeps a corner**: AppKit reports a fullscreen transition as a live resize too, and the event at hand then is whatever came last — the mouse-up of the double click that asked for it, a key, a message — so the corner was read off a click in the middle of the picture, and leaving fullscreen put the window back with its left edge on the screen's (measured: entering from x = 700 came back at x = 0, from every position). The `WillStartLiveResize` handler therefore records nothing unless the current event is a left mouse down or drag and no fullscreen transition is under way (`FS_TRANSITION`).
- **The picture is a child window on Windows, and mpv moves it a step late — which is the same hole as above, one layer lower.** `--wid` has mpv create a child of our window, and the only way it hears of a resize is a `WH_CALLWNDPROC` hook on *our* thread that answers `WM_WINDOWPOSCHANGED` by calling `SetWindowPos` on that child with **`SWP_ASYNCWINDOWPOS`** (`resize_child_win` in mpv's `w32_common.c`). Both halves of that are late: the message is sent once the window has already taken its new size, and an asynchronous request is *posted* to mpv's own window thread rather than carried out. So the strip the window has just grown by belongs to nobody — the web view is a frame or two behind as well, and the window is transparent, so what shows through the strip is the desktop. Measured on the shipping build, driving its thread the way a drag does (an external `SetWindowPos` **with** that same flag, so the caller does not wait for the window's thread either; both client rects sampled every ~0.07 ms): the child covered less than the window for **17.7–21.3 % of the resize**, in unbroken stretches of up to 2.65 ms, and the gap was always exactly one step of the drag — 4 px at 4 px a step, 12 at 12, 40 at 40. **The same resize without that flag shows none of it**, which is the trap in measuring this from outside at all: the caller then blocks for the whole 8–11 ms the window's thread takes, which is long enough for mpv to catch up before the call returns, and a drag never waits. What a viewer sees is two different things and the measurement separates them: mpv's swapchain is created with `DXGI_SCALING_STRETCH` (`d3d11_helpers.c`), so a child that *is* the right size shows the previous frame stretched into it until mpv's next draw — a scale nobody notices for one frame — while a child that is not the right size shows nothing at all where it does not reach, and that is what reads as a trail with the frame half-duplicated, or as a window with the desktop behind it. So the child is sized from our own subclass instead (`window_shape::cover_video`), from the parent's own messages and **synchronously**, since the posted request is the hop being removed. The rule is one line: **the video window never covers less than the window's client area.** `WM_WINDOWPOSCHANGING`, before the window changes, grows it to where the window is going and never shrinks it there, so a window that grows is never composed larger than the picture under it; `WM_SIZE`, once it has changed, sets the exact client size that message carries — which is also where a shrink lands, *after* the window, so the child is briefly larger and clipped rather than briefly smaller and see-through. The wait costs a round trip to mpv's window thread, which sits in `GetMessageW`: 1.1 ms median and 1.5 ms worst over a dozen calls, measured cross-process, against 8–16 ms of drag step. It cannot deadlock, and that is a property of the arrangement rather than luck — mpv's thread never waits on ours, because its hook runs on *our* thread and only posts. `SWP_NOCOPYBITS` goes with it: the system would otherwise blit the old client bits into the new rectangle, which is exactly what a half-duplicated frame looks like, and mpv repaints the whole surface regardless. None of it fights mpv's own hook, which still runs on the `WM_WINDOWPOSCHANGED` that follows and finds the two rects equal and nothing to do — so this replaces mpv's resize wherever the child can be found and falls back to it whole where it cannot, which is audio-only playback and any moment before the video output is up. **Measured again with the fix in, the same probe run against each build in turn: the hole is 0.0 % of the resize at every step size** — 4, 12, 24 and 40 px, with a file playing and on the start screen alike — against 17.7–21.3 % without it, and what is left is the child *ahead* of the window for 11–16 % of the resize, which is the harmless direction, since a child larger than its parent is clipped by it. That is the trap in measuring this at all, and the first verification run read as a failure because of it: a metric that asks only whether the two rects *differ* cannot see the fix, because it counts the child ahead exactly as it counts the hole. The sign is the whole result. **macOS has none of this, and the asymmetry is the explanation rather than a coincidence**: there the embedded view is ours (`patches/mpv-0.41.0-macos-wid-embedding.patch`) and carries `autoresizingMask = [.width, .height]`, so AppKit resizes it inside the window's own resize, in the same main-thread turn, and the opaque `NSWindow` background covers whatever is left.
- **A trackpad pinch is the window's size, and the decision has to be native — measured twice over, once for what the gesture is and once for what AppKit does with a frame.** What a pinch looks like from the web view, on a bare `WKWebView` and then the player's (wry leaves `allowsMagnification` off): for every `NSEventTypeMagnify` — one every ~8.3 ms, 120 Hz, a magnification of 0.01–0.13 each, a full spread about ×3–4 — the page receives *both* a Safari `gesturechange` (`scale` the running product of `1+magnification`) and a `wheel` with `ctrlKey` and `deltaY = −100 × magnification`, which is the event the zoom already reads; **the modifiers do not survive**: with ⌥ held every one of 69 native events carried it and none of the 222 wheel events on the page did, and ⌃ likewise. So ⌥+pinch cannot be told from a pinch in JavaScript, a pinch cannot be told from Ctrl+wheel there either, and the switch lives in a local `NSEvent` monitor on `Magnify` (`macos_chrome::watch_pinch`, next to the scroll-phase one): returning nil keeps both the wheel and the scale from the page (the rotate events that ride along still arrive as a `gesturechange` with scale 1 and no wheel, which nothing reads), and returning the event leaves the gesture the zoom it was. The decision is taken **once per gesture, at `Began`** — a modifier let go mid-gesture must not turn a zoom into a resize — from two halves: the frontend's, `pinchResizes` in window-fit.ts (pure, tested), which says whether the window is the picture's right now — the setting (`windowPrefs.pinch`, *resize* by default, a pill under Settings → General on macOS only), not fullscreen, not the mini player, not the start screen, and not `covered` (a dialog, the system file dialog, the casting screen: what fills the window cannot be taken away for a resize and would be drawn twice — see the rule above) — told to the native side by a standing effect in `initWindowShape` through `window_pinch_mode` whenever it changes; and the native half, ⌥ off the event. Every *no* is a *yes* for the zoom, which is right wherever the window cannot grow. **The frame is `window_shape::pinch_frame` of the frame the gesture began with and the scale it has accumulated** — never of the previous step, so spread and brought back the fingers put the window exactly where it was; and **the scale the gesture carries on is the one the window took** (`Pinched::scale`: where the floor or the ceiling stopped it, before rounding), not the one asked for — at the limit the fingers keep spreading while the window stands, and banking that surplus meant closing them paid it back invisibly before the window moved (reported exactly so; before rounding, or a slow pinch under half a point a step would be dropped every step and never add up) — about the start frame's center, in its shape, no smaller than the window's own minimum (the floor of the shape the fit wrote, applied as a size of the shape and not per axis) and no larger than the screen's `visibleFrame` less a margin (`PINCH_MARGIN`, the fit's own 24 pt), inside it, and set with `setFrame:display:` in the same main-thread turn the event arrived in: a round trip through the web view for each of 120 events a second is the lag the whole thing exists not to have (measured: ~1 ms a frame on average, 6–9 ms at worst). A pinch supersedes a glide in flight, and a superseded glide now answers **true** — it used to answer false, which sent the frontend's two-call fallback after the window the fingers had just taken; `chrome.unsteady` takes the bars away for the length of it through `say_resizing`, as for an edge being dragged, and `contentAspectRatio` does not argue with a frame it is given (the rule above). **The margin is not cosmetic, and "maximized" is not an input**: the first build stopped at the visible frame itself and took *fullscreen or maximized* as the shell owning the size — and a window pinched to the limit is at the largest frame of its shape in the visible area, which is AppKit's zoomed frame, so `isZoomed` (what tao calls maximized, for a titled resizable window) turned true, the next pinch was handed to the zoom, and the shell refused to drag the window (`onVideoPointerDown` declines a maximized one). Both from one pinch. So the pinch keeps the margin, never reaches that frame from inside, and reads fullscreen alone: on macOS maximized is a frame, not a mode, and one a pinch must be able to leave — the area passed in is widened to the frame the gesture began with, so a window that already stands past the margin (the green button, an edge drag) is not pulled back, it grows no further and shrinks in place. **Whole points, and a frame the window already has is not sent — that is the second measurement, and it cost three crashes.** On macOS 26.5.2 a fractional frame (1500.75 wide) at exactly the height the window already had, pinned against the top of the screen, went into `-[NSWindow _setFrameCommon:display:fromServer:]` finite and came out of it as `y = nan, height = nan` on the way to `_adjustNeedsDisplayRegionForNewFrame:`, whose Swift `isFinite` precondition then trapped (`brk #1`, nothing in any log — read off the registers under lldb, `d8 = NaN` for the vertical offset). The same request had been accepted as "unchanged" on the seven steps before, and only real gestures reached the failing cycle: 46 replays of the recorded magnifications, with the cursor inside, with the window key, with a mouse event of ours current, never did. Rounded and skipped, twelve real gestures and 1235 frames later nothing had, and the glide's `between` had been rounding to whole pixels all along, which is why it never crashed. The synthetic gesture that made the replays possible is in `docs/macos.md`. **Windows is untouched**: a precision touchpad's pinch arrives in WebView2 as the same Ctrl+wheel a mouse sends, nothing native tells them apart, and resizing a window by pinching is not a convention there. What is shared is the zoom's step (`zoom-step.ts`, pure, tested): a pinch zooms by `log2(1 + magnification)`, the same product the window scales by, and anything the size of a notch (40 px and up, or a line or page mode) stays the 0.1 step — every pinch used to run to the 800 % ceiling, since a gesture is 30–60 events and each was a step.
- **A file change goes through black, and the dark comes off over the time the window takes to reach its new shape.** It used to be three pictures in a row: the previous film's frame, the next film's first frame standing in the previous one's window with bars beside it, then the window moving. `curtain.svelte.ts` takes the old frame dark in `RAISE_MS` (80) **before** mpv is handed the next file — `raiseCurtain` is awaited in `beforeLoad` beside the resume, and ahead of the command in `advance` and `playEntry` — and `path` changing is the net under those for a file that reached mpv some other way, where the fade runs against the first frame rather than ahead of it. It lifts when the window says the picture has its window or is on its way there (`settled`, a hook on `initWindowShape`: `MORPH_MS` when a fit is about to move the window, zero when none is needed, said whatever the setting is), and only once the file is open (`armed`, on `file-loaded`): until then a picture reporting itself settled is the previous one. `playback-restart` makes the window look again, because a file of the same shape as the last can change none of the properties the window watches. **It must not be able to stay down**, since what it covers is a film that is playing, so it has three more ways back: a file that is open and has shown no picture (`NO_PICTURE_MS`, an audio file), nothing heard at all (`CAP_MS`, re-armed while the page says a load is under way), and the start screen. **How it is drawn is a measurement**: a fill in the web view leaves a strip along the growing edge of the window, 10 to 29 pt deep as the morph gathers speed, where the fill has not arrived and the picture shows at full brightness. On macOS `window_video_fade` fades the video view itself, which resizes in the same turn as the window, with the window's fill turned black for as long as the picture is less than whole (it is `#101016` otherwise, a visible gray next to a letterbox); recorded, the strip is gone. The view is found by what it is not — the content view's child that is not the web view — because its class is the embedder's to name. A fade that finds no view decides nothing beyond the dark it failed to make, which the web view then draws (`Curtain.svelte`, the player's first child, so that every other surface paints over it); it used to decide the rest of the session, and the first call of all, made at launch before mpv has a view, turned the native fade off before it had been tried. Elsewhere the fill is what there is, and the strip with it: **not yet seen on Windows**, where none of this has been run. The fade is quick going down and slow coming up, the bars beside a new picture being widest at the start of the morph. **A curtain that came down over no picture is `bare`**, and while it is, `chrome.unsteady` holds the bars and every `.afloat` surface back: opening from the start screen, the window is about to move to a shape not yet known, and the control bar and the "resuming" note used to come up, go at once for the move and fade back in — a blink on every open from "continue watching". Every way the curtain lifts ends it, and so does the loading plate coming up (`curtainCovered`, from the page), so a slow source is never kept waiting for a move that may be seconds off.
- **Hiding the cursor must trail the native button hide, never race it — and a timer is not a way to trail anything.** `set_buttons_visible` hides the traffic lights with `setHidden`, which asks AppKit for a title-bar relayout — and a relayout resets the window's cursor rectangles, putting the arrow back. With `cursor: none` applied at the same moment as `idle`, it was undone ~40 ms later, and with the pointer standing still nothing re-applied it, so it blinked once and stayed. (What WebKit answers with a cursor update while the pointer is still is a **style change** — which is why the class going on works at all, and why nothing brings it back once something else has overwritten it.) The tell is that it looks like a windowed-only bug while nothing in the cursor code mentions fullscreen: in fullscreen `set_buttons_visible` returns early, so there is no relayout to undo it. The first fix was `CURSOR_HIDE_MS = 200`, one flat margin covering the 40 ms button timer, the IPC round trip, the hop to the main thread and the relayout — four costs with no ceiling between them behind a single guessed number — and it was then reported as exactly what running out of margin looks like: the interface fades on idle and the arrow stays until the mouse is moved, intermittently, most often on a machine busy decoding. A margin cannot be made safe by enlarging it, so the wait is **causal** now. `window_buttons` is an `async` command that sends its result back over a `tauri::async_runtime::channel` from inside the `run_on_main_thread` closure, so its promise resolves only once `set_buttons_visible` has actually run — `run_on_main_thread` by itself returns as soon as the closure is *queued*, which is why the old call could tell the frontend nothing. `winButtonsSettled` is that promise, and `cursorEffect` waits on it before arming `CURSOR_SETTLE_MS` (120 ms) for the one cost still outstanding: AppKit resetting the cursor rectangles in its own layout pass. Two details there are load-bearing rather than tidy. The promise is read **a microtask after** the effect body, not inside it, because the effect that writes it runs in the same flush and the order the two were created in must not decide whether the cursor hides. And the wait is raced against `CURSOR_WAIT_CEILING_MS` (600 ms), because a reply lost to a stalled event loop would otherwise mean a cursor that never hides again — a worse failure than the race this replaced. Only the hiding is delayed: showing the cursor again answers the pointer moving, where any lag is felt at once.
- **Hiding the cursor on idle has exactly one exception, and it is a corner, not a band.** `.player.nocursor` applies in windowed mode too — there is no fullscreen condition. The exception is the macOS traffic lights: hovering them stops the webview from receiving mousemove, so the cursor sticks there, the idle timer fires anyway, and hiding it would be wrong because the user is working with the native popup on the green button and we cannot see it. That exception was originally the whole 48 px band across the full width on both platforms, which reads in use as "the cursor never hides in a window" — the pointer lands in that band constantly after dragging the window or using the buttons, while in fullscreen it rarely does, so the behavior looked like a windowed-vs-fullscreen difference that does not exist in the code. It is now `IS_MAC && y <= 48 && x <= 110` — and that box is a **latch**, which is the other half of the rule: it is written from the last mousemove, and the pointer stops sending those the moment it crosses onto a button, so a pointer that merely passed through the corner on its way out of the window left `pointerInTitlebar` raised and the arrow on screen for good. Nothing inside the webview can correct that, so the native side does: `set_buttons_visible` measures `NSEvent::mouseLocation()` against the buttons' real frames (with 6 pt of slack, for the popup that appears just under the green one), returns it as the command's answer, and `syncWindowButtons` writes that answer back over the flag on every call. The box is the opening bid; the reply settles it. Windows needs none of it, because the window buttons there are our own HTML and stop being hit-testable once the bar fades. Worth knowing when this comes up again: `cursor: none` cannot leak outside the window — it is a property of our document and only applies while the pointer is over our content, and re-entering the window fires mousemove, which restores it.
- **The chrome's hover flags are edge-triggered, so each one needs a way back.** `oscHover`, `barHover` and `chipHover` are what keep the bars up under a resting pointer, and every one of them is raised on `mouseenter` and cleared on `mouseleave`. `chrome.idle` is an AND over their negations, so **a single lost `mouseleave` pins the interface on screen for the rest of the session**: nothing else ever writes the flag back and no timer expires. They do get lost — the pointer crossing onto the macOS traffic lights or leaving the window through the title bar, a native window drag (`data-tauri-drag-region`) taking the mouse away mid-hover, the window changing space or application while a control is hovered, an element leaving the DOM under the pointer (the room chip lives behind `{#if wire.on}`). It is reported as the interface hanging there with the cursor nowhere near it, and the workaround people find by themselves says what it is: hover the bar and leave it again — delivering the missing `mouseleave` by hand. So `pokeUi` reconciles all three from the event it already has: one `closest('.osc, .topbar, .roomchip')` on the move target, which is the only signal that cannot be stale. One traversal for the three because they do not nest — the chip and the OSC are siblings of the bar, not children. The `mouseenter`/`mouseleave` pair stays: a *resting* pointer sends no moves, and holding the bars up under one is the entire job of these flags. The same failure reaches the chrome through `seek.dragging`, which pins it the same way: `pointercancel` is the one end of a drag that leaves no `pointerup`, so `onSeekCancel` closes it out — without a seek, since a cancelled gesture never said where it wanted to land, but with the un-pause, because the drag paused playback on its way in.
- **Coming back to the window counts as a mouse move.** Switching spaces with a gesture, or activating the window, makes AppKit rebuild what it draws — and, as with the traffic-light relayout above, that puts the arrow back without sending a single mousemove, so `cursor: none` is dropped and nothing re-applies it: after a swipe onto the player the cursor sits over the video until the mouse is touched. `wakeEffect` treats `focus` and a `visibilitychange` to visible as a `pokeUi()`: the chrome comes up, the idle cycle runs again from the top, and the class goes back on as a **style change** — the one thing WebKit does answer with a cursor update while the pointer stands still. Re-applying the class by hand would not do it, because it is already applied; nothing short of taking it off and putting it back is a change, and that is a frame of visible arrow. The cost is the bars showing for `UI_HIDE_MS` when you switch to the player, which is what touching the mouse does anyway.
- **The click that brings the window forward is not a command, and the window takes it anyway.** On macOS a click on an inactive window only activates it unless the view accepts the first mouse, and Tauri's default is not to (`acceptFirstMouse: false`). That default cost this player every first press: all of its dragging goes through the webview — `data-tauri-drag-region` on the bar, `startDragging` from the picture, `movableByWindowBackground` off in `macos_chrome.rs` — so an inactive window could not be moved until it had been clicked once, worst in the mini player, which lives beside another application. And it produced a bug with a shape: a double click meant as "fullscreen" whose first click was the activating one reached the page as a single click, i.e. a pause. So the main window sets `acceptFirstMouse: true`, and `input.svelte.ts` keeps the convention's one true half — the activating click pauses nothing. `ActivationGate` (`activation.ts`, pure, tested) swallows a click on the picture for the system's double-click interval after the window was activated; the double click still reaches `dblclick`, so a double click on an inactive window goes straight to fullscreen with no pause in between, and to pause an inactive player you click it and click again. Two signals feed it because the order WebKit delivers them in was read from its source, not measured: `document.hasFocus()` is still false at the activating click (the activity-state change is dispatched after the mouse event that caused it), and the `focus` event covers the other order and every non-click activation — at the cost of a click within half a second of ⌘-Tab doing nothing, which is visible and repeatable where a pause on the activating click was neither. macOS only: Windows delivers the activating click and the player has always acted on it there. Everything else the first press does — dragging, the controls, the mini player's exit button — is meant to work from that press; it is only the picture's own click that waits. What that click does at all is `windowPrefs.videoClick` (`both`, the default; `fullscreen`, where only the double click means anything and nothing blinks under it; `pause`, where the double click means nothing), a pill under Settings → General — the gate applies whenever the click may pause, and `onVideoDblClick` under `pause` skips its cast-click cancel too, or the one pending pause of a double click while casting would be lost.
- **Whether the chrome hides at all is the viewer's setting, and it is a term of `idle`, not a gate in front of the bars.** `windowPrefs.autoHide` (`frameplayer.window`) is `always` — the default and the behaviour before the setting existed — `fullscreen` or `never`, and `chrome.mayHide` is ANDed into `chrome.idle` itself. That placement is the whole rule: the bars, the macOS traffic lights (`syncWindowButtons` is fed `idle`), the cursor and the mini player's exit button all already read `idle`, so gating only the bars would leave one of them on the raw timer, and a visible bar over a vanished pointer is a bug, not a mode. `never` means never, fullscreen included — a setting called "never" that hides something in some mode is lying. **The mini player counts as fullscreen, not as a window**: it has no bar to leave standing, only controls drawn over a 420 px picture that is usually watched while the pointer is busy in another application, so under `fullscreen` they would cover a third of the picture for the whole film; `never` still keeps them, which is the one explicit ask. **The cursor is a second setting, and it reads the idle underneath the first.** `idle` is `mayHide && pointerIdle`, where `pointerIdle` is everything `idle` used to be — the timer, the hover flags, a held seekbar, an open overlay, a session. `windowPrefs.cursorHide` is `controls` (the default: the cursor goes exactly when the chrome does, so it follows `autoHide`), `always` (it reads `pointerIdle`, so it goes after the same second of rest **while a bar the viewer chose to keep stays up** — the combination asked for by anyone who wants the VLC bar and still no arrow over the film), or `never`. It had first been a switch that could only *keep* the cursor, on the theory that a visible bar over a vanished pointer is always a bug; that is true of the default and false as a rule, because the viewer who pins the bar is exactly the one who wants the arrow gone. What stays true in every mode is the part that made it a bug: `pointerIdle` is false while the pointer rests on a bar or the room chip, while a dialog is open and while the seekbar is held, so the cursor never vanishes from under something about to be clicked. On macOS the causal wait in `cursorEffect` needs nothing new — with the chrome kept up the traffic lights are never hidden, so there is no relayout to trail and `winButtonsSettled` is already resolved.
