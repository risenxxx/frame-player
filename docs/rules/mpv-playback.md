# Playback and mpv interop

Everything about driving libmpv: the state mirrors, the seek contract, the playlist, chapters, the picture and the audio chain.

Part of the rule book: its short form, [`.claude/rules/mpv-playback.md`](../../.claude/rules/mpv-playback.md),
carries each rule here in one paragraph (and [`CLAUDE.md`](../../CLAUDE.md) the
few that hold anywhere); this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.
The *why* behind it — what was tried, what was measured — is in
[`../architecture.md`](../architecture.md).

- **mpv state mirrors go stale** (event queue overflow drops property-change events). Toggles must use `command('cycle', [prop])`, never `setProperty(prop, !mirror)`. Mirrors are resynced every 1 s and on `queue-overflow` in `resyncState()` — **which mirrors is `RESYNC`, a `Record<ObservedName, boolean>`, so a newly observed property is a compile error until somebody says whether losing its event is survivable.** It is a table rather than a hand-written list because the mirrors split in two and the split is not obvious: the ones something re-reports anyway (a position, a buffering percentage, anything mpv sends again on the next file) heal on the next tick, and the ones that are merely *set* and then stand do not heal at all — they stay wrong until the viewer touches the thing again, which for a check mark in a menu can be never. `playlist-pos` was the one left out of the hand-written list; the same audit found `video-rotate`/`video-aspect-override`/`panscan` (worse, since `setPicture` writes the property and *not* the mirror, so those three depend entirely on the event coming back), the A–B marks, and `paused-for-cache`, whose dropped `false` leaves "waiting for data" standing over playing video with nothing left to take it down. Both paths into the mirrors now go through one `applyProperty` — the observer and the sweep were two hand-written copies of the same mapping, which is the shape the bug had: not a wrong line, a missing one, in the copy nobody reads while writing the other. The **hook stays outside** it, and that is what makes sharing safe: `hooks.property` is where the page acts on a change (flushing a position, releasing a torrent, resetting the seek probe), and a sweep must move a stale mirror without pretending the event happened — which is also why `path`/`filename`/`media-title` are deliberately not swept, since for them the hook *is* the work. One property failing no longer ends the sweep either: the reads used to sit in a single `try`, so an unavailable property early in the list — routine between files — silently skipped every mirror after it.
- **The end of a file is a moment the player owns, and that is a deliberate inversion.** `keep-open=always` (not mpv's `yes`, which stops only on the LAST playlist entry and advances silently everywhere else) parks mpv on the final frame of every entry, so advancing is ours: the end screen with previous/replay/next, a cancelable countdown, and the wrap of a repeating queue — `loop-playlist` can no longer fire it, because mpv never advances at all. Measured on a three-entry playlist: at the end of entry 1 of 3, `eof-reached=yes`, `pause=yes`, `playlist-pos` stays put. **That `pause=yes` survives a file change**, so anything that moves to another entry must unpause explicitly or the next episode opens on a still frame. Repeat-one never reaches any of this (mpv loops the file internally). The repeat control is three-state as on music services — off / all / one — mapping to `loop-playlist=inf` and `loop-file=inf`; `all` on a one-entry playlist already means "repeat this video", so no special case is needed. **The mode is our state, written to mpv and never read back**: reading it back would make `all` look like `one` wherever both properties end up set, and the value is re-asserted after `init()` because the user's mpv.conf is merged over `initialOptions` and would otherwise leave the button lying about what the player is doing. The old default was `loop-file=inf` for anyone who never touched the toggle — which meant a file repeated forever and a queue could never advance past its first entry; the migration reads a stored `inf` as `one` (a deliberate choice) and an absent key as `off`. **The end screen can be put away, and `ended` is not `shown`**: Hide or Escape (the last layer `closeTopmost` unwinds before leaving fullscreen) sets `endOfFile.dismissed` and cancels the countdown, so the final frame stays in view; `resetEnd` clears it, which means a rewind out of the ending or the next file. Enter takes the next entry only while the cards are `shown` — an offer the viewer put away is not still on the table.
- **A file's name in the queue comes from three places, and only the third costs anything.** mpv fills `playlist/N/title` from `media-title`, but **only for entries it has actually opened** — so everything ahead of the playhead was showing a bare file name until it played. The first fix is free: the fallback is `displayName()` (extension off, dots to spaces), the same one the start screen uses, rather than a raw basename. The second is `container_titles`, which opens each file's header and reads the `title` tag — `avformat_open_input` **without** `avformat_find_stream_info`, because a title lives in the header while the probe exists to identify streams. Measured on an MKV, warm: **0.10 ms** per file that way against **0.27 ms** with the probe, and a cold file is dominated by the disk either way; so naming a 300-entry folder is a fraction of a second, done once, 1.2 s after the playlist changes and never for a queue of one. Opening the queue panel reads immediately instead of waiting out that delay, which is why `openQueueMenu` now *awaits* `loadPlaylist`: fired against the previous list, the read would find nothing to do and the panel would sit on the timer it was meant to skip. What the measurement also said, and what decides the feature's worth: **most files have no title tag** — an ordinary rip held only `encoder` and `creation_time` — so this improves the minority that were authored with one, and `displayName()` is what carries the rest. Results are session-only (a Map, not a store: nothing persisted is one less place the privacy rules must be enforced) and each path is tried once, so a file without a tag is not reopened on every playlist change.
- **A queue is built from one opened file, never from several.** Dropping five files is an explicit selection and stays exactly what was given; opening a single episode is the case where the rest of the folder is wanted. `folder_entries` returns every plain file unfiltered and unsorted on purpose — what counts as a video (`VIDEO_EXTENSIONS`) and what natural order means (`Intl.Collator({numeric: true})`, which knows "ep2" precedes "ep10") both live in the frontend already, and a second copy in Rust is the kind that drifts. The opened file keeps its natural position rather than becoming entry zero: the files sorting before it go in with `loadfile … insert-at N` (mpv 0.38+; older builds throw and the queue is simply forward-only). Verified rather than assumed — `insert-at 0` on a playing file shifts `playlist-pos` 0 → 1 by itself, so what is playing keeps playing. Long folders are truncated *around* the opened file, not from the end: in a folder of thousands, the episodes that matter are its neighbours.
- **Seek flags are a performance contract, not a detail**: `hr-seek=yes` in `initialOptions` makes any seek without an explicit flag *exact*, and an exact seek costs decoding from the preceding keyframe. Measured on a 4K60 VP9 file with a 5 s GOP (mpv IPC, hwdec on): a far `absolute+exact` jump ≈ **1.9 s**, the same jump `absolute+keyframes` ≈ **0.05 s**; a nearby `relative` (still exact) ≈ 0.13 s. Crucially, that cost is a property of the **file**, not of the flag or the jump distance. Measured via mpv IPC, 30 steps of 2 s:
- **Frame stepping is mpv's, made fast in two moves, and both are undone by mpv itself when the file changes.** `frame-step.svelte.ts`, with the arithmetic in `frame-step-plan.ts` (pure, tested) and the group probe in `frame_step.rs`. Measured with mpv 0.41 on an M3 Max over its IPC, synthetic 60 s files (so absolute numbers are optimistic and the ratios are what transfer): a native `frame-back-step` is an exact seek, i.e. a decode from the previous keyframe, and costs **60 ms** on 1080p24 H.264 with 2 s groups, **160 ms** on 1080p60 H.264 with 10 s groups, **260 ms** on 1080p60 VP9 with 5 s groups, **1.0 s** on 1080p60 AV1 with 10 s groups and **1.6 s** on 4K HEVC with 10 s groups — in *software*. **In VideoToolbox the same steps cost 190 ms, 1.9 s, 1.3 s, 2.3 s and 1.8 s**: hardware decoding is 2–10× slower at a one-frame seek, and the cost is nearly flat across the group because hr-seek only drops non-reference frames. A forward `frame-step` is one frame period everywhere (17 ms at 60 fps, 42 ms at 24), which is the floor for anything shown through mpv. So: **(1) a step back takes the decoder to software for the session** (`file-local-options/hwdec=no`, measured to apply in ~10 ms with the very next step already at software speed), whenever `hwdec-current` is hardware, at any size. A 1440p ceiling shipped first, set on the synthetic 4K file where software won by 15 %; on a real 4K HEVC web release (8-bit, 23.976 fps, two-second groups) a native step back costs **130–220 ms in software against 230–410 ms in VideoToolbox**, and the ceiling's other reason — playing on in software — had already gone with the play controls giving the decoder back. **A runtime `hwdec` change queues an exact seek to the current frame** (`UPDATE_HWDEC` in mpv's command.c), and **mpv drops a `frame-back-step` sent while a precise seek runs** (`add_step_frame` checks `hrseek_active`): in the app the first step of every session left the picture where it was, so the swap waits for its own seek to land and the first step of a session pays one software decode on top. **The decoder comes back only while mpv is paused**: a decoder change re-initialises at once, and during playback the new decoder is fed the packets already in flight — the middle of a group — which a hardware AV1 or VP9 decoder fails on (`Missing reference frame`, then `Attempting next decoding method`), and mpv then keeps software for the rest of the file, since its list of attempted decoders is cleared only by the next change. A hand-over at a keyframe during playback was tried and measured clean on `time-pos` (39 ms on AV1) while leaving `hwdec-current` at `no` — the reason it is not used. So the decoder comes back **before our own controls unpause** — the play button, Space, a click on the picture and the media keys all reach `togglePlayback`, which awaits `frameStepBeforePlay`: turn forward, restore the decoder, wait for the one exact seek both queue, then unpause. That seek is in hardware and is what the resume costs, measured in the app: **1.4–1.6 s on the 1080p60 AV1 file, 0.4–0.6 s on VP9, 0.7–0.8 s on the H.264 film**, against 5–50 ms for a resume with no session behind it. The alternative was measured too and is why the wait was chosen: playing on in software costs, on the same M3 Max with no frame dropped, **25 % of a core against 10 % on the film, 33–42 % against 8–12 % on 1080p60 VP9, 46 % against 9–11 % on 1080p60 AV1, 45 % against 11 % on 1440p60 VP9** (macOS energy impact tracks the same ratios) — three to four times the power for the rest of the file, and more on a smaller machine, where it was not measured. A resume that does not come through our controls (the room, the end of a cast) cannot be waited on, so it gives the decoder back at the next pause, or with a seek made while paused, where the viewer's seek replaces the one the change queues; a step pressed while that runs waits for it. In a room the wait means this viewer starts up to 1.6 s after the others, which the reconciler absorbs like any late start. **(2) Where a step back is still slow, mpv decodes backward**: `play-direction=backward` decodes the group once into its reversal queue and a play-mode `frame-step` then walks back one frame period per press. Entering costs 1.3–2× one native step (90 ms, 480 ms, 530 ms, 1.95 s, 3.2 s on the five files; 20–60 % more with an audio track) and turning forward again is one hr-seek (25–580 ms, growing with the position in the group). It runs only on bytes on this disk — a local file, or a torrent's file (`torrent_local_path`, which the probe then reads; mpv itself keeps reading the loopback URL). **A torrent still downloading is sparse, and a hole reads back as zeros rather than failing**, so on one nothing is read or decoded backward without the map of arrived bytes (`torrent.buffered`, the same map the previews use) covering it in **one** band, widened by the previews' margin (`stretchInBands`, pure and tested): the probe needs the 20 s behind the position (`PROBE_LOOKBACK_S`) and is asked again at the next step rather than given up on; entering, and **every step while backward**, needs two of the longest groups and a second over (`reverseStretch` — the group being walked and the one mpv starts decoding as soon as the current one is handed out). Short of it, the step turns forward and goes native, which reads only the group already there. What is behind the playhead in ordinary watching has arrived — it was played; the hole is the stretch before a seek into what had not downloaded. If a read still reaches one, the loopback server holds it until librqbit fetches the piece, with no timeout of ours: a step on a torrent still downloading that has not finished after a second raises a sticky "waiting for the torrent" (`WAITING_AFTER_MS`), replaced by "this part has not downloaded yet" when the step gives up without moving and taken down (`dismissOsd`) when it lands; a backward step that did not move at all there turns forward without marking the file, since that is the network and not the file. Not measured against a live downloading torrent — the logic is unit-tested against the map — in software, without an A–B loop or an audio mix through `lavfi-complex` (the graph owns the tracks, so the sound could not be switched off, and a graph decoded backward was never tried), from the **second step back in a row** (a step forward resets the count: a viewer alternating back and forth would otherwise pay the turn — 2.3 s on the AV1 file, against 0.45 s for a native step — at every change of direction), once a native step back on the file has measured over `SLOW_BACKSTEP_MS` (100 — it was 150, and the 4K release above stepped in 133 ms at some positions and stayed native while reading as slow beside a 42 ms step forward; a 1080p film with two-second groups steps in ~60 ms and still does) — any step can set that verdict and none clears it, like the seek probe, because a first step just after a keyframe decodes a handful of frames and measured fast on a VP9 file whose later steps cost 280 ms — and only when the longest group around the position (`frame_step_probe`: packets and key flags only, milliseconds) fits the budget — decoded size × `average-bpp` × frames × 1.1 against a quarter of physical memory, at most 4 GiB, which becomes `video-reversal-buffer`. **mpv holds a whole group, not the frames up to the position**: it starts decoding the previous group as soon as the current one is handed out, so a step that sits near a keyframe still needs the full group, and measured resident size matched the formula (4K 8-bit, 240 frames: 3.0 GB of a predicted 2.99). **An overflowing reversal buffer is silent and lands the position seconds away** (39.9 → 33.5 at 4K with the default 1 GiB, 39.9 → 35.4 on AV1), so every entry and every step checks its landing (`landedRight`: two and a half frames or 0.1 s, tight enough for the five-frame skip below) and a bad one turns forward, seeks exactly to where the step should have gone and marks the file native for good. **The audio track is switched off for backward decoding** (`file-local-options/aid=no`, for the rest of the session — the steps are muted anyway): mpv decodes audio backward too, and on that 4K release with a 5.1 E-AC3 track it **tripled the entry, 2.0 s against 0.7 s, and made one step in forty skip five frames** (600.350 → 600.141). It comes back where the session ends — the play controls, a seek, a resume by anyone — and **only after the turn forward**: a track selected while mpv still decodes backward queues its seek backward-style and lands on the *next* keyframe (599.349 → 600.600, 600.809 → 602.602, measured), while the same write after the `play-direction` one lands exactly. Measured in the app on that release with all of this: entry 0.69 s, then 37–48 ms a step, one step of 340 ms where the walk crosses a keyframe, and playback resuming from the frame it stopped on with the dub and VideoToolbox back. Hardware decoding is never used backward: the frames would live in GPU memory the buffer does not count, and the manual warns it exhausts that memory. Four things that bit or would have: **every option is written through `file-local-options/`**, so mpv restores the direction, the decoder and the buffer at the end of the file — verified — because a next episode opening backward from its last frame is the failure nothing else would catch in time. **mpv's absolute seeks replace a queued one** (`queue_seek`), and turning the direction queues one, so a seek sent before the turn is silently lost: `issueSeek` and `seekRelative` go through `frameStepBeforeSeek` (turn forward, then give the decoder back, then seek; a relative seek is still right after the turn, because mpv adds it to the queued absolute one), the play button through `frameStepBeforePlay`, and anything else — a chapter, the room, the end of a cast — is caught after the fact by a `playback-restart` nobody stepping asked for. **A forward step unpauses mpv for one frame**, and the observer usually folds that flicker away but not always, and may deliver it just after the step resolved: a `pause=false` within 150 ms of a step is rechecked before it counts as the viewer resuming. **The same folding hides a step's own `time-pos`**: a step back then a step forward (34.450 → 34.433 → 34.450) can arrive as no event at all, because the observer compares with the last value it *sent* — in the app the forward step waited out its whole 4 s timeout — so a step that plays a frame is confirmed by a fresh read, with the event only as the wake-up (`waitMovedFrom`). **Backward, the start of the file is mpv's end**: `eof-reached` is ignored by the end screen while `frameStep.reverse`, and a step back on the first frame does nothing. The forward step carries the `mute` flag, which zeroes the output's gain for that frame without touching the `mute` property. Embedded subtitles are not demuxed backward, so they are absent while stepping back and return with the turn forward. Settings → Video carries the switch for (2) (`frameplayer.frameStep`); (1) has none, since it changes nothing but the speed. The FFmpeg sidecar (`step_engine.rs`) lost to this for reasons that are in its own code: it kept RGBA at source size (8.3 MB a 1080p frame, so its 700 MB cap held 1.4 s at 60 fps and re-decoded at every edge), pushed each frame through IPC into a canvas, and could not match mpv's colour.

- On a normal file keyframe seeking buys **nothing**, while *switching modes mid-gesture* is plainly visible as a jerk (previews sit on a keyframe, the final frame lands on the exact position). So the mode is probed once per file — `issueSeek()` times the first exact seek, `fileSlowSeek`/`wantExact()` decide from then on, `resetSeekProbe()` on `path` change (IINA does the same via `useExactSeekForCurrentFile` with a 0.05 s threshold). Fast file → exact everywhere, no mode changes at all. Slow file → keyframe previews, exact only where a frame is actually being asked for. Notes: hwdec **halves keyframe seek time but doubles exact seek time**, so "turn hwdec off" is not a win either way; `vd-lavc-fast`/`skiploopfilter` change nothing for VP9; `demuxer-max-back-bytes` is not implicated.

- The two gestures deliberately differ on pausing. **The seekbar drag pauses** (from the first move, not from pointer-down, so a plain click never touches playback): playing video drifts forward between throttled preview seeks and the next preview yanks it back — visible as forward/backward judder. **The wheel scrub does not pause** — it self-terminates after 180 ms, and with only ~12 keyframes in a 60 s span a paused scrub degenerates into a slideshow, which is what "less responsive than IINA" actually meant; it mutes instead, so frames keep moving between landings without machine-gunning the audio. While either gesture owns the position, `time-pos` must not write `seekValue` — and that block must extend past pointer-up (`seekSettling`) until the final seek lands, or the knob snaps back to the preview position and then forward again. Drag previews run on the same one-in-flight pump, **never a time throttle**: a seekbar is a brutal magnifier (a 57-minute film across ~900 px is 3.8 s *per pixel*), so an 80 ms throttle leaves the shown frame seconds behind the cursor and releasing then visibly jumps by that gap. `scheduleDragSettle()` closes the rest: 120 ms after motion stops it re-seeks *exactly* to where the cursor rests — that is the frame the user is actually aiming at — and `onSeekUp` skips its own seek when that already landed (`dragShownAt`/`dragShownExact`), so a considered release changes nothing at all. **The arrows follow that same verdict**, which they did not always do: the coarse step went by keyframes *unconditionally*, and a keyframe landing is up to a GOP away — so a 5 s arrow actually moved 6 s on an ordinary file and 10 s on a network stream with long fragments. It had always done that; only the popup hid it, by reporting the promise rather than the landing. They also carry the probe themselves (`noteSeekCost`), because an arrow is often the first seek on a file and a slow one would otherwise go undiagnosed until the bar was touched. Shift+arrow stays exact regardless. Beating the keyframe ceiling on pathological files needs our own decoded-frame source (StepEngine), not a different flag; IINA has no such thing (its `FFThumbnail` cache is the seekbar hover popup, same as ours). Two more rules the gestures depend on: keep **exactly one seek in flight** (`pumpScrubSeek`) rather than firing on a timer — a fixed interval builds a queue that keeps "playing out" after the fingers stop; and while a gesture owns the position, `time-pos` must not write `seekValue` (`!scrubbing`/`!dragging` in the observer) or the knob jitters between the finger and mpv's lagging report. Note `onSeekUp` now ends a drag with an exact seek when it is near — a *deliberate, narrowed* rollback of the architecture.md "drag is keyframes-only, including the final one" rule, because keyframe landing made the knob visibly snap backwards on release. If the frame-blink ever returns, revert there first. When a seek lands on a keyframe, the optimistic OSD position is wrong — refresh it from `time-pos` afterwards (`refineSeekOsd`), but **not when the seek command resolves**: `command('seek', …)` returns when mpv *accepts* the command, and `time-pos` there is still the position before the jump. Reading it then showed the target, flicked back to the starting point and stayed — three figures for one key press. `playback-restart` is the event that means the seek is done; the timeout beside it exists so a seek that never completes cannot leave the popup waiting on a promise.
- **Frame export and external tracks go through mpv, not around it.** `screenshot-to-file` keeps exactly what the VO decoded, HDR tone mapping included — which is precisely what the StepEngine canvas path got wrong, so do not reintroduce a canvas-based grab. `screenshot-raw` is not an option either: it returns a node, and node reads crash the wrapper. Clipboard copy therefore round-trips through a temp PNG decoded in Rust — and **mpv's PNG defaults are a latency trap**: zlib level 7 is a size-first choice that buys nothing here. Measured on a 4K frame of photographic content (libavcodec's PNG encoder, the one mpv screenshots go through): level 7 = 1.46 s / 16.4 MB, level 3 = 0.73 s / 16.4 MB, level 0 = 0.21 s / 23.8 MB. A 10-bit source doubles every figure, because `screenshot-high-bit-depth` defaults to yes and writes 16-bit PNG. Hence level 3 globally, and level 0 + no row filter + 8-bit for the throwaway clipboard file, which reaches the clipboard as 8-bit RGBA no matter what. `withFastScreenshot()` restores the previous values in a `finally` — leaving compression off would silently bloat every frame saved afterwards. This encode runs on mpv's core thread, so getting it wrong stutters playback as well as making the user wait. Dropped files are split by extension in `loadFiles`: subtitle/audio files become `sub-add`/`audio-add` (an `.srt` handed to `loadfile` used to be *played*), and when they arrive together with a video they wait in `pendingAttach` until `file-loaded` — `sub-add` before that fails. Track delays use `add`, never `set` from the mirror, for the same reason toggles use `cycle`.
- **Every list property is read through sub-properties, and they do not all behave alike.** `track-list`, `chapter-list`, `playlist` and `audio-device-list` are all implemented on mpv's side by the same helper, which exposes `<prop>/count` plus `<prop>/N/<field>` in simple formats — so none of them needs the `node` format that crashes the wrapper, and none of them needs native code either (the roadmap's worry about `audio-device-list` is unfounded). `readList()` in player/tracks.ts is that pattern; the sequence guard stays at the call site, because a read is dozens of sequential round-trips and there are several reasons to start one. What is *not* shared is how a missing field reports itself, and copying the track code blindly gets it wrong: measured on mpv 0.41, `track-list/N/title` of an untitled track is **unavailable** (the read fails, `.catch(() => null)` produces the fallback), while `chapter-list/N/title` of an untitled chapter is **available and reads back as the literal `(unnamed)`** — which would put an English placeholder into a Russian chapter list. Hence `MPV_UNNAMED`. Two more measured facts behind the chapter code: a file without chapters has `chapter-list/count` = 0 (available, not an error) while the `chapter` property is *unavailable*, so the current-chapter mirror needs its own fallback; and chapter navigation goes through the `chapter` property rather than a seek to the chapter's `time`, because with ordered chapters (MKV) the content can live in another file entirely and only mpv's own chapter seek follows that. It is also clamped at both ends — mpv's `add chapter ±1` walks off into the neighbouring playlist entry, and "previous chapter" opening the previous episode is not what the key says. **An arrow-key accelerator on an NSMenuItem does not fire** — measured: ⌘⇧←/→ on the View items did nothing at all, while the same keystrokes reach the webview normally, so chapter navigation is a frontend binding (`isChapterKey`) and those menu items carry no accelerator. On macOS it needs a modifier beyond Ctrl, since plain Ctrl+arrow is Mission Control and never arrives; hence ⌃⌘←/→ there against plain Ctrl+arrow on Windows. Testing `e.ctrlKey` alone is the trap that hides all of this: it silently accepts ⌃⌘, ⌃⇧ and every other Ctrl+arrow as the same gesture, so the binding *appears* to work on macOS while Ctrl+Shift+arrow quietly stops being the 1 s exact seek it looks like.
- **"Skip intro" matches the whole chapter title, never a substring.** `skipKind()` offers a skip button for the first `SKIP_WINDOW` seconds of a chapter that names itself an opening, a recap, a preview, a trailer, the credits or an ad. A **kind exists only to label the button**, which is what decides how finely they are split: a trailer is not filed under "preview" because an episode's preview announces the next episode while a disc rip's "Trailer" is a promo for another film, and "Пропустить анонс" over one of those is the same mistake as "Skip credits" over an opening, in miniature. Adding a kind is therefore a `SkipKind` member plus an entry in `SKIP_LABEL`, which the compiler demands. The obvious implementation — search for "intro"/"ending"/"credits" inside the title — is wrong in the common case, not a rare one: those are ordinary English words, so "Ending the war for good" becomes the closing credits and "Opening the vault" becomes a title sequence. Announcement chapters name themselves and stop, so the patterns are anchored to the entire title (with only the decorations rips actually use: a leading "01. " and trailing "…"), plus a five-word cap as the outer bound for the open-ended tails like "Previously on <show>". Anchoring also settles "субтитры" contains "титры" for free, and it puts the failure on the harmless side: an unusual name simply offers no button. Two traps inside the patterns: **`\b` is ASCII-only in JS**, so `ранее в\b` never matched anything at all — Cyrillic alternatives need an explicit `\s`; and the intro-first ordering, which **used** to matter ("Opening credits" matched both while the patterns were substring searches) and is now inert — anchoring them to the whole title made the alternatives disjoint, verified by enumerating every title they match from a corpus of their own literals and diffing the verdicts under both orders. It stays as defense against a future un-anchoring, and the comment at the table says so rather than claiming to be a rule; reversing it therefore changes no test result, which is worth knowing before reading that as a gap in the tests. The window is measured from `chapterAt(timePos)`, not from the `chapter` mirror, so the elapsed time and the chapter it belongs to cannot disagree after a seek; and the button lives **outside `.osc`** on purpose — it has to stay up while the UI is idle, which is the entire point of it. Which costs it a `z-index`: `.osc` comes later in DOM order and its scrim reaches 44 px above the controls, so an unlayered button gets the gradient washed over its top half. **How long it stays is `min(chapter length, SKIP_MAX_WINDOW)`**, bounded at both ends and never a bare constant. Longer than the few seconds it started at, because the decision to skip lands when you recognize the music rather than at the first frame, and a short window took the offer away while its reason was still on screen. Shorter than the chapter, because an offer sitting over the picture for a whole minute stops reading as an offer. And never longer than the chapter itself, so a five-second bumper cannot leave a button hanging for three times as long as the thing it offers to skip — which is also what keeps a misread title ("Introduction" on a two-hour lecture) down to a brief button rather than a permanent one. Everything the button shows about time therefore comes from the position, not from a CSS clock — the draining wash is `background-size` driven by `--skip-left`, and the tail fade is an inline `opacity`, both smoothed by a transition because `time-pos` arrives in steps. That is what lets it survive a seek into the middle of an opening (a from-mount animation would show a full bar with ten seconds left) and what makes a paused film freeze the countdown with nobody arranging it. Two shapes that were tried and are wrong: a `::before` scaled with `transform` (a transform distorts what it scales — the wash's corners flattened and its square left edge crept out from under the pill's rounded one, and it dragged in the `z-index: -1` + `isolation` pair from the scrim rule in [css.md](css.md)), and percentage keyframes over the whole lifetime (fine at 5 s, but they stretch a 0.2 s entrance into three seconds on a minute-long opening). On the **last** chapter the offer becomes the next queue entry, and **that entry has to be a different file** — `neighbour()` answers "what plays next", which under repeat is legitimately this one again: with a single entry and repeat-all it wraps straight back to index 0, and it does the same from a stale `playlist-pos`. Either way the credits of a lone episode grew a "Следующая серия" button that restarted what was already playing. The two questions are different — repeating one file is exactly what repeat-all on a one-entry queue *means* — so the guard belongs at the button, not in `neighbour`, and it tests both the path (against `filePath`, mpv's own answer) and the index, because those two fail in different situations. Related and the reason the stale case is not self-healing: **`playlist-pos` was missing from `resyncState`**. Every other mirror is re-read each second, so a dropped property-change event costs a tick; this one stayed wrong until something moved the playhead, and everything about neighbours — both end-screen cards, the auto-advance, this button — is computed from it.
- **The media info panel is a live readout, not a snapshot, and half of it is legitimately missing.** Every field comes from a plain `getProperty` — measured on a 4K HEVC file, `video-codec` gives the readable name ("H.265 / HEVC…") while `video-format` gives "hevc", `audio-params/channels` gives "5.1(side)" where `channel-count` gives 6, and `current-tracks/audio/lang` names the dub. **`video-bitrate` is a rolling average of recent packets**, so it is simply absent for the first seconds of a file (measured: audio had a figure while video still had none) and drifts afterwards — hence the 1 s refresh while the panel is open, and hence the average computed from `file-size / duration` next to it, which is exact and available immediately. Rows with no value are not rendered at all: which properties exist depends on the container, the codec and how long playback has run, and a column of "—" reads as breakage. Values are stored raw and formatted at render time, so a language switch relabels the units without waiting for the next refresh.
- **Picture geometry is per file, and reset only if we touched it.** `video-rotate`, `video-aspect-override` and `panscan` are global mpv options: a phone clip turned upright stays turned for the next episode, so they are reset on `file-loaded`. But only when the viewer actually used the menu (`pictureTouched`) — an unconditional reset would overwrite a `video-aspect-override` line in the user's own mpv.conf on every file. Two measured facts the menu depends on: **`video-rotate` does not change `dwidth`/`dheight`** (it is a VO-level transform: both keep reading the size *before* the turn, and the turn itself — the file's own rotation plus this option — is `video-out-params/rotate`, which is what the window's shape reads; see the shape rule in [window](window.md)), and **an aspect override is reported as a decimal**, so `4:3` reads back as 1.333333 and the menu has to compare numerically rather than against the string it sent. Auto is any negative value; mpv's own default is -2. **`video-crop` (ROADMAP 34) is the fourth of them and the one that is remembered.** It survives a `loadfile` like the other three (measured on 0.41), goes through `setPicture` so the same guard covers it, and is then put back by `restoreCrop`. **The mode is the playlist's and the rectangle is each file's own**: a choice is recorded for the folder or the torrent (`cropMode` in the folder store, `none` included, so turning it off on one episode turns it off for the ones already cached), and each file applies it to itself — auto measures that file, a named shape is computed from its frame — and caches the rectangle it came to, empty for "no bars", valid only while its mode is still the playlist's. A rectangle is never copied between files: that is what would cut picture off. On opening, a named shape waits only for `video-params/w` (it is not there at `file-loaded`); auto waits 1.5 s more so its decode does not compete with the first frames, and a torrent with too little downloaded is retried every 30 s, four tries in all. Unlike `video-rotate`, it **does** change `dwidth`/`dheight` (measured, paused included), so the hover preview's shape follows it on its own — the window's shape does not read `dwidth` and applies the crop itself (`decodedShape`, see [window](window.md)); the preview's thumbnails are still full frames, which is why `crop.objectPosition` exists. mpv refuses a rectangle that does not fit the frame *and clears the property* (`Ignoring invalid --video-crop`), which is the whole defence against a remembered crop outliving a re-encoded file — so the menu ticks a mode only while the mirror is non-empty. "Auto" is `crop_detect` in the sidecar, never mpv's `cropdetect` filter: that one sees the frames being played, so it answers for the current scene, needs playback running and puts a software filter (a hardware download, under hwdec) in the chain. The sidecar decodes eight keyframes spread over 10–90 % of the file and keeps, per edge, the second-smallest bar (crop.rs) — one frame with a burnt-in subtitle in the bar is outvoted, two frames reaching an edge make it picture. Measured: exact on letterboxed and pillarboxed fixtures, including a 10-bit HEVC one and dark fireworks and space footage, no answer on five full-frame files, under a second on 4K HEVC. **A torrent is measured from its cache file**, and while that is still arriving only at positions `positionBuffered` accepts — the same test the hover previews pass — spread over whatever is down (`detectionTarget`), with "too little yet" said out loud below three points. Fewer scenes can only make it crop less: measured on copies with the middle half zeroed, samples from the downloaded ends gave the exact rectangle, and even samples placed *inside* the hole gave no wrong answer (a frame that does not decode is skipped, and one that decodes to garbage reads as "no bars", which the smallest-bar rule turns into less cropping, never more). A plain stream is not offered it: eight seeks are eight requests for data nobody has.
- **The A–B loop is mpv's to run; ours only to mark.** Both points set means mpv loops the segment by itself — measured, playback stays inside the range and wraps without anything watching the position. Two things the marks need on our side: they read back as the **literal string `no`** when unset (asking for a double gives nothing at all), so the mirrors parse rather than cast — `Number('no')` is NaN and would read as a position; and they survive a file change, so they are cleared on load, or a segment measured in the previous episode traps playback in an unrelated stretch of the next one with no visible cause. B before A is refused rather than sent: mpv accepts the pair and then simply never loops, which reads as the feature being broken instead of the marks being the wrong way round. **mpv disarms the loop while the position is past B** and re-arms it when playback is inside the segment again, keeping the marks throughout — measured, and it is the right call for a destination but wrong for a nudge, so a *relative* seek wraps inside the segment (`wrapInAbLoop`, modulo rather than a clamp, because a loop is a circle and five seconds forward should stay five seconds). The wheel scrub is **clamped** to the segment instead, and the split is the nature of the two gestures rather than taste: fingers traveling right mean "later", so wrapping would break that correspondence and spin the picture around a short loop under a steady swipe, while a key press has no such correspondence to keep and would go dead at the edge if it clamped. Clamping is also what the scrub already does at the ends of the file, so a segment is tighter bounds rather than a new rule. Its upper bound stops a frame short of B, because landing exactly on B disarms the loop and the gesture would end by silently switching it off. Absolute gestures — a seekbar click or drag, a digit jump — deliberately keep mpv's behavior and leave; the band on the bar then goes faint, because a control that keeps drawing a loop while nothing loops is the actual bug in that situation.
- **A speaker's lag is kept per output device, and `audio-delay` is the sum of two things only `tracks.svelte.ts` keeps apart.** A Bluetooth speaker adds a delay the system reports to mpv only in part, so the picture leads by a fixed amount *for that speaker*; the per-file delay is for a file muxed out of sync and must not learn it. `audio-output.svelte.ts` holds the offset per device (`frameplayer.audioOffsets`, keyed by the system's own id — CoreAudio's device UID, the WASAPI endpoint id — which is also what follows the prefix in mpv's device names, so one speaker has one key whether it is chosen in the settings or reached through `auto`). Under `auto` mpv does not say which device it plays through, so `audio_output.rs` asks the system for its default output every 1.5 s on its own thread and emits `frameplayer://audio-output` on a change. mpv gets `file delay + device offset`; `deviceInForce` is the device's part of that, taken out of every read-back before a file remembers its delay, shown out of the menu's file row, and a device change is applied with `add` (the difference) so a nudge not yet read back survives it. Measured in a dev build on macOS: offset and file delay add up, change independently and come back together on reopening. **Not measured**: a real Bluetooth device appearing and leaving, and anything on Windows beyond compiling.
- **Volume leveling is a labeled `af` filter, and its state is ours.** `af add @fpnorm:lavfi=[dynaudnorm=…]` / `af remove @fpnorm` — the label is what lets it be removed again without touching an `af` line from the user's own mpv.conf, and it is also why this setting is the one playback option kept in localStorage instead of written there: `mpv_conf_set` replaces the last uncommented line of a key, and for `af` that would silently eat someone's filter chain. Reading the state back is not an option either — measured, `af` answers with its own escaping (`@fpnorm:lavfi=graph=%27%dynaudnorm=f=250:g=15:p=0.9`), so ours is the record, exactly as with the repeat mode. It is disabled while `audio-spdif` is on and says so: bitstreaming hands the receiver an undecoded stream and a filter has nothing to attach to, so the honest thing is to explain rather than quietly do nothing. **mpv lists a device once per audio output that can reach it**, so the picker showed every speaker two or three times with nothing to tell the copies apart: the macOS build carries `coreaudio`, `coreaudio_exclusive` and `avfoundation` (verified in the bundled libmpv), and only the `name` prefix differs — the `description` is identical. Deduplicated by description, first entry wins, which is mpv's preferred output; the cost is exclusive mode, which cannot be labeled here without inventing jargon and belongs in mpv.conf anyway. Worth knowing when a device's name looks wrong rather than duplicated: **the description is CoreAudio's, not the speaker's**. macOS exposes AirPlay as a single virtual device literally called "AirPlay", and which speaker it streams to is chosen above that layer, in the system output menu — so a JBL on AirPlay legitimately appears as "AirPlay" here and in every other app that enumerates CoreAudio devices. **`audio-device-list` needs no native code**, contrary to what the roadmap assumed — like every list in mpv it answers to `count` and `N/name`, `N/description`, so `readList()` covers it; the list is read when the dialog opens, since mpv builds it lazily on first read and there is nothing to keep fresh while the dialog is shut. Its first entry is `auto`, which is also mpv's default, so it maps to `null` and choosing it clears the mpv.conf line.
- **SDR color on macOS is a choice between two curves, and ICC is not part of either.** mpv hands the display BT.1886 code values untouched; QuickTime decodes BT.709 with a pure ~1.961 power and encodes it with the sRGB curve, which measures up to 12 levels brighter through the mid-tones (Y = 128: 140 against 129) — the whole of the "mpv is darker" report, and independent of whether the file declares its colour: a BT.709-tagged copy measured bar for bar the same as an untagged one. "As in macOS" (`applySdrColor('system')`, stored as `frameplayer.sdrcolor` in localStorage, macOS only) is four things, and only the four together matched — to about a level across the grey scale, to the unit on the primaries: `@fpsdr:format=gamma=gamma2.2`, `gamma-factor=1.1218765935747068`, `target-trc=srgb` and **`treat-srgb-as-power22=no`**, without which mpv 0.41 encodes "srgb" as pure 2.2 and lifts the shadows by up to eight levels. **Never add `icc-profile-auto` to it**, though the recipe it came from has it: our Vulkan layer is already colour-managed by ColorSync as sRGB, so mpv's conversion to the display profile applies a second one and desaturates every primary (BT.709 red 232,51,35 → 213,68,49). The mode touches a picture only while `video-params/gamma` is `bt.1886` — the picture *entering* the filter chain, so our own `format` filter (which changes `video-out-params`) cannot feed back into the decision; PQ, HLG and RGB images (`srgb`) are left alone, and with no video the state in force stays so an episode change does not flash the other curve. Every part is a runtime property and takes effect at once, paused frames included; on the way into an HDR10 file the options are back at 214 ms and the first frame is presented at 233 ms. A key the viewer set in mpv.conf is skipped in both directions (`userConfKeys`), and the filter is labeled for the same reason `@fpnorm` is. `hwdec` stays `videotoolbox` with the filter in the chain. **Check the mode on a grey ladder against QuickTime, never on colour bars against "BT.709 as sRGB"**: that reference *is* mpv's passthrough, so "As in mpv" scores 0.27 levels by construction while QuickTime and "As in macOS" score 3.3–3.6 for matching each other (and against the unexpanded code values 180/16 the bars rank players by whether they expand limited range at all — the same pixels score 12.85 decoded correctly and 1.94 read as full range), and 7 of the 27 SMPTE patches sit at 0 or 100 %, where every curve agrees — tuning the mode towards a better bar score would be tuning it away from QuickTime. The measurements, and the variants that did not match, are in [../sdr-color.md](../sdr-color.md).
- **Picture adjustments have three scopes, and the narrowest one with a record wins.** `brightness`, `contrast`, `saturation` and `gamma` (ROADMAP 36, `picture-adjust.svelte.ts`) are kept for this file (the tracks store, by `sourceId`), for its playlist (the folder track store, by `folderScopeKey`: the folder, or the torrent) or for every file (`frameplayer.picture`), and `restoreAdjust` takes the first of those that exists; with none it is "this file" at zero, because the common case is one film graded too dark, and that correction must not follow the viewer into the next. The panel's scope is where the values came from and where a change is written back. **Widening deletes the narrower records for this source** — "every file" with this file's own record left in place would change every file except the one on screen — and all zeros are stored only when a broader scope would otherwise show through. All four are options and leak across `loadfile` (measured: `gamma` 40 on one file was 40 on the next), so every file gets an explicit value for each, zero included; a key set in the viewer's mpv.conf is skipped (`isUserConfKey`). Measured on 0.41 with gpu-next: all four reach `screenshot-to-file … video`, and `gamma` **composes** with the SDR mode's `gamma-factor` rather than replacing it (grey at mid-frame: 90 plain, 130 with gamma 40, 137 with both, 94 with the factor alone), so the two need no arbitration. The sliders live in the context menu's picture panel, and dragging one turns both menus transparent except for that slider's row (`peeking`): the adjustment is judged against the whole frame. Two things that gesture has to defend against, both in `startPeek`: the panel's hover-close timer (a drag routinely leaves it), and the `click` a release over the video produces, which would dismiss the menu mid-adjustment; and the input is blurred on release, because a focused range input is a text field to the hotkeys and Space would stop working. The global values are also in the settings sheet (Video), which edits `all` whether or not anything plays and repaints the open file only when it `followsGlobal` — showing the global values, or nothing of its own; otherwise the sheet says the file overrides them. **Moving to a scope that already holds different values asks rather than overwrites** (`conflict`): the case is a file tuned on its own, a different global correction set in the settings, then "all files" picked in the panel, and either set surviving is reasonable, so the panel offers both (`resolveAdjustConflict('mine' | 'theirs')`); the question is dropped with the panel. **`chrome.tuning` hides the bars from the first touch of a picture slider until its surface closes** — every mouse move raises them, and a slider is nothing but mouse moves — and hides nothing else: `idle` includes it, and the cursor effect takes it back out. The settings sheet turns see-through while dragging too (Dialog's `peek`, keeping the child marked `.peek-keep`), and `holdSlider` (dom.ts) carries the release-click and blur defences for both. Refused while casting (`Feature` `picture`) and `personal` in a room.
- **The upscaler is a shader mpv runs only when the picture is drawn larger than it was decoded, and the panel has to say when it is not running.** Three modes (`upscale.svelte.ts`): `video` is ArtCNN C4F16 DS (the variant trained to denoise and sharpen, at plain C4F16's cost), `anime` is Anime4K Upscale CNN x2 M, `strong` is Anime4K Upscale **GAN** x2 M, all shipped verbatim in `src-tauri/shaders/` (`bundle.resources`, and `build.rs` copies them beside the dev binary) and listed in `licenses/manifest.json`; they are the lightest of their families because the heavier ones are not a switch — measured on an M3 Max into 3400×2000, GPU time per frame from `vo-passes`, 1080p source: 2.9 ms bare, 8.5 ms ArtCNN C4F16 DS, **37 ms C4F32** (past a 24 fps frame on the fastest Mac), 6.4 / 8.6 / 15 ms Anime4K CNN M / L / VL, 20.7 ms GAN x2 M, 44 ms Restore GAN UL + GAN x2 M, 39 ms GAN x4 UL. **`strong` is the only one that invents texture**, which is what reads as detail across the whole frame, and it pays twice: faces pick up artifacts (it was trained on animation) and the texture differs from frame to frame — two consecutive frames of a 480p film were 35.4 dB apart in PSNR plain, 34.6 with ArtCNN, 33.9 with GAN x2 M and 31.3 with Restore GAN in front of it. So it runs only on sources up to 1280×720 by their long and short side (`STRONG_MAX`, `shaderFor`) and stands in as `video` above that, saying so in the panel (`upscaleNote`); the size arrives from the codec, so `video-params/w`/`h` re-decide through the page's `property` hook (`upscaleSourceChanged`). A switch costs one compile, measured ~0.27 s and three dropped frames with no shader cache, the same for every mode — **on the Mac. On Windows the same compile is two orders of magnitude worse for one shader, and it lands in the middle of a resize** (issue #18, "freezes upon resizing"): libplacebo on D3D11 turns each pass into DXBC with FXC, which took **~2.2 s for each of ArtCNN's five compute passes plus 1.1 s for the sixth — 12.1–12.3 s, every time, on an RTX 5080 (driver 32.0.16.1062, FXC 10.0.28000)** against 0.1 s for all of Anime4K CNN M and 0.34 s for GAN x2 M. It is the compute passes themselves, not their float16: with the f16 branch forced off FXC took the same 2.2 s a pass. A pass compiles the first time its `//!WHEN` is true, so with the mode chosen in a small window the cost falls on the drag (or the full-screen switch) that crosses the threshold, and the render thread spends it with the picture standing still, stretched, while the window and the interface stay responsive (`WM_NULL` answered in ≤13 ms throughout); once compiled it is kept in memory for the life of the VO, so later resizes and the next files cost nothing. Hence **`gpu-shader-cache-dir`** in `initialOptions` (`mpv_shader_cache_dir`, `<cache>/shaders`, portable-aware): the mpv CLI caches by default, libmpv has no directory and so recompiled in every session; with the cache the second encounter is 0 compiles and 0 frozen frames, across restarts (~290 KB on disk with ArtCNN in it). The first encounter on a machine still costs the 12 s, and **the player says so** (`initUpscaleWatch`, the veiled `LoadingOverlay`: "Preparing upscaling — only the first time on this computer", with a clock). Nothing announces a compile, and it shows in two different ways, measured through the webview's own mirrors: begun by a resize or by a redraw while paused it **holds mpv's core** — a `getProperty` sent as it began came back 12.4 s later, `osd-dimensions` stays at the last size before it and `engaged` may still read false — while begun by the first frame of a file opening into a large window the core **goes on answering** and only `time-pos` stands still. So the watch asks `pause` every 250 ms, one question at a time, and the plate is up while one is unanswered for 0.5 s or, in playback with the shader engaged, while the position has not moved for 0.7 s; it comes down when the answer arrives or the position flows again (three updates in a second — one report arrives from inside a compile). It watches only what mpv **holds** (`given`, set once `change-list` returns), not the mode on screen — the list outlives `loadfile` and the next file's is sent on `file-loaded`, so a file set to Off can open into the previous file's compile — and only until that shader has run once this session (engaged for 1 s and then answering or moving: the mirrors say "engaged" a frame *before* the compile starts, which is why `engaged` alone cannot end it). Off, the default, the watch never runs. Not covered: a file opening *paused* into a compile shows neither sign. Measured and not shipped: `gpu-api=vulkan` takes the same six passes in ~0.6 s (driver compiler, ~110 ms a pipeline) — changing the Windows backend is a decision of its own, not a fix. And nothing can compile the passes ahead of time in the same renderer: they are built only when `//!WHEN` is true, and `video-zoom` does not grow `OUTPUT`. Hypothesis "the six `osd-dimensions` observers flood the IPC during a resize" was measured and ruled out on the same machine: with the upscaler off, fast and slow drags from 854×481 to 3280×1846, maximize and full screen kept `WM_NULL` under 7 ms and the picture moving. Hardware decoding does not stop them: the same eight passes appear with `hwdec=videotoolbox`. **Every pass decides for itself, per frame, from its `//!WHEN` line** — `OUTPUT` over `LUMA`/`MAIN` above 1.3 (ArtCNN) or 1.2 (Anime4K) on both axes — so a 1080p film on a 1080p screen, or anything 4K, costs nothing and changes nothing whatever the switch says; `upscale-plan.ts` repeats the test (`upscaleRatio`, from the `osd-dimensions/*` mirrors and `video-params/w,h`) so the panel can say "active, ×1.6" or "not needed at this size" instead of looking broken. What the two sides are was measured by counting passes, and two answers are not what the names suggest: `LUMA` is the **whole decoded plane** (`video-crop` does not shrink it) and `OUTPUT` is the **part of the picture inside the window** (`video-zoom` does not grow it); the comparison is per axis in the frame's own orientation, so a 90° turn swaps them. **Two scopes, file and playlist (`folderScopeKey`), the file's record winning, and no global one** — whether a picture is worth enlarging belongs to a source, and an always-on network would be paid for on battery by every 4K film; with nothing stored it is off and the panel speaks about this file. A file's `off` is stored only where its playlist would turn the shader on (`fileRecord`), and moving to the playlist *replaces* what the playlist held rather than asking, unlike the adjustments: there both sets are somebody's tuning, here the viewer has just said what the season gets. **`glsl-shaders` is an option and leaks across `loadfile`**, so every file is given its list — sent only when it changes, since a change rebuilds libplacebo's passes — as `change-list … clr` then `append`, because `set` splits its value on the path separator and `append` takes one path whole. A list from the viewer's mpv.conf (any `glsl-shader*` key) is theirs: the panel says so and sends nothing. Refused while casting (`Feature` `picture`), `personal` in a room.
- **Anything mpv keeps across a file change is a leak waiting to be noticed.** `video-rotate`, `video-aspect-override`, `panscan`, the A–B loop points and — measured — **`sub-delay`, `audio-delay` and `sub-speed`** all survive a `loadfile`, so a correction dialled in for one episode silently applies to the next. Every one of them is therefore given an explicit value on `file-loaded`: its own, or the default. The delays are stored per source in the track entry (the same store, because they answer the same question — how this file needs to be played — and outlive the position), and **never per folder**: a mux error belongs to one file, and applying one episode's correction to the next would be inventing a fault. The value written is read back from mpv rather than computed, since `nudgeDelay` uses `add` and mpv owns the result, and it is debounced because a delay is dialled in by repeated presses and only where it settles is worth keeping. Zero deletes the record instead of storing a zero, or resetting a delay would leave an entry behind for ever. `sub-speed` (the subtitle frame-rate stretch) lives in the same entry by the same reasoning, is applied by the same `applyTiming`, and 1 deletes it the way zero deletes a delay.
- **Now Playing on macOS is the player's own, and mpv's is switched off.** mpv's integration (`osdep/mac/remote_command_center.swift`) is built for mpv.app: its `EventHelper` refuses to start unless `NSApp` is mpv's own `Application` class, which under libmpv it never is, so the remote command center never hears `pause`, `time-pos` or `media-title`. What that produced, measured on 1.20.1: a Control Center entry reading "mpv" with mpv's icon, state "playing" from the first second, and buttons that did nothing — the commands it turned into key events (`PAUSEONLY`, `PLAYONLY`, `PLAY`) reached nothing, and binding them (1.20.0) changed nothing, because the system was not sending them to a listing it could not tell was playing. So `input-media-keys=no` goes into `initialOptions` on macOS and `now_playing.rs` + `now-playing.svelte.ts` take its place: the frontend reports title, length, position, rate and the queue's edges to `MPNowPlayingInfoCenter` through `now_playing_set`, only when one of them changes or the position strays more than `DRIFT_S` from the system's own extrapolation; `MPRemoteCommandCenter`'s handlers emit `frameplayer://remote`, which `onRemote` answers with the verbs in `playback` — so a pause from the AirPods pauses a television the player is casting to, and next/previous go through `advance` and its curtain. `now_playing_start` is called by the frontend once it is listening, never from `setup`, so no command is answered into the void. The framework is spoken to with `msg_send!` rather than a bindings crate; the constants and selectors are listed in the module. Windows is untouched: its media controls (`osdep/win32/smtc.cpp`) set mpv's properties directly and `media-controls` in `initialOptions` is that side's switch.
- **Several audio tracks play through one file-local `lavfi-complex`, and every one of its edges was measured.** `[aid1][aid2]…amix=inputs=K:normalize=0:weights=1 0 …,alimiter=limit=1:level=0[ao]` (tracks.svelte.ts, "Several audio tracks at once"): `normalize=0` keeps each track at its recorded level, the limiter catches the sum, `level=0` stops its make-up gain. **Every graph change is an exact refresh seek** (`update_lavfi_complex`), and one that switches on a stream the demuxer was not reading made the picture jump forward while one that did not was invisible — so the graph takes *every* audio track when the mode is switched on and a tick changes only the weights; the jump happens once, on the switch. With every track in the graph each one reads `selected` and `aid` reads `no`, so what is heard is ours (`audioMix.ticked`); `set aid` succeeds and **does nothing** while a graph stands, so a single pick clears it first; clearing it leaves **no** audio, so going back always names a track — **through `aid=no` first** (`clearMixGraph`): the option still holds the track picked by hand before the mix, and writing the same id again is no change to mpv, so it answered success and selected nothing, every later click on that track included (measured on 0.41; any other id was selected). Written to `file-local-options/` because a graph left over from the previous file stops a file lacking one of its tracks from opening at all — file-local, mpv drops it on every load path. Not remembered, refused under bitstream, and `can.audioMix` is off while a cast session is even being prepared.
