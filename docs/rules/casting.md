# Casting: Google Cast and DLNA

The two transports, what each can carry, and the rules the player keeps while a television owns playback.

Part of the rule book: [`CLAUDE.md`](../../CLAUDE.md) carries the one-line
version of each rule here, this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.
The *why* behind it — what was tried, what was measured — is in
[`../casting.md`](../casting.md).

- **Casting (Google Cast) is a URL handoff, and while it runs the window is a remote control.** The TV fetches the file from a LAN HTTP server in cast.rs and decodes it itself; mpv stays **paused with the file loaded**, so tracks, chapters, duration and the hover storyboard keep feeding the UI, and disconnecting is a seek to the TV's position plus unpause — never a reopen. The rules that must not break, with the reasoning in `docs/casting.md`: **nothing opens at startup** — mDNS browses only while the picker is open (the `$effect` cleanup in +page.svelte covers every way it closes), the server binds when a device is picked, on the interface whose subnet contains the device (`pick_lan_ip`, if-addrs netmasks — never `127.0.0.1`, never `0.0.0.0`), and everything tears down on disconnect. **The server answers for exactly one file behind a random 128-bit token** — never a directory — and for a path under a private root the URL basename is the token itself plus the extension and the LOAD carries no title, which makes `cast_load` the **fifth** privacy enforcement point beside the four listed in [sources-and-privacy.md](sources-and-privacy.md). **The CASTV2 protocol is spoken directly** (`wire::encode`/`decode`, a select! pump, a dedicated reader task because `read_exact` inside `select!` is not cancellation-safe): `rust_cast` was read and rejected — it holds its stream mutex across a blocking read with no timeout, so a command issued while its receive loop parks waits for up to the 5 s heartbeat, which is a broken remote. The TLS provider is **pinned to ring** (`builder_with_provider`): the tree compiles both ring and aws-lc-rs, and rustls' plain `builder()` panics with two providers enabled. **The remote seekbar is release-only** — no preview seeks, no probe, no drag settle (those are about local decode cost; every preview here would cost the TV seconds of buffering); Rust sets `cast.time` optimistically when SEEK is sent, which is what lets the page's `$effect` follow `cast.time` without a `seekSettling` twin and without the knob springing back. **Everything that moves the position has to be re-routed, and the ones that were missed all failed the same way.** The chapter *keys* were routed from the start; the chapter *list*, the skip button and the skip guard were not, and each of them talked to the paused local player instead — the knob jumped to the timestamp and the next status report dragged it back, the offer never appeared because `time-pos` is frozen while casting, and the guard that mutes a used skip never released for the same reason. The rule is one line: while `cast.remote`, read `cast.time`/`cast.duration` rather than mpv's, and act with `castSeek`/`castFollow`. The Windows **taskbar progress** was the fourth, and it adds a second half worth knowing: reading the right source is not enough when nothing is left to fire the update. It hangs off mpv's property observers, and with the local player parked `time-pos` never arrives — so the bar was written once, at the handoff, and held that position and its "paused" colour for the whole session while the television played through the film. Its driver while casting is therefore the cast poll (the same `$effect` that follows `cast.time`), and the call sits **inside** the `remote` guard: the local branch reads mpv's mirrors, so calling it there unconditionally would make that effect depend on `time-pos` and re-run ten times a second through ordinary playback. Anything else that only wakes on an mpv event inherits this bug by default. **Seeking while paused is refused by the measured renderer** — measured, UPnP 501 "Action Failed" — so `dlna_control` resumes, seeks and pauses again, which is the standard controller remedy and is verified end to end (the position moves, the state comes back paused, the TV fetches the new range); it costs a fraction of a second of playback, against a seekbar that would otherwise stop working exactly when a viewer reaches for it. It also needs a second guard the playing case does not: **a paused renderer keeps reporting the position it had before the seek** until playback resumes, so the target outranks its answer until a report lands near it (`seek_target`, bounded) — believing the renderer there is the same "jumps and returns" from the other end. **Keys and wheel are re-routed, not disabled silently**: `runCastAction` maps playback keys to the TV (chapter keys become remote seeks to the local chapter list's times — never mpv's `chapter` property, which would move the paused player out from under the session), the wheel is TV volume, and local-only concepts (frame step, zoom, speed, loops, screenshots, delays, mini) refuse with an OSD saying so. **A transport that fails must hand over, not stop.** `auto` can be wrong about DLNA in three ways that look identical from here — the container is listed but the codec inside is not decodable, the device advertises less than it can, or a renderer-only device simply cannot take this file — so the failure itself is the evidence: the session falls back to the Cast ladder, which names its own refusals, and the container is remembered as refused **for this device for this run** (not persisted: an under-declaring renderer deserves a fresh try next launch, but not one per episode of a season). Three detectors feed it, and the third is the one that matters: a `dlna_load` that errors, a renderer that stops before it ever played (its "ended" and "failed to start" are one state), and **fetched-but-never-playing past `START_TIMEOUT_MS`** — the failure that used to be perfectly silent, no error frame and no state change. That last one only became detectable once `load_url` stopped ending in an optimistic `playing`: claiming playback the renderer had not confirmed blinded every check downstream, so it now ends in `buffering` and the poll reports what the device actually says. Zero fetches is deliberately *not* a fallback case — nothing was read, so the file is not the problem and Chromecast would be served by the same blocked server; that stays the firewall message. **Discovery is not a one-shot question, and on macOS it cannot be.** The system asks for Local Network permission the first time something multicasts, a third-party firewall may ask again per destination, and both prompts are answered *after* the search has started — while the sockets refused in the meantime stay refused, so re-sending queries on them changes nothing. Two consequences, both learned from a real install: **discovery is torn down and rebuilt** after a few empty polls, which is what turns "allow" into devices appearing instead of the viewer having to close the panel and open it again; and the panel **never announces failure while it is still searching** — the first version said "no devices found" after six seconds, which is exactly when the prompt is still on screen waiting to be answered. It now says it is still looking, names the prompt, and only reaches "here is why a television is invisible" after a couple of rebuilds, by which time a granted permission would have taken effect. `NSLocalNetworkUsageDescription` and `NSBonjourServices` are in `src-tauri/Info.plist` so the prompt can say what it is for. **Errors are four different facts**: TCP/TLS connect failed, LAUNCH_ERROR, LOAD failed, and "LOAD accepted but zero fetches within 8 s" — that last one is the firewall signature (the CASTV2 channel worked, the media port is blocked) and gets the firewall message, which the picker also pre-empts by warning about the Defender prompt before the first bind. **The compatibility ladder is `castVerdict`** (cast.svelte.ts): direct play (MP4/M4V/WebM with receiver-decodable audio) → **prepare** (`cast_prepare` in cast.rs: the bundled ffmpeg CLI remuxes into a `+faststart` MP4 with video always stream-copied, `-tag:v hvc1` on HEVC only, audio copied when compatible and transcoded to E-AC-3 640k otherwise — `-ac 6` only above 6 channels, or a stereo source would be upmixed) → refuse, which only incompatible *video* earns now, named rather than generic. H.264/HEVC/VP9/AV1 and AC-3/E-AC-3 pass as *attempts* — device class and the HDMI passthrough chain are unknowable from the sender (E-AC-3 passthrough and 4K HEVC HDR10 are **measured working** on one real television). Prepared files live in `<app_cache>/cast/` keyed by path+size+mtime+track+rung, LRU-pruned to 20 GB; a private-root file's prepared copy is deleted with its session (`cast_forget_prepared`). **`cast.remote` vs `cast.active` is load-bearing**: during a prepare, local playback deliberately keeps running, so keys/wheel/seekbar/volume and the casting screen flip to the TV only on `remote` — gating them on `active` puts two writers on one seekbar. **The prepare rung spawns the ffmpeg CLI, and both platforms now ship one.** Windows: `ffmpeg.exe` from the BtbN SDK, a 0.5 MB shim over the bundled DLLs. macOS: Homebrew's `ffmpeg` binary relinked by `scripts/bundle-macos-libs.sh` — it is a shim over the very dylibs that script already bundles, so it joins the closure as a root (which is how libvmaf arrived), gets its load commands rewritten to `@rpath` and **one** rpath, `@executable_path/lib`. One is enough because the CLI is placed so that the relative position is identical in both layouts: `target/<profile>/ffmpeg` beside `target/<profile>/lib` in dev (build.rs copies it), and `Contents/Resources/ffmpeg` beside `Contents/Resources/lib` in the bundle. That is also why `ffmpeg_bin()` takes an `AppHandle` and probes the **resource dir**: on macOS the exe lives in `Contents/MacOS`, so "next to the exe" and "next to the resources" are different places, and the Windows-shaped lookup found nothing inside a `.app`. Consequence for a fresh macOS checkout: `bundle-macos-libs.sh` must run before the first build, because `ffmpeg-macos/bin/ffmpeg` is a declared bundle resource and **a resource pattern that matches no file fails tauri-build** — the same trap that broke the macOS build when `ffmpeg/bin/ffmpeg.*` was added to the base config without its `null` twin in `tauri.macos.conf.json` (a Windows-only resource needs that twin the day it is added; the platform config is merged even for a bare `cargo check`). **The transport is no longer a setting, and that is a conclusion.** The «ТВ» tab (two-character label on purpose: the nowrap tab row silently clips an eighth wide tab) held a `prepare`/`hls` pill; it is gone, because HLS was built to stream an incomplete torrent and both halves of that job went elsewhere — DLNA carries the release untouched, a direct-play file streams over Cast as it is — while measurement showed HLS carries only H.264 with stereo. As a choice it was worse on everything it could carry and unable to carry the rest: a menu entry whose every selection makes the result worse. The code path survives for the one case neither other reaches (a receiver with no DLNA, an incomplete torrent needing repacking — not yet wired) and as a debugging knob (`localStorage frameplayer.castMode = 'hls'`). What remains in the tab is the cache: its cap, the cache cap (0/5/20/50 ГБ — travels to `prune_cast_cache` as a parameter; zero also deletes the served copy at session end), the measured size and a clear button. **A per-device check lives in the picker instead** (`cast_diagnose`, the gear panel): our address on the device's subnet, the Chromecast port and handshake, the renderer's description, its accepted formats, whether it offers `Seek`, and what it says about volume — every one of them a question the normal flow already asks and throws away, written down here with a copy button, because on somebody else's television the difference between "the network cannot reach it", "the receiver refused the file" and "this device does not do that" is invisible from outside and decides everything. It deliberately stops short of `LAUNCH`: answering a diagnostic question by starting an app on someone's TV is a surprise. Three things about its shape. **Rust returns an id and data, never prose** — the report is shown in a localised window and Rust cannot reach the dictionary (the macOS menu's problem again), so a check names itself with a stable id the frontend translates, and `detail` carries only what this side knows: addresses, lists, the device's own error text. The frontend adds the sentence from `diag.<id>_<state>` **when there is one to add** — `t()` echoing an unknown key is the signal that the data speaks for itself. **The report is a dialog, not a panel inside the picker**: eight lines of prose in a 280px column that scrolls is a list of two-word fragments. And **the button is small and the row says what it is for** — `Не получается транслировать?` beside a link-sized `Проверить`, because a lone "check this device" is a button whose purpose the viewer has to guess, and a full `.btn-outline` there reads as the panel's main action rather than as a way out of a rare problem. `cast_hls_prepare` builds a full VOD rendition (TS segments) into a transient `cast/.hls/<rand>/` dir — removed at disconnect, on displacement by a track switch, and swept at the next HLS start minus the served dir; the server's directory mode validates the path after the token to one flat non-dot component. In HLS mode even direct-play files go through the segmenter (the mode is the transport) — **except HEVC, which cannot go over HLS at all and silently takes the progressive rung instead**. **The two transports have different codec ladders, and that is measured rather than assumed**: progressive reaches the TV's own decoder, so 4K HEVC HDR10 and E-AC-3 5.1 passthrough both work; HLS goes through the receiver's browser pipeline, which on the measured television takes **H.264 + AAC stereo and nothing else** — E-AC-3 refused in TS and in fMP4 and refused again when a master playlist merely *declares* `CODECS="ec-3"`, AC-3 refused, HEVC refused the same way with `hvc1` correct, and AAC **5.1** accepted and then killed the receiver app a few segments in. So `cast_hls_prepare` always transcodes audio to AAC stereo (`transcode_audio` describes the progressive rung and is deliberately ignored there), `hlsVariant()` answers `null` for anything but H.264, and the settings hint says the mode costs surround. **That fold-down must carry the LFE by hand, because a plain `-ac 2` deletes it** — measured on the rotating-tone file, the LFE second goes from −13.9 dB in the source to **−90.3 dB** in the downmix, which on a soundbar is the most audible thing about the mode; `lfe_mix_level` on the resampler does nothing, so a `pan` matrix (ITU coefficients normalized by 1/(1+2·0.707), LFE at the same weight as center and surround) puts it back at −16.8 dB with the file's peak *lower* than before. It is written in channel **indices** and applied only at exactly six channels: 5.1 and 5.1(side) share the order FL FR FC LFE S/BL S/BR, and a formula written with channel names silently fails on whichever of the two it was not written for. The progressive path is untouched by all this and is where surround actually lives — **E-AC-3 5.1 passthrough is confirmed by ear** (the LFE reaches the subwoofer, which a fold-down cannot fake). **The LOAD must carry `hlsVideoSegmentFormat` and never `hlsSegmentFormat`**: the latter is the format of an HLS *audio* segment, and sending it beside a muxed A/V stream made the TV reject the LOAD with a bare `LOAD_FAILED` — no `detailedErrorCode`, after it had already fetched the playlist, the init segment and segment zero. That one field cost fMP4 entirely and read as "the receiver cannot do fMP4", because fMP4 was only ever tried with HEVC, which fails for its own unrelated reason. Two properties of that receiver worth keeping in mind whenever a LOAD fails: **a bare `LOAD_FAILED` carries no reason at all** on that device, so the HTTP log is the diagnosis (nothing fetched = the request was refused; playlist only = it would not parse; init + a segment = the media was refused), and **a rejection by declared codec arrives before any segment is fetched**. `load_probe` in cast.rs is the tool that produced all of this — it drives a whole cast (bind, LAUNCH, LOAD, watch, stop) from `cargo test` against a rendition built by hand, so a receiver question costs one command instead of a GUI run and a copy-pasted log. **Complete torrent files cast** via `resolveCastSource` → `torrent_local_path` (complete only — sparse holes read as zeros). **An incomplete one streams, and only over DLNA**: `cast_serve_torrent` registers `(info hash, index)` in place of a path and the LAN server streams through `TorrentService::serve_file`, i.e. librqbit's blocking reads, so the television's Range requests become piece priority exactly as mpv's do — reading the sparse file instead would serve zeros silently. **Two doors, and neither is a preference.** A renderer that lists the container takes the release untouched — the wide one, since torrents are MKV. A Chromecast takes an incomplete torrent only when the verdict is `direct`, i.e. the file needs no repacking at all: it then fetches over HTTP with Range exactly as it fetches a prepared file, so "not finished" stops being a reason to refuse (`cast_load_url` LOADs a URL somebody else registered, the Cast twin of `dlna_load_url`). Anything that would need preparing still waits for the whole file, and that is not a limitation to lift later — half a film remuxed is half a film, so no amount of progress changes the answer; only completion does, which is why the picker re-reads the plan while a torrent source is open. A lead of `STREAM_LEAD_BYTES` is built before the LOAD, announced and capped, because the receiver's tolerance for a blocked read is the one thing about this rung that cannot be known from the sender side. **Every transport that borrows the LAN server must release it** — DLNA ends through its own disconnect and used to leave the server up, so the token outlived its session, which is the single promise that server makes. Known limit: `-c:v copy` cuts segments at keyframes only, so a file with minute-long GOPs degrades HLS to giant segments (real releases are 2–4 s). `docs/casting.md` carries the measured numbers behind all of this — the audio transcode at 276× realtime is why local-file seeking is solved by preparing the whole file rather than by segmenting it.
- **DLNA is the second way to a television, and the one that asks the least.** A UPnP MediaRenderer *is* the TV's own player, so a release it already decodes plays untouched — measured on the real set: a 6.3 GB 4K HEVC Main-10 HDR10 MKV with E-AC-3 5.1, no prepare, no remux, seeking included. It reuses the Cast half wholesale: the same Range server (`cast::serve_one_file`, which honours the private-root rule and is therefore the **sixth** privacy enforcement point), the same status shape, the same store, seekbar, keys and casting screen; the frontend only picks which command name to invoke (`dlna_*` against `cast_*`), which is why the transport cost the UI almost nothing. Four rules it added. **The picker is one row per television, merged by IP address** — the same set answers on both protocols and cannot be joined by identifier, measured: its Cast id and its renderer's UDN are different UUIDs. **The remembered profile is keyed differently from the merge** (`frameplayer.tv-devices`): an address is a DHCP lease, so a profile is filed under the most stable id the device has and matched by name+model as a fallback, because an LG renderer's UDN looks service-scoped and may not survive a reboot. **A row must not pass judgement on what it does not know yet**: SSDP sweeps for the first seconds, so a device whose DLNA half has not arrived is not a device without DLNA — for a torrent still downloading that difference *is* the answer, and a half-downloaded film was being told to finish first. The line says it is checking until the sweep settles, but only where the missing half could change the verdict (a file the Cast rung already plays untouched says so at once). **The picker reasons about the resolved source, never about `player.filePath`** — for a completed torrent those are different things (the player holds a loopback URL, the cast is pointed at the file on disk), and asking the URL made `isNetworkSource` true, so auto answered "Chromecast" for a file that in fact goes over DLNA: the row contradicting what clicking it does. The resolved path lives in `cast.plan.src` beside the verdict, computed once per picker opening. **The row states a consequence, not a protocol** ("играет как есть" / "подготовка перед стартом" / "поток · звук стерео"), computed once per picker opening from the file's verdict; auto prefers DLNA whenever the renderer's `GetProtocolInfo` lists the container — that Sink list is the capability API Cast never gave us. The protocol names live under a per-row gear, which **expands the row in place rather than opening a second floating panel**: a panel hoisted out of the picker would need the context menu's hover bridge, its click guards and its narrow-window drill-down, all for one control. And **seekability is declared in the DIDL metadata, not in HTTP headers** — with a bare `<res>` the TV grays out its own seek buttons before fetching a byte and answers a sender `Seek` with "not available"; with the DLNA flags in `protocolInfo`, `size` and `duration` (read from the container via libav) it reads the MKV's cues itself and range-requests the offset. Known device quirk, and the reason the volume slider stays disabled there: this TV answers `GetVolume` with a valid `0` while playing at almost full, and refuses the action outright to another client, so a level is trusted only once a non-zero one has been seen — and **mute is disabled with the slider**, because it is part of the same control rather than a capability of its own, and a device that ignores a volume ignores a mute too (the icon flipping back by itself is what that looks like; the keyboard path keeps the explanation). **Audio tracks cannot be switched over DLNA at all**, and that is read from the renderer rather than assumed: its AVTransport declares `SetAVTransportURI, GetMediaInfo, GetTransportInfo, GetPositionInfo, GetDeviceCapabilities, GetTransportSettings, Stop, Play, Pause, Seek, Next, Previous, GetCurrentTransportActions, SetNextAVTransportURI, X_LG_Seek` and its RenderingControl adds `X_GetSubtitle`/`X_SetSubtitle` and a 3D formatter — vendor extensions exist here, and none of them is about audio. So the file goes over with every track in it and the television chooses; the only alternatives would be its own remote or an explicit remux that copies the whole film to drop tracks, which would cost exactly what this transport exists to avoid. (`X_SetSubtitle` is the lead for subtitles over DLNA when phase 3 comes.) Because the choice cannot be read back either, the track menu **says so** while a DLNA session runs instead of showing a selection it cannot vouch for. **An optimistic state has to outlive the renderer's report, or play/pause looks broken**: this TV answers `Pause` properly and then keeps saying `PLAYING` for a poll or two — after a load it says `TRANSITIONING` six times — so the next status overwrote the optimism and the button sprang back, which is the seekbar's `seekSettling` problem in another costume and gets the same answer (a 2.5 s window in which a command's own state outranks the poll). Related, and the reason that bug hid: **a refused command must not vanish into an empty catch** — refusals here are meaningful (606 "not authorized", 701 "transition not available"), so they raise an OSD. Two more rules the same live session produced. **The optimistic state is armed before the round trip, never after**: a SOAP call takes a few hundred milliseconds and the frontend polls twice a second, so setting it afterwards leaves a gap for a poll to read the state mid-change — which is exactly the resume flicker (new icon, old icon, new icon again); armed first, the window does not exist, and a refusal rolls the value back. **`Stop` goes before every `SetAVTransportURI`**: a renderer that is already playing refuses a new URI with 701, and it will be playing more often than not — the previous session, a session that did not end cleanly, another sender on the same television. **A refused `Play`, on the other hand, is not a failed load** — and reading it as one is what made a perfectly good cast report that the television could not open the file. The measured renderer starts fetching on `SetAVTransportURI` alone, so it answers `Play` with 701 *while already doing the thing being asked of it*, and how long that lasts scales with the file rather than with our requests: on a 10 GB 2160p HDR MKV it stayed `TRANSITIONING` from the first poll to the last, served a HEAD, a read from byte 0, then the Matroska cues from the 10 GB mark ~18 s in — while a fixed six-attempt budget expired around seven seconds and tore the session down, and the same cast succeeded at once on a second try against a player that was by then already up. So the loop **asks `GetTransportInfo` rather than counting refusals**: `PLAYING` or `TRANSITIONING` both mean started, only "still neither when the wall-clock budget runs out" is a failure, and that budget stays inside the frontend's own `START_TIMEOUT_MS`, because judging whether a television that took the file ever shows anything is that detector's job. Every refusal is printed, since collapsing them all into `load_failed` is what made this indistinguishable from a file the set cannot decode — it took a `FP_CAST_DEBUG` wire log to tell apart. The resume `Seek` that follows stays best-effort: a renderer still `TRANSITIONING` has no index yet and cannot turn a time into an offset, and losing the resume point is a far smaller failure than refusing the load over it. And **click-to-pause inverts its trade while casting**: locally the toggle fires immediately because a double click cancels itself and half a second of delay on "resume" costs more than the artifact, but on a television a pause and a resume 100 ms apart is a decode restart rather than a frozen frame, while the delay is free next to the remote's own latency — so the cast path waits out the **system's** double-click interval (`double_click_time`, which had been registered and unused until now) and the double click cancels it. The casting screen carries the same handler, or the gesture the player is built around stops existing the moment a cast starts. `dlna.rs` also carries the two things that make a device answerable without the GUI — `FP_DLNA_PROBE=1` dumps what the network holds and what each renderer accepts, and `FP_DLNA_PLAY=<file>` drives a whole session *through the shipping commands*; both must run inside the app, because macOS silently drops multicast for a process without Local Network permission and a CLI probe reports an empty network whatever is on it.
- **Everything DLNA knows about a television has to be read off that television, because the next one is a different make.** Every rule above was measured against one set, and the failure mode of measuring against one device is that the code encodes it — silently, since a renderer that disagrees does not report an error, it declines. Six places where that had happened, and the shape each one takes. **The MIME spelling is the device's, not ours** — a container has several live names (Matroska is `video/x-matroska`, `video/x-mkv` and `video/mkv`; AVI has four), a strict renderer answers a name it did not list with UPnP 714, and `cast_mime` — written for the Cast ladder, where anything but MP4 and WebM is prepared first — returns `application/octet-stream` for exactly the containers only this transport carries. So `negotiate_mime` picks whatever the `GetProtocolInfo` Sink list advertises and falls back to our own first spelling, never to octet-stream. It is matched **case-insensitively on both sides**, and `mime_candidates` in dlna.rs and `DLNA_MIME` in cast.svelte.ts answer *different* questions — what to send, and whether to offer the device at all — so a spelling missing from the frontend copy is a television that reads as incapable with nothing on screen to say why. Keep them in step; a divergence now costs a worse guess rather than a failure, because Rust re-negotiates what the frontend chose. **`REL_TIME` is not the only seek unit** — `ABS_TIME` is all some renderers implement, so `seek_to` walks a ladder and remembers what worked; deliberately a runtime probe rather than a reading of the SCPD's `A_ARG_TYPE_SeekMode`, since a device that declares a mode may still refuse it, which is this very television's habit with `Seek` while paused. The resume seek after a load pointedly does **not** teach the ladder: a refusal there means "too early", not "wrong unit", and recording `ABS_TIME` from it would pin the session to the fallback. **`URLBase` outranks the LOCATION** for resolving control URLs — deprecated in UPnP 1.1 and still emitted, sometimes on a different port, in which case every control URL is silently wrong; and a path-relative URL resolves against the description's *directory*, not the origin, which is a fix to a test that had been asserting the bug. **A description may hold more than one device**: the spec lets a root device embed others, so a combined server+renderer box gave its MediaServer's ConnectionManager to a walk that took every `<service>` in the document — and where the root *is* the server, the renderer was dropped from the picker entirely. `renderer_device` narrows to the MediaRenderer's own subtree, and only on a positive identification, so an unrecognised device keeps the old whole-document reading rather than disappearing. **The opposite rule holds in upnp.rs** — an InternetGatewayDevice keeps its WAN services two levels down, so narrowing there would find nothing; the two modules read the same shape of document for opposite reasons, and the note at each end says so. **The DIDL is escaped twice, and one round was missing** — it is a document embedded as *text* inside `CurrentURIMetaData`, so the title is escaped for the DIDL and the whole DIDL escaped again for the envelope; escaping once means the receiver unescapes once and hands its parser a bare `&`, which any film with an ampersand in its name produces and a strict renderer rejects outright. **And reqwest sends no `User-Agent`** — the trap the tracker announce already paid for, now closed for every UPnP call by one shared client, which also keeps a connection pool alive across the poll's several SOAP actions a second. Two smaller ones in the same sweep: `RelTime` is optional and is answered `NOT_IMPLEMENTED` by real devices, so the position falls back to `AbsTime` or the seekbar sits at zero for the whole film; and `CurrentTransportStatus` reaching `ERROR_OCCURRED` **before the first `PLAYING`** is a load that died, which beats waiting out the frontend's eight-second "fetched and never played" detector — after a `PLAYING` it is ignored, since a device that stumbled and recovered must not have its session torn down.
- **The tolerance of the string-scanning XML lives in one function, and it is the price of not taking a parser.** `tag`/`chunks` compare a **local** name against everything up to the first whitespace, so an attribute (`<friendlyName xml:lang="en">`), a namespace prefix (`<av:CurrentTransportState>` — the schema says out-arguments are unqualified and not every renderer obeys) and an empty element all read correctly, while the delimiter check keeps `deviceType` from answering a search for `device`. Anything shown to a person goes through `unescape` as well, or a set called "Living Room &amp; Kitchen" is listed as its markup. The module header is no longer "recon-shaped, parsing gets a real dependency if the branch proves out" — the branch proved out and shipped, and the decision now is that a dozen leaf elements do not justify a crate plus its licensing entry. **If this ever needs a third special case, take the dependency instead.** What makes that affordable is that all of it is pure: `parse_description` is split from the fetch precisely so a device nobody here owns can be reproduced as a fixture, and the vendor shapes above are pinned that way. Nothing in the transport half is — `soap`, the poll, the play budget, the paused-seek workaround are covered only by `FP_DLNA_PLAY` against a real television, which must run inside the app.
- **Discovery is multicast, and a router may not carry multicast between the machine and the television — so every search is also a unicast sweep.** A machine on a cable or 5 GHz and a television on 2.4 GHz can share a subnet, route unicast to each other and never see each other's group traffic, which leaves the picker empty for a device that would cast perfectly. A precaution, not a measured fix: no such router has been tested yet. While the picker is open each address is asked directly — Cast by `probe_cast` (`:8009` connects, then `:8008/setup/eureka_info` names it; failing that, a TLS handshake on 8009 admits it under its address), DLNA by unicast `M-SEARCH` to `host:1900` (`ssdp_sweep`). **Do not replace the Cast half with an mDNS query aimed at the host**: measured, a Cast device ignores it in every form (ephemeral port, 5353, QU bit) while the router answers the same packet. **Which addresses is the rule:** `frameplayer.tv-hosts` first (the last `HOSTS_LIMIT` addresses any device answered at — a hint, not an identity), then every host of each private interface's subnet, whole up to `WIDEST_PREFIX` (/22) and only the surrounding /24 beyond it; tunnels and virtual switches are skipped by name (`is_tunnel_name`), because a video player must not sweep somebody's corporate VPN. `SWEEP_PARALLEL` × `SWEEP_CONNECT` is the round time (6 s for a /24, measured), `SWEEP_CONNECT` is 3 s because a Wi-Fi device on power save missed 1.5 s, and swept devices age out after `SWEEP_FORGET` since nothing announces a departure. A device multicast also found is shown once, as the multicast entry (`Discovery::list`). It does not help against client isolation or a guest network: there the television could not fetch from our server either. `FP_TEST_CAST_IP=<ip>|sweep` runs `cast::tests::unicast_probe_smoke` against the real LAN.
