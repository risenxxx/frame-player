# Bundling, licensing and releases

What ships inside the application, the LGPL and GPL obligations that follow, code signing on both platforms and the release workflow.

Part of the rule book: [`CLAUDE.md`](../../CLAUDE.md) carries the one-line
version of each rule here, this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.
The *why* behind it — what was tried, what was measured — is in
[`../distribution.md`](../distribution.md).

- **Everything the player needs at runtime is bundled; yt-dlp is the single exception.** `src-tauri/lib` carries libmpv, the wrapper and every transitive dependency (~65 MB and ~50 dylibs on macOS: FFmpeg, libass, libplacebo, MoltenVK, LuaJIT, x264/x265, OpenSSL…; on Windows `libmpv-2.dll` plus the FFmpeg SDK in `src-tauri/ffmpeg`, both fetched by `scripts/fetch-libs.ps1`). `build.rs` lays them out next to the dev exe and declares two rpaths — `@executable_path/lib` for dev and `@executable_path/../Resources/lib` for inside a `.app` — and `bundle.resources` puts them in the installer. So nothing is taken from the user's system: a machine with no Homebrew and no FFmpeg runs the player. **Nothing may block `init(mpvConfig)`** — whatever waits there holds up the whole window, and until mpv is up a click on a file does nothing at all, which reads as a dead player rather than a slow one. The lesson cost a session: the yt-dlp probe ran `yt-dlp --version` to prove the binary worked, and that call takes **11 seconds** on a macOS universal build (a 36 MB PyInstaller bundle that unpacks itself and is re-verified by the system on every exec) — twice over, before init, so the player ignored roughly the first twenty seconds of clicks. The probe now only *looks* (file present, executable bit set) and is not awaited; a broken binary is caught where it matters, when a link fails and the dialog offers to install or update. **yt-dlp alone is looked up at runtime** and is optional by design — without it, local files and direct links still work and only websites do not, which the link dialog says. It can also be installed from that dialog, into `<app_data>/bin` — the only place we may overwrite afterwards, since Program Files needs administrator rights and a binary inside a `.app` cannot be replaced without invalidating the signature. **Keeping it current is yt-dlp's own job, not ours**: `-U` fetches the release, checks it against the signed checksums published with it and replaces the binary in place, so writing a downloader would mean reimplementing verification that already exists and is maintained by people shipping it every few weeks. We only fetch the *first* copy. The update button appears **only for the copy we installed** (`managed`) — a Homebrew or pip install belongs to its package manager, where `-U` either refuses or starts a fight. Expect staleness rather than absence to be the failure: a September 2025 build already fails on YouTube, so a failed link reopens the dialog with that explanation and the button, instead of a popup that fades before it can be acted on. **macOS ships too, and `bundle.targets: ["nsis"]` in tauri.conf.json is only half the story**: `tauri.macos.conf.json` overrides it to `["app"]` and is what `bun run tauri:macos:build` (and CI) uses. The release workflow builds the `.app`, then packages the dmg in a step of its own — Tauri's `bundle_dmg.sh` drives Finder over AppleScript to place the icons, which a headless runner has no session for, so it passes silently and ships an image with no `.DS_Store` that opens as a plain folder; `dmgbuild` writes one directly. **The macOS build is signed with a Developer ID and notarised, and the two things that decide are the hardened runtime's, not Apple's paperwork.** The chain is `macos-sign.sh` (imports the certificate, signs the 35 dylibs and the ffmpeg CLI) → `tauri build` → `macos-notarize.sh` on the `.app` → `build-dmg.sh` → `macos-notarize.sh` on the image, and the order is load-bearing at both ends. The libraries are signed **before** the build because they reach the bundle as `bundle.resources`, i.e. copied in carrying whatever they already had — the ad-hoc signature `bundle-macos-libs.sh` applies after rewriting their load commands — and an ad-hoc Mach-O anywhere inside fails notarisation on identity; signing them inside the built `.app` instead would break its seal and force the image and the updater archive to be rebuilt. At the other end, `macos-notarize.sh` **repacks `.app.tar.gz`**, because Tauri writes it during the build, i.e. before the ticket exists — ship it unrepacked and the disk image is notarised while every automatic update carries an unstapled bundle, which is the failure that only reaches existing users. Two entitlement facts, both measured against a probe that loads the bundled libmpv with `zoompan.lua` under each signature (LuaJIT 2.1 is what `zoompan.lua` runs on): **`com.apple.security.cs.allow-jit` does not work** — it authorises `MAP_JIT`, which this LuaJIT does not use, and the process dies with `EXC_BAD_ACCESS`, "Invalid Page", faulting inside a private `r-x` `VM_ALLOCATE` region — while `allow-unsigned-executable-memory` alone does, so that is the file's single entry. And **the hardened runtime is only turned on when there is a real certificate** (`macos-build.sh`), because it enables library validation, which requires every dylib to carry the process's Team ID: with a Developer ID that is free, and ad-hoc code has no Team ID at all, so the ad-hoc fallback dies at launch on `Library not loaded: @rpath/libavutil.60.dylib … (non-platform) have different Team IDs`. Three traps around that. `hardenedRuntime: false` **does not turn it off on its own** — measured on CLI 2.11.4, a config naming an entitlements file is signed `--options runtime` regardless, so the override has to clear `entitlements` too (verified it is the bundler and not codesign: `codesign --entitlements … --sign -` without `--options runtime` gives a plain `0x2(adhoc)`). A probe that `dlopen`s the libraries survives all of this, so **testing the library set in isolation proves nothing about the bundle** — only launching it does. And `codesign --verify --deep --strict` passes on the broken bundle in silence; the symptom is a crash dialog offering to report to Apple. The ad-hoc path is still exactly what shipped for the first thirty releases and is what a checkout with no Apple account produces: sealed but uncertified, which Gatekeeper stops with an **Open Anyway** button rather than the *"file is damaged"* dead end that an unsealed binary gets.
- **The application is GPL-3.0-or-later, and that is the conclusion the LGPL work was for.** Keeping every bundled library strictly LGPL bought exactly one thing: the freedom to make this player closed or paid. MIT — which the project carried by default — handed that same freedom to anyone who wanted to close a fork and sell it, which for an *application* buys nothing back: permissive licensing pays off for a library, where the win is being embedded, and users of a player install a binary. Copyleft costs the sole copyright holder nothing (dual licensing stays available) and costs a closed fork everything. **3.0 rather than 2.0** because 306 crates in the graph are Apache-2.0, which is incompatible with GPL-2.0-only; the whole graph was checked and is GPL-3-compatible, including the odd ones (`webpki-roots` is CDLA-Permissive-2.0, a certificate dataset with no copyleft). The App Store argument does *not* apply here and should not be reached for — that channel is already closed by the private API the embedding depends on (`distribution.md`). GPL §4 also means `LICENSE` itself is now a bundle resource, and `gen-notices.mjs` embeds it as the last section of the notices, read from the file rather than restated — so editing one without the other leaves the committed notices stale and the gate fires.
- **Licensing is a build output, not a document somebody remembers to update.** The player links libmpv, FFmpeg, libplacebo, GLib, FriBidi, Graphite2 and the gettext runtime — all LGPL-2.1 — which a proprietary application may do under §6, but only against three obligations the bundle carried *none* of until this existed: a prominent notice naming the libraries, a copy of the license, and a route to the source. `THIRD-PARTY-NOTICES.md` is all three, it is a bundle resource on both platforms (`"../THIRD-PARTY-NOTICES.md": "./"` — traced through `tauri-utils::resources`: a pattern **without a `*`** is a plain file, and for a plain file a *non-empty* destination becomes the target path itself, so `{"x.md": "./folder/"}` writes a file literally named `folder`; `"./"` normalises to empty, which is the branch that keeps the file name), and `build.rs` copies it beside the dev exe so the settings-footer link works while developing rather than only in a release nobody clicks. What keeps it true is the coverage check: **every dylib in `src-tauri/lib` must be named by the manifest**, or rendering fails. That check must match by declared name plus a version suffix and never by stripping digits — the digits in `libX11`, `liblcms2`, `libpng16` and `libpcre2-8` are part of the name, and the first version of it reported three covered libraries as missing, which is the failure mode that gets a gate weakened instead of fixed. Three traps in the data itself, all found by looking rather than trusting: a keg's `COPYING` is often a **pointer** (pcre2's says "see LICENCE", FreeType's describes two licenses and ships neither), **gettext's `COPYING` is GPL-3.0** because it covers the tools while we ship only the LGPL runtime, and **Homebrew's `license` field describes Homebrew's build** — its `ffmpeg` is GPL-3.0 and its `mpv` is GPL-2.0, so copying that field would have labelled our own `--disable-gpl` builds as GPL. Hence `license` in the manifest means *the artifact we ship*, with `note` recording which option was taken where a project is multi-licensed. Windows was audited the same way and is LGPL too, proven from mpv's own configuration string embedded in `libmpv-2.dll` (`-Dgpl=false -Drubberband=disabled`): the alarming strings there are innocent — `x264` is libavcodec's SEI **decoder**-side encoder detection (zero encoder symbols), `modplug` is libopenmpt, `xvid` is the MPEG-4 decoder's quirk table. Its component list is deliberately *over*-inclusive and carries no `libs`: `fetch-libs.ps1` takes the **latest** upstream release, so a list read out of today's DLL would be stale within a week, and listing a component the current build lacks costs nothing while omitting one it has is the actual violation. **The rendered file has to be byte-identical on every machine, and the first version was not.** `--check` compares a fresh render against the committed copy, so anything that varies by platform makes the gate fail somewhere and only somewhere: one upstream text (libopenmpt's) ships with **CRLF**, git normalised it to LF in the blob while leaving the working copy alone, so the machine that fetched it embedded CRLF into the notices — and the Windows runner, checking *everything* out as CRLF against `\n` joins, produced a third string again. The CI failure reproduces exactly by CRLF-ing a copy of the tree and running the old script: same two digests. Fixed at the read — every input is normalised to LF, so the output depends on content and not on anybody's `core.autocrlf` — with a scoped `.gitattributes` (`LICENSE`, the notices, `licenses/**` → `eol=lf`) keeping the working copies matching their blobs. Both are kept deliberately: the script guarantees the comparison, the attributes guarantee the files, and neither substitutes for the other. **Showing them is a surface of its own**, because pointing at the file is not showing it: `revealItemInDir` gives a location, `open-path` is not in the capabilities (its permission needs a scope), and a `.md` has no reliable handler on Windows. So `third_party_notices` reads the resource in Rust — a filesystem plugin to read one read-only document we ship ourselves would be a far wider permission than the job needs — and `LicensesDialog` renders it as selectable text (the page sets `user-select: none`, which every child inherits, and WebKit still needs the prefixed property). Measured in a WKWebView harness rather than feared: 560 KB is **171 075 px** of `pre-wrap`, 52 ms of forced layout, 263 ms from load to ready and instant scrolling — no reason to split it. It is a layer *above* the settings sheet in `closeTopmost`, so Escape gives the settings back. **On macOS the About panel takes `credits`, never `license`**: `orderFrontStandardAboutPanel` has a fixed key set and muda passes only ApplicationName, ApplicationVersion, Version, Copyright, ApplicationIcon and Credits — `AboutMetadata.license` is for the Windows and Linux dialogs and is dropped in silence here, which is how the first attempt shipped a panel showing nothing but a name and a copyright line. And **`licenseFile` is deliberately unset**: traced to `!insertmacro MUI_PAGE_LICENSE` in the NSIS template, it adds an "I agree" page to the Windows installer and is not read for `.app` or `.dmg` at all — so it buys no part of the obligation and would make the two platforms' installs differ.
- **Releases**: `bun run set-version release` (the bump the pending changesets call for), or `0.21.0` / `patch` / `minor` / `major`, then push to main — see the release-notes line below for what that bump also writes. **Five files carry the version** — package.json, package-lock.json, tauri.conf.json, Cargo.toml, Cargo.lock — and they cannot be collapsed into one: `tauri.conf.json`'s `version` accepts a path to a package.json instead of a literal, but the release workflow reads that literal with `jq` to decide whether a push *is* a release, so making it indirect would leave the gate with nothing to compare; and Cargo cannot read a version out of JSON at all. So `scripts/set-version.mjs` writes them, with one anchored line per file rather than a JSON round-trip (which reformats tauri.conf.json's hand-written inline arrays — measured on the `endpoints` array) and with **every anchor required to match exactly once**, since a bump that silently skipped a file is the whole failure being prevented. Run with **no argument** it reports instead of writing and exits non-zero on disagreement: worth doing before a release, because this drift is invisible — `package-lock.json` had been sitting at **0.1.0** since the first commit, which is exactly what the script found on its first run. `src-tauri/tauri.conf.json` remains the authority: a `patch`/`minor`/`major` bump is measured from what *it* says, whatever the others have drifted to. CI needs repo **secrets** `TAURI_SIGNING_PRIVATE_KEY` (passwordless), `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ACCOUNT_ID` and `FP_OPENSUBTITLES_KEY`; six more for macOS signing — `APPLE_SIGNING_IDENTITY` (the whole `Developer ID Application: … (TEAMID)` string), `APPLE_CERTIFICATE` (base64 of a `.p12` exported from **My Certificates**, which is the view that carries the private key with it) and `APPLE_CERTIFICATE_PASSWORD` for the certificate, plus `APPLE_API_KEY`, `APPLE_API_ISSUER` and `APPLE_API_KEY_P8` for notarisation. **Every one of those six is optional**: without them the build is ad-hoc and the notarisation steps skip themselves, saying so in the job summary — a fork can still cut a release. Plus repo **variables** `R2_BUCKET_UPDATES`, `R2_BUCKET_LIBS`, `R2_PUBLIC_URL_UPDATES`, `R2_PUBLIC_URL_LIBS` — bucket names and public URLs are not secrets, and as variables they are readable in a failed log instead of appearing as `***`, which is the difference between diagnosing a 404 and guessing at one. Each is guarded against being empty, because an unset variable expands to nothing and would otherwise upload to `s3:///` — the OpenSubtitles *application* key, baked in with `option_env!` at build time. Two things about that one. It is not really a secret (it identifies the app, not the user, and cannot be hidden inside a desktop binary); what a leak costs is **availability**, since abuse gets it revoked and subtitle search then breaks for everyone at once — which is why `opensubtitles.rs` looks in `<app_data>/opensubtitles.key` *before* the compiled-in value, so a revoked key can be replaced without a release. **Nothing delivers that file yet**: today it is a manual escape hatch, and wiring it to the signed R2 channel next to `latest.json` is the piece still missing. And `option_env!` is read at compile time **without** registering a dependency on the variable, so `build.rs` carries `rerun-if-env-changed=FP_OPENSUBTITLES_KEY` — without it a warm target directory keeps baking in the previous key. An absent secret is not a build failure: the feature simply reports that this build has no key. Updater pubkey lives in tauri.conf.json. **The `publish` job needs its own checkout, and it has to be the first step**: the job began life as downloaded artifacts and nothing else, so it had none — and the moment it called a script from the repository it died with a 127 *after* every artifact and `latest.json` were already uploaded, leaving the update channel live and no GitHub Release at all. Order matters because `actions/checkout` clears the workspace before cloning, so placed after the download it would delete `dist` and the failure would read as the build producing nothing. The same incident moved the retention sweep **after** `Create Release` and into a step of its own: it had been the tail of the upload step, which put the least important thing in the job in front of the most important one. It still fails loudly rather than being swallowed — pruning that quietly stopped working is how the bucket reached nine gigabytes.
- **A Windows update replaces the files in place, and the one thing it may not do is change which files there are.** Two artifacts and two manifest keys: `windows-x86_64` is the NSIS installer and stays what every client older than this reads, `windows-x86_64-zip` is the installation itself as a zip (`scripts/pack-windows-update.ps1`, built from `bundle.resources` and the main binary, signed with the same minisign key, published alongside). The client is `src-tauri/src/update.rs` — `update_check` (the in-place key first, the installer key second, so a release that published only the installer is still announced), `update_prepare` (download, unpack, decide) and `update_commit` (swap, relaunch) — and the frontend's button is unchanged on both platforms. **The Windows file semantics are measured, not assumed**: with the process running and the images mapped, renaming a loaded DLL inside its directory **works**, renaming the running `.exe` **works**, writing a new file at the name just vacated **works**, *deleting* the renamed image is **refused** (access denied), and deleting it after the process exits works — so the swap is two renames per file (target → `*.fp-old`, incoming into its place) and the leftovers can only be removed by a later process. Which is why the relaunched copy is spawned with `--after-update=<pid>` and **waits for that process id** before it sweeps: not only for the files, but because the single-instance guard is a named mutex plus a window, and a copy that finds the window hands over its argv and exits — i.e. the player would vanish after updating. (A directory holding a loaded DLL *can* be renamed, measured, contrary to the usual telling; per-file is what runs because it is what rolls back one file at a time.) **The file set may not change**, because the NSIS uninstaller deletes a list fixed when it was written and only an installer run rewrites it — so a release that renames a library would leave ninety megabytes behind after an uninstall, in silence. `file_sets_match` compares the incoming paths with what is on disk (a *walk* of the installation, so the first in-place update needs no transition release; `uninstall.exe`, the staging directory and any top-level dot-entry are excluded, the last of those being the room a portable copy's marker will need) and anything else takes the installer, which rewrites the uninstaller as it always did. **That comparison is also what makes this safe to ship**: if the zip's layout ever stops matching what the installer lays down, every client refuses the swap and falls back, so the failure mode of getting the packaging wrong is last year's update path and not a broken installation. The rest, briefly: the staging directory is `<install>.update`, inside the installation so that every move into place is a rename on one volume rather than a copy of 260 MB; a file whose sha256 already matches the manifest is **neither unpacked nor moved**, so the usual release swaps one file; `swap.txt` lists the moves before the first rename and the next launch finishes an interrupted swap from it (idempotent by construction — an entry whose incoming file is gone from staging has already been applied); `DisplayVersion` and `EstimatedSize` are written afterwards and never fatally, since a stale line in Apps & Features is not worth refusing an update over; and `uninstall.exe` is never in the payload and never swapped. **Compression is deflate and that is a measurement**: 259.8 MB of installation is 105.9 MB deflated against 85.6 MB for the solid-LZMA installer, where zstd-19 would give 93.0 MB at the price of a C codec in the reader and a zip writer of our own — and the in-place update drops both the uninstall pass and the LZMA decompression, so it is faster end to end on anything but a slow link. The reader is the `zip` crate, already in the tree through the updater plugin, with `deflate-flate2` (pure Rust over the miniz_oxide already there) as the only feature this adds. **Two things a portable copy will have to honour**, neither of them decided yet (that is its own issue) and both of them constraints this code already imposes. Its own state has to live under a **dot-prefixed top-level name**, or the file-set comparison reads it as a path the payload dropped and sends the update to the installer — which for a portable copy installs a second, ordinary copy into the profile and leaves the portable one old; the walk and the sweep would also recurse into it, and a torrent root there is hundreds of thousands of files at every launch. And the refusal itself needs a third `Plan.mode`: a portable copy's fallback is "download the new version", not "run the installer". `fixedRuntime` is the related trap on the other side — it is what would make a portable copy self-contained (Tauri points `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` at `<exe dir>/<path>` on startup, so a runtime beside the executable is found with no installer, at about 180 MB), but the bundler lays those files down without them being in `bundle.resources`, so the packer would have to learn about them or every update would refuse itself. **It is testable without a release and without the signing key**: a debug build — and only a debug build, so nothing in a release binary's environment can redirect it — takes `FP_UPDATE_ENDPOINT` and `FP_UPDATE_PUBKEY`, and `scripts/update-test.ps1` generates a throwaway key, packs and signs a payload, serves it over loopback and runs a staged copy of a real installation against it.

- **A portable copy keeps everything beside its own executable, and one file decides that it is one.** `.portable` next to the binary, read once before any path is resolved (`portable.rs`); everything then lives under `.data/` in `config/`, `data/`, `cache/` and `webview/`, mirroring the platform's three directories one for one so that nobody reading both has to learn a second vocabulary. **Inferring the mode is not an option** — deducing it from, say, a missing uninstall registry entry would mean that an ordinary installation whose entry was removed stopped finding its own watch history. Both names begin with a dot because the in-place update's file-set rule excludes exactly that (`is_foreign_top_level`): without it a portable copy's own state would read as paths the payload had dropped, every update would refuse itself, and the fallback would install a *second*, ordinary copy into the profile and leave the portable one old. **Where the state lives and how the copy was delivered are two questions, and conflating them was a bug.** `.portable` answers the first; the second is answered by `portable::installed()` — an uninstall entry whose `InstallLocation` is *this* directory, which is also the lookup update.rs writes `DisplayVersion` through, so the two cannot disagree (and "an entry exists" is not enough: a portable copy unpacked beside an installation must not read the installation's entry as its own). Delivery is what decides two things. `Plan`'s third mode, `download`, is for a copy **nobody installed**: it is sent to the release page, where an installation — portable or not — has an installer to fall back on and is sent to that. And the shell registration is only the player's to make when nobody installed it; an installation got its protocol and associations from its installer, so the settings sheet says who owns them instead of offering a switch that would take them over. The installer's own checkbox is what makes a copy both at once, which is why neither question may stand in for the other. **That checkbox is on the welcome page, and not by choice**: `MUI_PAGE_CUSTOMFUNCTION_SHOW` is a *generic* define that the first page inserted after it consumes and undefines, and the template's first page is the welcome one — so a hook file included at its line 35 can reach that page and no other. The finish page, the only other candidate, has both its checkbox slots taken (desktop shortcut, run the player). Every base directory in the player goes through `portable::{config,cache,data}_dir`, which also creates the directory — the ten call sites each used to do that by hand and half of them did not. **The main window moved out of `tauri.conf.json` into `create_main_window`** for one line of it, and the move is the dangerous part rather than the line: localStorage — positions, track choices, hotkeys, geometry — lives inside the webview's data store, the configuration's `dataDirectory` is documented as *relative* to `appDataDir()/<label>` and an absolute one is refused outright ("is not a relative path, ignoring config"), so an absolute path needs `WebviewWindowBuilder::data_directory`. **An ordinary installation passes nothing**, because Tauri's manager forces `LocalData/<identifier>` when nothing else sets it (`manager/webview.rs`) — downstream of the configuration, so the default does not depend on this code reproducing it, and computing a "same" path by hand would be one typo away from losing every viewer's history. Verified differentially rather than by reading: the window the Rust builder makes and the one 1.26.0 declared have identical `GetWindowLong` style and exstyle words and identical outer size, and no new directory appears beside `EBWebView`. `min_inner_size` there is the duplicate `MIN_WINDOW_W/H` in window-prefs names. **The shell registration is the one thing a folder cannot carry.** A protocol handler and a file type are machine-side registrations — Windows has no folder-local form of either — so a portable copy writes them itself under `HKEY_CURRENT_USER`, the protocol through the deep-link plugin's own `register` (which writes exactly what the installer writes, down to `URL:<identifier> protocol`) and the associations in `shell_handler.rs`. It does so on launch unless the switch says otherwise, and the switch is enforced **both ways** on every launch, so the preference is what is true rather than what was once asked for. Two consequences are inherent and are in the settings hint rather than left to be discovered: with an ordinary installation beside a portable copy **whichever ran last owns the association**, and a portable folder that is simply deleted leaves keys pointing at a path that is gone. Which is why everything displaced is kept beside what replaced it — the previous ProgId per extension under `<ProgId>_backup`, the installer's own name for it, and the ProgId's previous command under `fp-previous-command` — and giving the registration back restores them. **Both halves of that were wrong first and both were caught by running it**: with no backup the first version wrote an *empty* ProgId, and it deleted the shared `Video` key outright, either of which takes an installed copy's association down with the portable one. The rule now is that nothing is undone unless something was displaced; measured by polling the keys while the undo ran, the ProgId goes back to the installation and returns to the portable copy half a second later when the preference re-asserts itself. **The file associations cannot be read from `app.config()`**, which is how the sixteen extensions came to register silently as nothing while the protocol worked: `ToTokens for BundleConfig` writes `file_associations` into the binary as `quote!(None)`, so the field is always empty at runtime. They are parsed instead from `include_str!("../tauri.conf.json")`, which keeps one list rather than two. **The runtime is the one dependency the archive does not carry.** The binaries need nothing redistributable — only `api-ms-win-crt*`, the Universal CRT that is part of Windows 10, and `d3d11.dll` — but the whole interface is HTML over mpv's view, so a missing WebView2 runtime is not a degraded window, it is no window and nowhere to put the explanation. An installation gets it from the installer; a portable copy runs `webview2::ensure()` before the builder: `tauri::webview_version()` to ask, Microsoft's permanent bootstrapper link silently and without elevation to fix it, and a message box with the download page when that cannot work. It runs for **both** kinds of copy, so an installation whose runtime was removed heals the same way. The archive is `scripts/pack-windows-update.ps1 -Portable` — the update payload's files plus the marker and without the manifest — published to the **GitHub release only**, because a release keeps its assets where the update bucket is pruned to five versions, and because a portable copy updates itself from the ordinary payload, whose file set is the same one. One thing stays outside the folder on purpose: the OpenSubtitles password is in the Windows credential store, since a password in a file inside a folder people copy onto other machines would be worse, and the settings sheet says so.

- **Release notes are written with the change and published with the version, and one file carries them to all three places.** A change a viewer will notice gets a changeset in `.changeset/` when it is made (the `changesets` format, so `bunx changeset` writes one too; `.changeset/README.md` is the format): `minor`/`major` is listed under *New*, `patch` under *Improvements and fixes*, the first line is the headline and one paragraph under it the detail, and a changeset with **empty frontmatter** is the release's one-sentence summary. `set-version` turns them into `changelog/<version>.md` — version, date and summary in the frontmatter, the two `###` sections in the body — and deletes them; with nothing pending it refuses unless given `--allow-empty`, because a release without notes is nearly always a forgotten changeset. That file is the GitHub release's body (`scripts/changelog.mjs notes`, run by the runner's own Node — hence the parser is loaded lazily, the publish job has no `npm ci`), the site's `/updates` page, its Atom feed and Markdown twin, the three cards on the home page, and **`latest.json`'s `notes`** — which the updater hands the player as `Update.body` and the title bar's update button shows as its tooltip: the summary and the headlines only (`src/lib/release-notes.ts`, pure and tested, because a manifest from before notes existed has none and the hover must still work), in English whatever the interface language, with the tooltip's `white-space: pre-line` keeping the lines. A viewer several versions behind sees only the newest release's notes; the rest are on `/updates`. **`changeset version` is deliberately not used**: it would bump one of the five version files and write a `CHANGELOG.md` without dates or summaries. **The site shows only what `latest.json` says is out** (`site/src/releases.ts`): the bump commit carries the new file and rebuilds the site half an hour before the installers exist. What goes into a changeset is the next reader's problem, not the author's — a fix to something *not yet released* amends that thing's changeset rather than adding a *Fixed* line, a refactor gets none, and everything in it is public: English, no identifiers from the code, no hosts, accounts, machines or people. `bun run changelog:check` (a gate) checks every changeset, every release file, and that the version in `tauri.conf.json` has one; `bun run changelog:preview` prints the next release's notes.
- **The mpv patches are a set, and the set is part of what the macOS libraries are.** `build-macos-libs.sh` applies every `patches/mpv-<version>-*.patch` in the order the shell sorts them, which is the same glob `macos-libs-key.sh` hashes — so adding, editing or deleting one renames the published set, and the next release builds it from source (~20 min) unless the `macOS libs` workflow was run first. There is deliberately no list of names in the script: a patch added to the directory and not to a list would change the name of the set and nothing inside it. Three things follow. A patch written against another has to **sort after it**, since nothing else orders them. The unpacked tree carries a stamp of the set it was patched with (`.patch-stamp`, written last so an interrupted run is not taken for a finished one): the tree used to be patched only when it was unpacked, so on a machine that had built before, a newly added patch was skipped in silence and the old library came out under the new name. And a bump of `MPV_VERSION` with no patch file of that version **refuses to build** — an unpatched libmpv on macOS builds, links, loads and opens a window of its own. Every patch is also **described in `licenses/manifest.json`** (`patches.list` of the project it changes): a patch is a change to an LGPL library, and the notices that ship inside the player have to state it. `gen-notices.mjs` renders that statement from the directory — the files a patch touches are read out of the patch — and refuses when the manifest and `patches/` disagree in either direction, so the notices gate fails on a patch nobody described and on a description whose patch is gone. It exists because the notices said "every component below is unmodified upstream code" for as long as the first patch did: the sentence was a string in one file and the patch a file in another, and nothing connected them. A backport says in its own header which upstream change it is and what deletes it (`patch` ignores everything before the first diff), so the condition travels with the file instead of living in somebody's memory; the measurements behind the one that exists, and behind the one that was written and left out, are in [`../macos.md`](../macos.md).
