# Bundling, licensing and releases

What ships inside the application, the LGPL and GPL obligations that follow, code signing on both platforms and the release workflow.

Part of the rule book: [`CLAUDE.md`](../../CLAUDE.md) carries the one-line
version of each rule here, this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.
The *why* behind it — what was tried, what was measured — is in
[`../distribution.md`](../distribution.md).

- **Everything the player needs at runtime is bundled; yt-dlp is the single exception.** `src-tauri/lib` carries libmpv, the wrapper and every transitive dependency (~65 MB and ~50 dylibs on macOS: FFmpeg, libass, libplacebo, MoltenVK, LuaJIT, x264/x265, OpenSSL…; on Windows `libmpv-2.dll` plus the FFmpeg SDK in `src-tauri/ffmpeg`, both fetched by `scripts/fetch-libs.ps1`). `build.rs` lays them out next to the dev exe and declares two rpaths — `@executable_path/lib` for dev and `@executable_path/../Resources/lib` for inside a `.app` — and `bundle.resources` puts them in the installer. So nothing is taken from the user's system: a machine with no Homebrew and no FFmpeg runs the player. **Nothing may block `init(mpvConfig)`** — whatever waits there holds up the whole window, and until mpv is up a click on a file does nothing at all, which reads as a dead player rather than a slow one. The lesson cost a session: the yt-dlp probe ran `yt-dlp --version` to prove the binary worked, and that call takes **11 seconds** on a macOS universal build (a 36 MB PyInstaller bundle that unpacks itself and is re-verified by the system on every exec) — twice over, before init, so the player ignored roughly the first twenty seconds of clicks. The probe now only *looks* (file present, executable bit set) and is not awaited; a broken binary is caught where it matters, when a link fails and the dialog offers to install or update. **yt-dlp alone is looked up at runtime** and is optional by design — without it, local files and direct links still work and only websites do not, which the link dialog says. It can also be installed from that dialog, into `<app_data>/bin` — the only place we may overwrite afterwards, since Program Files needs administrator rights and a binary inside a `.app` cannot be replaced without invalidating the signature. **Keeping it current is yt-dlp's own job, not ours**: `-U` fetches the release, checks it against the signed checksums published with it and replaces the binary in place, so writing a downloader would mean reimplementing verification that already exists and is maintained by people shipping it every few weeks. We only fetch the *first* copy. The update button appears **only for the copy we installed** (`managed`) — a Homebrew or pip install belongs to its package manager, where `-U` either refuses or starts a fight. Expect staleness rather than absence to be the failure: a September 2025 build already fails on YouTube, so a failed link reopens the dialog with that explanation and the button, instead of a popup that fades before it can be acted on. **macOS ships too, and `bundle.targets: ["nsis"]` in tauri.conf.json is only half the story**: `tauri.macos.conf.json` overrides it to `["app"]` and is what `npm run tauri:macos:build` (and CI) uses. The release workflow builds the `.app`, then packages the dmg in a step of its own — Tauri's `bundle_dmg.sh` drives Finder over AppleScript to place the icons, which a headless runner has no session for, so it passes silently and ships an image with no `.DS_Store` that opens as a plain folder; `dmgbuild` writes one directly. **The macOS build is signed with a Developer ID and notarised, and the two things that decide are the hardened runtime's, not Apple's paperwork.** The chain is `macos-sign.sh` (imports the certificate, signs the 35 dylibs and the ffmpeg CLI) → `tauri build` → `macos-notarize.sh` on the `.app` → `build-dmg.sh` → `macos-notarize.sh` on the image, and the order is load-bearing at both ends. The libraries are signed **before** the build because they reach the bundle as `bundle.resources`, i.e. copied in carrying whatever they already had — the ad-hoc signature `bundle-macos-libs.sh` applies after rewriting their load commands — and an ad-hoc Mach-O anywhere inside fails notarisation on identity; signing them inside the built `.app` instead would break its seal and force the image and the updater archive to be rebuilt. At the other end, `macos-notarize.sh` **repacks `.app.tar.gz`**, because Tauri writes it during the build, i.e. before the ticket exists — ship it unrepacked and the disk image is notarised while every automatic update carries an unstapled bundle, which is the failure that only reaches existing users. Two entitlement facts, both measured against a probe that loads the bundled libmpv with `zoompan.lua` under each signature (LuaJIT 2.1 is what `zoompan.lua` runs on): **`com.apple.security.cs.allow-jit` does not work** — it authorises `MAP_JIT`, which this LuaJIT does not use, and the process dies with `EXC_BAD_ACCESS`, "Invalid Page", faulting inside a private `r-x` `VM_ALLOCATE` region — while `allow-unsigned-executable-memory` alone does, so that is the file's single entry. And **the hardened runtime is only turned on when there is a real certificate** (`macos-build.sh`), because it enables library validation, which requires every dylib to carry the process's Team ID: with a Developer ID that is free, and ad-hoc code has no Team ID at all, so the ad-hoc fallback dies at launch on `Library not loaded: @rpath/libavutil.60.dylib … (non-platform) have different Team IDs`. Three traps around that. `hardenedRuntime: false` **does not turn it off on its own** — measured on CLI 2.11.4, a config naming an entitlements file is signed `--options runtime` regardless, so the override has to clear `entitlements` too (verified it is the bundler and not codesign: `codesign --entitlements … --sign -` without `--options runtime` gives a plain `0x2(adhoc)`). A probe that `dlopen`s the libraries survives all of this, so **testing the library set in isolation proves nothing about the bundle** — only launching it does. And `codesign --verify --deep --strict` passes on the broken bundle in silence; the symptom is a crash dialog offering to report to Apple. The ad-hoc path is still exactly what shipped for the first thirty releases and is what a checkout with no Apple account produces: sealed but uncertified, which Gatekeeper stops with an **Open Anyway** button rather than the *"file is damaged"* dead end that an unsealed binary gets.
- **The application is GPL-3.0-or-later, and that is the conclusion the LGPL work was for.** Keeping every bundled library strictly LGPL bought exactly one thing: the freedom to make this player closed or paid. MIT — which the project carried by default — handed that same freedom to anyone who wanted to close a fork and sell it, which for an *application* buys nothing back: permissive licensing pays off for a library, where the win is being embedded, and users of a player install a binary. Copyleft costs the sole copyright holder nothing (dual licensing stays available) and costs a closed fork everything. **3.0 rather than 2.0** because 306 crates in the graph are Apache-2.0, which is incompatible with GPL-2.0-only; the whole graph was checked and is GPL-3-compatible, including the odd ones (`webpki-roots` is CDLA-Permissive-2.0, a certificate dataset with no copyleft). The App Store argument does *not* apply here and should not be reached for — that channel is already closed by the private API the embedding depends on (`distribution.md`). GPL §4 also means `LICENSE` itself is now a bundle resource, and `gen-notices.mjs` embeds it as the last section of the notices, read from the file rather than restated — so editing one without the other leaves the committed notices stale and the gate fires.
- **Licensing is a build output, not a document somebody remembers to update.** The player links libmpv, FFmpeg, libplacebo, GLib, FriBidi, Graphite2 and the gettext runtime — all LGPL-2.1 — which a proprietary application may do under §6, but only against three obligations the bundle carried *none* of until this existed: a prominent notice naming the libraries, a copy of the license, and a route to the source. `THIRD-PARTY-NOTICES.md` is all three, it is a bundle resource on both platforms (`"../THIRD-PARTY-NOTICES.md": "./"` — traced through `tauri-utils::resources`: a pattern **without a `*`** is a plain file, and for a plain file a *non-empty* destination becomes the target path itself, so `{"x.md": "./folder/"}` writes a file literally named `folder`; `"./"` normalises to empty, which is the branch that keeps the file name), and `build.rs` copies it beside the dev exe so the settings-footer link works while developing rather than only in a release nobody clicks. What keeps it true is the coverage check: **every dylib in `src-tauri/lib` must be named by the manifest**, or rendering fails. That check must match by declared name plus a version suffix and never by stripping digits — the digits in `libX11`, `liblcms2`, `libpng16` and `libpcre2-8` are part of the name, and the first version of it reported three covered libraries as missing, which is the failure mode that gets a gate weakened instead of fixed. Three traps in the data itself, all found by looking rather than trusting: a keg's `COPYING` is often a **pointer** (pcre2's says "see LICENCE", FreeType's describes two licenses and ships neither), **gettext's `COPYING` is GPL-3.0** because it covers the tools while we ship only the LGPL runtime, and **Homebrew's `license` field describes Homebrew's build** — its `ffmpeg` is GPL-3.0 and its `mpv` is GPL-2.0, so copying that field would have labelled our own `--disable-gpl` builds as GPL. Hence `license` in the manifest means *the artifact we ship*, with `note` recording which option was taken where a project is multi-licensed. Windows was audited the same way and is LGPL too, proven from mpv's own configuration string embedded in `libmpv-2.dll` (`-Dgpl=false -Drubberband=disabled`): the alarming strings there are innocent — `x264` is libavcodec's SEI **decoder**-side encoder detection (zero encoder symbols), `modplug` is libopenmpt, `xvid` is the MPEG-4 decoder's quirk table. Its component list is deliberately *over*-inclusive and carries no `libs`: `fetch-libs.ps1` takes the **latest** upstream release, so a list read out of today's DLL would be stale within a week, and listing a component the current build lacks costs nothing while omitting one it has is the actual violation. **The rendered file has to be byte-identical on every machine, and the first version was not.** `--check` compares a fresh render against the committed copy, so anything that varies by platform makes the gate fail somewhere and only somewhere: one upstream text (libopenmpt's) ships with **CRLF**, git normalised it to LF in the blob while leaving the working copy alone, so the machine that fetched it embedded CRLF into the notices — and the Windows runner, checking *everything* out as CRLF against `\n` joins, produced a third string again. The CI failure reproduces exactly by CRLF-ing a copy of the tree and running the old script: same two digests. Fixed at the read — every input is normalised to LF, so the output depends on content and not on anybody's `core.autocrlf` — with a scoped `.gitattributes` (`LICENSE`, the notices, `licenses/**` → `eol=lf`) keeping the working copies matching their blobs. Both are kept deliberately: the script guarantees the comparison, the attributes guarantee the files, and neither substitutes for the other. **Showing them is a surface of its own**, because pointing at the file is not showing it: `revealItemInDir` gives a location, `open-path` is not in the capabilities (its permission needs a scope), and a `.md` has no reliable handler on Windows. So `third_party_notices` reads the resource in Rust — a filesystem plugin to read one read-only document we ship ourselves would be a far wider permission than the job needs — and `LicensesDialog` renders it as selectable text (the page sets `user-select: none`, which every child inherits, and WebKit still needs the prefixed property). Measured in a WKWebView harness rather than feared: 560 KB is **171 075 px** of `pre-wrap`, 52 ms of forced layout, 263 ms from load to ready and instant scrolling — no reason to split it. It is a layer *above* the settings sheet in `closeTopmost`, so Escape gives the settings back. **On macOS the About panel takes `credits`, never `license`**: `orderFrontStandardAboutPanel` has a fixed key set and muda passes only ApplicationName, ApplicationVersion, Version, Copyright, ApplicationIcon and Credits — `AboutMetadata.license` is for the Windows and Linux dialogs and is dropped in silence here, which is how the first attempt shipped a panel showing nothing but a name and a copyright line. And **`licenseFile` is deliberately unset**: traced to `!insertmacro MUI_PAGE_LICENSE` in the NSIS template, it adds an "I agree" page to the Windows installer and is not read for `.app` or `.dmg` at all — so it buys no part of the obligation and would make the two platforms' installs differ.
- **Releases**: `npm run set-version 0.21.0` (or `patch`/`minor`/`major`), then push to main. **Five files carry the version** — package.json, package-lock.json, tauri.conf.json, Cargo.toml, Cargo.lock — and they cannot be collapsed into one: `tauri.conf.json`'s `version` accepts a path to a package.json instead of a literal, but the release workflow reads that literal with `jq` to decide whether a push *is* a release, so making it indirect would leave the gate with nothing to compare; and Cargo cannot read a version out of JSON at all. So `scripts/set-version.mjs` writes them, with one anchored line per file rather than a JSON round-trip (which reformats tauri.conf.json's hand-written inline arrays — measured on the `endpoints` array) and with **every anchor required to match exactly once**, since a bump that silently skipped a file is the whole failure being prevented. Run with **no argument** it reports instead of writing and exits non-zero on disagreement: worth doing before a release, because this drift is invisible — `package-lock.json` had been sitting at **0.1.0** since the first commit, which is exactly what the script found on its first run. `src-tauri/tauri.conf.json` remains the authority: a `patch`/`minor`/`major` bump is measured from what *it* says, whatever the others have drifted to. CI needs repo **secrets** `TAURI_SIGNING_PRIVATE_KEY` (passwordless), `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ACCOUNT_ID` and `FP_OPENSUBTITLES_KEY`; six more for macOS signing — `APPLE_SIGNING_IDENTITY` (the whole `Developer ID Application: … (TEAMID)` string), `APPLE_CERTIFICATE` (base64 of a `.p12` exported from **My Certificates**, which is the view that carries the private key with it) and `APPLE_CERTIFICATE_PASSWORD` for the certificate, plus `APPLE_API_KEY`, `APPLE_API_ISSUER` and `APPLE_API_KEY_P8` for notarisation. **Every one of those six is optional**: without them the build is ad-hoc and the notarisation steps skip themselves, saying so in the job summary — a fork can still cut a release. Plus repo **variables** `R2_BUCKET_UPDATES`, `R2_BUCKET_LIBS`, `R2_PUBLIC_URL_UPDATES`, `R2_PUBLIC_URL_LIBS` — bucket names and public URLs are not secrets, and as variables they are readable in a failed log instead of appearing as `***`, which is the difference between diagnosing a 404 and guessing at one. Each is guarded against being empty, because an unset variable expands to nothing and would otherwise upload to `s3:///` — the OpenSubtitles *application* key, baked in with `option_env!` at build time. Two things about that one. It is not really a secret (it identifies the app, not the user, and cannot be hidden inside a desktop binary); what a leak costs is **availability**, since abuse gets it revoked and subtitle search then breaks for everyone at once — which is why `opensubtitles.rs` looks in `<app_data>/opensubtitles.key` *before* the compiled-in value, so a revoked key can be replaced without a release. **Nothing delivers that file yet**: today it is a manual escape hatch, and wiring it to the signed R2 channel next to `latest.json` is the piece still missing. And `option_env!` is read at compile time **without** registering a dependency on the variable, so `build.rs` carries `rerun-if-env-changed=FP_OPENSUBTITLES_KEY` — without it a warm target directory keeps baking in the previous key. An absent secret is not a build failure: the feature simply reports that this build has no key. Updater pubkey lives in tauri.conf.json. **The `publish` job needs its own checkout, and it has to be the first step**: the job began life as downloaded artifacts and nothing else, so it had none — and the moment it called a script from the repository it died with a 127 *after* every artifact and `latest.json` were already uploaded, leaving the update channel live and no GitHub Release at all. Order matters because `actions/checkout` clears the workspace before cloning, so placed after the download it would delete `dist` and the failure would read as the build producing nothing. The same incident moved the retention sweep **after** `Create Release` and into a step of its own: it had been the tail of the upload step, which put the least important thing in the job in front of the most important one. It still fails loudly rather than being swallowed — pruning that quietly stopped working is how the bucket reached nine gigabytes.
