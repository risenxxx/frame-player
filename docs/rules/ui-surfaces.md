# UI surfaces: dialogs, menus, the start screen and the floating boxes

The settings sheet and the context menu, the start screen, tooltips, the OSD and the arithmetic that places anything floating.

Part of the rule book: [`CLAUDE.md`](../../CLAUDE.md) carries the one-line
version of each rule here, this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.

- **mpv option surface**: defaults are set in `initialOptions` in +page.svelte; user overrides come from `%APPDATA%/<identifier>/mpv.conf` (command `user_mpv_conf`, template in lib.rs, `wid` filtered out). The interactive editor (`SETTINGS` array in +page.svelte) persists via `mpv_conf_set` (surgical line edit: comments/unknown keys survive) and live-applies via `command('set', ...)`. To add a setting: one `SettingDef` entry. The dialog was once split by **who owns the setting** — one tab for exactly what ends up in mpv.conf, one for state the player keeps itself. That boundary is real and still shapes the code (`SettingDef` covers only the mpv.conf half; volume leveling and the queue options are localStorage), but it turned out to be a poor map for someone hunting for "subtitle size", which is how a settings dialog is actually read. It is now topical sections — Основные / Видео / Проигрывание / Аудио / Субтитры / Раздачи / ТВ / Клавиши — with each `SettingDef` naming its own `tab`. **There are eight, and the eighth only fits because its label is two characters** («ТВ», not «Трансляция»): the row is measured below at seven Russian labels plus that, so a ninth tab, or a wider eighth, silently goes over the edge. What the ownership boundary still owns is the footer: it says mpv's settings live in mpv.conf rather than claiming everything on the page does, because the Audio section deliberately mixes both. **Adding a section means re-measuring the dialog's width**, and skipping that is invisible rather than ugly: `.tabs` is `nowrap` with `overflow-x: auto` and `scrollbar-width: none`, so a tab past the right edge is simply *gone* — the six-tab row had quietly been overflowing a 428px sheet and clipping "Клавиши" before anyone added a seventh. Measured against the built stylesheet (a hand-written copy of the rules is how this class of bug gets missed twice): seven Russian labels are **510px** at 13px with a 13px gap, English 408, so the sheet is 598 — an *outer* number, since every box here is a border box, which leaves the tab row 50px of slack inside the sheet's 36px of horizontal room and 2px of border. That slack is now the same in every state, and getting there fixed a jump the sheet had always had: **a scrollbar takes its width out of the content box and leaves `padding-right` inside it**, so everything right-aligned in a scrolling sheet sits 10px further in than it does in a short one. Measured on the built stylesheet, with the fix reproduced by `sed`-ing the rule back: the × was 19px from the sheet's edge on a short tab and **29px** on a tall one, and the tab row was 560px against 550px — so switching between "Раздачи" and "Основные" moved the close button and quietly cost the row a fifth of its slack. The space is reserved by **`overflow-y: scroll`**, not by `scrollbar-gutter: stable`, and the sheet's padding is written asymmetrically (`16px 8px 14px 18px`) *so that it is symmetric on screen*: 8px of padding plus the bar's own 10px is the same 18px as the left. Do not "tidy" that back to a single 18px — the tidy version is the bug. **`scrollbar-gutter` is not honoured by WKWebView**, which inverted this fix rather than delivering it: with the padding already cut to 8px, a sheet that did *not* scroll had 9px on the right against 19px on the left, and only a scrolling one looked right. Measured against the built stylesheet in a WKWebView harness — `auto` + `stable`, short content: `offsetWidth − clientWidth` = 0, gaps 19/9; scrolling: 19/19. Chromium honoured it in both, so this was macOS-only. The trap is that **`CSS.supports('scrollbar-gutter','stable')` returns `true` there and the computed style reads back `stable`** — neither feature detection nor the computed value would have caught it; only measuring the box did. Forcing the bar on costs nothing on screen (transparent track, and WebKit draws no thumb on a sheet that fits) and measures 19/19 on both engines in both states. Torrents earned a tab of their own for the reason the topical split exists at all: seeding and the piece cache were correctly filed under privacy and storage, and a viewer looking for anything about torrents still had to read "Основные" to the bottom to find them. Destructive actions there are real buttons (`.btn-danger`), never `.settings-link` — a link promises navigation, not deletion. The context menu is **grouped, not listed**: anything with more than two related entries (file, frame, playback, picture, window) is a submenu, which took it from ~19 rows to 11 — a menu that had to scroll in an ordinary window was the sign it had outgrown a flat list. What stays at the top level is what has no group and is reached often. Two things the grouping cost, both worth knowing before moving a panel again. **A panel moved out of its parent loses the parent's event guards** — the menu stops clicks with `onclick={e => e.stopPropagation()}` so they do not reach the handler that closes it, and a hoisted panel is no longer covered by it: every click inside a submenu, the back row included, closed the whole menu. And **five submenus need one implementation, not five** — `submenuHead`/`submenuPanel` snippets keyed by a `CtxSub`, with the anchors in a `Record` rather than a ref each, or the fifth copy is where the divergence starts. The context-menu submenu needs **both** a hover bridge (`.ctxmenu.submenu::before`, `inset: 0 -10px`, `z-index: -1` so it does not eat clicks) and a delayed close: the diagonal path from the parent item to the submenu crosses the gap between them, which belongs to neither element, so `mouseleave` fires and the menu collapses under the cursor. Reset it with `closeSubmenuNow()`, never a bare flag, or a pending timer from the previous menu closes a freshly opened one. **One control shape per job**, or the UI stops being readable: underlined `.tabs` switch sections, pill `.segmented` picks one of several named values, `.switch` is boolean on/off. Reusing the pill for a Да/Нет pair made a setting look like navigation. A switch is **two** classes and the inner one is `.switch-knob`: the seeding toggle was written with a bare `.knob`, which has no rule anywhere in the project, so it rendered as a track with nothing sliding in it and on/off could only be told apart by the background color. Nothing catches that — an unknown class is not an error and Svelte's unused-selector warning fires on the CSS, not on the markup.
- **Returning to the start screen is a destination, not a blank to wait out.** `showEmpty` is debounced by 300 ms because a playlist transition blanks `filename` for a moment and the picker must not flash through it. That is right for an *involuntary* blank and wrong for a deliberate close: `backToStart` issues `stop`, and for those 300 ms the player's own chrome stood over a VO that had already stopped — a black frame under a seekbar reading 00:00, which is what going back looked like. So the two paths are separated. `enterStartScreen()` raises the picker and refreshes what it lists; the `filename` handler still calls it on the timer, and `backToStart` calls it **before** issuing the stop, where the destination is already known. `.player.no-video` is opaque, so raising it first covers the video and nothing in between is ever seen. Two details that are not decoration: the position is flushed *first*, or the card this file is about to appear on carries the previous write rather than the moment it was left at; and the handler skips its timer when the picker is already up, or the recents list is rebuilt a second time and the cards visibly reshuffle as the posters arrive again. **Releasing the torrent belongs here too, for the same reason the picker does**: the `filename === null` handler also does it, but that path is *inferring* the departure from an event, and a dropped property change (a queue overflow costs them — hence the 1 s resync) then leaves the swarm running and the download readout standing over the start screen. A path that knows it is leaving says so; the handler's own call then finds nothing left to release. The **other** half of that same symptom is a poll that outlives its file: `torrent_status` is a round trip and the timer fires every second, so closing a film routinely catches one in the air, and clearing the interval does nothing to a promise already sent — it resolves afterwards and writes the status back, permanently, since nothing will clear it again. Hence the sequence guard on `trackTorrentPlayback`'s polls, the same one `loadTracks()` carries.
- **A control's actions belong to the control, not to the list around it.** The delay stepper's reset used to be a `.menu-item` under the −/+ pill, which is correct for a list row and wrong beside a control: a menu row is full-bleed and indented to line its text up with the list, so next to a 6px-inset pill its hover highlight was a different width and started in a different place — one setting wearing two shapes, and only visible on hover. It is now a fourth cell of the same pill, `[−][value][+] │ [Сброс]`, with a hairline divider saying it belongs to the group without belonging to the stepper. Two things the move cost, both measured in a WKWebView harness against the built stylesheet rather than eyeballed. **The label had to become one word**: `Сбросить задержку` is right for a menu row and wrong for a cell — the noun is already on the section title above — and at 75px it squeezed the readout hard enough to wrap the unit onto a second line; `Сброс`/`Reset` measure 60px and 56px, and the value stays on one line. And **`padding: 0 10px` for the horizontal inset silently took the vertical padding to zero**, so the cell was 12px tall inside a 27px row and its hover read as a long thin pill rather than a button; `align-self: stretch` plus `place-items: center` makes it the row's full content height like the two glyph buttons, with the text centered by the grid instead of by a padding that would have to be kept in step with theirs. It keeps being rendered-and-disabled rather than hidden, for the reason it always was: the menu is anchored by its bottom edge, so a control appearing there would move the row the moment the delay leaves zero — right under the cursor that is clicking it.
- **The settings dialog has two control shapes, and the choice between them is about the value, not the layout.** A pill (`.segmented`) picks one of several *named* values; a slider covers a continuous range. Subtitle size is the case that forced the second one — the useful adjustment is "a bit bigger than that", which three pills cannot express. A slider fires on every pixel of the drag, so applying live is immediate while the mpv.conf write is debounced (`CONF_WRITE_MS`), with **one timer per key**: a single shared one lets a second slider cancel the first one's write. Landing exactly on mpv's own default clears the line from mpv.conf rather than pinning the default in writing, which is what "по умолчанию" means for every pill above — so the step has to divide the distance from `min` to the default exactly, or the default is unreachable and the line never clears. Values are snapped to the declared precision before being written, because a range input hands back 1.2000000000000002. Subtitle defaults worth knowing, measured on mpv 0.41 and different from what older documentation says: `sub-border-size` is **1.65**, `sub-border-style` is `outline-and-shadow` (`background-box` is the readable-on-bright-frames alternative), and **`sub-ass-override` already defaults to `scale`** — so `sub-scale` and `sub-pos` reach ASS subtitles without forcing anything, which is the usual reason this feature disappoints in other players.
- **A slow operation must say so before it starts, not after it finishes.** Two places had the same silence. Opening a URL sits on a black window for as long as yt-dlp takes to resolve the page and the stream takes to buffer, with nothing to show it is alive — hence the `opening` indicator, raised in `beforeLoad` for a network source only (a local file opens faster than it would fade in) and dropped on `file-loaded`. It reports a real figure rather than a guess: mpv's `cache-buffering-state` is the cache fill, and it is **absent while there is no cache yet**, which means "still resolving" and not "0 %"; `paused-for-cache` is playback stalled on the network as opposed to on the viewer. And saving or copying a frame is a second of PNG encoding on mpv's own thread on a 4K file, which used to pass in silence — the menu closed and nothing happened, which reads as a click that missed. Both now announce first, which is what `sticky` on `showOsd` is for: a popup that fades halfway through says the work finished, and finishing is the one thing that has not happened. Anything raising a sticky popup owes it a replacement on every exit path.
- **Start screen recents**: `RECENT_LIMIT` cards, candidates drawn from a pool 3× that size — a dead file (renamed, deleted, unplugged drive) is replaced by the next candidate rather than leaving a gap, and is *not* purged from the history, since an unplugged drive comes back and the record could not be rebuilt. **It is a rail, not a wrapping grid**, and that is a structural fix rather than a tuned number: a grid was the only part of the start screen that grew with its content, so once network entries stopped being dropped it went three rows deep and pushed the torrents section 220px below the fold at 1280x800 — measured, and a section nobody scrolls to may as well not exist. One row keeps the page a fixed height whatever the history holds. It needs **`justify-content: safe center`, never a bare `center`** — the same trap the start overlay already carries a note about: a centered flex container that overflows does so in *both* directions, and rendered with a bare `center` twelve cards began at the fifth with the first four unreachable off the left edge. The trackpad scrolls it with no work at all, because `.overlay` is in `WHEEL_SURFACES` and `onWheel` returns early there, handing wheel events straight to the browser. **The list is verified before it is published, and a missing poster is not evidence of a missing file.** It used to go on screen in full and then shed entries one at a time as `poster_frame` failed on them, which reads as the player briefly showing files that then vanish — a grid of black cards collapsing, including things renamed months ago. Worse, `poster_frame` opens a *path*, so it fails for every network source: a YouTube link or a torrent episode was dropped on that basis and could never stay in this list at all, which silently disabled resuming a torrent from a card. So existence is now settled up front by `paths_exist` (one batched `stat`, microseconds against a poster decode) for local files only — a URL does not rot the way a renamed file does — and the poster loop only decides whether there is a picture. A network entry keeps its place and shows the link mark, the same answer the end-of-file cards already give. The overlay scrolls, which needs two non-obvious things: `justify-content: safe center` (a centered flex container overflows in *both* directions, so the top of the content becomes unreachable — the scrollbar will not go there), and a wheel that scrolls rather than changing the volume, which is now one rule in `onWheel` (`WHEEL_SURFACES`) rather than a `stopPropagation` on each surface. The `::-webkit-scrollbar` rules in app.css are **universal, not opt-in** — Windows otherwise draws its native light-gray bar, which is wide and alien in a dark UI; declaring them also switches macOS off overlay scrollbars, so the two platforms stop diverging. They were a `.scrollable` class first, itself a replacement for a list of surface selectors, and both failed the same way: a surface that starts scrolling without anyone telling it to. The context-menu submenus inherited `overflow-y: auto` from the class they share with the menu and drew native bars on Windows — invisible on macOS, where the overlay bar is dark and nearly transparent. There is no page content here that should keep the platform's own bars, so the safe default is all of them. A horizontal bar also needs `height` — `width` alone styles the vertical one, which is why the horizontal bar came out two to three times thicker — and `::-webkit-scrollbar-corner` needs a color of its own, or the square where the two bars meet stays the platform's white. Related and easy to miss: **setting one overflow axis computes the other from `visible` to `auto`**, so a menu that only ever scrolls vertically still raised a horizontal bar (and lost a row's height to it) whenever a row was a fraction of a pixel too wide — `overflow-x: hidden` is part of making something scroll vertically, not an extra. The start overlay starts at `top: 48px` (title-bar content height) so the bar does not run into the window buttons, and mirrors its scrollbar reserve because its content is centered — holding space only on the right shifts it off-center relative to the title bar. That was `scrollbar-gutter: stable both-edges` and therefore did nothing on macOS (see the settings sheet above): measured, a centered child sat at 100/100 while the content fitted and at **90/110** once it scrolled, which is the whole shift the rule existed to prevent. It is now `overflow-y: scroll` plus a matching `padding-left`, measured at 100/100 in both engines and both states — and 10px wider than `both-edges` was on Chromium, which reserved a gutter on each side.
- **The start screen must be complete in its first frame.** `loadRecent` and `refreshTorrents` used to be fired un-awaited before `show()`, so the window appeared holding the panel and its two buttons and then grew a rail and a torrent list underneath them — a reflow on every launch, at the one moment the player has nothing else to do but be ready. Both are now awaited, which is affordable precisely because of where each one stops: the recents list settles after a single batched `paths_exist`, and its **posters keep filling in afterwards on their own** (`loadPosters`, fired and not awaited, guarded by the same `seq`). Awaiting the posters instead would hold the window for a dozen keyframe decodes, which is the trade this split exists to avoid — the cards are on screen at their final size with a placeholder, which is what stops the layout moving. `enterStartScreen` deliberately does *not* await: there the picker has to cover a stopped video immediately, and a list arriving a moment later is the lesser fault.
- **Start-screen layout must not depend on its own content.** `.overlay` is a `grid` with `place-items: center`, which sizes the column from content — so the recents grid was measured from the cards, and the cards changed as posters arrived, moving the whole page. `.overlay.start` overrides it to `flex` + `align-items: center` so widths flow container → children, plus a mirrored scrollbar reserve (`overflow-y: scroll` + `padding-left`; see the note above for why not `scrollbar-gutter`). Its padding lives on the inner `.start-inner`, never on the scroll container itself: a scroll container's `padding-bottom` is not part of its scrollable area, so the bottom gap vanished exactly at the height where the content was flush but no scrollbar had appeared yet. Separately, `restoreGeometry()` must `settleLayout()` before `show()`: the resize reaches the webview asynchronously, so the window was being shown with the layout of its previous size — the giveaway is the title-bar logo sitting too far from the right edge, since that is outside the overlay entirely.
- **Placing a floating box is three rules, and they belong in one place.** Flip to the other side of the anchor when the preferred one has no room, shift along the other axis to stay inside, cap the size when the box is simply bigger than the space. `floating.ts` is those rules as two functions (`flipAxis`, `shiftAxis`) with unit-tested arithmetic; tooltips, the context menu and its submenu all placed themselves before, which is exactly why each of them was wrong in a different way. Floating UI would be this plus scroll containers, virtual anchors and auto-update — none of which exists here (one non-scrolling viewport, every anchor a real element), so the dependency buys nothing the 40 lines do not. Three findings are baked into the call sites. **A box laid out at `left: x` may only use the width to its right**, so a tooltip near the right edge wrapped to one word per line — and the measure-then-clamp pass that followed read the *wrapped* width and called it a fit, which is why it never recovered. The tip is therefore laid out at the window origin and moved with a `transform`, which happens after layout instead of deciding it. **A cap is not a clamp**: in the mini player the context menu is taller than the whole window, so no position shows all of it and it has to scroll — hence `max-height` from the placement's `room`. And **a panel must not be rendered inside a scroll container it is meant to escape.** The moment the context menu got a `max-height`, its submenus were cut off at its edge — only the sliver overlapping the menu's own box was left. `position: fixed` in viewport coordinates is supposed to be the escape, and it measures as one: a fixed box inside an `overflow: auto` parent lays out *and hit-tests* at full size in both engines (checked in headless Chrome and in a WKWebView harness built for this, since macOS is WebKit and Windows is Blink). It was still cut off on screen. Rather than argue with the screen, the submenus are now rendered as **siblings of the menu** instead of children of the item that opens them — nothing about the placement changed, since it was already in viewport coordinates, and the hover bridge is geometric so it did not care either. The parent still closes them on scroll: fixed panels do not travel with the content underneath. The general rule that came out of it: when a floating panel has to leave its parent's box, take it out of the parent, and keep `overflow` for things that are genuinely inside. Two more traps live in the same code. **A cap only means what the placement measured because every box is a border box** — the reset in app.css is what makes `max-height` cover padding and border, and before it existed the menu rendered 14px taller than it was told, ate the 8px margin it was meant to keep and ended up past the window edge, which read as "the placement has no padding". Anything new that hands a floating box a size inherits that guarantee and must not opt out of it with a local `box-sizing`. And **a submenu needs a plan for having no room at all**: in the mini player the window is narrower than two menus side by side, and flipping to "the roomier side" then half-overlaps the parent, which reads as a menu growing out of its own middle and being clipped by it. When the chosen side cannot fit the box (`room < size`), it is placed *over* the parent and aligned to it instead — the drill-down every small-screen menu uses. **That changes how submenus open, not only where they land**, which is the half that is easy to miss: a submenu covering its parent must not open on *hover*, or the parent stops being usable — every pointer move across it lands on another submenu head, and it cannot even be scrolled, so reaching an item means aiming at the corners of the ones that are not submenus. Below `SIDE_BY_SIDE_MIN` (the two menus' widths plus their margins) hover is therefore inert, the parent is hidden behind the panel (`visibility`, so the placement can still measure it — which works only because the panel is no longer its descendant), and the panel carries a back row, since otherwise the only way out is closing the menu and opening it again.
- **The OSC panels are anchored to the bar, not to a number somebody added up.** The four panels that open from the control bar — the queue, the chapters, the televisions and either track list — are one rule, `.menu` in app.css, positioned inside `.osc`. Its `bottom` used to be a flat `100px`: the bar's height worked out by hand, 12 (its own bottom padding) + 42 (the play button) + 8 (the controls' margin) + 16 (the seekbar's 4px track in 6px of padding) + 6 (its margin) + the 12px time line. That arithmetic was right to within about two pixels, and those two pixels were the whole gap — the panel sat directly on the timestamps, while every other pair of rows in the bar is spaced. It is now `calc(100% + 12px)`: `.osc` has no top padding and the panels are out of flow, so `100%` is the top edge of the seekbar row, which is the top of the elapsed/duration line, and the offset is the gap above it. 12px because that is the gap already under those timestamps — `.seekwrap` contributes `margin-top: 6px` and `padding: 6px 0` before the track — so the panel, the times and the bar are spaced alike. The percentage is the point: it follows the bar's height instead of restating it, which matters most where the sum does not hold at all, the mini player. `max-height` still carries a literal (`100vh - 142px`, the bar and gap plus 32px of clearance from the top of the window) and has to move with it.
- **The control bar's right-hand cluster folds into one button, and what decides it is arithmetic rather than a breakpoint.** `.controls` is a `1fr auto 1fr` grid, and a `1fr` column's automatic minimum is its own content: when the right cluster outgrows its share the column takes what it needs and the centre column slides along with it, so play, prev and next sit visibly left of centre. How wide that is depends on the **file**, not on the window — a release with chapters, several dubs, subtitles and a queue carries seven buttons where a plain stream carries three — and the numbers are far apart: seven break a ~770px window, three would not break a 500px one (`.controls` is 36px per button and a 6px gap, the centre cluster 146px, the bar 48px of padding). A media query would have to be written for the worst case and would fold the bar away on every file that fits, so the predicate is the grid's own sizing rule instead: the centre stays centred while `available - centre >= 2 x (count x (button + gap) - gap)`. The button, the gap, the centre cluster and the available width are measured from the live DOM (a `ResizeObserver` on the row and on the centre cluster); only the count is code, and it is the same set of flags the buttons branch on — `showQueue`/`showChapters`/`showAudio`/`showSubs`/`showCast`, computed once in `Controls` and handed to `MoreMenu` as props, because the cast condition alone is a line of markup nobody would have thought to keep in step with a second copy. **Not one term of the predicate is read from the current layout**, which is what keeps it from oscillating: folding the cluster away changes none of them, so the answer cannot flip back the moment it acts — the classic overflow-menu loop is a predicate that measures what it just did. Two consequences worth keeping: the overflow panel is a peer of the other OSC menus (`overlays.menu === 'more'`), so picking a row *replaces* it rather than nesting, and its button carries `.menu-toggle` — without that class `dismissOnOutsideClick` would close the panel on the way to the button's own toggle and it would reopen in the same gesture. And widening the window while the panel is up has to close it (`Controls`' second effect): the button would be gone, and a panel with no control left holds the chrome open through `overlays.any`. **Once folded, every panel it opens needs a way back**, and it is the same flag that decides it: `overlays.folded` is written by `Controls` (the only thing that measures the bar) and read by `MenuBack`, one component rather than the same six lines in four panels. Widening the window takes the row away by itself — the flag falls, the button is in the bar again, and there is nothing left to go back to. The row is **sticky**, which the chapter list forces: it scrolls itself to the chapter being played the moment it opens, so a row that scrolled with the content would be gone before it was ever seen. Sticky inside `.menu` means measuring from that panel's *padding* box, so the row takes the panel's 6px of padding as negative margin and hands the same amount back as padding — otherwise rows slide through the strip above and beside it — and its background has to be opaque where the panel's own is 0.94, including the hover state, for the same reason. The square corners need no rounding: a scroll container clips to its padding box, which is already round. **The glyph is a gear and the panel is named for playback, not for overflow.** Three dots are the accurate signifier for "what did not fit", and they were what this shipped with first; what people expect behind a gear in a player is exactly what is behind this one, so the heading follows the icon (`osc.more_title`, "Playback") rather than the mechanism. The gear already in the player means something else — `.tv-gear`, the per-device profile in the cast panel — and is drawn as sliders, so the two do not read as the same control.
- **The hover preview keeps the video's own aspect, not 16:9.** mpv reports `dwidth`/`dheight` — the size with the aspect already applied — the moment a file opens, so the box can be shaped correctly before any frame exists. It used to be a hardcoded `aspect-ratio: 16 / 9` on the placeholder, which meant the first real frame resized the whole popup: invisible on a 16:9 film and a jump on every hover for a 4:3 one, a phone clip, or a 2.39:1 scope transfer. Torrents merely made it obvious, since there the placeholder is on screen for much longer. The **crossfade layer** was the other half of that blink and a separate bug: `.thumb.fading` inherits `.thumb`'s `width` and 16:9 `aspect-ratio`, while the inline aspect that corrects them sits only on the in-flow frame — so on anything wider than 16:9 (a 1920x816 rip is ordinary) it computed 105px over an 80px box and overflowed onto the timestamp for the length of the fade. The tell was that arriving from an un-downloaded position never blinked: there is no outgoing frame there, so the element is never created. An overlay must take its size from the box it covers — `width/height: 100%` and **not** `auto`, because an `<img>` is a replaced element whose `auto` means its intrinsic size rather than the insets (measured: 484px), and the global border-box reset is what stops its own 2px border landing on top of that 100%. The frame is **184px** including that border, which is the figure `.hover-chapter` and `onSeekHover`'s 92px clamp are both written against; one consequence of the border box is that `aspect-ratio` now shapes the outlined frame rather than the picture inside it, so the video's shape is exact at the outline and off by the 2px inset (under 2%, absorbed by `object-fit: cover`) at the image. **And the shape must only ever move to a real value.** `dwidth`/`dheight` are observed with `none`, so mpv reports them *unavailable* whenever the VO reconfigures — which on a torrent is every stall for pieces. Read directly, the box fell back to 16:9 for those frames and snapped back, a visible blink while hovering; the swap of one frame for another was measured stable at 139px throughout, so the flicker was never the image. Same rule as `media-title`: a transient null must not erase what is already known. Related: a position of a torrent that has not downloaded gets a **distinct** state, not an empty box — the arrow the download readout already uses — because an empty outlined rectangle reads as a preview that broke rather than one that was never coming, which is the same mistake the end-of-file cards were fixed for.
- **A scrolling box says it has more below it, and the shape of that is forced rather than chosen.** `ScrollFade` is a bottom gradient with a chevron, rendered as the **last child of the container that scrolls** — one line per list and no wrapper, which is what made it affordable in five places at once: the dialog shell (so every sheet gets it, and the ones that fit never show it), the subtitle results, the torrent file picker, the link recents and the language list. Three things it cannot be, each measured in a WKWebView harness against the built stylesheet rather than reasoned about. It cannot be `position: absolute`: inside a scroll container that resolves against the *content* box, whose bottom is the end of the content, so `bottom: 0` sits under the last row and scrolls out of view — precisely backwards, and the alternative is a positioned wrapper around all five. The paint cannot be a negative offset on the sticky box either, because a sticky box is clamped to its containing block: on the settings sheet (`padding: 16px 8px 14px 18px`) `bottom: -14px` lands in exactly the same place as `bottom: 0`, 15px above the sheet's outer edge — and content scrolls *through* that 14px band, so the fade would leave a sharp strip of half-cut text under a faded one. An absolutely positioned **child** of the sticky box is not clamped, only clipped, and a scroll container clips at its **padding** box, so the paint reaches the border with a negative `bottom` of the container's own padding (measured flush: 1px from the outer edge, which is the border). And the two numbers it needs — that padding and the container's `row-gap` — are read off the container rather than passed in as props: a prop per call site is a number that drifts the day the sheet's padding changes, and a zero-height child of a flex column still takes a gap before it (12px in the diagnosis dialog), which a fade adding space to the box it describes cannot afford. Measured with the compensation in place, the layout cost is 0 and a box that fits does not begin to scroll. Detection is `scroll` + `ResizeObserver` + **`MutationObserver`**, and the third is not belt-and-braces: subtitle results arrive into a box with a `max-height`, so the content grows while the container's own size never changes and nothing else fires — measured, that case turns the fade on and no resize is involved. It is `pointer-events: none` and `aria-hidden`: a caption on the scroll position rather than a control (a click there is a click on the row underneath, the rule the bars' gradient tails already carry), and "there is more below" is something a screen reader already has from the scroll container itself. **Only a scroll earns the transition.** Growing in over 140ms is right when the fade answers the viewer's own gesture and wrong for everything else: switching from a settings tab that fits to one that scrolls left a shadow creeping up from the bottom edge a beat after the content had landed, which reads as a flicker rather than as an answer, and opening the sheet on such a tab is the same thing at mount. So a mount, a content change and a resize land at their final value in the frame the content itself paints (`instant`, a class that sets `transition: none`), and only scrolling is animated. Two things that has to get right: the flag and the state must be written in **one synchronous block** so they reach the DOM in one flush — a `transition: none` arriving a flush later would animate the very change it exists to suppress — and the flag is given back on the next frame, where the value is already committed and restoring a transition animates nothing retroactively. **The way that first went wrong is worth more than the feature**: deciding on `if (instant)` rather than on the local it had just been assigned from made the effect *read* a `$state` it writes, so it re-ran, re-registered its observers, took the `ResizeObserver`'s initial callback again — which re-armed the flag — and did it again the next frame. Writing state from an effect is fine; reading it back subscribes the effect to itself. Nothing reports it: no error, no warning, and the only symptom is a flag that never clears, i.e. a transition silently dead everywhere rather than a loop anybody notices. Measured on an idle probe: **95 class writes in 1.5s against zero mutations in the container**, and zero after the fix. Two traps in *testing* any of this. `requestAnimationFrame` does not tick in a webview that is in no window or in a window parked off every display, so the harness reads the initial state and every later one as identical — the first run said the fade never turns off, and the only thing wrong was the harness. And **`getComputedStyle().opacity` is not evidence in WebKit**: opacity is an accelerated property and reads back as its *final* value while a transition runs, so a fade mid-flight measures as 1 and every case looks instant. `Element.getAnimations()` is what actually answers — a running `CSSTransition` is listed there — and it is what separates the three cases above.
- **Tooltips**: put `data-tip="..."` (+ matching `aria-label`) on any element — a delegated handler renders the custom tooltip. Don't use `title`. **A tooltip is cleared by the pointer not being over an anchor, never by being told it left one.** Two measured browser facts make the obvious implementation leak: **`pointerout` is not delivered when the hovered node is removed**, and **a detached element's `getBoundingClientRect()` is all zeros** — which `flipAxis`/`shiftAxis` faithfully place in the top-left corner of the window. Going from the start screen into playback removes anchors under a stationary cursor by the handful (the torrent file picker is the one that gets noticed), so a tip whose 450 ms timer outlived its anchor rendered in the corner with nothing left to dismiss it: moving the mouse onto the video hit `onTipOver`'s early return, so only a click — which clears it in the pointerdown capture handler — or landing on another anchor took it away. Hence `el.isConnected` is checked **on both sides of the `await tick()`**, since a tick is exactly when a pending unmount flushes, and `onTipOver` over a non-anchor now *clears* rather than returning. Note `closest('[data-tip]')` still matches on a detached node, so guarding on the selector alone proves nothing. Tips go **above** their anchor by default, which is right for anything in a bar; `data-tip-below` beside the `data-tip` flips the preference for the case where what the tip explains sits *above* it and would be covered. Only the preference moves — `flipAxis` still takes whichever side has the room, so a card near the bottom of the window gets its tip above anyway. **The tip belongs on the part it answers, not on the whole control.** A recents card had it on the entire button, so pointing at the poster raised a path over the poster — the frame is the one thing on that card that needs no caption, and the tip covered it to say so. It now hangs on `.card-meta`, the wrapper around the name and the remaining time, which is where the truncated name that prompts the question actually is. That wrapper is deliberately boxless: `.card-name`'s top margin collapses through it, so it covers the two lines and not the gap above them, and the card's height is unchanged. **A raw source string is not a tooltip** (`readableLink` in format.ts): a URL is percent-encoded, so a Cyrillic path arrives as a run of `%D0%B1` and the one thing meant to answer "which link is this" became the least readable text in the dialog; and a magnet is long not because it says a lot but because it carries a *tracker list*, which is how a client finds peers and not how a person tells two magnets apart. So trackers are dropped and what is left is the name and the hash — and deliberately **not** the row's own label, which is the name alone: a tooltip that repeats what it is pointing at is noise.
- **OSD**: `showOsd(text, { sub, progress, sticky })` — a label, an optional bar and an optional smaller second line, up for 1.2 s. No icons: an icon took space and said nothing about the point, while text labels give every action a similar width. **It is the topmost thing the player draws that a viewer can be told something by** — `z-index: 80`, above the dialog backdrop's 70, below the tooltip's 90 and the veil's 100. That ordering is load-bearing rather than tidy: most popups report the outcome of a button *inside* a dialog (the torrent cache cleared, seeding restarted, port forwarding switched, a torrent updated, "this torrent did not come from the catalog"), and under the backdrop none of them vanished — the backdrop is `rgba(0,0,0,0.45)`, so measured in headless Chrome against the built stylesheet the popup's label rendered at 127,127,130 instead of 232,232,236, i.e. showing through a dimmed screen and reading as something that had escaped to the background. It is safe there only because the popup takes no clicks (`pointer-events: none`), which is what keeps it from making anything behind it unreachable — **anything else promoted above 70 owes the same guarantee**. The cost is paint: a 598px sheet centred in a window under ~1040px wide reaches left of the popup's own 18 + 202, so a tall dialog loses its top-left corner for those 1.2 s.
