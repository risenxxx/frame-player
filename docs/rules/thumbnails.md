# Thumbnails, posters and background decoding

The seekbar storyboard and everything that decodes a frame outside playback: what it costs, what colour it comes out, and which frame it has to be.

Part of the rule book: [`CLAUDE.md`](../../CLAUDE.md) carries the one-line
version of each rule here, this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.

- **Whether the sidecar shares mpv's FFmpeg depends on the platform, and the prefix on a log line tells you who is talking.** On macOS `src-tauri/ffmpeg-macos/lib/*.dylib` are **symlinks into `src-tauri/lib/`** (verified with `otool -D`: both carry the install name `@rpath/libavcodec.62.dylib`) — mpv and the thumbnail service load one and the same library. On Windows they are separate DLLs: `libmpv-2.dll` against `ffmpeg/bin/*.dll`. What is constant is the logging: mpv installs an `av_log` callback and its lines read `[ffmpeg/video] hevc: …`, so **a bare `[hevc @ 0x…] …` is libavcodec's default callback** and did not come through mpv — in practice the sidecar decoding a file in software, not playback. Hence `log::set_level(Error)` next to `ffmpeg_the_third::init()`: a chatty file (Dolby Vision RPU notices on a DV remux, for one) otherwise buries everything else in the dev console. Note the asymmetry it inherits: the log level is global to a library, so on macOS that call also caps mpv's own libav messages, while on Windows it only affects ours. If mpv-side FFmpeg warnings are ever needed for debugging, that line is where they went.
- **Background decoding competes with playback — budget it explicitly.** The thumbnail storyboard decodes in *software*, so it degrades the player identically whether mpv's hwdec is on or off; that symmetry is the tell. Measured on a 197 s 4K60 VP9 file: an unbudgeted storyboard (`threads = ncpu`, 5 ms sleep) took ~3 cores for ~35 s right after the file opened, and made seeking feel broken. Now bounded three ways: `DECODE_THREADS` (capped, not `ncpu` — 292 % → ~150 % CPU), a duty cycle sleeping `1/YIELD_RATIO` of the time the last cell took, and `background_qos()` (ffmpeg's frame-thread workers inherit the creator's QoS, so one call at thread start is enough). **Both knobs have a floor as well as a ceiling**: the first attempt (`QOS_CLASS_BACKGROUND` + 1:1 duty) was over-corrected — BACKGROUND pins the work to efficiency cores and a 3-minute 4K60 storyboard then took minutes, so thumbnails were not ready when the user reached for them. `QOS_CLASS_UTILITY` is the right class: P-cores stay available, but the player preempts the storyboard rather than the reverse. Keep any future background work under the same three constraints. **And a fourth: do not start it when nobody is waiting for it.** While a television owns playback the storyboard is a prefetch for a gesture nobody is making — it decodes the whole file to make hovering instant, and the viewer is looking at the TV — so it is suspended for the length of a cast session and resumed when the session ends (`suspendThumbs`, set by the cast module so `thumbs` keeps depending on nothing). Hovering still works meanwhile, one on-demand decode per hover instead of none. This is the case that made it visible: casting a torrent that is still downloading means the file **completes during the session**, and the status poll then dutifully starts a 4K storyboard behind a paused player. **And a fifth: on battery the same pass runs at a third of the rate** (`power::on_battery()`, `BATTERY_YIELD_MULT`/`BATTERY_MAX_YIELD_MS` — rest is twice the time the cell took rather than a third of it). Two measured facts shape that. The **ceiling, not the ratio, is what decides the rate on the files this matters for**: a 4K HEVC cell costs ~1.3 s, so `MAX_YIELD_MS` of 120 makes the mains pass a ~90 % duty cycle — raising the ratio while leaving the cap would change nothing at all. And the *ratio* is what keeps a cheap file from resting for two seconds a cell. Measured on a 6.3 GB 4K HEVC file with a cold cache: mains **164–208 % for ~40 s**, battery **64–105 % for ~60 s**, warm reopen a flat 21–24 % on either supply (which is also the check that the throttled pass still finishes — a partial storyboard would resume and burn processor again on reopen). Only the *background* pass is throttled: a hover is somebody waiting, and it decodes at full speed regardless. The supply is asked per cell so that unplugging is noticed within a few of them, behind a 10 s cache, and both platforms answer with one call — macOS `IOPSGetTimeRemainingEstimate()` (`kIOPSTimeRemainingUnlimited` is mains, and is also what a desktop with no battery answers; verified against `pmset -g batt`), Windows `GetSystemPowerStatus`. **A machine that declines to answer is treated as plugged in**, because degrading the player on a machine that merely failed to report is the worse way to be wrong.
- **A preview is a decoded frame, and a decoded frame has a colour space — which the thumbnail service used to ignore entirely.** `scaling::Context::get` was given the two pixel formats and nothing else, so swscale fell back to its own default coefficients (**BT.601**) whatever the file said. Three sizes of wrong come out of that, and the third is the one that gets reported. On an ordinary BT.709 file it is a small hue error. On BT.2020 it is not: measured against a correct conversion of the same frame, up to **32/255 on the green channel**, i.e. every HDR preview in the player was off. And on **Dolby Vision profile 5 the picture comes out pink**, which is what "the previews are broken and the video is fine" means — profile 5 encodes the picture as IPT-PQ-C2 rather than Y'CbCr and carries **no colour tags at all** (the file this was found on reports `yuv420p10le(tv)` and stops there, because the colour lives in the RPU), so a YUV decoder reads the chroma planes as something they are not. mpv is right about it for the same reason we were wrong: libplacebo applies the RPU, and libavcodec does not. So SDR keeps the swscale path — now with `sws_setColorspaceDetails`, which is the whole of that fix — and anything else goes through `color.rs`: swscale is asked for `yuv444p16le` (a resize and a format change, no matrix in it) and the transfer, the matrix, the tone map and the primaries are done in floating point. **2.74 ms per 320px frame**, measured in release, against a decode that costs hundreds of milliseconds — and only on the frames that need it. Four things worth knowing before touching it, and two of them were got wrong first. **Dolby Vision must be asked about before the transfer characteristic**, since a profile 5 stream has none, and it must be asked about *narrowly*: profiles 7 and 8 have an HDR10-compatible base layer and are already handled correctly by the PQ path, so dragging them through the IPT inverse would break what works. The record is read from `AVCodecParameters::coded_side_data` (FFmpeg 8 moved stream side data there; `Stream::side_data` in the crate still reads the old `AVStream` field and finds nothing) and `dovi_meta.h` is outside the sys crate's bindings, so the nine-byte struct is declared locally behind a size check. **It is IPT and not ICtCp** — the two are near neighbours, every reference to "Dolby Vision uses ICtCp" leads to the second, and the wrong one is wrong in a way that hides: interiors and skin look plausible under both. What separates them is a frame whose colour is not negotiable, and a greenhouse the player renders green is that frame — over the bank of leaves the ICtCp inverse gives `r/g/b 0.53 / 0.27 / 0.20`, i.e. red foliage, against IPT's `0.40 / 0.44 / 0.15`. The plane order goes with the matrix: `I, P, T`, so the **U plane carries P**, the red–green axis, where a Y'CbCr reader expects blue–yellow. **The exposure is one number per encoding and never the frame's own light.** PQ and HLG mean nits, so white is the ITU reference 203. A profile 5 base layer means nothing until the RPU has reshaped it, so its anchor is fitted — 60 nits, against the player's own output on four scenes spanning a sunlit park, a warm interior, a dim greenhouse and a near-black night exterior. Stills settle the hue and leave about half a stop of brightness inside the noise, which is why that number went 40 → 60 after the previews were seen in the player rather than side by side with a screenshot; it is a knob, and raising it darkens every scene by the same amount. Exposing each frame from its own percentile is what shipped first and it is the mistake worth naming: it hands every frame the same average brightness, so a night scene comes back as a grey afternoon — measured across those four scenes, the 99.5th percentile runs 4.8 → 95.8 nits, so the gain it picks is off by twenty-fold in exactly the direction that destroys what a preview is for. (Reading a profile 5 frame at 203 like PQ is the opposite error and renders that interior almost black: the robe carrying the scene measures 2.9 nits.) And the result is an **approximation, deliberately**: without the RPU the reshaping is missing, so the colour is close and the level is a calibration. Measured on the reported file, over the pixels bright enough to read (luma > 60), the magenta signature — blue *and* red both above green — goes from `B−G 7.7` and `4.5` on two interior scenes to `0.4` and `−0.5`, while the warmth the scene actually has stays. What is *not* approximate is anything the viewer looks at properly: saving or copying a frame goes through mpv's own `screenshot-to-file` and is unaffected by any of this. `FP_TEST_POS` and `FP_TEST_DUMP` on `thumb_smoke` are how this was checked and are the only way to check it — a thumbnail of the right size in the wrong colour passes every assertion that can be written about it.
- **The preview must show the frame you land on, and both halves of that were wrong.** The hover thumbnail comes from a grid whose step is `clamp(duration/240, 0.25, 10)` — 10 s for anything longer than 40 minutes. The position was mapped to its cell by *truncation*, so the preview sat up to a full step **earlier** than the cursor, while the seek that follows is exact: the two errors added instead of canceling, which is why the played frame was reliably *ahead* of the previewed one. Measured on a 24-minute file, 30 hover positions, "different scene" = PSNR < 18 dB between the previewed frame and the one playback starts on: **60 %** with truncation, **37 %** with rounding to the nearest cell, 30 % at a 3 s step, 20 % at 2 s, 0 % at 1 s. Rounding is free (cell N still holds the frame at `N*interval`, so existing caches stay valid — no `CACHE_MAGIC` bump) but it only halves the error; what removes it is fetching the **exact** frame when the cursor comes to rest, the same trade `scheduleDragSettle()` makes with the video. Two consequences worth keeping: that refinement visibly *replaces* the thumbnail in roughly 40 % of hovers — inherent, since those are exactly the cases where the grid frame was a different scene — and its cost is one GOP of software decode, measured worst-case **120 ms** on 1080p h264, **1330 ms** on 4K30 HEVC 10-bit, **1940 ms** on 4K60 VP9 (GOP 5 s). So on 1080p it reads as the preview sharpening ~200 ms after you stop; on 4K it is a late, visible flip that also burns three decode threads next to playback. **The decode itself cannot be made cheaper** — measured per GOP against the baselines above, `skip_loop_filter=all` gives 4K60 VP9 nothing at all (1950 vs 2010 ms, noise), 4K30 HEVC ~10 %, 1080p h264 ~8 %, and `skip_frame=bidir` ~18 % on h264 while costing a landing a few frames off — so the latency budget that *is* controllable is the scheduling: `SETTLE_MS` is 70 ms rather than `scheduleDragSettle()`'s 120 (this gates a 320px thumbnail, not a seek of the video), armed from the **pointer move** and not from every request (the throttle's trailing call re-enters up to 85 ms later, and re-arming there delayed the exact frame by that much for nothing the user did), with **one exact request in flight at a time** — a slow sweep would otherwise queue seconds of GOP decoding whose results are all stale on arrival. Firing an exact request also cancels the pending trailing grid request: it is for the same resting position, and it is the only way a grid frame could land *after* the exact one and overwrite it. If the 4K case becomes a problem, the fix is a probe in the shape of `fileSlowSeek`/`wantExact()` — time the first refinement and stop refining that file past a threshold — or a decode session of its own for hover requests, so they stop re-seeking the storyboard's; *not* a finer grid, which needs a 1–2 s step and therefore decodes the whole file in the background. The replacement **crosses over rather than cuts** (`.thumb.fading`, 140 ms), and the layer on top is the **outgoing** frame, never the incoming one: an `<img>` keeps showing its previous content until a new `src` decodes, so putting the new frame on top would let the pre-refinement frame show through underneath for a frame — with the outgoing frame on top, whatever is beneath it is always the newest. Grid frames are swapped with no animation at all, since those track a moving cursor. `frame_exact_at` must never touch `refine_mode`: that flag is the storyboard's verdict about the file, and one hover request must not push the whole background pass into linear decoding.
- **No storyboard means no space for one.** With thumbnails gated for streams the hover popup was still reserving its 180px frame and filling it gray, which reads as a preview that broke rather than one that was never coming. The popup drops the frame entirely for a network source and shows the timestamp alone (and the end-of-file cards, which cannot decode a poster out of a URL either, put a link mark where the frame would be rather than an empty outlined rectangle) — and `hoverX`, whose clamp is half the popup's width, has to narrow with it or a bare timestamp stops following the cursor well before either end of the bar. What could bring previews back for YouTube specifically is its own storyboard sprites, which yt-dlp exposes as `sb0`/`sb1` formats; that is a feature, not a fix. The other half of the complaint — slow seeking — has one real lever, and it is `ytdl-format`: the hook's default takes the best available stream, so a 4K one is what every seek then pays for. Hence the quality setting.
