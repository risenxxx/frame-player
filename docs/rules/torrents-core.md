# Torrents: the session, adding, storage and deletion

How a magnet becomes a playing file, what the session is allowed to keep open, where the data lives and what may be deleted.

Part of the rule book: [`CLAUDE.md`](../../CLAUDE.md) carries the one-line
version of each rule here, this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.
The *why* behind it — what was tried, what was measured — is in
[`../torrents.md`](../torrents.md).

- **A file descriptor is not a renewable resource on macOS, and running out of them does not fail like running out of something.** launchd gives a GUI application a soft `RLIMIT_NOFILE` of **256** (`launchctl limit maxfiles`), which this player cannot live inside: librqbit holds one open descriptor per file of every torrent in its session, and persistence restores *every* torrent ever added when the session is built. Measured on one installation: 9 torrents, 135 files, 144 descriptors held — one of them a Blu-ray release whose BDMV folder is 79 `.clpi`/`.mpls` files nobody was watching — beside ~35 peer sockets, mpv's connections to the loopback stream server, WebKit and Metal's shader caches. What that costs is **not** an error anybody sees. Measured: a **cold** `AudioComponentInstanceNew` on a full table answers `-1` (mpv logs `unable to open audio component ([255][255][255][255]/-1)` and falls back to an `avfoundation` output whose clock never advances), and `VTIsHardwareDecodeSupported(kCMVideoCodecType_HEVC)` answers `0`, which reaches libavcodec as `kVTCouldNotFindVideoDecoderErr` — "VideoToolbox decoder for this format not found" — and drops every hwdec rung into software. **Both verdicts are then cached for the life of the process**: measured, they still fail after every descriptor has been released, so one brief moment at the ceiling costs the whole session its hardware decoding and its audio clock. With mpv syncing video to audio, the picture simply stops — reported as "the pause icon toggles and the video never plays", reproduced end to end against our own libmpv (`t=0.167` for ever; the same poisoned process plays at real time with `audio=no`), and with nothing on screen, in any log of ours, or in the file itself to connect it to a limit. Two halves, and the first is not optional. **`raise_fd_limit()` runs as the first statement of `run()`** — librqbit ships `try_increase_nofile_limit()` and its own CLI calls it, so embedding the library means inheriting the obligation; the hard limit under launchd is unlimited and the `rlimit` crate knows the stricter ceiling macOS keeps in `kern.maxfilesperproc`, so it is one call that takes 256 into six figures. **And `torrent_storage.rs` stops the waste**: a storage of our own that opens a torrent file when it is read and closes it when a process-wide budget says so, given to `SessionOptions::default_storage_factory`. Three things it keeps deliberately, because each is load-bearing elsewhere — the files are still *created* at `init` (`torrent_offline_file` and `dir_size` read what is on disk, and lazy must change how many descriptors are held, never what exists), Windows still gets `FSCTL_SET_SPARSE` before the first write, and `take()` still leaves the old storage unusable. Two traps in writing one, both found by the tests rather than by reading: `JsonSessionPersistenceStore::update_db` **refuses to record a torrent whose factory is not `FilesystemStorageFactory`**, so a storage that does not answer to that `TypeId` is dropped from the session store the moment it is added — no resume data, no restore, a full re-hash on every open; and `StorageFactoryExt::boxed()` **discards the `is_type_id` override** (its wrapper answers for itself and never asks the factory inside, which is why librqbit's own `timing`/`slow` middlewares' overrides are dead code), so the factory has to be `Box`ed as `Storage = Box<dyn TorrentStorage>` directly rather than through `.boxed()`. Related and now out of date above: **librqbit 9.x does call `FSCTL_SET_SPARSE`** (`try_mark_sparse`, on the first write) where 8.x never did, so the Windows reasoning that treats every torrent file as fully allocated is a version behind.
- **A torrent is a network source that steers itself, and both halves of that are the design.** A magnet becomes a list of files, each served from our own loopback HTTP server at `/t/<infohash>/<index>/<name>`; mpv opens that URL and its Range requests are the "the viewer is here" signal librqbit turns into piece priority. **The identity lives in the path, never the port** — `sourceId()` reads `torrent:<hash>/<index>` straight back out (`parseTorrentUrl` in source.ts, matched to `stream_url` in torrent.rs by a test at each end), because the port is ephemeral and a key taken from the transport forgets the film every session. The trailing file name is load-bearing too: it gives ffmpeg an extension to probe by, and it is why `displayName` now percent-decodes — without that an ordinary film reads as `The%20Movie%202024`. **Nothing is downloaded until it is read**: the torrent is added *paused with nothing selected* and the HTTP handler itself puts a file into `only_files` and unpauses when a request for it arrives, which is the same principle as piece priority one level up. **"Nothing selected" has to be said explicitly — `only_files: Some(vec![])`, never left unset.** librqbit reads an absent selection as "everything" and stretches every file of the torrent to its full length (`set_len`) at the end of initialization; on APFS and ext4 that is free, but **NTFS has no sparse file unless somebody calls `FSCTL_SET_SPARSE`, and librqbit never does**, so on Windows a nine-episode season occupied all of itself from the first open with two episodes fetched — reported, correctly, as "the empty files take up space". An empty selection is legal (`compute_only_files` only range-checks the indices) and costs nothing later, because `update_only_files` — which `select` already calls — does not preallocate at all: the file grows as pieces are written. It also gives `torrent_offline_file` back a signal it had lost, since that gate compares the file's length against the torrent's and everything was full length, which on Windows (where the allocated size *is* the length) made an untouched file indistinguishable from a finished one. `an_unopened_torrent_allocates_nothing` pins it, and **has to wait out `Initializing` to do so**: `add` returns before the preallocation happens, so a check made straight after it passes whatever `only_files` says — which is how the first version of that test came to pass against the unfixed code. That is what makes a twelve-episode torrent a twelve-entry queue costing nothing but the episode playing — `queueTorrent` hands mpv every video's URL, and a URL is only a string. The session is **lazy** for the same reason the yt-dlp probe stopped blocking init: a player that joins the DHT on startup is not one people keep. **Opening an episode already on disk costs nothing, and getting there took two separate fixes.** First, `select` returns early when `file_complete` — initialization has just verified the pieces, and `stream()` reads from a *paused* torrent perfectly well (it only blocks on a missing piece), so a rewatch makes **zero peer connections**; librqbit's own `maybe_reconnect_needed_peers_for_file` already declines to reconnect for a finished file, so nothing fights this. Second, and bigger: **a magnet opened once is never resolved again.** librqbit used to run with `persistence: None`, forgetting the torrent between runs and going back to the DHT every time — measured at 1.5–10 s — even to reopen a season sitting on disk. The metadata *is* the torrent file, so it is cached at `<cache>/torrents/.meta/<infohash>.torrent` and replayed through `AddTorrent::from_bytes`; a corrupt or stale one falls back to the magnet rather than making the torrent unopenable. Measured on the same torrent back to back: resolve **1.52 s → 4.45 ms**, and a re-read of an already-fetched region **1.20 s → 0.8 ms**. Both are pinned by `complete_file_needs_no_swarm`, which builds a torrent from a local file with `create_torrent`, seeds the cache and the folder by hand, and asserts the served bytes plus `state == "paused"` — **fully offline**, so it runs in an ordinary `cargo test` and catches a reordering of `select` that would quietly start the swarm. **Piece re-verification is skipped too, and that took measuring the fear rather than accepting it.** Without `fastresume` librqbit hashes the *whole torrent* on every open — holes included, since at the time the files were all created at full length — so reopening a 7.5 GB season with 46 MB fetched cost **3208 ms**, and that grows with the torrent rather than with what was watched (hashing measures ~2.3 GB/s here). `fastresume` needs `persistence`, which was refused on the grounds that it resumes torrents at startup; measured, three of the four worries were unfounded. The stored metadata is written as a separate `.torrent` file and read back, so restoring costs **no DHT lookup**. Data deleted behind our back is caught rather than trusted — librqbit reports 0 bytes held and a read blocks for pieces, instead of quietly serving the zeros a sparse file gives back. Session creation with a torrent in the store is 21 ms. The one real risk is that **a torrent recorded as running is restored running**, which would talk to peers for something nobody asked to watch — so `pause_restored` stops everything the session brought back, and it has to **wait out `Initializing` first**, because librqbit refuses to pause a torrent in that state and the moment initialization ends it would go live. Result on the same season: 3208 ms → **2.38 ms**. Two bugs fell out of enabling it, both of which would have bitten in the app: librqbit does **not** create the persistence folder, and without it every torrent fails its initial check with "error storing initial check bitfield"; and the DHT's own state file pins the port it bound and rebinds it next time, so tearing the session down and building another — which the **seeding switch does** — hit "address already in use" and left the player unable to open anything until a restart. `disable_dht_persistence` settles that and, as a bonus, stops librqbit writing to `com.rqbit.dht` in the OS cache root, outside the directory this feature can be cleared from.
- **A torrent arrives three ways, and a `.torrent` file is not a file the player opens.** A magnet is pasted, a `.torrent` URL is pasted, and a `.torrent` **file** is dropped or picked — and only the first two fit a box that takes text, which is why torrent support was invisible in a dialog called "Открыть ссылку". Three things make the file first-class. `AddTorrent::Url` understands `http:`, `https:` and `magnet:` **and nothing else** (a local path reaches it as "provided path is not a valid magnet URL"), so `add` reads the bytes itself and goes through `AddTorrent::from_bytes` — and since a `.torrent` file *is* the metadata, `librqbit::torrent_from_bytes` gives the info hash locally, which means the hash-named folder, the metadata cache and the history all work exactly as for a magnet. A `.torrent` URL is now the only source left with no hash to read. Classification happens **in `loadFiles`**, where a drop is already sorted by extension, rather than at each of the four entry points (drop, picker, argv, the Apple Event) — reached through an `openTorrentFile` hook, because player.svelte.ts must not know that a torrent client exists; and only when nothing else in the drop is playable, since a folder holding both a film and its `.torrent` should play the film. **What gets remembered is a magnet built from the hash, never the path** (`magnetFor` in source.ts): a `.torrent` file is thrown away after use and a tracker page can go down, while the info hash plus the metadata cache reopens the torrent with no lookup at all — so a file opened once keeps working after it is deleted. One consequence worth keeping in mind: `openTorrent` is now reached with **no dialog open**, so its failure path raises one, or a corrupt file would fail in complete silence. The file association is deliberately **not** declared in tauri.conf — claiming `.torrent` system-wide would take it from whatever BitTorrent client the machine has, which is not a video player's to do. **The box surviving a close and the box being reopened are different events**, and conflating them is what left the previous link typed in it: the text and its error line are kept on purpose, because a link that fails reopens the dialog with both — that is what makes the yt-dlp button usable — but those paths raise the dialog themselves and never go through `openLinkDialog`, which is somebody choosing to open a link and therefore clears all three. Finding the last magnet still there is wrong twice over: it has to be deleted by hand before anything can be pasted, and **the recents list is hidden while the field is non-empty**, so the one place the previous links are offered disappears with it. A torrent that resolves into a file picker closes the box for the same reason a single-file one does (`playTorrentFile` always did); left open it sits *under* the picker and comes back when the picker is dismissed.
- **A freshly added torrent is not ready to be touched, and the order of the three steps is load-bearing**: `add_torrent` returns while the torrent is still `Initializing` (checking and allocating files on disk, which scales with the size of the *torrent*, not of the file being watched), and in that state librqbit refuses `update_only_files` outright ("can't update initializing torrent") while `stream()` accepts only `Paused` or `Live`. So it is wait → select → unpause → wait again, with the lock dropped across each wait or every parallel connection ffmpeg opens serializes behind it. On Sintel (129 MB, one file) that window is too short to see; on a nine-episode 7.5 GB season it swallowed the whole of playback. It cost a diagnosis only because the handler answered a bare **404** for every failure, which reads as "no such file" — hence the reason is now logged and a not-ready answers **503**, since the two are different facts and a torrent that plays on small releases and dies on large ones is otherwise indistinguishable from a broken URL. Three things fell out for free because a stream is `http://127.0.0.1:…`: `isNetworkSource` already gated the storyboard (the collision the roadmap warned would be discovered late), the posters and the folder queue. What is **not** solved is the seek: a cold jump costs *downloading*, so the measured seek contract below does not apply, and there is no map of what is buffered — librqbit keeps the piece bitmap behind `pub(crate) with_chunk_tracker` and the finest public measure is `TorrentStats::file_progress`, a percentage. Measured against the live Sintel swarm (the analysis's spike #1, kept as `sintel_smoke`): magnet → file list **10.0 s**, first byte of a tail range **7.9 s**, a cold seek into the middle **1.3 s**, 13 peers at 664 KB/s. Which is why a torrent stall must say *why* — peers and rate under the label — since mpv's own answer is `paused-for-cache` and nothing more, and "no peers" and "slow swarm" are different problems that must not look the same.
- **Seeding is off by default, and the switch has to be able to stop it *now*.** In Germany and several other jurisdictions the exposure from uploading is categorically worse than from downloading, so a player must not opt anyone into it silently. The mechanism is librqbit's `disable-upload`, which is a **compile-time feature unlocking a runtime flag** — without the feature there is no way to stop seeding at all, since `LimitsConfig.upload_bps` is a `NonZeroU32` and cannot even express zero. What it does is thorough rather than a rate limit: no bitfield, no `have` messages (peers are never told what we hold), piece requests refused outright, peers dropped once the file is complete. What it does **not** do, and the settings hint says so, is make the client invisible — finding peers means announcing to trackers and the DHT, so membership of the swarm is still observable. The flag is baked into the session when it is built, so changing the preference **tears the session down and rebuilds it**, which costs the running torrent; that is the honest trade, because a switch reading "off" while pieces are still going out would be a lie about the one behavior here with legal weight attached.
- **A finished episode leaves no trace, so the torrent store keeps its own record of them.** `frameplayer.positions` *deletes* an entry past `FINISHED_FRACTION` — which is what takes a film out of "continue watching" — so a watched file is indistinguishable from one never opened, and neither "delete the ones I have seen" nor a mark in the file picker can be built on it. Hence `watched: string[]` on the `frameplayer.torrents` entry, by **file name** rather than index (an uploader who inserts an episode renumbers everything after it, the same reason positions are re-keyed by name when a torrent is superseded). It is written from the **status poll** rather than from `persistPosition`, and that is the dependency direction rather than convenience: the position store must not know what a torrent is, while the poll already holds the info hash, the index and the playhead, and ticks once a second for exactly as long as a torrent is playing. `rememberTorrent` runs on *every* open, so it has to carry the list forward — dropping it would forget every watched episode each time the season was reopened, in silence. Deleting them is `torrent_forget_files`, which prunes rather than forgets: the folder, its `.meta` and the magnet all stay, so the torrent reopens for nothing and the kept episodes play at once. **It is safe only because of `validate_fastresume`** — librqbit verifies at least one piece of every file its resume data claims plus a random sample, and one failure throws the whole bitfield away, so a file removed behind its back cannot be served as zeros; the price is one re-check on the next open (~3.2 s for a 7.5 GB season). The order is load-bearing: the torrent leaves the session *before* anything is unlinked, since on Windows an open file cannot be deleted and on macOS it can, which is worse — librqbit keeps writing through a handle to a file with no name. Matching is by file name **against what is already inside the folder**, so nothing is joined onto a path and no name can escape. And the store itself joined `IDENTIFIED_STORES` in the process: it had never been in it, so "forget everything" left behind a magnet for every torrent ever opened — which names what was watched as plainly as a position does.
- **Once the viewer can choose where torrents are written, "the torrent directory" is three questions, and answering them with one path is how a video player deletes somebody's films.** `Dirs` keeps them apart. **`state`** is ours unconditionally — the metadata cache, librqbit's session store and the record of the roots — and stays in the app cache directory whatever is chosen, which keeps the chosen folder pure video, leaves `prune_orphaned_store` and the clear-cache button pointed where they always were, and means a removable drive going missing costs data and not the player's bookkeeping. **`root`** is where *new* torrents go. **`roots`** is everywhere data may already be — the current root, every root used before it, and `state` — because changing the setting must not orphan a season downloaded last week: lookups scan all of them and **nothing is ever moved by a change of setting**. The dangerous half is what may be *deleted*, and `is_ours` is the single rule: inside `state` the answer is yes for anything (the player owns that directory, and a folder from the older name-based layout has to stay deletable), anywhere else the folder name must parse back to an info hash. It is enforced in Rust in front of every destructive path rather than in the UI — `list` skips what it does not recognise (not even measuring it: walking somebody's media drive to print a number is its own kind of rude), `forget` takes a **path** and refuses one whose parent is not a known root, and `torrent_clear_cache` — which used to remove *every entry it found*, correct while the directory was ours alone — now removes only recognised folders, sweeping loose files in `state` and nowhere else. Roots are compared with `same_dir`, i.e. canonicalised, so a symlinked home (which macOS hands out routinely) is one directory rather than two, and a path that cannot be canonicalised is refused rather than guessed at. Two consequences elsewhere: `relocate` renames **beside the folder it replaces** rather than into the current root, since `fs::rename` does not cross a volume and the two may now be different ones; and the chosen root is recorded in a dot-file beside the state rather than in localStorage, because commands can arrive before the frontend has said anything and a preference that is only sometimes in effect would put files in two places. `a_chosen_root_protects_what_it_did_not_create` is the test that matters — it points every destructive path at a directory holding somebody's films and proves they survive.
- **The torrent's folder carries its info hash, and disk is the source of truth for storage.** `ManagedTorrentOptions.output_folder` is `pub(crate)`, so a folder named after the torrent alone could never be *read back* and the mapping from torrent to directory would have to be guessed — hence the name is ours to compose and it always ends in the hash: `<cache>/torrents/<Name> [<infohash>]`, parsed back by `folder_hash` and resolved by `folder_for`, which **prefers whatever folder already exists** so nothing on disk is moved by an upgrade. A side file mapping hash to directory would answer the same question and be a second source of truth to keep in step with the filesystem — a rename, a half-written index or a folder restored from a backup puts the two out of agreement, and the failure is either a torrent that cannot be found or a delete aimed at the wrong path. `sanitize_name` is what a torrent name has to survive first, and every rule in it is Windows': the forbidden characters, **reserved device names** (`AUX`, `com1.2026` — the *stem* is what makes a name reserved, so the escape goes at the end of the stem and not of the name, which is where it was first written and achieved nothing), a **trailing dot or space** (silently dropped by Win32 after the folder is created, so every path built afterwards misses it), and a length cap cut on a **character** boundary, since a byte-wise cut leaves a Cyrillic name invalid UTF-8. Brackets are stripped from the name too, or a release called `Show [1080p]` makes its own suffix unparseable. A folder that is a bare hash is renamed the first time `add` can read a name for it — one torrent at a time, at the moment it is opened, rather than a sweep over the whole cache at startup — and that rename **must not happen under a live torrent**: on Windows the files are open and it fails, on macOS it succeeds and leaves librqbit writing through handles to a path that no longer exists, so the torrent leaves the session first. It costs `fastresume` (the store entry goes with it) and therefore one re-hash of what is on disk, ~3.2 s for a 7.5 GB season, once per torrent ever; a failed rename costs nothing, since `folder_for` finds the old folder by hash regardless. **The name is only knowable before the add because the metadata is fetched first** — `list_only` resolves a magnet and returns before any storage is created, so `add` now goes: bytes (a `.torrent` file, our `.meta` cache, or one `list_only` lookup) → cache them → name the folder → add from those bytes, which reaches no network at all. The hash comes from `Magnet::parse` (no network) rather than a `list_only` resolve, which would double a ten-second DHT lookup. `torrent_list` reads the directory and never consults our records, so a folder from a previous run or the older layout is still visible and deletable — storage management keeps working with history off, and the remembered magnets only add the ability to *reopen*. **Size must be measured in allocated blocks, not `len()`**: librqbit creates every file at full size up front and APFS/ext4 make them sparse, so a nine-episode season with one episode part-fetched reports **7.45 GB** by length and **142 MB** by blocks (verified against `du` to the byte). Reporting the length would tell the viewer to delete something to reclaim space that was never taken. Windows keeps `len()` — NTFS needs an explicit `FSCTL_SET_SPARSE` that librqbit never asks for. **"In the session" is not "playing right now", and `torrent_list` must not answer the second.** It used to: the row's `active` flag was session membership, and since `release` *pauses* rather than removes (the pieces stay, so re-opening continues), a torrent stayed in the session for the rest of the run — so returning to the start screen found its delete button disabled and labeled "сейчас проигрывается", permanently, from the moment anything had been watched. Deleting a merely-loaded torrent is safe anyway, because `forget` takes it out of the session *before* removing the directory. So the flag left Rust entirely and became `torrentIsPlaying(row)`, read from `parseTorrentUrl(player.filePath)` — **not** from `torrent.info`, which is set when a magnet resolves and would still claim to be playing after the file picker was canceled — and it is a **function, not a field of the row**, because the list is fetched ~300 ms after the file is unloaded and a snapshot taken there is how a button gets stuck disabled. **A row also names itself from the disk, because our record of it is not where the truth lives.** The name and the magnet are in `frameplayer.torrents`, i.e. in *localStorage*, which is per webview, while the data directory is per identifier — so two builds of the player (a `.app` and an unbundled dev binary, which WKWebView files under the executable name) share every byte on disk and neither one's store, and a season downloaded by one showed up in the other as "Раздача без названия · ссылка не сохранена" with a dead button. The cure is that everything needed is already beside the data: `cached_name` reads the torrent's own name out of `.meta/<hash>.torrent` (measured warm on a 227 KB file: **0.16 ms**, and the parse borrows rather than copies), and `listTorrents` builds the magnet from the folder's own info hash when nothing was remembered — which reopens with **no lookup at all**, since that same metadata is what `add` resolves from. Opening such a row records it, so it is nameless once and never again. `start.torrent_unknown` now belongs to folders from the older name-based layout alone.
- **A deleted torrent used to come back, one per restart, as an empty copy of itself.** `torrent_forget` removed the directory and our record, but took the torrent out of librqbit's own store only when it was in `inner.torrents` — which `add` alone fills, so it covered a torrent opened *in that run* and nothing else. Everything else on disk is in the session only because it was **restored**, and a restore recreates the folder: `Initializing` calls `FileStorage::init`, which is `create_dir_all` plus `create(true)` on every file, with `ensure_file_length` giving the `only_files` entries their full length back. So the next session rebuilt the folder, the magnet was gone with the record, and the start screen grew a nameless 0 MB row — 0 MB because `dir_size` counts allocated blocks and nothing had been downloaded into the resurrection. Two halves, both needed: `forget` now deletes **by hash** (`Session::delete` resolves one against its own db, restored torrents included) and removes the cached metadata with it, and `prune_orphaned_store` drops entries whose `output_folder` is gone **before** the session is built — which is the only moment it can, and the half that also covers the common case where there is no session at all (it is lazy, and deleting from the start screen rarely follows opening something), plus `torrent_clear_cache` and a viewer emptying the folder in Finder. It reads the store as plain JSON, since librqbit's types are private, and leaves anything unparseable exactly as it is: the cost of skipping is a ghost row, the cost of guessing wrong is somebody's downloaded season. Both halves are pinned by tests that fail without them (`deleted_torrent_does_not_come_back`, `forget_removes_a_restored_torrent_from_the_store`), and both run offline against a torrent built on the spot.
- **Deleting a torrent must not be able to fail quietly, and three separate things made it able to.** Reported as "«удалить всё» пишет «освобождено 0 МБ», раздача остаётся, у неё по-прежнему 14 ГБ", and the diagnosis cost a day because every layer had swallowed its own half. **The message was the error path**: `forgetTorrent` ended in `.catch(() => 0)` and `deleteWatchedFiles` in the same, so a refused path, a directory that would not go and a command that never returned all produced the OSD success shows, with nothing in the console — a torrent that could not be deleted is then indistinguishable from one that was deleted and came back. **The list kept working regardless**, because `list` reads only the disk and never touches the `inner` mutex, so the row went on printing a correct size next to a dead button. And the mutex is where the failure lives: [`release`](../../src-tauri/src/torrent.rs) held it **across** `session.pause(...).await`, the one place in the file that did, while `session.pause` → `ManagedTorrent::pause` blocks on the torrent's own state lock — which a stream read holds for the whole of its `pread` and which upstream refuses outright while the storage is still borrowed. `torrent_release` runs at exactly the wrong moment for that: leaving a film for the start screen, i.e. the click before the delete button. What everything below the session now depends on is that the session step **cannot decide whether files may be touched**: `drop_from_session` is that step, once instead of four hand-written copies (`forget`, `forget_files`, `relocate`, `rename_legacy_folder`), spawned with a deadline and logged rather than propagated. Spawning is not decoration — `Session::delete` carries an `expect` on metadata a magnet still resolving does not have, and **a panic inside a Tauri command resolves the promise never**, so the frontend waits for ever and the row it disabled stays disabled for the rest of the run; a spawn turns that into an error, and the deadline turns a blocking call into somebody else's stuck thread. `withDeadline` on the frontend is the same backstop one layer up, for the failure that has no other way out but restarting the player. The general rules, both of which had been kept everywhere else in this file and broken exactly once: **a lock is dropped before an await**, and **a destructive command's failure is shown, never turned into a plausible number**. What proved nothing was wrong with the deletion itself, and is the shape of evidence to reach for next time: directory mtimes (APFS updates a directory's mtime on unlink, verified) said no file had ever been removed from either folder, so the command was aborting before any disk work — and a faithful replay of `Dirs::load`/`is_ours`/`folder_hash`/`dir_size` against the real paths passed on every one of them.
