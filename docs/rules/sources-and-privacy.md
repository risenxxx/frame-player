# Sources, identity and the privacy roots

What a source *is* as opposed to how the player reaches it, how files arrive from the system, and the watch history with the seven places privacy has to be enforced.

Part of the rule book: [`CLAUDE.md`](../../CLAUDE.md) carries the one-line
version of each rule here, this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.

- **A network source is not a file, and a surprising amount of the player assumes otherwise.** `isNetworkSource()` gates the three that matter: the thumbnail storyboard (it decodes the *whole* file in the background — over a stream that pulls the entire thing a second time, in an order unrelated to playback, while the player is trying to buffer), the folder queue (`folder_entries` would take a URL for a path), and "show in Finder" (nothing to show). Watch positions and remembered tracks work unchanged, since a URL is a perfectly good key. **yt-dlp is enabled explicitly** (`ytdl=yes`): the CLI turns the hook on by default, the manual is ambiguous about the client API, and a feature depending on which side of that line libmpv falls is not worth the saved line. Finding the binary is ours to do, because **a GUI process does not have the shell's PATH** — launched from Finder or Explorer it inherits the session's minimal environment, so a perfectly good `~/bin/yt-dlp` is invisible to mpv's own lookup. `ytdlp_path` probes the usual locations, *runs* the candidate (a file being present says nothing about it being runnable), hands mpv the absolute path through `ytdl_hook-ytdl_path` and puts its directory on PATH as well. Measured: the hook logs "No youtube-dl found … in config directories" — which is about mpv's config dir only — and then spawns exactly that absolute path. Expect the failure mode to be **staleness, not absence**: a September 2025 yt-dlp already fails on YouTube with "The page needs to be reloaded", so the error message names updating it rather than installing it.
- **Opening files ("Open with", associations)**: two delivery paths that must both work. Windows/Linux put the paths in `argv` (first launch) or route them through `tauri-plugin-single-instance` (already-running app); **macOS never puts them in `argv`** — Finder sends an Apple Event, surfaced as `RunEvent::Opened { urls }`, which is why `run()` is `.build(...)` + `.run(callback)` and not `.run(context)`. Both paths funnel into `deliver_files()`. **The event is a signal, not a transport**: the paths always go into a buffer first and the frontend fetches them with `take_pending_files` (argv is consumed once, via `argv_taken`). This matters because a single missed emit used to mean a silently lost file — the Apple Event lands long before `onMount`, mpv init takes hundreds of ms, and the webview may be inactive. There are therefore *two* independent triggers for draining: the event, and **window focus** — opening a file from Finder always activates the app, which makes focus a guaranteed backstop and is what fixed "opening a second file in an already-running player does nothing". `drainPendingFiles()` guards against re-entry so the two triggers cannot split one list between them.
- **What a source *is* is not how the player reaches it.** Everything remembered about a video — position, chosen tracks, title — is filed under `sourceId()` (source.ts), not under the path. A path is a fine key for a file and a poor one for anything else: the same YouTube video arrives as `youtu.be/ID?si=<tracking>` from a share button and as `youtube.com/watch?v=ID` from the address bar, and a torrent stream (ROADMAP 21) is served from `http://127.0.0.1:<port>/…` where **the port changes every run**, so a key taken from the transport forgets the file every session. Local paths are their own identity, which is what makes this free: `sourceId('/a/b.mkv')` is `/a/b.mkv`, so every record ever written still reads and there is nothing to migrate. Records now carry `src` beside the key — the id answers "which video is this", `src` answers "how do I open it", and the two are only the same thing for local files. The resume snapshot deliberately keeps a path for that reason: it is not a lookup key. URL canonicalisation drops the fragment, lower-cases scheme and host but **not** the path (which is case-sensitive), removes tracking parameters and sorts the rest, and leaves `t`/`start`/`list` alone — dropping those would be a guess about what the viewer meant rather than a fact about the video. One consequence worth knowing: a **site** gets no folder scope for remembered tracks, because a URL has no folder — taking one would put every video on it into a single `youtube.com/watch` bucket deciding the dub for all of them. A **torrent** is the exception and gets one, since an info hash is the most exact folder there is: one torrent is one season. See `folderScopeKey`.
- **A video's name is asked for only when it is not already free, and only from the site serving it.** mpv supplies `media-title` for anything that plays (yt-dlp resolves the page), so that is recorded into one cache keyed by `sourceId` and costs nothing. What it cannot cover is a link in the recents list that never played, or one whose title never arrived — there `oembed_title` asks **the provider's own oEmbed endpoint** (YouTube, Vimeo), never a third-party aggregator like noembed. The distinction is not fussiness: YouTube already knows you are watching the video because you are streaming it from them, while an aggregator learns it for the first time — the same objection that keeps subtitle search talking straight to OpenSubtitles. The cost is coverage, and it is the right trade because everything actually watched gets its name for free anyway. The lookup is skipped for private paths, runs one request at a time, and for the title bar waits a moment first to see whether mpv produces a title on its own.
- **The start screen shows the title the player showed, not the file name.** A path is written for sorting, not for reading, and for a link it is a video id with a tracking query attached — so `frameplayer.positions` carries the `media-title` mpv reported (the container's own metadata, or the name yt-dlp resolved) alongside the position. It is only ever overwritten by a real one: mpv reports `media-title` a beat after the file opens, and the null in between must not erase what an earlier viewing recorded. `displayName()` is the fallback for anything never watched long enough to be recorded — extension off, query and fragment off, dots to spaces *between non-space characters only*, so a name that already reads properly is left alone. It is also what the title bar falls back to, since mpv's `filename` for a shared YouTube link is `TfUP5fQcbCM?si=…`.
- **Watch history & privacy**: a file enters the history only once playback passes `min(15 s, 5 % of duration)` and leaves it again past 97 % — the relative half of that floor is not optional, a flat 15 s made anything shorter than ~15.5 s permanently unrecordable (a 17 s clip had a two-second window between "not started" and "already finished"). Writes happen on pause, on file change, on unload, and every ~5 s from `resyncState`. The start screen lists unfinished videos from `frameplayer.positions` with posters from `poster_frame` (reads a ready frame out of the storyboard cache when there is one, decodes a single keyframe otherwise; deliberately a throwaway session so it does not reset the live `ThumbState`, and loaded one at a time rather than eight decoders at once). Privacy has to be enforced in **seven** places or it leaks: `persistPosition`, `saveResumeSnapshot` (a plain-text snapshot that auto-restores after an update), the on-disk thumbnail cache, `subs_search` — those two live in Rust, hence `set_private_paths` and `thumb_service::is_private` — and `cast_load` (the frontend passes `hidden` from `isPrivatePath`, and cast.rs then names the URL after the token and sends no title to the TV). Seven is today's count, not a property of the design: **every new path by which something about a file leaves this machine is another enforcement point**, and the check is easy to forget precisely because such a path is usually being added for an unrelated reason. Subtitle search was predicted as the fourth and duly became it — a file hash sent to OpenSubtitles names what is being watched as surely as a stored position does; casting became the fifth the same way, a LAN URL and a LOAD title naming the file to the network and the TV; DLNA the sixth, and **watching together the seventh — and the most direct of them, because the other six speak to a service or to a device on the same network while this one names the file to other people**. That last one is `contentOf` in `sync/content.ts`, which is deliberately the only place a `ContentRef` is ever built: a private-root file publishes `{kind:'hidden'}` and the room is told nothing but that something is playing. Path matching is on a component boundary (`/Movies` must not swallow `/Movies2`), case-insensitive and separator-insensitive **on both sides**, and it is mirrored in JS (`pathUnder`, now in `format.ts` beside `samePath` and `normalizePath` — there had been three copies of "compare two paths" and the privacy one was the laxest) and Rust (`path_under`). "Change one, change the other" is no longer a note: the cases live in **`shared/path-under.txt` and both test suites read that file**, so a vector added there fails on whichever side does not already agree. Verified by adding a contradictory case and watching both go red. Each side also asserts a floor on how many vectors parsed — a file that moved, or was reformatted so every line reads as a comment, would otherwise pass in silence, which is the one way a shared contract quietly stops being one. **Excluding a folder also erases what is already recorded for it**, and that is a correction rather than a refinement: filtering on read (which is all it used to do) left the entries in localStorage and the frames in the thumbnail cache, so the start screen was clean while the disk was not — and removing the folder from the list brought everything back, which is how the gap was found. **Which stores those are is a list, `IDENTIFIED_STORES`, not three lists.** Three operations walk the same set — excluding a folder, forgetting a torrent, clearing the history — and each used to enumerate it by hand, which is one copy too many before they even disagree. They did: **`clearHistory` named three keys and cleared three of six**, so asking for everything to go left the remembered titles (keyed by source id, which for a local file *is* the path — that store on its own is a list of everything ever watched), the per-folder track memory, and the path of every subtitle the player had downloaded. Now one list, four predicates: a folder asks a path-shaped question (`pathUnder`), a torrent an id-shaped one (`torrent:<hash>/` prefix), forgetting one card asks for one id, and clearing asks for the key itself — a store the predicate has nothing to say about simply matches none of its entries, which is why the path-keyed stores need no special case when a torrent is forgotten. The per-folder track store is the one that answers **both** shapes, and deliberately: a torrent's folder key *is* that prefix (`torrentFolderKey`, called by the scope and by the purge, so the two cannot drift), which is what makes forgetting a season take the dub chosen for it. **Every one of those predicates is asked about the identity, and asking it about `src` instead is a bug that hides for months.** Positions carry both — the id answers "which video", `src` answers "how do I open it" — and they coincide only for a local file, so anything that deletes by `src` deletes local files and silently keeps everything else. It happened twice, and it is the same mistake at two scales. `forgetRecent` deleted `map[item.path]` from two stores by hand, which is a **loopback URL** for a torrent episode and the share URL with `?si=` still on it for a link: measured, both entries survived, so the card left the in-memory list at once and came back at the next `loadRecent` — reported, correctly, as "I delete it and it is back after a restart". And the store list itself read the positions identity as `entry.src ?? id`, so `purgeTorrentHistory` — an id-shaped question — matched nothing a real session had written and left a position behind for every episode of a deleted torrent. That one passed its tests because the fixture wrote `{ pos: 1 }` by hand, with no `src`, which `persistPosition` never does: **a fixture that the app could not have produced is not a fixture**, and the test now seeds through the writer. Both are pinned by cases verified against the unfixed code (four go red per mutation). `frameplayer.links` is deliberately outside the list (a URL has no folder, so nothing in it can belong to one) and is cleared by name. Thumbnails are handed to Rust. The tests restate the store list rather than importing it, on purpose: a test walking the same registry the code walks would pass for a store the registry has forgotten, which is the only failure worth catching. The folder is added to the list **before** the purge runs, so a write racing it — the position timer fires every ~5 s — is already refused rather than landing behind the deletion. Purging thumbnails is what forced `CACHE_MAGIC` to v4: the cache file name is a hash of path + size + mtime, so without the source path *inside* the file an entry cannot be attributed to a folder at all. Entries in an older format are deleted too, since they cannot be attributed either and are unreadable to the current build anyway. Because this deletes data irreversibly, the settings hint says so before the folder picker opens. "History off" is a separate `all` flag, **not** a synthetic `/` root: roots get their trailing separators trimmed, so `/` collapses to an empty string and would match nothing.
