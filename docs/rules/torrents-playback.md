# Torrents: playing one, and what a partial file can be used for

The queue, the buffer map, the readouts, subtitles that ship inside a release, and replacing a torrent with its re-upload.

Part of the rule book: [`CLAUDE.md`](../../CLAUDE.md) carries the one-line
version of each rule here, this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.
The *why* behind it — what was tried, what was measured — is in
[`../torrents.md`](../torrents.md).

- **Opening from the history must give back the queue as well as the file.** A local file gets it for free (`loadFiles` builds the folder queue through `filesOpened`), but a torrent episode did not: `resolveTorrentFile` handed back one URL and dropped the file list, so the same episode had a next episode when opened from the torrent list and none when opened from the history — one behavior per entry point, invisible from outside. It now returns the torrent with the URL and `openRecent` queues the season. Related and the reason the folder case can fail the same way silently: `samePath` is separator-insensitive as well as case-insensitive, because the two sides come from different places (a stored record or mpv's `path` against a directory read in Rust) and on Windows one mixed `E:/Videos\ep1.mkv` costs the whole queue — `findIndex` answers −1 and `queueAround` returns without a word. That return now logs what disagreed. **A torrent entry in the watch history cannot be reopened from what it stores.** Its `src` is a loopback URL and the port died with the session that issued it, so every torrent card led to a refused connection after a restart — the problem `sourceId` solves for the *key* showing up again one layer higher, in the thing you actually open. `RecentItem` therefore carries `id` beside `path`, and `openRecent` sends anything `torrent:`-shaped through `resolveTorrentFile`, which re-resolves the remembered magnet. That store (`frameplayer.torrents`, privacy-gated like positions — a magnet names what is being watched) is also what puts a **torrent list on the start screen**, and the unit there is deliberately the *torrent*, not the file: the grid above already holds individual episodes with positions, while a torrent's never-started episodes have no representation anywhere else, so one row per torrent is how you get back into a season without the magnet rather than a duplicate of the grid. It is styled as compact rows rather than poster cards for the same reason — a second grid would compete with the first and turn the start screen into a download manager, which the roadmap is explicit this player is not. **Clicking a row resumes rather than asking**: the row already prints "продолжить: S01E03 — осталось 23:14", and dropping the same nine-name file picker a fresh magnet gets, to hunt for the episode you were already watching, is the player forgetting something it plainly knows. The picker is what happens when there is nothing to continue. Its resume point comes from `positionsLoad()` directly, **not** `history.recent`, which holds only the twelve newest entries across everything — a torrent watched last week has fallen out of that long before its data has fallen off the disk. The picker itself marks which files have positions (brighter name, "осталось X"), since a season is nine names differing by two characters. It carries no progress *bar*, and that was tried: a full-width rule under the name reads as an underline rather than a value — at 91% it is indistinguishable from a border and a list of them turns the panel into stripes. The card grid needs one only because a poster leaves no room for words.
- **A torrent stalling mid-playback used to be completely silent.** `opening` is raised in `beforeLoad` and cleared on `file-loaded`, so the loading overlay — the one thing that reports peers and rate — is gone by the time playback starts. A swarm that dries up at minute twelve then froze the picture with nothing on screen to explain it, which is the difference between "give it a moment" and "this player is broken". Hence `.torchip`, a small readout below the top bar: rate, peers and how much of *this file* is on disk. It sits **outside `.topbar`** so it can survive the UI going idle, exactly like the skip button sits outside `.osc` and for the same reason — idle is precisely when a stall happens. The rest of the time it fades with the chrome, so the picture stays clean; it is suppressed while `opening` is up (the overlay is already saying all of it) and once the file is fully fetched. Its sentence comes from the same `torrentLabel` the overlay uses rather than a second copy of the logic. It goes **top-right**, and the left is not merely a worse choice but a broken one: `.osd` — the popup every volume change, seek and speed change raises — is `top: 60px; left: 18px`, two pixels from where this first sat, so the next volume nudge covered it outright. A status readout that vanishes exactly when a hand is on the keyboard is worse than none. The right is free below the bar on both platforms: the window buttons and the macOS logo end at 48px, and the skip button is bottom-right. **Zero peers is a reading for ten seconds and a diagnosis after twenty** (`PEERLESS_ADVICE_MS`): past that the loading overlay stops describing the swarm and names the likely cause, because peers *seen* with none *connected* is the signature of BitTorrent being filtered — a VPN that forbids it, an ISP that throttles it — and it is the only cause a viewer can do anything about, while everything else about it looks exactly like a slow film. It is deliberately *not* part of `torrentLabel`: that line is also this chip, and a readout beside the picture cannot grow into a paragraph. And **mpv giving up on a torrent stream must not be reported as a broken link**: the stream is `http://127.0.0.1:…`, so `isNetworkSource` is true and `reportLoadFailure` answered with the most confident wording in the player — "usually this means yt-dlp is out of date" — about a swarm nobody is seeding. `parseTorrentUrl` is the branch that separates them, and that URL must also never become `lastLink`, which is what the dialog's retry reloads.
- **A torrent cannot gain an episode, so replacing one is a first-class action.** The info hash covers the file list and every piece hash — verified by building two torrents from the same folder and adding a file, which changes it — so an uploader who adds an episode publishes a *different* torrent with a different magnet. Left alone that costs a whole season re-downloaded and its watch history reset, which for an airing series is the common case rather than an edge one. The fix is **a rename done before the new torrent is added** (`torrent_relocate`): the data lands in the folder the new hash will ask for, `overwrite: true` makes librqbit verify it, and `add` needs no changes at all. Crucially the "folder name is the info hash" invariant survives, which is what keeps deletion unambiguous — the thing qBittorrent gives up by sharing one save path, and why cross-seeding there needs manual `Force recheck` and third-party tools to avoid deleting a neighbour's files. **Positions are re-keyed by file name, not index**, since one inserted episode renumbers everything after it; the name comes out of the URL each record already stores, so no new store was needed and entries written before this still migrate. The link box also *detects* the case (`findSupersededTorrent`), because pasting the new magnet where links go is the obvious move and would otherwise silently start a second copy — matched by **token overlap** rather than a prefix, since "Серии: 1-9 из 9" → "1-10 из 10" changes digits in the middle of a forty-word title. Discovery is the feed's job (next bullet), and only for a torrent that came from one; a pasted magnet still learns nothing by itself.
- **An RSS feed is a link to a *release*, and that is what makes discovery possible without becoming a background client.** Many trackers publish a feed per release whose next item is the re-upload with the next episode, so a feed is accepted wherever a magnet is — the link box and the update dialog — and remembered on the torrent (`RememberedTorrent.feed`: the URL and the title of the item it was opened from). **It is read only on the viewer's gestures**: when pasted, when the start screen lists its torrent (at most once per `FEED_RECHECK_MS` per feed), and when the update button is pressed. A found upload is **offered, never applied** — the row says so and its update button is lit, and the dialog still confirms, because replacing a torrent re-checks everything on disk. Four things decide whether that is right. **Items are matched by stem, not by name similarity** (`releaseStem` in feed.ts): the reference feed lists `… | AVC | 1-11` and `… | HEVC | 1-11` side by side, and the link box's token overlap scores those 6/7 — fine for a question the viewer answers, wrong for an offer the player makes by itself. So only the episode *range* is removed and everything else must be equal; a lone number is kept, which is what stops a feed with one torrent per episode (nyaa's `Show - 11`, `Show - 12`) from ever being read as re-uploads — relocating one episode's folder into another's would be the failure. **Parsing is a real parser** (quick-xml, already in the tree, named by local name so a prefix costs nothing): the torrent can be in `<enclosure>`, `<link>`, Atom's `rel="enclosure"`, `nyaa:infoHash`, `torrent:magnetURI`, `showrss:info_hash` or `torznab:attr`, the hash in any of them or only in a 40-hex `<guid>`, and the declaration may say windows-1251 — past what the string scanning in dlna.rs is allowed to grow into. **An item's `.torrent` is fetched and written into the metadata cache** (`feed_torrent` → `torrent::cache_metadata`) and the torrent then opened as a magnet built from its hash: a `.torrent` URL is the one source `add` cannot name a folder for, and a bare hash is a DHT resolve, while a cached one opens in milliseconds through the ordinary path. Verified live (`FP_TEST_FEED=<url> cargo test --lib feed::tests::live_feed`): on the reference feed and on nyaa, every claimed hash equals the hash of the file fetched. **Both requests go through the torrent proxy** — a feed URL names what is being watched as plainly as a magnet. A URL is routed to the feed path by shape (`isFeedLink`) and Rust answers `not_feed` for anything that is not RSS or Atom, which sends it on to mpv unchanged, so a wrong guess costs one request. The feed rides in `frameplayer.torrents`, so every purge that forgets a torrent forgets its feed, and with history off nothing is remembered and nothing is checked.
- **The buffer map needed no fork of librqbit, and finding that out was the whole job.** `with_chunk_tracker` is `pub(crate)`, which reads as "patch required" — but `Api::api_dump_haves` is public and hands out the same bitmap, as a `format!("{:?}")` of a `BitSlice`, evidently for debugging. Measured, the string was `BitSlice<u8, …> { addr: 0x…, head: 000, bits: 10 } [1, 0, 1, 1, …]`; only the bracketed tail mattered, taken with `rfind` because the header has brackets of its own. Undignified rather than fragile: the format was pinned by Cargo.lock, the scanner was tested against the real string, and a parse failure cost the map and nothing else. **9.x returns the bitfield itself** — `(BF, u32)`, the pieces and how many of them are real — so the scanner and its test are gone, which is the shape every "undignified but pinned" workaround should be expected to take eventually. `file_ranges` then intersects the pieces with the file's own byte span — **the first and last piece of a file are shared with its neighbours**, so without that intersection the bar would draw buffer belonging to another episode. If this ever needs to be done properly the upstream PR is ten lines (`have_pieces()`), and vendoring is the fallback: `[patch.crates-io]` with a local path, **636 KB and 76 files** for the crate itself — the roadmap's "1.5M SLoC" was the whole dependency tree, not the thing that would be forked. What the map buys is two things, and the seekbar bands matter more than the previews: they answer "will a jump land or wait", which is what a torrent's bar is actually read for.
- **Previews before a file is complete are per-position, not per-file.** `thumb_get(exact)` opens its own decode session, so single frames need no storyboard — but the background grid pass walks a file start to end and would decode straight through a hole, so it still waits for the whole file (`thumbs.partial` is the distinction). The gate lives inside `issueThumb` rather than at the call sites, so no future caller can skip it, and it is fractional because the map is of *bytes*: for a variable-bitrate file bytes and seconds are not proportional, hence `BUFFER_MARGIN` keeping requests off the edge of a band where the estimate is worst. Expect previews to appear where they are least wanted — you have downloaded what you already watched, not what you are about to jump to — with the redeeming case being that rewinding is the common gesture on a file still arriving, and the past is always there.
- **Three things a torrent gains once its file is on disk, and one it cannot.** A torrent routinely **ships its own subtitles** (Sintel carries ten) — `sub-auto` finds nothing, since there is no local file to look beside, so they sat unreachable while the viewer searched OpenSubtitles for what was already downloaded. `sub-add` takes a URL, so each is a request to our own server; matched by name (same stem, stem plus a language tag, or a subfolder named after the episode) because a season carries one set per episode and attaching all ninety would make the menu useless, and `auto` rather than `select` so `slang` still decides. **The next episode is prefetched** once the current file is complete — one ahead and no further, which is the line between "the season does not stop between entries" and a background client filling the disk with what may never be watched; "next" is `torrentVideos` order, not mpv's playlist, which may hold a folder or a drop of loose files. And **the seekbar storyboard works**, which the network gate used to forbid for good reason that no longer applies: the data is an ordinary file here, so decoding costs nothing. `torrent_local_path` answers **only for a complete file**, and that is load-bearing rather than cautious — the files are sparse, so a stretch that has not arrived reads back as *zeros* rather than failing, and a storyboard over one would be black frames and mush with nothing to say it went wrong. Since a file completes *during* playback, `maybeStartThumbs` had to become retryable (`startedFor` is set only when a storyboard actually starts) and the status poll calls it on completion. **Start-screen posters now work too, and the obstacle that kept them off was the wrong one.** Completeness cannot be answered by `torrent_local_path` without the session — but it does not need to be: the cached `.torrent` beside the data names the file and its length, the info hash names the folder, and completeness is the allocated-blocks measure `torrent_list` already uses, so `torrent_offline_file` answers from the disk alone, with no session, no DHT and no peer. It answers only for a **complete** file, because the holes in an incomplete one read back as zeros and a poster decoded from one is a black rectangle presented as a frame of the film. (On Windows librqbit never marks the file sparse, so allocation cannot tell an empty file from a finished one there; a poster that fails to decode is treated as "none yet" rather than as an error.) **And an incomplete episode gets one too, captured while it plays** (`poster_capture`): that is the only window in which the data is on disk at all, so the picture is taken then and outlives both the download and the file. Two things distinguish it from the on-demand poster. Candidates come from the **buffered map**, spread across the bands rather than clustered at the playhead — a poster should be a scene, and three neighbouring frames are one scene — because asking for a second that has not arrived decodes zeros. And the winner is chosen **by content, not by position**: `rgb_score` is the mean absolute deviation of luma weighted by how far the mean sits from either extreme, which is near zero for a black frame, a white flash or a flat title card, and everything below `MIN_POSTER_SCORE` is refused outright — better no poster than a black one, and the next viewing tries again. Bounded like every other background decode: once per file, at most a handful of seeks, at the storyboard's QoS, and not before `POSTER_AFTER_S` of playback. It is written beside the thumbnail cache **with the source path inside the file**, for the same reason `CACHE_MAGIC` v4 carries it — an entry that cannot be attributed to a folder cannot honour a privacy root — and `forget_thumbs_under`/`clear_thumb_cache` clear both stores, or the second one is the leak nobody checks.
