# Torrents: the swarm, the network and the preferences that rebuild the session

The DHT, the trackers, encryption, the proxy and port forwarding — the half of the feature that is about reaching peers at all.

Part of the rule book: [`CLAUDE.md`](../../CLAUDE.md) carries the one-line
version of each rule here, this file carries the whole of it — the identifiers,
the measurements and the failure the rule was written against.
The *why* behind it — what was tried, what was measured — is in
[`../torrents.md`](../torrents.md).

- **Windows kills the stock DHT, and the tracker was never a backup — two librqbit bugs whose combination left Windows with no peer source at all.** The symptom read as a network problem (magnet never resolves; a `.torrent` lists its files but playback sits on "Connecting to the swarm… / No peers" while qBittorrent on the same machine finds 150 seeds in seconds) and the network was fine. Upstream librqbit-dht's UDP reader dies on the **first** `recv_from` error — permanently, for the life of the session, i.e. of the app — and Windows produces such errors in normal operation, which Unix never does: **WSAECONNRESET (10054)** when any of the thousands of DHT nodes contacted turns out dead and its ICMP "port unreachable" comes back (an error about one datagram, not the socket — libtorrent suppresses it with `SIO_UDP_CONNRESET`), and **WSAEMSGSIZE (10040)** when a node's datagram exceeds the 16 KB read buffer (Unix truncates silently). Both were caught live here; the stock DHT died 89 s into a session with `framer quit … os error 10054`, timing a lottery decided by the first dead node to answer. That alone should have degraded, not killed — except the fallback source was also broken: the HTTP announce **replaces** the URL's own query (`Url::set_query`), so a tracker announce path carrying its own query (`/ann?magnet`, a passkey) loses its marker and answers **403**, and with no listener the announce says `port=0`, which trackers refuse outright ("Port can't be 0"). macOS never noticed any of this because a live DHT carries a popular swarm by itself — which is why the fix is three-legged and the first leg is the only Windows-specific one: vendored `librqbit-dht` tolerates recv errors (log + continue, fatal only after 100 *consecutive* — the behavior librqbit's own UDP tracker client already has), vendored `librqbit-tracker-comms` re-appends the announce URL's original query, and `listen_port_range` gives announces a real port (which also lets NAT-ed home seeds connect inward; UPnP stays off on purpose). Verified with a probe on the failing machine: stock — resolve works only while the DHT happens to be alive, dead by 90 s; patched — two recv errors absorbed, and a fresh magnet still resolves in under a second 2.5 minutes into the session. The two tracker fixes reached the 9.x line and came back with the bump to 9.0.1; **the recv fix is still nowhere**, verified by reading 9.0.1 rather than trusting the note (`socket.recv_from(&mut buf).await.map_err(Error::Recv)?`), hence `src-tauri/vendor/` + `[patch.crates-io]` — see vendor/README.md before touching those crates or bumping librqbit. Worth knowing while debugging any of this: peers from such swarms often cut plaintext BitTorrent handshakes mid-stream (DPI on Russian ISPs; the fix would be MSE encryption, which no rqbit version implements — that is what qBittorrent has and we do not), so expect some handshake noise in logs even when everything works.
- **The HTTP announce was dead on every platform, and the DHT hid it.** Two more vendored fixes, found together and each fatal on its own. **reqwest sends no `User-Agent` at all** by default, and the WAF trackers sit behind refuses such a request outright — measured against one such tracker with a byte-identical query, **403 without the header, 200 with it**, and the value is irrelevant (a single letter passes); presence is the whole requirement. And **`complete`/`incomplete` are required fields** in librqbit's `TrackerResponse` while real trackers omit them — one such tracker answers `d8:intervali3595e12:min intervali3595e5:peers180:…e` and nothing more — so even a 200 failed to deserialize and **every peer in it was discarded**. Both failures are invisible from outside: the announce is a clean HTTP exchange, the error is one level below it, and the torrent merely says "connecting to the swarm". What made them survive so long is that **the DHT covers for the tracker until it doesn't**: two releases of the same film from one tracker, one with 24 seeders that would not fetch a byte in five minutes and one at 3 MB/s, and the difference was entirely whose DHT records were fresh — the working one's peers all came from the DHT, and the broken one's DHT entries were the same IPs on stale ports (`66.56.80.137` at eight different ones, none of them the port the tracker gave). So the lesson is the diagnosis, not the fix: **a torrent that will not download is a question about where its peers came from**, which is what `swarm_probe` exists to answer — peers *seen* against peers *live* against bytes, plus per-peer attempt/error counters. Peers seen but never live means the addresses are wrong (i.e. no tracker), not that the swarm is dead. Verified end to end on the failing magnet: seen 22 → 44, live 0 → 5, and 0 B/s → ~800 KB/s with the first megabyte read in 8 s. **A third leg was hiding behind those two, and it is ours rather than the vendored client's**: a torrent is added *paused*, and upstream ties the announced **port** to whether the torrent is started (`make_peer_rx` passes `None` unless it is), so the announce that fetches a magnet's metadata goes out as `port=0` — which a tracker reads as "cannot accept connections" and answers accordingly. Measured on one info hash: **1 peer from port 0 against 26 from a real one**. Adding paused is not negotiable (it is what makes "what is in this torrent" cost no download), so metadata was left to the DHT alone, and a torrent whose DHT records have gone stale then never resolved at all — three fresh opens of that same 24-seeder release, three 90-second timeouts. Fixed without forking librqbit: `announce_peers` asks the magnet's own HTTP trackers once, directly, and hands the addresses over as `initial_peers`. Resolve went **90 s (timeout) → 0.9 s**. It is a head start and never a prerequisite — a tracker that fails, times out or is UDP-only costs nothing, since the DHT is running regardless (Sintel, whose magnet carries only UDP trackers, is unaffected and is the control for that). Its response is *scanned* for the `peers` field rather than deserialized, deliberately: a strict parser is precisely what caused the bug above, so the length being a non-zero multiple of six is the only check, and anything else degrades to "no peers" rather than to wrong addresses. **And it goes through the proxy when there is one**, which is the rule any future request of our own inherits: librqbit's tracker traffic is built with the session's client, so a direct announce from here would hand a tracker this machine's address while every other packet went somewhere else — the leak the setting exists to close, in the one place the setting does not reach by itself.
- **A network can refuse a torrent by where it is going or by what it is, and the player can answer only the first.** That distinction is what decides everything below, and it was reported as one bug: a viewer whose VPN forbids torrents, and whose ISP would not carry them either with the VPN off. The first half is a *destination* rule and has an answer — a **SOCKS5 proxy**, `SessionPrefs::proxy`, which librqbit puts under the outgoing peer connections and its own HTTP announces. The second half is a *content* rule (DPI on the plaintext BitTorrent handshake, which is what the mid-handshake cuts in the peer probe are), and its only answer is MSE/PE encryption, which **no librqbit release implements** — 8.1.1 and 9.0.1 alike carry no RC4 and no DH anywhere. It exists upstream as an open PR (`ikatson/rqbit#633`), and **it is now vendored** — `src-tauri/vendor/librqbit`, the largest thing in this repository that belongs to somebody else, to be dropped the day it merges. Four checks decided that, in an order where each could have ended it: it applies to 9.0.1 unchanged (every source hunk, no conflict — only the manifest differs), it compiles with this player's features, its own 16 tests pass (DH-768 against external vectors, a duplex handshake, the responder after a plaintext sniff, every fallback path), and — the only one that could not be answered by reading — **it interoperates with the real world**: with `Forced`, where a peer that will not encrypt is dropped, `FP_TEST_MAGNET=1 FP_TEST_MSE=only` resolved the magnet *from the swarm* in 840 ms and streamed at 2.2 MB/s from 24 peers. The resolve half is the one that matters, because a magnet that will not resolve is the symptom this started from. The cryptography is not in the patch (`crypto-bigint` for the modular exponentiation, RustCrypto's `rc4` for the cipher); what is hand-written is the handshake framing, where a mistake costs a connection rather than a secret. The setting is a three-state pill and **the default is the middle one**, which prefers MSE and redials in the clear for a peer that will not do it — never worse than what shipped before, which is why nobody should have to find it. What the proxy does **not** cover has to be said wherever it is offered, because both halves are found the hard way otherwise: the DHT and the UDP trackers keep their own sockets (SOCKS5 carries UDP only through an ASSOCIATE neither side uses here), and what travels through it is still unencrypted BitTorrent. A real split tunnel — the socket leaving past the VPN rather than through it — is upstream too, as `SessionOptions::bind_device_name`, and it is **macOS and Linux only**: `BindDevice::new_from_name` answers `BindDeviceNotSupported` on Windows, where the mechanism would be `IP_UNICAST_IF`. It is also the option that quietly puts this machine's address in front of the swarm, which is what most people had the VPN on for, so it stays unbuilt rather than half-built.
- **Three preferences are baked into the session and one comparison decides whether it can be reused.** Seeding, the port mapping and the proxy are all fixed when `Session::new_with_opts` runs, so changing any of them tears the session down and costs the running torrent — which the settings hints say, because a field that appears to save and takes effect at the next magnet is worse than one that warns. They live in `SessionPrefs` rather than as three parameters for the reason the tables elsewhere in this file exist: written out, the reuse check is one `&&` per preference and the fourth one added is the one somebody forgets, which fails as a setting that does nothing at all until the app is restarted. As a struct it is one `==`, and the frontend sends the same object rather than a field per call.
- **The bump from librqbit 8.1.1 to 9.0.1 is what made those two possible, and it moved five things worth knowing.** `SessionOptions` grew sub-structs — `dht`, `listen`, `connect` — so the DHT persistence flag, the port range and the UPnP switch all moved; `tcp_listen_port()` became `listen_addr()`; `handle.stream()` became async; peer counts became `u32`; and the metainfo's info dict arrives wrapped with its own raw bytes (`meta.info.data`, and `validate()` before a file list can be walked). The listener is the one that needed a decision rather than a rename: 9.x takes **one address where 8.x took a range**, and a port that will not bind is fatal to the whole session, so the walk is ours now (`listen_port`) and it falls back to an ephemeral port rather than failing — a stable port is only *nicer* (a router mapping and a manual forward survive a restart), while a session that will not start takes the torrent feature with it until the app is restarted.
- **Peer count has exactly one large lever, and it is not the one that suggests itself.** One private tracker's swarm was probed one address at a time, and the failures separate cleanly: of ~30 peers the tracker handed out, **20–22 never answered a SYN**, 5 completed a handshake, 2–3 refused the connection outright, and exactly **1** showed the mid-handshake cut that means DPI. So this is NAT, not filtering and not a dead swarm — those twenty can only ever be reached if *they* dial *us*. Four things that look like levers were measured and are worth nothing here, which is the more useful half of the result because each is the obvious next idea: **public trackers** know 0–1 extra peers for a tracker-exclusive release (opentrackr, demonii, torrent.eu.org, stealth.si, exodus, nyaa — so `SessionOptions.trackers` stays empty, and the privacy cost of announcing to strangers buys nothing); **`numwant`** changes nothing, the tracker caps at ~25–30 whatever is asked for; **IPv6** is moot, the tracker sends no `peers6` field at all; and **PEX** already runs (librqbit enables `ut_pex` for any non-`private` torrent — visible as `seen` growing past what the tracker gave). Hence `enable_upnp_port_forwarding`, **opt-in and off by default**, because it is the one setting here that changes the *machine* rather than the app: it makes a port reachable from the internet for as long as a torrent is open. It helps even with seeding off, which is the counter-intuitive part — a seed serves us whether or not we serve anyone, so reachability is about who can *start* a connection. The flag is baked into the session exactly like `disable_upload`, so both directions of the switch cost the running torrent (`rebuild_if` is the shared mechanism). **And the switch reports what the router said, not what it asked for**: librqbit's forwarder is a `run_forever` task that tells nobody whether it worked, and a router with UPnP disabled swallows the request in silence — so `upnp.rs` finds the gateway and asks it for the mapping, and "on" and "working" stay two different things on screen. Two traps in reading that answer: UPnP error **714 is the answer, not a failure** (`NoSuchEntryInArray` is how a gateway says "nothing is mapped there", and treating it as an error reports a working router as an absent one); and on macOS an empty search is **ambiguous** — a router without UPnP and a refused Local Network permission look identical from here — hence the log line, and hence the fact that this path cannot be tested from a CLI at all (multicast from a terminal process is dropped, the same reason `FP_DLNA_PROBE` has to run inside the app).
