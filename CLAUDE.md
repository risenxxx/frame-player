# CLAUDE.md — Frame Player

Windows and macOS video player: **Tauri 2 + Svelte 5 (SvelteKit static) + in-process libmpv** via `tauri-plugin-libmpv` (wid embedding: mpv renders into a child HWND / NSView *behind* the transparent webview; the entire UI is HTML on top). On macOS that needs a patched libmpv — stock mpv does not implement `--wid` there at all; see `patches/` and `scripts/build-macos-libs.sh`.

The UI is **localised (ru/en)** — every user-facing string goes through `t()`, see "Localisation" below. Code comments and docs are **English**.

## Where the documentation is

This file is the state of record: how the code works now, and which rules must
not be broken. The reasoning behind it — measurements, dead ends, options tried
and rejected — lives in **`docs/`**, which is part of the repository.

| `docs/…` | What it holds |
|---|---|
| `architecture.md` | Stack decisions, the embedding model and the constraint list — mandatory reading before touching mpv interop, seeking, fullscreen or zoom |
| `ROADMAP.md` | Shipped, planned and considered features; a comment saying "ROADMAP 21" means a numbered item there |
| `macos.md` | Why stock `--wid` cannot work on macOS, what the patch does, and the platform's own traps |
| `casting.md` | Casting to a television: the two transports, what each can carry, the measured limits and the decision rules |
| `watch-together.md` | A shared timeline over a small relay: why the wire carries state rather than actions, why drift is corrected with speed rather than a seek, and what a room may know about what you are watching |
| `catalog.md` | The catalog: why the TMDB key is in a service and not in the player, what the poster traffic costs and who decides where it comes from, how the indexer's fuzzy search is filtered, and the measurements that say a translation-type filter cannot be built |
| `torrents.md` | Torrent streaming: piece priority from playback, what a partial file can be used for, casting one |
| `distribution.md` | Shipping: signing, Gatekeeper, SmartScreen, updates, stores |

A finding earns a line in this file when breaking it would break the player; it
stays in `docs/` when its value is saving the next investigation. **The
repository is public**: nothing committed — code, comments or documents — may
name a host, an account, a machine, a person or an address on somebody's
network. Device behavior is recorded by model and by what it did, never by
whose device it was.

## Commands

```bash
npm install
npm run fetch-libs        # one-time: downloads libmpv, FFmpeg SDK, libclang into src-tauri/{lib,ffmpeg,tools}
npm run tauri dev         # dev run (vite on :1420 + cargo)
npm run check             # svelte-check — run after ANY frontend change (expect 0 errors; a few known a11y warnings are OK)
npm run gates             # check + check-runes + check-imports + css-orphans + test, in one go
npm test                  # vitest, the pure end of the codebase (see "Tests" below)
npm run check-runes       # a `$effect` at a .svelte.ts top level (throws on import), a `$state` its own file never writes, a declaration whose code left
npm run check-imports     # import cycles: no error, no warning, a module-evaluation order nobody chose
npm run css-orphans       # a CSS rule whose markup moved into another component
npm run tauri build       # NSIS installer (no updater signature locally unless TAURI_SIGNING_PRIVATE_KEY is set)
npm run set-version       # report the version in all five files; exits 1 if they disagree
npm run set-version 0.21.0   # …or `patch` / `minor` / `major`. See "Releases" below
```

The macOS bundle, and the one decision its build makes for you:

```bash
npm run tauri:macos:build     # → scripts/macos-build.sh. With no APPLE_SIGNING_IDENTITY in the
                              # environment it signs ad-hoc and turns the hardened runtime OFF —
                              # see the macOS bullet below for why those two are one decision
scripts/macos-sign.sh         # signs the ~35 dylibs + the ffmpeg CLI; run BEFORE the build
scripts/macos-notarize.sh <p> # notarise + staple a .app or a .dmg (and repack .app.tar.gz)
```

A signed build locally is the same three commands with the identity exported, which is also the
cheapest way to test a change to any of them without spending a release on it:

```bash
export APPLE_SIGNING_IDENTITY="Developer ID Application: … (TEAMID)"
export APPLE_API_KEY=… APPLE_API_ISSUER=… APPLE_API_KEY_PATH=…/AuthKey_….p8
scripts/macos-sign.sh && npm run tauri:macos:build
scripts/macos-notarize.sh "src-tauri/target/release/bundle/macos/Frame Player.app"
```

Rust validation while the user's dev instance may be running (target/ is locked by the running exe):

```bash
cd src-tauri && CARGO_TARGET_DIR=/some/tmp/target-check cargo check
```

Sidecar smoke tests (both engines: stepping + thumbnails). Generate the fixture with the bundled ffmpeg:

```bash
src-tauri/ffmpeg/bin/ffmpeg.exe -f lavfi -i testsrc2=duration=60:size=1280x720:rate=30 -c:v mpeg4 -q:v 5 test.mp4
cd src-tauri && FP_TEST_VIDEO=<abs path to test.mp4> cargo test --lib -- --nocapture
```

(The LGPL ffmpeg build has **no GPL encoders** — use `mpeg4`, not libx264.)

Torrent streaming against a real swarm (ROADMAP 21's spike, kept as a test — off
by default because it needs the network, live seeders and up to a minute):

```bash
cd src-tauri && FP_TEST_MAGNET=1 cargo test --lib torrent::tests::sintel_smoke -- --nocapture
```

And its sibling for when a torrent does *not* download — a minute of peers seen
vs peers connected vs bytes, then per-peer counters (attempts, errors, chunks).
`sintel_smoke` can only report that as a read which never returns; this says why:

```bash
cd src-tauri && FP_TEST_SWARM='magnet:?xt=…' cargo test --lib torrent::tests::swarm_probe -- --nocapture
```

The Go services (`services/`) are their own tree and their own test run — Node's
gates do not touch them. The workspace at the repository root is what lets one
command cover both; note the pattern is `frameplayer/...` and never `./...`,
because the root is not itself a module:

```bash
go vet frameplayer/... && go test -race frameplayer/...
go run ./services/relay                                  # :8080
go run ./services/relay/cmd/probe -play -drive           # a second peer, so one machine is enough
```

Casting smoke test against whatever Cast devices the LAN has (browse + TLS +
receiver GET_STATUS; deliberately never launches an app on the device):

```bash
cd src-tauri && FP_TEST_CAST=1 cargo test --lib cast::tests::discover_smoke -- --nocapture
```

On macOS a test binary in a custom target dir cannot find the bundled dylibs
(`@executable_path/lib` resolves next to `deps/`, where build.rs did not copy
them), so any `cargo test` there also needs `DYLD_FALLBACK_LIBRARY_PATH=$PWD/lib`.

## Critical gotchas (violating these causes crashes or subtle breakage)

1. **libmpv-wrapper bugs (upstream, unfixed)** — see architecture.md for details:
   - Never `getProperty(..., 'node')` and never observe properties in `node` format → stack corruption crash. Use string/flag/int64/double; read track-list via `track-list/N/...` sub-properties — and observe `track-list/count` (int64) to know *when* to re-read it, because tracks keep appearing after `file-loaded` (external subs via `sub-auto`, lazily parsed containers): reading once on that event left the subtitles button missing until something else happened to refresh the list. `loadTracks()` is a long chain of sequential reads with several possible triggers, so it needs a sequence guard or a slow earlier run finishes last and overwrites the fresh list.
   - Never send broadcast `script-message` → AV crash in the wrapper's client-message serializer. Only targeted `script-message-to <script> ...`.
2. **ffmpeg-the-third seeking**: always `ictx.seek(ts, ..=ts)` (inclusive). `..ts` silently fails with EPERM.
3. **mpv state mirrors go stale** (event queue overflow drops property-change events). Toggles must use `command('cycle', [prop])`, never `setProperty(prop, !mirror)`. Mirrors are resynced every 1 s and on `queue-overflow` in `resyncState()` — **which mirrors is `RESYNC`, a `Record<ObservedName, boolean>`, so a newly observed property is a compile error until somebody says whether losing its event is survivable.** It is a table rather than a hand-written list because the mirrors split in two and the split is not obvious: the ones something re-reports anyway (a position, a buffering percentage, anything mpv sends again on the next file) heal on the next tick, and the ones that are merely *set* and then stand do not heal at all — they stay wrong until the viewer touches the thing again, which for a check mark in a menu can be never. `playlist-pos` was the one left out of the hand-written list; the same audit found `video-rotate`/`video-aspect-override`/`panscan` (worse, since `setPicture` writes the property and *not* the mirror, so those three depend entirely on the event coming back), the A–B marks, and `paused-for-cache`, whose dropped `false` leaves "waiting for data" standing over playing video with nothing left to take it down. Both paths into the mirrors now go through one `applyProperty` — the observer and the sweep were two hand-written copies of the same mapping, which is the shape the bug had: not a wrong line, a missing one, in the copy nobody reads while writing the other. The **hook stays outside** it, and that is what makes sharing safe: `hooks.property` is where the page acts on a change (flushing a position, releasing a torrent, resetting the seek probe), and a sweep must move a stale mirror without pretending the event happened — which is also why `path`/`filename`/`media-title` are deliberately not swept, since for them the hook *is* the work. One property failing no longer ends the sweep either: the reads used to sit in a single `try`, so an unavailable property early in the list — routine between files — silently skipped every mirror after it.
4. **Multiple mpv properties are never visually atomic** from outside — even back-to-back Rust `set_property` calls let the VO redraw in between. If several properties must land in one frame (zoom+pan), go through `zoompan.lua`-style script handlers.
5. **Seekbar**: the original rule was "click = one `absolute+exact`; drag = `absolute+keyframes` only, *including the final one*", because a trailing exact seek after keyframe previews caused a frame-blink. That has since been deliberately narrowed — see "Seek flags are a performance contract" below for what replaced it and why. If the blink ever returns, `onSeekUp` is the first place to look.
6. **Fullscreen transitions**: order matters — set veil state → wait double-rAF + ~30 ms (frame must be presented) → show shutter window → `setFullscreen`. Do not "simplify" this sequence; each step masks a distinct Windows artifact.
7. **Hidden `veil` window keeps the app alive** — main-window `Destroyed` explicitly calls `app.exit(0)` in lib.rs. Removing that resurrects zombie processes that swallow Explorer "open with" requests via single-instance.
8. **Hotkeys use `e.code`** (physical keys) so they work in any keyboard layout. Keep it that way — the editor stores codes for the same reason. They live in `ACTIONS` in [keys.svelte.ts](src/lib/keys.svelte.ts), not in a `switch`: `onKeydown` resolves a chord to an action and calls `runAction`, and every place that *shows* a key reads `hint()` from the same table. Two defaults worth knowing: `L` is seek-forward (the J/K/L trio) and **loop is `Shift+L`** — mpv's own binding; the A–B loop that would have taken mpv's plain `l` therefore lives on `A` (`Shift+A` clears it). `noRepeat` and `quiet` are fields of the *action*, not lists of key codes, because neither is a property of a key once the key can be moved.
9. **A bar's gradient tail must not be part of its hit area.** `.topbar` and `.osc` extend well past their controls to fade the scrim (76 px vs 48 px of content; 44 px of top padding on the OSC). While that padding belonged to the element, clicks in it were swallowed by the bar — the user is visibly clicking video and the player ignores them. The gradients live in `::before` with `pointer-events: none`, and the elements themselves are sized to their content. **An absolutely-positioned `::before` paints *above* in-flow children**, so `.osc::before` needs `z-index: -1` plus `isolation: isolate` on `.osc` — without it the gradient covered the control row and every button looked disabled. `.topbar` survives without it only because its children are themselves absolutely positioned and come later in DOM order; do not rely on that when adding children. Anything targeting the scrim must therefore target `::before` (e.g. `.player.no-video .topbar::before`), and `data-tauri-drag-region` still needs the bar itself to receive events, which is why `pointer-events: none` on the whole bar is *not* the fix.
10. **The window is transparent, so "nothing painted" means "desktop visible"** — `.player` is transparent on purpose (mpv renders *behind* the webview), which makes any moment when neither party paints a hole through the window. Hiding the start screen (`showEmpty = false`) must therefore never be conflated with dropping the background: at launch with a file that flag flips before `init(mpvConfig)`, so the window was shown see-through until mpv's VO came up. `videoReady`/`.player.backdrop` keeps a dark fill until mpv paints. Erring long is free (mpv's own field is black underneath); erring short shows the desktop. The same hole exists one layer lower and *before* any of our code runs: on macOS the frame view draws the traffic lights the instant the window is ordered in, while the webview's first composite is a frame or two behind — so the buttons appear over bare desktop. Fixed natively in `macos_chrome::apply` by giving the NSWindow an opaque `#101016` `backgroundColor` (it sits below both the mpv view and the webview, so it only shows where nobody painted). Do **not** pair it with `setOpaque(true)` — that costs the system's rounded corners and edge shadow. Related: the window-appear animation is disabled via `setAnimationBehavior(None)`, which dates from when traffic-light placement lagged AppKit by a frame; that is fixed (see 15), so the line is now a taste choice rather than a workaround.
11. **Buttons/inputs get `font-family: inherit`** via a reset in +page.svelte — form controls don't inherit fonts by default and silently fall back to the system font.
12. **HMR resets JS mirrors** (videoW/videoH etc.) while mpv keeps state and won't re-fire unchanged property events — after editing +page.svelte, reproduce bugs with a full dev restart, not just HMR.
13. **tauri.conf.json / capabilities / icons changes need a dev restart** (and icons are tracked by build.rs `rerun-if-changed`); frontend-only changes hot-reload.
14. **Code after `updater.downloadAndInstall()` never runs on Windows** — the NSIS installer kills the process inside that call. Anything that must survive the update (e.g. the `frameplayer.resume` snapshot) has to be persisted *before* install starts (see `saveResumeSnapshot()`); `relaunch()` after it is effectively dead code on Windows.
15. **Never move the macOS traffic lights by hand — grow the title bar instead.** There is no positioning API (the buttons belong to the private frame view), so the obvious approach is to set their frames and re-set them whenever AppKit puts them back. That was built, in full, and it is a dead end. Three measured reasons, worth keeping because each one costs a day to rediscover: AppKit resets the buttons on every title-bar relayout and the causes cannot be enumerated (`setTitle` alone does it every time, and a container view of our own does not stop it); **position is only half of moving a button** — the ×/−/+ glyphs come from `NSTrackingArea`s AppKit lays out from its own model of where the traffic light is, never from the buttons' frames, so moved buttons keep the hover region of unmoved ones (glyphs lighting up 7.2 pt above and left, and the zoom button, past the stale rect's right edge, not responding at all); and **that cannot be repaired** — replacing the tracking area with a correctly positioned copy of itself (rect/options/owner/userInfo are all public) fixes the geometry and kills hover completely, because AppKit keys on the identity of the area *it* created, leaving glyphs that appear only while a button is held. What works instead is to change the title bar and let AppKit do the rest: an empty `NSToolbar` + `NSWindowToolbarStyle::Unified` grows it 28 → 66 pt, and AppKit itself places the buttons at (19, 33) with tracking rects to match — measured stable in the window, across resizes, after `setTitle`, and in fullscreen, where they keep the system's own placement and hover (which is exactly how Spotify behaves). It needs no per-relayout maintenance at all: `macos_chrome.rs` lost ~185 lines, a `CFRunLoopObserver`, a custom `NSView` subclass and a Tauri command to it. **The one thing the toolbar costs is fullscreen**: a window that has one shows it there *permanently*, as a tall opaque band whose buttons only appear once the system menu bar is revealed — instead of the thin strip that slides down on hover. So the toolbar is removed on `WillEnterFullScreen` and put back on `DidExitFullScreen` (measured: title-bar host 66 pt → 32 pt, buttons to the standard (9, 9) with their tracking rect). Restoring must wait for **Did**, not `WillExitFullScreen` — measured, a toolbar set there has no effect at all: AppKit ignores it while the transition is in flight, and the window animates back and sits for several frames with the short title bar. That gap is visible as the buttons sitting at the system position and then jumping to ours, and there is no earlier hook to close it — so it is masked instead: hide the buttons on `WillExitFullScreen`, unhide right after the toolbar is back, and they appear already in the right place. What comes back must be the frontend's last instruction (`BUTTONS_VISIBLE`, recorded by `set_buttons_visible`), **not** the button's own `isHidden`: AppKit shows the buttons itself in the fullscreen strip, so reading them back returned an idle-faded UI with its traffic lights on, which the next idle pass then blinked away. **Recording that intent and acting on it are two different things**, and both halves are load-bearing. The frontend reports the idle state in fullscreen as well — excluding it (the rule once read `idle && !fullscreen`) left the record saying "visible" the whole time, so leaving fullscreen while idle flashed the traffic lights on and the idle effect hid them a frame later. But `set_buttons_visible` then declines to *apply* a hide while the window is fullscreen: there the buttons belong to the strip that slides down from the top edge, and the idle timer emptied a strip the user had just pulled down — including while the pointer rested on a control they were about to click. Separately: **force `darkAqua` on the window**. The frame view draws itself to match the appearance, not the background color, so under the light system theme it put a bright highlight along the window's **top edge** — far stronger than the shadow on the other three sides and obvious against the dark fill. Screenshots settled the cause: the line is identical with and without the toolbar (so not the toolbar's doing), `titlebarSeparatorStyle = .none` changes it by not one pixel, and it all but disappears under the dark appearance. Two properties it quietly depends on, both verified, both worth re-checking if the chrome changes: the 66 pt system title bar **does not swallow clicks** (anything below 10 pt from the top hit-tests to the content view, so `data-tauri-drag-region` and the HTML top bar keep working) — that follows from `FullSizeContentView` plus a transparent, item-less toolbar, and giving the toolbar items would end it; and **window geometry is unchanged** (frame == content == `contentRectForFrameRect`), so size persistence and fit-to-video do not drift by the title-bar height.

## Conventions & flows

- **mpv option surface**: defaults are set in `initialOptions` in +page.svelte; user overrides come from `%APPDATA%/<identifier>/mpv.conf` (command `user_mpv_conf`, template in lib.rs, `wid` filtered out). The interactive editor (`SETTINGS` array in +page.svelte) persists via `mpv_conf_set` (surgical line edit: comments/unknown keys survive) and live-applies via `command('set', ...)`. To add a setting: one `SettingDef` entry. The dialog was once split by **who owns the setting** — one tab for exactly what ends up in mpv.conf, one for state the player keeps itself. That boundary is real and still shapes the code (`SettingDef` covers only the mpv.conf half; volume leveling and the queue options are localStorage), but it turned out to be a poor map for someone hunting for "subtitle size", which is how a settings dialog is actually read. It is now topical sections — Основные / Видео / Проигрывание / Аудио / Субтитры / Раздачи / ТВ / Клавиши — with each `SettingDef` naming its own `tab`. **There are eight, and the eighth only fits because its label is two characters** («ТВ», not «Трансляция»): the row is measured below at seven Russian labels plus that, so a ninth tab, or a wider eighth, silently goes over the edge. What the ownership boundary still owns is the footer: it says mpv's settings live in mpv.conf rather than claiming everything on the page does, because the Audio section deliberately mixes both. **Adding a section means re-measuring the dialog's width**, and skipping that is invisible rather than ugly: `.tabs` is `nowrap` with `overflow-x: auto` and `scrollbar-width: none`, so a tab past the right edge is simply *gone* — the six-tab row had quietly been overflowing a 428px sheet and clipping "Клавиши" before anyone added a seventh. Measured against the built stylesheet (a hand-written copy of the rules is how this class of bug gets missed twice): seven Russian labels are **510px** at 13px with a 13px gap, English 408, so the sheet is 598 — an *outer* number, since every box here is a border box, which leaves the tab row 50px of slack inside the sheet's 36px of horizontal room and 2px of border. That slack is now the same in every state, and getting there fixed a jump the sheet had always had: **a scrollbar takes its width out of the content box and leaves `padding-right` inside it**, so everything right-aligned in a scrolling sheet sits 10px further in than it does in a short one. Measured on the built stylesheet, with the fix reproduced by `sed`-ing the rule back: the × was 19px from the sheet's edge on a short tab and **29px** on a tall one, and the tab row was 560px against 550px — so switching between "Раздачи" and "Основные" moved the close button and quietly cost the row a fifth of its slack. The space is reserved by **`overflow-y: scroll`**, not by `scrollbar-gutter: stable`, and the sheet's padding is written asymmetrically (`16px 8px 14px 18px`) *so that it is symmetric on screen*: 8px of padding plus the bar's own 10px is the same 18px as the left. Do not "tidy" that back to a single 18px — the tidy version is the bug. **`scrollbar-gutter` is not honoured by WKWebView**, which inverted this fix rather than delivering it: with the padding already cut to 8px, a sheet that did *not* scroll had 9px on the right against 19px on the left, and only a scrolling one looked right. Measured against the built stylesheet in a WKWebView harness — `auto` + `stable`, short content: `offsetWidth − clientWidth` = 0, gaps 19/9; scrolling: 19/19. Chromium honoured it in both, so this was macOS-only. The trap is that **`CSS.supports('scrollbar-gutter','stable')` returns `true` there and the computed style reads back `stable`** — neither feature detection nor the computed value would have caught it; only measuring the box did. Forcing the bar on costs nothing on screen (transparent track, and WebKit draws no thumb on a sheet that fits) and measures 19/19 on both engines in both states. Torrents earned a tab of their own for the reason the topical split exists at all: seeding and the piece cache were correctly filed under privacy and storage, and a viewer looking for anything about torrents still had to read "Основные" to the bottom to find them. Destructive actions there are real buttons (`.btn-danger`), never `.settings-link` — a link promises navigation, not deletion. The context menu is **grouped, not listed**: anything with more than two related entries (file, frame, playback, picture, window) is a submenu, which took it from ~19 rows to 11 — a menu that had to scroll in an ordinary window was the sign it had outgrown a flat list. What stays at the top level is what has no group and is reached often. Two things the grouping cost, both worth knowing before moving a panel again. **A panel moved out of its parent loses the parent's event guards** — the menu stops clicks with `onclick={e => e.stopPropagation()}` so they do not reach the handler that closes it, and a hoisted panel is no longer covered by it: every click inside a submenu, the back row included, closed the whole menu. And **five submenus need one implementation, not five** — `submenuHead`/`submenuPanel` snippets keyed by a `CtxSub`, with the anchors in a `Record` rather than a ref each, or the fifth copy is where the divergence starts. The context-menu submenu needs **both** a hover bridge (`.ctxmenu.submenu::before`, `inset: 0 -10px`, `z-index: -1` so it does not eat clicks) and a delayed close: the diagonal path from the parent item to the submenu crosses the gap between them, which belongs to neither element, so `mouseleave` fires and the menu collapses under the cursor. Reset it with `closeSubmenuNow()`, never a bare flag, or a pending timer from the previous menu closes a freshly opened one. **One control shape per job**, or the UI stops being readable: underlined `.tabs` switch sections, pill `.segmented` picks one of several named values, `.switch` is boolean on/off. Reusing the pill for a Да/Нет pair made a setting look like navigation. A switch is **two** classes and the inner one is `.switch-knob`: the seeding toggle was written with a bare `.knob`, which has no rule anywhere in the project, so it rendered as a track with nothing sliding in it and on/off could only be told apart by the background color. Nothing catches that — an unknown class is not an error and Svelte's unused-selector warning fires on the CSS, not on the markup.
- **Returning to the start screen is a destination, not a blank to wait out.** `showEmpty` is debounced by 300 ms because a playlist transition blanks `filename` for a moment and the picker must not flash through it. That is right for an *involuntary* blank and wrong for a deliberate close: `backToStart` issues `stop`, and for those 300 ms the player's own chrome stood over a VO that had already stopped — a black frame under a seekbar reading 00:00, which is what going back looked like. So the two paths are separated. `enterStartScreen()` raises the picker and refreshes what it lists; the `filename` handler still calls it on the timer, and `backToStart` calls it **before** issuing the stop, where the destination is already known. `.player.no-video` is opaque, so raising it first covers the video and nothing in between is ever seen. Two details that are not decoration: the position is flushed *first*, or the card this file is about to appear on carries the previous write rather than the moment it was left at; and the handler skips its timer when the picker is already up, or the recents list is rebuilt a second time and the cards visibly reshuffle as the posters arrive again. **Releasing the torrent belongs here too, for the same reason the picker does**: the `filename === null` handler also does it, but that path is *inferring* the departure from an event, and a dropped property change (a queue overflow costs them — hence the 1 s resync) then leaves the swarm running and the download readout standing over the start screen. A path that knows it is leaving says so; the handler's own call then finds nothing left to release. The **other** half of that same symptom is a poll that outlives its file: `torrent_status` is a round trip and the timer fires every second, so closing a film routinely catches one in the air, and clearing the interval does nothing to a promise already sent — it resolves afterwards and writes the status back, permanently, since nothing will clear it again. Hence the sequence guard on `trackTorrentPlayback`'s polls, the same one `loadTracks()` carries.
- **The end of a file is a moment the player owns, and that is a deliberate inversion.** `keep-open=always` (not mpv's `yes`, which stops only on the LAST playlist entry and advances silently everywhere else) parks mpv on the final frame of every entry, so advancing is ours: the end screen with previous/replay/next, a cancelable countdown, and the wrap of a repeating queue — `loop-playlist` can no longer fire it, because mpv never advances at all. Measured on a three-entry playlist: at the end of entry 1 of 3, `eof-reached=yes`, `pause=yes`, `playlist-pos` stays put. **That `pause=yes` survives a file change**, so anything that moves to another entry must unpause explicitly or the next episode opens on a still frame. Repeat-one never reaches any of this (mpv loops the file internally). The repeat control is three-state as on music services — off / all / one — mapping to `loop-playlist=inf` and `loop-file=inf`; `all` on a one-entry playlist already means "repeat this video", so no special case is needed. **The mode is our state, written to mpv and never read back**: reading it back would make `all` look like `one` wherever both properties end up set, and the value is re-asserted after `init()` because the user's mpv.conf is merged over `initialOptions` and would otherwise leave the button lying about what the player is doing. The old default was `loop-file=inf` for anyone who never touched the toggle — which meant a file repeated forever and a queue could never advance past its first entry; the migration reads a stored `inf` as `one` (a deliberate choice) and an absent key as `off`.
- **A file's name in the queue comes from three places, and only the third costs anything.** mpv fills `playlist/N/title` from `media-title`, but **only for entries it has actually opened** — so everything ahead of the playhead was showing a bare file name until it played. The first fix is free: the fallback is `displayName()` (extension off, dots to spaces), the same one the start screen uses, rather than a raw basename. The second is `container_titles`, which opens each file's header and reads the `title` tag — `avformat_open_input` **without** `avformat_find_stream_info`, because a title lives in the header while the probe exists to identify streams. Measured on an MKV, warm: **0.10 ms** per file that way against **0.27 ms** with the probe, and a cold file is dominated by the disk either way; so naming a 300-entry folder is a fraction of a second, done once, 1.2 s after the playlist changes and never for a queue of one. Opening the queue panel reads immediately instead of waiting out that delay, which is why `openQueueMenu` now *awaits* `loadPlaylist`: fired against the previous list, the read would find nothing to do and the panel would sit on the timer it was meant to skip. What the measurement also said, and what decides the feature's worth: **most files have no title tag** — an ordinary rip held only `encoder` and `creation_time` — so this improves the minority that were authored with one, and `displayName()` is what carries the rest. Results are session-only (a Map, not a store: nothing persisted is one less place the privacy rules must be enforced) and each path is tried once, so a file without a tag is not reopened on every playlist change.
- **A queue is built from one opened file, never from several.** Dropping five files is an explicit selection and stays exactly what was given; opening a single episode is the case where the rest of the folder is wanted. `folder_entries` returns every plain file unfiltered and unsorted on purpose — what counts as a video (`VIDEO_EXTENSIONS`) and what natural order means (`Intl.Collator({numeric: true})`, which knows "ep2" precedes "ep10") both live in the frontend already, and a second copy in Rust is the kind that drifts. The opened file keeps its natural position rather than becoming entry zero: the files sorting before it go in with `loadfile … insert-at N` (mpv 0.38+; older builds throw and the queue is simply forward-only). Verified rather than assumed — `insert-at 0` on a playing file shifts `playlist-pos` 0 → 1 by itself, so what is playing keeps playing. Long folders are truncated *around* the opened file, not from the end: in a folder of thousands, the episodes that matter are its neighbours.
- **Whether the sidecar shares mpv's FFmpeg depends on the platform, and the prefix on a log line tells you who is talking.** On macOS `src-tauri/ffmpeg-macos/lib/*.dylib` are **symlinks into `src-tauri/lib/`** (verified with `otool -D`: both carry the install name `@rpath/libavcodec.62.dylib`) — mpv and the thumbnail service load one and the same library. On Windows they are separate DLLs: `libmpv-2.dll` against `ffmpeg/bin/*.dll`. What is constant is the logging: mpv installs an `av_log` callback and its lines read `[ffmpeg/video] hevc: …`, so **a bare `[hevc @ 0x…] …` is libavcodec's default callback** and did not come through mpv — in practice the sidecar decoding a file in software, not playback. Hence `log::set_level(Error)` next to `ffmpeg_the_third::init()`: a chatty file (Dolby Vision RPU notices on a DV remux, for one) otherwise buries everything else in the dev console. Note the asymmetry it inherits: the log level is global to a library, so on macOS that call also caps mpv's own libav messages, while on Windows it only affects ours. If mpv-side FFmpeg warnings are ever needed for debugging, that line is where they went.
- **Background decoding competes with playback — budget it explicitly.** The thumbnail storyboard decodes in *software*, so it degrades the player identically whether mpv's hwdec is on or off; that symmetry is the tell. Measured on a 197 s 4K60 VP9 file: an unbudgeted storyboard (`threads = ncpu`, 5 ms sleep) took ~3 cores for ~35 s right after the file opened, and made seeking feel broken. Now bounded three ways: `DECODE_THREADS` (capped, not `ncpu` — 292 % → ~150 % CPU), a duty cycle sleeping `1/YIELD_RATIO` of the time the last cell took, and `background_qos()` (ffmpeg's frame-thread workers inherit the creator's QoS, so one call at thread start is enough). **Both knobs have a floor as well as a ceiling**: the first attempt (`QOS_CLASS_BACKGROUND` + 1:1 duty) was over-corrected — BACKGROUND pins the work to efficiency cores and a 3-minute 4K60 storyboard then took minutes, so thumbnails were not ready when the user reached for them. `QOS_CLASS_UTILITY` is the right class: P-cores stay available, but the player preempts the storyboard rather than the reverse. Keep any future background work under the same three constraints. **And a fourth: do not start it when nobody is waiting for it.** While a television owns playback the storyboard is a prefetch for a gesture nobody is making — it decodes the whole file to make hovering instant, and the viewer is looking at the TV — so it is suspended for the length of a cast session and resumed when the session ends (`suspendThumbs`, set by the cast module so `thumbs` keeps depending on nothing). Hovering still works meanwhile, one on-demand decode per hover instead of none. This is the case that made it visible: casting a torrent that is still downloading means the file **completes during the session**, and the status poll then dutifully starts a 4K storyboard behind a paused player. **And a fifth: on battery the same pass runs at a third of the rate** (`power::on_battery()`, `BATTERY_YIELD_MULT`/`BATTERY_MAX_YIELD_MS` — rest is twice the time the cell took rather than a third of it). Two measured facts shape that. The **ceiling, not the ratio, is what decides the rate on the files this matters for**: a 4K HEVC cell costs ~1.3 s, so `MAX_YIELD_MS` of 120 makes the mains pass a ~90 % duty cycle — raising the ratio while leaving the cap would change nothing at all. And the *ratio* is what keeps a cheap file from resting for two seconds a cell. Measured on a 6.3 GB 4K HEVC file with a cold cache: mains **164–208 % for ~40 s**, battery **64–105 % for ~60 s**, warm reopen a flat 21–24 % on either supply (which is also the check that the throttled pass still finishes — a partial storyboard would resume and burn processor again on reopen). Only the *background* pass is throttled: a hover is somebody waiting, and it decodes at full speed regardless. The supply is asked per cell so that unplugging is noticed within a few of them, behind a 10 s cache, and both platforms answer with one call — macOS `IOPSGetTimeRemainingEstimate()` (`kIOPSTimeRemainingUnlimited` is mains, and is also what a desktop with no battery answers; verified against `pmset -g batt`), Windows `GetSystemPowerStatus`. **A machine that declines to answer is treated as plugged in**, because degrading the player on a machine that merely failed to report is the worse way to be wrong.
- **Seek flags are a performance contract, not a detail**: `hr-seek=yes` in `initialOptions` makes any seek without an explicit flag *exact*, and an exact seek costs decoding from the preceding keyframe. Measured on a 4K60 VP9 file with a 5 s GOP (mpv IPC, hwdec on): a far `absolute+exact` jump ≈ **1.9 s**, the same jump `absolute+keyframes` ≈ **0.05 s**; a nearby `relative` (still exact) ≈ 0.13 s. Crucially, that cost is a property of the **file**, not of the flag or the jump distance. Measured via mpv IPC, 30 steps of 2 s:

| file | exact | keyframes |
|---|---|---|
| HEVC 4K 25 fps, GOP 2 s | 25 ms | 25 ms |
| h264 4K 60 fps, GOP 2 s | 36 ms | 37 ms |
| VP9 4K 60 fps, GOP 5 s | 1219 ms | 50 ms |

On a normal file keyframe seeking buys **nothing**, while *switching modes mid-gesture* is plainly visible as a jerk (previews sit on a keyframe, the final frame lands on the exact position). So the mode is probed once per file — `issueSeek()` times the first exact seek, `fileSlowSeek`/`wantExact()` decide from then on, `resetSeekProbe()` on `path` change (IINA does the same via `useExactSeekForCurrentFile` with a 0.05 s threshold). Fast file → exact everywhere, no mode changes at all. Slow file → keyframe previews, exact only where a frame is actually being asked for. Notes: hwdec **halves keyframe seek time but doubles exact seek time**, so "turn hwdec off" is not a win either way; `vd-lavc-fast`/`skiploopfilter` change nothing for VP9; `demuxer-max-back-bytes` is not implicated.

The two gestures deliberately differ on pausing. **The seekbar drag pauses** (from the first move, not from pointer-down, so a plain click never touches playback): playing video drifts forward between throttled preview seeks and the next preview yanks it back — visible as forward/backward judder. **The wheel scrub does not pause** — it self-terminates after 180 ms, and with only ~12 keyframes in a 60 s span a paused scrub degenerates into a slideshow, which is what "less responsive than IINA" actually meant; it mutes instead, so frames keep moving between landings without machine-gunning the audio. While either gesture owns the position, `time-pos` must not write `seekValue` — and that block must extend past pointer-up (`seekSettling`) until the final seek lands, or the knob snaps back to the preview position and then forward again. Drag previews run on the same one-in-flight pump, **never a time throttle**: a seekbar is a brutal magnifier (a 57-minute film across ~900 px is 3.8 s *per pixel*), so an 80 ms throttle leaves the shown frame seconds behind the cursor and releasing then visibly jumps by that gap. `scheduleDragSettle()` closes the rest: 120 ms after motion stops it re-seeks *exactly* to where the cursor rests — that is the frame the user is actually aiming at — and `onSeekUp` skips its own seek when that already landed (`dragShownAt`/`dragShownExact`), so a considered release changes nothing at all. **The arrows follow that same verdict**, which they did not always do: the coarse step went by keyframes *unconditionally*, and a keyframe landing is up to a GOP away — so a 5 s arrow actually moved 6 s on an ordinary file and 10 s on a network stream with long fragments. It had always done that; only the popup hid it, by reporting the promise rather than the landing. They also carry the probe themselves (`noteSeekCost`), because an arrow is often the first seek on a file and a slow one would otherwise go undiagnosed until the bar was touched. Shift+arrow stays exact regardless. Beating the keyframe ceiling on pathological files needs our own decoded-frame source (StepEngine), not a different flag; IINA has no such thing (its `FFThumbnail` cache is the seekbar hover popup, same as ours). Two more rules the gestures depend on: keep **exactly one seek in flight** (`pumpScrubSeek`) rather than firing on a timer — a fixed interval builds a queue that keeps "playing out" after the fingers stop; and while a gesture owns the position, `time-pos` must not write `seekValue` (`!scrubbing`/`!dragging` in the observer) or the knob jitters between the finger and mpv's lagging report. Note `onSeekUp` now ends a drag with an exact seek when it is near — a *deliberate, narrowed* rollback of the architecture.md "drag is keyframes-only, including the final one" rule, because keyframe landing made the knob visibly snap backwards on release. If the frame-blink ever returns, revert there first. When a seek lands on a keyframe, the optimistic OSD position is wrong — refresh it from `time-pos` afterwards (`refineSeekOsd`), but **not when the seek command resolves**: `command('seek', …)` returns when mpv *accepts* the command, and `time-pos` there is still the position before the jump. Reading it then showed the target, flicked back to the starting point and stayed — three figures for one key press. `playback-restart` is the event that means the seek is done; the timeout beside it exists so a seek that never completes cannot leave the popup waiting on a promise.
- **The preview must show the frame you land on, and both halves of that were wrong.** The hover thumbnail comes from a grid whose step is `clamp(duration/240, 0.25, 10)` — 10 s for anything longer than 40 minutes. The position was mapped to its cell by *truncation*, so the preview sat up to a full step **earlier** than the cursor, while the seek that follows is exact: the two errors added instead of canceling, which is why the played frame was reliably *ahead* of the previewed one. Measured on a 24-minute file, 30 hover positions, "different scene" = PSNR < 18 dB between the previewed frame and the one playback starts on: **60 %** with truncation, **37 %** with rounding to the nearest cell, 30 % at a 3 s step, 20 % at 2 s, 0 % at 1 s. Rounding is free (cell N still holds the frame at `N*interval`, so existing caches stay valid — no `CACHE_MAGIC` bump) but it only halves the error; what removes it is fetching the **exact** frame when the cursor comes to rest, the same trade `scheduleDragSettle()` makes with the video. Two consequences worth keeping: that refinement visibly *replaces* the thumbnail in roughly 40 % of hovers — inherent, since those are exactly the cases where the grid frame was a different scene — and its cost is one GOP of software decode, measured worst-case **120 ms** on 1080p h264, **1330 ms** on 4K30 HEVC 10-bit, **1940 ms** on 4K60 VP9 (GOP 5 s). So on 1080p it reads as the preview sharpening ~200 ms after you stop; on 4K it is a late, visible flip that also burns three decode threads next to playback. **The decode itself cannot be made cheaper** — measured per GOP against the baselines above, `skip_loop_filter=all` gives 4K60 VP9 nothing at all (1950 vs 2010 ms, noise), 4K30 HEVC ~10 %, 1080p h264 ~8 %, and `skip_frame=bidir` ~18 % on h264 while costing a landing a few frames off — so the latency budget that *is* controllable is the scheduling: `SETTLE_MS` is 70 ms rather than `scheduleDragSettle()`'s 120 (this gates a 320px thumbnail, not a seek of the video), armed from the **pointer move** and not from every request (the throttle's trailing call re-enters up to 85 ms later, and re-arming there delayed the exact frame by that much for nothing the user did), with **one exact request in flight at a time** — a slow sweep would otherwise queue seconds of GOP decoding whose results are all stale on arrival. Firing an exact request also cancels the pending trailing grid request: it is for the same resting position, and it is the only way a grid frame could land *after* the exact one and overwrite it. If the 4K case becomes a problem, the fix is a probe in the shape of `fileSlowSeek`/`wantExact()` — time the first refinement and stop refining that file past a threshold — or a decode session of its own for hover requests, so they stop re-seeking the storyboard's; *not* a finer grid, which needs a 1–2 s step and therefore decodes the whole file in the background. The replacement **crosses over rather than cuts** (`.thumb.fading`, 140 ms), and the layer on top is the **outgoing** frame, never the incoming one: an `<img>` keeps showing its previous content until a new `src` decodes, so putting the new frame on top would let the pre-refinement frame show through underneath for a frame — with the outgoing frame on top, whatever is beneath it is always the newest. Grid frames are swapped with no animation at all, since those track a moving cursor. `frame_exact_at` must never touch `refine_mode`: that flag is the storyboard's verdict about the file, and one hover request must not push the whole background pass into linear decoding.
- **Frame export and external tracks go through mpv, not around it.** `screenshot-to-file` keeps exactly what the VO decoded, HDR tone mapping included — which is precisely what the StepEngine canvas path got wrong, so do not reintroduce a canvas-based grab. `screenshot-raw` is not an option either: it returns a node, and node reads crash the wrapper. Clipboard copy therefore round-trips through a temp PNG decoded in Rust — and **mpv's PNG defaults are a latency trap**: zlib level 7 is a size-first choice that buys nothing here. Measured on a 4K frame of photographic content (libavcodec's PNG encoder, the one mpv screenshots go through): level 7 = 1.46 s / 16.4 MB, level 3 = 0.73 s / 16.4 MB, level 0 = 0.21 s / 23.8 MB. A 10-bit source doubles every figure, because `screenshot-high-bit-depth` defaults to yes and writes 16-bit PNG. Hence level 3 globally, and level 0 + no row filter + 8-bit for the throwaway clipboard file, which reaches the clipboard as 8-bit RGBA no matter what. `withFastScreenshot()` restores the previous values in a `finally` — leaving compression off would silently bloat every frame saved afterwards. This encode runs on mpv's core thread, so getting it wrong stutters playback as well as making the user wait. Dropped files are split by extension in `loadFiles`: subtitle/audio files become `sub-add`/`audio-add` (an `.srt` handed to `loadfile` used to be *played*), and when they arrive together with a video they wait in `pendingAttach` until `file-loaded` — `sub-add` before that fails. Track delays use `add`, never `set` from the mirror, for the same reason toggles use `cycle`.
- **A subtitle found by the file's hash and one found by its title are different results, and the panel says which.** The hash (size + every 64-bit word of the first and last 64 KiB) identifies a *release*, so what comes back is already in sync; a title match is a guess about which rip you have and may be off by seconds. Conflating the two is what makes subtitle search disappointing elsewhere, so which one produced the list is reported and shown as a sentence. **The two searches must therefore be separate requests, and the verdict must come from the results rather than from the request** — this is the bug the first version shipped with. Sent together, the API answers with the **union**: measured, a hash alone returned 11 subtitles all flagged `moviehash_match`, the same hash plus an unrelated query returned 50 with still only those 11 flagged. The panel then announced "matched by the file itself" over a list of unrelated films — a file called `master.mkv` (an episode of a series) was offered *Master and Commander* under that heading. So: hash first, alone, with `moviehash_match=only`; the typed title only if that came back empty; and `match_kind` derived by looking at what arrived. The empty hash result is itself worth saying — "OpenSubtitles has nothing for this exact file" is a fact about the file, and it is what the viewer needs in order to stop trusting the list below it. Measured against the live API on 2026-08-03, and three of the four facts contradict what our own research assumed: **the rate limit is 5 requests per second**, not 1; **searching is not quota'd at all** while downloading is; **downloading works with no user account** (5/day per IP, and 100/day for a consumer marked *Under Development* — an anonymous `POST /download` returned `remaining: 99`), so signing in raises the ceiling rather than unlocking the feature. **Which bucket is being charged is in the response**: `uk` reads `app_ud_<consumer>` for a key in development — one allowance shared by everyone using that build — and `app_<consumer>_<ip>` for a released one, which is the per-IP allowance. Running a production key dry confirmed both the model and the refusal: five downloads answer 200 with `remaining` counting down, the sixth returns **HTTP 406** with `remaining: -1`, a human-readable `message` and `reset_time`. 406 is the daily quota and 429 is the rate limit — collapsing the two into "request failed" throws away the only thing worth telling the viewer, which is when it comes back and that signing in moves the ceiling; and the API's own relevance sort is not usable — searching "interstellar" put a documentary *about* the film first, hence the client-side sort of hash matches before download count. Two consequences in the code. A hash that matches nothing is the normal case for anything but a well-known release, so an empty hash search silently retries by title — free against a 5/s limit, and the difference between an empty panel and a usable list. And the key is the *application's*: OpenSubtitles bans apps that make their users register their own, so it ships with the binary, cannot be a secret, and is looked up in an order (`app_data` file → dev file → compiled-in) whose only purpose is that a revoked key can be replaced through the signed R2 channel without a release — the real cost of a leak is availability, not privacy. **There is no duration anywhere in the API** — verified by dumping a whole result and walking every key of the subtitle, its `files[]`, its `feature_details` and the `/features` record — so "will this one fit" is answered by `fps` instead, flagged when it differs from `container-fps` by more than 0.1: a 25 fps subtitle on a 23.976 fps file does not start late, it drifts further out the longer you watch, which is the failure viewers hit and cannot diagnose. An episode's own `title` is usually the literal "Episode 3", so episodes are labeled from `parent_title` + `season_number`/`episode_number` or a list of them says nothing. **Those two numbers are also what reaches a series at all**, and without them the feature simply misses: measured, `query=the day of the jackal` returns the **1973 film**, the same query with `season_number=1&episode_number=3` returns **122 subtitles for the 2024 series**, and `year=2024` is not a substitute — it answered with 10 000 results of "Empty Movie (SubScene)". They come from the file name (`parseEpisode` in format.ts), which also yields a far better query than the whole name. Only unambiguous markers are read — `S01E03` and its spacings, the spelled-out forms in both languages, and `1x03` bounded by non-digits so `1920x1080` cannot become "season 20, episode 10" — because a bare number in a release name is never an episode: `1080p`, `2024`, `x264` and `5.1` all sit exactly where a naive parser would read one. The panel says which season and episode it took, or a list of episodes appearing for a two-word query reads as the search guessing. **Removing a subtitle is two different actions, and which one applies is not a preference.** An embedded track cannot be removed at all — it lives in the container, taking it out would mean rewriting the video, and mpv's `sub-remove` refuses it anyway — so the × appears for external tracks only (`track-list/N/external`, with `external-filename` beside it). For an external one, detaching is the queue's gesture and would be enough, except for a consequence of our own naming: a subtitle we downloaded is called `<video>.<lang>.srt` *so that* `sub-auto=fuzzy` finds it next time, so detaching without deleting means it is back at the next launch and the removal reads as broken. Hence the file is deleted too — **but only for files we created**, recorded in `frameplayer.subs` (privacy-gated like the positions, since the path is named after the video). A subtitle the viewer made, corrected or dragged in is only ever detached; an unrecorded path is treated as theirs, which is the safe direction to be wrong in. `subs_delete_file` checks the extension as a second lock: a delete-by-path command that accepts any path is one wrong argument away from removing the video. **Signing in is an upgrade, never a gate**, and the code is shaped that way: downloading works signed out, so nothing checks for an account before trying, and what an account buys is the ceiling (5 a day per IP → 10–1000). What is stored follows from what losing it costs — the **token** goes into the OS keychain by default (it expires by itself, is revocable from the site, and lasts 24 h with no refresh endpoint, so without keeping it the viewer signs in again for practically every film), while the **password** is stored only behind an explicit opt-in, because it is the most sensitive thing this app will ever hold and is probably reused elsewhere; what it buys is silent renewal. Neither ever touches localStorage. Three details that are easy to get wrong: `/login` has its own rate limit of **1 request per second** where search allows 5, so nothing may retry in a loop; a **VIP account is answered by a different host**, handed over as `base_url` at login and used for everything afterwards, or a 1000-download account quietly behaves like a 20-download one; and a keychain refusal is **reported rather than swallowed** (`keychain_failed`) — on macOS the ACL is bound to the code signature, so dev builds re-prompt whenever the signature changes, and a session that silently lasts only until quit is worse than one that says so. The downloaded file goes beside the video as `<name>.<lang>.srt` so mpv's `sub-auto=fuzzy` finds it by itself next time, with nothing remembered on our side; a read-only folder falls back to the cache directory, and an existing file is never overwritten.
- **Closed captions are a subtitle track that isn't in the container.** `eia_608`/`eia_708` captions ride inside the video stream (SEI), so `ffprobe -select_streams s` shows nothing while mpv lists `--sid=1 (eia_608)` — do not conclude from ffprobe that a file has no subtitles. Two consequences the player has to live with, both inherent to the format rather than bugs in our code: captions are positioned on a 15×32 character grid, so the text is indented and off-center by design (the decoder literally emits leading spaces); and the decoder is stateful — roll-up/paint-on modes build the screen over many packets — so seeking into the middle of a caption leaves residue. This player seeks harder than stock mpv, which compounds that residue into captions from several scenes stacked on top of each other, hence `sub-clear-on-seek=yes` in `initialOptions`. IINA shows the same smear on the same file, so do not go looking for the cause in our render path. Such a track carries no title and no language, so `loadTracks()` names it from the codec — otherwise the menu offers a bare "Track 1" with no hint of what it is.
- **The subtitles get out of the control bar's way, and `sub-pos` is the only lever measured to work.** While the chrome is up the last line of dialogue sits behind the seekbar — exactly while it is being read, since what raised the bar was the viewer's own hand. `sub-shift.svelte.ts` lifts it by the bar's measured height, as a percentage of the *window* (which is what `sub-pos` speaks, so the device scale cancels out), and the height is `offsetHeight` on the `.osc` element rather than a constant: the mini player gives it less padding, and the bar is translated 10px down while hidden, which a bounding rect would report and a border-box height does not. `sub-margin-y` would be additive and need no base at all, but nothing here has established that it survives ASS override, while `sub-pos` reaching ASS subtitles is already measured (`sub-ass-override` defaults to `scale`) — and being wrong about it is silent, since the subtitles simply do not move. **The lift is the bar's height minus where the subtitle already sits**, and leaving that term out is the mistake this shipped with first: mpv holds subtitles `sub-margin-y` above the bottom edge, in "scaled pixels" of 1/720 of the window, so the two clearances added and left a whole scrim's height of empty picture between the text and the controls. It is read from mpv rather than assumed to be 22 (it is an option somebody's mpv.conf may set) and it cannot be a constant in pixels at all, since it scales with the window — 33px at 1080p, 66px at 4K; it is fetched once on `player.ready` rather than lazily beside the base, or the first appearance of the bar would be a two-step move. It is only an estimate for ASS, which takes its margin from its own style, but both live in the same 10–30 range against the same 720 reference. What is left is an 8px gap, which deliberately does **not** clear the scrim: `.osc::before` is drawn in the webview and therefore lies *over* mpv's picture, reaching 44px above the controls, so a subtitle there carries about 0.18 of black — a slight dimming against its own outline, where clearing it would cost 44px more. Two rules follow from `sub-pos` being the viewer's setting as well as ours. The base is **re-read from mpv on every apply**, never remembered across a session: the settings slider writes `sub-pos` live and directly, so whatever it last wrote is the truth. And the shift **stands down while a dialog is up** (`chrome.sheetOpen`), which is what guarantees that slider can only ever be dragged against an unshifted value — otherwise a position dialled in there would be measured from ours and shifted again on top of itself when the sheet closed. Writes are serialized through one promise chain, because restoring the base and reading it back are the same property and a restore in flight would be read as the base by the apply behind it. The move is instant against the bar's 0.25s fade: mpv has no animation for a property, driving one from here would be ~15 writes on its core thread per fade, and going first reads as the subtitles getting out of the way, which is what they are doing.
- **Every list property is read through sub-properties, and they do not all behave alike.** `track-list`, `chapter-list`, `playlist` and `audio-device-list` are all implemented on mpv's side by the same helper, which exposes `<prop>/count` plus `<prop>/N/<field>` in simple formats — so none of them needs the `node` format that crashes the wrapper, and none of them needs native code either (the roadmap's worry about `audio-device-list` is unfounded). `readList()` in player.svelte.ts is that pattern; the sequence guard stays at the call site, because a read is dozens of sequential round-trips and there are several reasons to start one. What is *not* shared is how a missing field reports itself, and copying the track code blindly gets it wrong: measured on mpv 0.41, `track-list/N/title` of an untitled track is **unavailable** (the read fails, `.catch(() => null)` produces the fallback), while `chapter-list/N/title` of an untitled chapter is **available and reads back as the literal `(unnamed)`** — which would put an English placeholder into a Russian chapter list. Hence `MPV_UNNAMED`. Two more measured facts behind the chapter code: a file without chapters has `chapter-list/count` = 0 (available, not an error) while the `chapter` property is *unavailable*, so the current-chapter mirror needs its own fallback; and chapter navigation goes through the `chapter` property rather than a seek to the chapter's `time`, because with ordered chapters (MKV) the content can live in another file entirely and only mpv's own chapter seek follows that. It is also clamped at both ends — mpv's `add chapter ±1` walks off into the neighbouring playlist entry, and "previous chapter" opening the previous episode is not what the key says. **An arrow-key accelerator on an NSMenuItem does not fire** — measured: ⌘⇧←/→ on the View items did nothing at all, while the same keystrokes reach the webview normally, so chapter navigation is a frontend binding (`isChapterKey`) and those menu items carry no accelerator. On macOS it needs a modifier beyond Ctrl, since plain Ctrl+arrow is Mission Control and never arrives; hence ⌃⌘←/→ there against plain Ctrl+arrow on Windows. Testing `e.ctrlKey` alone is the trap that hides all of this: it silently accepts ⌃⌘, ⌃⇧ and every other Ctrl+arrow as the same gesture, so the binding *appears* to work on macOS while Ctrl+Shift+arrow quietly stops being the 1 s exact seek it looks like.
- **"Skip intro" matches the whole chapter title, never a substring.** `skipKind()` offers a skip button for the first `SKIP_WINDOW` seconds of a chapter that names itself an opening, a recap, a preview, a trailer, the credits or an ad. A **kind exists only to label the button**, which is what decides how finely they are split: a trailer is not filed under "preview" because an episode's preview announces the next episode while a disc rip's "Trailer" is a promo for another film, and "Пропустить анонс" over one of those is the same mistake as "Skip credits" over an opening, in miniature. Adding a kind is therefore a `SkipKind` member plus an entry in `SKIP_LABEL`, which the compiler demands. The obvious implementation — search for "intro"/"ending"/"credits" inside the title — is wrong in the common case, not a rare one: those are ordinary English words, so "Ending the war for good" becomes the closing credits and "Opening the vault" becomes a title sequence. Announcement chapters name themselves and stop, so the patterns are anchored to the entire title (with only the decorations rips actually use: a leading "01. " and trailing "…"), plus a five-word cap as the outer bound for the open-ended tails like "Previously on <show>". Anchoring also settles "субтитры" contains "титры" for free, and it puts the failure on the harmless side: an unusual name simply offers no button. Two traps inside the patterns: **`\b` is ASCII-only in JS**, so `ранее в\b` never matched anything at all — Cyrillic alternatives need an explicit `\s`; and the intro-first ordering, which **used** to matter ("Opening credits" matched both while the patterns were substring searches) and is now inert — anchoring them to the whole title made the alternatives disjoint, verified by enumerating every title they match from a corpus of their own literals and diffing the verdicts under both orders. It stays as defense against a future un-anchoring, and the comment at the table says so rather than claiming to be a rule; reversing it therefore changes no test result, which is worth knowing before reading that as a gap in the tests. The window is measured from `chapterAt(timePos)`, not from the `chapter` mirror, so the elapsed time and the chapter it belongs to cannot disagree after a seek; and the button lives **outside `.osc`** on purpose — it has to stay up while the UI is idle, which is the entire point of it. Which costs it a `z-index`: `.osc` comes later in DOM order and its scrim reaches 44 px above the controls, so an unlayered button gets the gradient washed over its top half. **How long it stays is `min(chapter length, SKIP_MAX_WINDOW)`**, bounded at both ends and never a bare constant. Longer than the few seconds it started at, because the decision to skip lands when you recognize the music rather than at the first frame, and a short window took the offer away while its reason was still on screen. Shorter than the chapter, because an offer sitting over the picture for a whole minute stops reading as an offer. And never longer than the chapter itself, so a five-second bumper cannot leave a button hanging for three times as long as the thing it offers to skip — which is also what keeps a misread title ("Introduction" on a two-hour lecture) down to a brief button rather than a permanent one. Everything the button shows about time therefore comes from the position, not from a CSS clock — the draining wash is `background-size` driven by `--skip-left`, and the tail fade is an inline `opacity`, both smoothed by a transition because `time-pos` arrives in steps. That is what lets it survive a seek into the middle of an opening (a from-mount animation would show a full bar with ten seconds left) and what makes a paused film freeze the countdown with nobody arranging it. Two shapes that were tried and are wrong: a `::before` scaled with `transform` (a transform distorts what it scales — the wash's corners flattened and its square left edge crept out from under the pill's rounded one, and it dragged in the `z-index: -1` + `isolation` pair from gotcha 9), and percentage keyframes over the whole lifetime (fine at 5 s, but they stretch a 0.2 s entrance into three seconds on a minute-long opening). On the **last** chapter the offer becomes the next queue entry, and **that entry has to be a different file** — `neighbour()` answers "what plays next", which under repeat is legitimately this one again: with a single entry and repeat-all it wraps straight back to index 0, and it does the same from a stale `playlist-pos`. Either way the credits of a lone episode grew a "Следующая серия" button that restarted what was already playing. The two questions are different — repeating one file is exactly what repeat-all on a one-entry queue *means* — so the guard belongs at the button, not in `neighbour`, and it tests both the path (against `filePath`, mpv's own answer) and the index, because those two fail in different situations. Related and the reason the stale case is not self-healing: **`playlist-pos` was missing from `resyncState`**. Every other mirror is re-read each second, so a dropped property-change event costs a tick; this one stayed wrong until something moved the playhead, and everything about neighbours — both end-screen cards, the auto-advance, this button — is computed from it.
- **The media info panel is a live readout, not a snapshot, and half of it is legitimately missing.** Every field comes from a plain `getProperty` — measured on a 4K HEVC file, `video-codec` gives the readable name ("H.265 / HEVC…") while `video-format` gives "hevc", `audio-params/channels` gives "5.1(side)" where `channel-count` gives 6, and `current-tracks/audio/lang` names the dub. **`video-bitrate` is a rolling average of recent packets**, so it is simply absent for the first seconds of a file (measured: audio had a figure while video still had none) and drifts afterwards — hence the 1 s refresh while the panel is open, and hence the average computed from `file-size / duration` next to it, which is exact and available immediately. Rows with no value are not rendered at all: which properties exist depends on the container, the codec and how long playback has run, and a column of "—" reads as breakage. Values are stored raw and formatted at render time, so a language switch relabels the units without waiting for the next refresh.
- **Picture geometry is per file, and reset only if we touched it.** `video-rotate`, `video-aspect-override` and `panscan` are global mpv options: a phone clip turned upright stays turned for the next episode, so they are reset on `file-loaded`. But only when the viewer actually used the menu (`pictureTouched`) — an unconditional reset would overwrite a `video-aspect-override` line in the user's own mpv.conf on every file. Two measured facts the menu depends on: **`video-rotate` does not change `dwidth`/`dheight`** (it is a VO-level transform, so rotating does *not* trigger `maybeFitWindow` or disturb the zoom clamp — the obvious worry is unfounded), and **an aspect override is reported as a decimal**, so `4:3` reads back as 1.333333 and the menu has to compare numerically rather than against the string it sent. Auto is any negative value; mpv's own default is -2.
- **The A–B loop is mpv's to run; ours only to mark.** Both points set means mpv loops the segment by itself — measured, playback stays inside the range and wraps without anything watching the position. Two things the marks need on our side: they read back as the **literal string `no`** when unset (asking for a double gives nothing at all), so the mirrors parse rather than cast — `Number('no')` is NaN and would read as a position; and they survive a file change, so they are cleared on load, or a segment measured in the previous episode traps playback in an unrelated stretch of the next one with no visible cause. B before A is refused rather than sent: mpv accepts the pair and then simply never loops, which reads as the feature being broken instead of the marks being the wrong way round. **mpv disarms the loop while the position is past B** and re-arms it when playback is inside the segment again, keeping the marks throughout — measured, and it is the right call for a destination but wrong for a nudge, so a *relative* seek wraps inside the segment (`wrapInAbLoop`, modulo rather than a clamp, because a loop is a circle and five seconds forward should stay five seconds). The wheel scrub is **clamped** to the segment instead, and the split is the nature of the two gestures rather than taste: fingers traveling right mean "later", so wrapping would break that correspondence and spin the picture around a short loop under a steady swipe, while a key press has no such correspondence to keep and would go dead at the edge if it clamped. Clamping is also what the scrub already does at the ends of the file, so a segment is tighter bounds rather than a new rule. Its upper bound stops a frame short of B, because landing exactly on B disarms the loop and the gesture would end by silently switching it off. Absolute gestures — a seekbar click or drag, a digit jump — deliberately keep mpv's behavior and leave; the band on the bar then goes faint, because a control that keeps drawing a loop while nothing loops is the actual bug in that situation.
- **A control's actions belong to the control, not to the list around it.** The delay stepper's reset used to be a `.menu-item` under the −/+ pill, which is correct for a list row and wrong beside a control: a menu row is full-bleed and indented to line its text up with the list, so next to a 6px-inset pill its hover highlight was a different width and started in a different place — one setting wearing two shapes, and only visible on hover. It is now a fourth cell of the same pill, `[−][value][+] │ [Сброс]`, with a hairline divider saying it belongs to the group without belonging to the stepper. Two things the move cost, both measured in a WKWebView harness against the built stylesheet rather than eyeballed. **The label had to become one word**: `Сбросить задержку` is right for a menu row and wrong for a cell — the noun is already on the section title above — and at 75px it squeezed the readout hard enough to wrap the unit onto a second line; `Сброс`/`Reset` measure 60px and 56px, and the value stays on one line. And **`padding: 0 10px` for the horizontal inset silently took the vertical padding to zero**, so the cell was 12px tall inside a 27px row and its hover read as a long thin pill rather than a button; `align-self: stretch` plus `place-items: center` makes it the row's full content height like the two glyph buttons, with the text centered by the grid instead of by a padding that would have to be kept in step with theirs. It keeps being rendered-and-disabled rather than hidden, for the reason it always was: the menu is anchored by its bottom edge, so a control appearing there would move the row the moment the delay leaves zero — right under the cursor that is clicking it.
- **The settings dialog has two control shapes, and the choice between them is about the value, not the layout.** A pill (`.segmented`) picks one of several *named* values; a slider covers a continuous range. Subtitle size is the case that forced the second one — the useful adjustment is "a bit bigger than that", which three pills cannot express. A slider fires on every pixel of the drag, so applying live is immediate while the mpv.conf write is debounced (`CONF_WRITE_MS`), with **one timer per key**: a single shared one lets a second slider cancel the first one's write. Landing exactly on mpv's own default clears the line from mpv.conf rather than pinning the default in writing, which is what "по умолчанию" means for every pill above — so the step has to divide the distance from `min` to the default exactly, or the default is unreachable and the line never clears. Values are snapped to the declared precision before being written, because a range input hands back 1.2000000000000002. Subtitle defaults worth knowing, measured on mpv 0.41 and different from what older documentation says: `sub-border-size` is **1.65**, `sub-border-style` is `outline-and-shadow` (`background-box` is the readable-on-bright-frames alternative), and **`sub-ass-override` already defaults to `scale`** — so `sub-scale` and `sub-pos` reach ASS subtitles without forcing anything, which is the usual reason this feature disappoints in other players.
- **Volume leveling is a labeled `af` filter, and its state is ours.** `af add @fpnorm:lavfi=[dynaudnorm=…]` / `af remove @fpnorm` — the label is what lets it be removed again without touching an `af` line from the user's own mpv.conf, and it is also why this setting is the one playback option kept in localStorage instead of written there: `mpv_conf_set` replaces the last uncommented line of a key, and for `af` that would silently eat someone's filter chain. Reading the state back is not an option either — measured, `af` answers with its own escaping (`@fpnorm:lavfi=graph=%27%dynaudnorm=f=250:g=15:p=0.9`), so ours is the record, exactly as with the repeat mode. It is disabled while `audio-spdif` is on and says so: bitstreaming hands the receiver an undecoded stream and a filter has nothing to attach to, so the honest thing is to explain rather than quietly do nothing. **mpv lists a device once per audio output that can reach it**, so the picker showed every speaker two or three times with nothing to tell the copies apart: the macOS build carries `coreaudio`, `coreaudio_exclusive` and `avfoundation` (verified in the bundled libmpv), and only the `name` prefix differs — the `description` is identical. Deduplicated by description, first entry wins, which is mpv's preferred output; the cost is exclusive mode, which cannot be labeled here without inventing jargon and belongs in mpv.conf anyway. Worth knowing when a device's name looks wrong rather than duplicated: **the description is CoreAudio's, not the speaker's**. macOS exposes AirPlay as a single virtual device literally called "AirPlay", and which speaker it streams to is chosen above that layer, in the system output menu — so a JBL on AirPlay legitimately appears as "AirPlay" here and in every other app that enumerates CoreAudio devices. **`audio-device-list` needs no native code**, contrary to what the roadmap assumed — like every list in mpv it answers to `count` and `N/name`, `N/description`, so `readList()` covers it; the list is read when the dialog opens, since mpv builds it lazily on first read and there is nothing to keep fresh while the dialog is shut. Its first entry is `auto`, which is also mpv's default, so it maps to `null` and choosing it clears the mpv.conf line.
- **`hwdec-current` is shown in the settings footer** — a silent fallback to software decoding is otherwise invisible and is the first thing to check when seeking feels slow.
- **Everything the player needs at runtime is bundled; yt-dlp is the single exception.** `src-tauri/lib` carries libmpv, the wrapper and every transitive dependency (~65 MB and ~50 dylibs on macOS: FFmpeg, libass, libplacebo, MoltenVK, LuaJIT, x264/x265, OpenSSL…; on Windows `libmpv-2.dll` plus the FFmpeg SDK in `src-tauri/ffmpeg`, both fetched by `scripts/fetch-libs.ps1`). `build.rs` lays them out next to the dev exe and declares two rpaths — `@executable_path/lib` for dev and `@executable_path/../Resources/lib` for inside a `.app` — and `bundle.resources` puts them in the installer. So nothing is taken from the user's system: a machine with no Homebrew and no FFmpeg runs the player. **Nothing may block `init(mpvConfig)`** — whatever waits there holds up the whole window, and until mpv is up a click on a file does nothing at all, which reads as a dead player rather than a slow one. The lesson cost a session: the yt-dlp probe ran `yt-dlp --version` to prove the binary worked, and that call takes **11 seconds** on a macOS universal build (a 36 MB PyInstaller bundle that unpacks itself and is re-verified by the system on every exec) — twice over, before init, so the player ignored roughly the first twenty seconds of clicks. The probe now only *looks* (file present, executable bit set) and is not awaited; a broken binary is caught where it matters, when a link fails and the dialog offers to install or update. **yt-dlp alone is looked up at runtime** and is optional by design — without it, local files and direct links still work and only websites do not, which the link dialog says. It can also be installed from that dialog, into `<app_data>/bin` — the only place we may overwrite afterwards, since Program Files needs administrator rights and a binary inside a `.app` cannot be replaced without invalidating the signature. **Keeping it current is yt-dlp's own job, not ours**: `-U` fetches the release, checks it against the signed checksums published with it and replaces the binary in place, so writing a downloader would mean reimplementing verification that already exists and is maintained by people shipping it every few weeks. We only fetch the *first* copy. The update button appears **only for the copy we installed** (`managed`) — a Homebrew or pip install belongs to its package manager, where `-U` either refuses or starts a fight. Expect staleness rather than absence to be the failure: a September 2025 build already fails on YouTube, so a failed link reopens the dialog with that explanation and the button, instead of a popup that fades before it can be acted on. **macOS ships too, and `bundle.targets: ["nsis"]` in tauri.conf.json is only half the story**: `tauri.macos.conf.json` overrides it to `["app"]` and is what `npm run tauri:macos:build` (and CI) uses. The release workflow builds the `.app`, then packages the dmg in a step of its own — Tauri's `bundle_dmg.sh` drives Finder over AppleScript to place the icons, which a headless runner has no session for, so it passes silently and ships an image with no `.DS_Store` that opens as a plain folder; `dmgbuild` writes one directly. **The macOS build is signed with a Developer ID and notarised, and the two things that decide are the hardened runtime's, not Apple's paperwork.** The chain is `macos-sign.sh` (imports the certificate, signs the 35 dylibs and the ffmpeg CLI) → `tauri build` → `macos-notarize.sh` on the `.app` → `build-dmg.sh` → `macos-notarize.sh` on the image, and the order is load-bearing at both ends. The libraries are signed **before** the build because they reach the bundle as `bundle.resources`, i.e. copied in carrying whatever they already had — the ad-hoc signature `bundle-macos-libs.sh` applies after rewriting their load commands — and an ad-hoc Mach-O anywhere inside fails notarisation on identity; signing them inside the built `.app` instead would break its seal and force the image and the updater archive to be rebuilt. At the other end, `macos-notarize.sh` **repacks `.app.tar.gz`**, because Tauri writes it during the build, i.e. before the ticket exists — ship it unrepacked and the disk image is notarised while every automatic update carries an unstapled bundle, which is the failure that only reaches existing users. Two entitlement facts, both measured against a probe that loads the bundled libmpv with `zoompan.lua` under each signature (LuaJIT 2.1 is what `zoompan.lua` runs on): **`com.apple.security.cs.allow-jit` does not work** — it authorises `MAP_JIT`, which this LuaJIT does not use, and the process dies with `EXC_BAD_ACCESS`, "Invalid Page", faulting inside a private `r-x` `VM_ALLOCATE` region — while `allow-unsigned-executable-memory` alone does, so that is the file's single entry. And **the hardened runtime is only turned on when there is a real certificate** (`macos-build.sh`), because it enables library validation, which requires every dylib to carry the process's Team ID: with a Developer ID that is free, and ad-hoc code has no Team ID at all, so the ad-hoc fallback dies at launch on `Library not loaded: @rpath/libavutil.60.dylib … (non-platform) have different Team IDs`. Three traps around that. `hardenedRuntime: false` **does not turn it off on its own** — measured on CLI 2.11.4, a config naming an entitlements file is signed `--options runtime` regardless, so the override has to clear `entitlements` too (verified it is the bundler and not codesign: `codesign --entitlements … --sign -` without `--options runtime` gives a plain `0x2(adhoc)`). A probe that `dlopen`s the libraries survives all of this, so **testing the library set in isolation proves nothing about the bundle** — only launching it does. And `codesign --verify --deep --strict` passes on the broken bundle in silence; the symptom is a crash dialog offering to report to Apple. The ad-hoc path is still exactly what shipped for the first thirty releases and is what a checkout with no Apple account produces: sealed but uncertified, which Gatekeeper stops with an **Open Anyway** button rather than the *"file is damaged"* dead end that an unsealed binary gets.
- **A slow operation must say so before it starts, not after it finishes.** Two places had the same silence. Opening a URL sits on a black window for as long as yt-dlp takes to resolve the page and the stream takes to buffer, with nothing to show it is alive — hence the `opening` indicator, raised in `beforeLoad` for a network source only (a local file opens faster than it would fade in) and dropped on `file-loaded`. It reports a real figure rather than a guess: mpv's `cache-buffering-state` is the cache fill, and it is **absent while there is no cache yet**, which means "still resolving" and not "0 %"; `paused-for-cache` is playback stalled on the network as opposed to on the viewer. And saving or copying a frame is a second of PNG encoding on mpv's own thread on a 4K file, which used to pass in silence — the menu closed and nothing happened, which reads as a click that missed. Both now announce first, which is what `sticky` on `showOsd` is for: a popup that fades halfway through says the work finished, and finishing is the one thing that has not happened. Anything raising a sticky popup owes it a replacement on every exit path.
- **An `end-file` error is not a failed attempt.** mpv's ytdl hook raises one on the way to succeeding — it opens the URL, gives up on it and loads what yt-dlp resolved instead — and playlist transitions do the same. Reporting on the event threw an error dialog over videos that were about to play, which is worse than saying nothing. The verdict now waits `LOAD_FAIL_GRACE` and `onFileLoaded` cancels it: if anything opened, whatever failed on the way was a step and not an outcome.
- **No storyboard means no space for one.** With thumbnails gated for streams the hover popup was still reserving its 180px frame and filling it gray, which reads as a preview that broke rather than one that was never coming. The popup drops the frame entirely for a network source and shows the timestamp alone (and the end-of-file cards, which cannot decode a poster out of a URL either, put a link mark where the frame would be rather than an empty outlined rectangle) — and `hoverX`, whose clamp is half the popup's width, has to narrow with it or a bare timestamp stops following the cursor well before either end of the bar. What could bring previews back for YouTube specifically is its own storyboard sprites, which yt-dlp exposes as `sb0`/`sb1` formats; that is a feature, not a fix. The other half of the complaint — slow seeking — has one real lever, and it is `ytdl-format`: the hook's default takes the best available stream, so a 4K one is what every seek then pays for. Hence the quality setting.
- **A torrent is a network source that steers itself, and both halves of that are the design.** A magnet becomes a list of files, each served from our own loopback HTTP server at `/t/<infohash>/<index>/<name>`; mpv opens that URL and its Range requests are the "the viewer is here" signal librqbit turns into piece priority. **The identity lives in the path, never the port** — `sourceId()` reads `torrent:<hash>/<index>` straight back out (`parseTorrentUrl` in source.ts, matched to `stream_url` in torrent.rs by a test at each end), because the port is ephemeral and a key taken from the transport forgets the film every session. The trailing file name is load-bearing too: it gives ffmpeg an extension to probe by, and it is why `displayName` now percent-decodes — without that an ordinary film reads as `The%20Movie%202024`. **Nothing is downloaded until it is read**: the torrent is added *paused with nothing selected* and the HTTP handler itself puts a file into `only_files` and unpauses when a request for it arrives, which is the same principle as piece priority one level up. **"Nothing selected" has to be said explicitly — `only_files: Some(vec![])`, never left unset.** librqbit reads an absent selection as "everything" and stretches every file of the torrent to its full length (`set_len`) at the end of initialization; on APFS and ext4 that is free, but **NTFS has no sparse file unless somebody calls `FSCTL_SET_SPARSE`, and librqbit never does**, so on Windows a nine-episode season occupied all of itself from the first open with two episodes fetched — reported, correctly, as "the empty files take up space". An empty selection is legal (`compute_only_files` only range-checks the indices) and costs nothing later, because `update_only_files` — which `select` already calls — does not preallocate at all: the file grows as pieces are written. It also gives `torrent_offline_file` back a signal it had lost, since that gate compares the file's length against the torrent's and everything was full length, which on Windows (where the allocated size *is* the length) made an untouched file indistinguishable from a finished one. `an_unopened_torrent_allocates_nothing` pins it, and **has to wait out `Initializing` to do so**: `add` returns before the preallocation happens, so a check made straight after it passes whatever `only_files` says — which is how the first version of that test came to pass against the unfixed code. That is what makes a twelve-episode torrent a twelve-entry queue costing nothing but the episode playing — `queueTorrent` hands mpv every video's URL, and a URL is only a string. The session is **lazy** for the same reason the yt-dlp probe stopped blocking init: a player that joins the DHT on startup is not one people keep. **Opening an episode already on disk costs nothing, and getting there took two separate fixes.** First, `select` returns early when `file_complete` — initialization has just verified the pieces, and `stream()` reads from a *paused* torrent perfectly well (it only blocks on a missing piece), so a rewatch makes **zero peer connections**; librqbit's own `maybe_reconnect_needed_peers_for_file` already declines to reconnect for a finished file, so nothing fights this. Second, and bigger: **a magnet opened once is never resolved again.** librqbit used to run with `persistence: None`, forgetting the torrent between runs and going back to the DHT every time — measured at 1.5–10 s — even to reopen a season sitting on disk. The metadata *is* the torrent file, so it is cached at `<cache>/torrents/.meta/<infohash>.torrent` and replayed through `AddTorrent::from_bytes`; a corrupt or stale one falls back to the magnet rather than making the torrent unopenable. Measured on the same torrent back to back: resolve **1.52 s → 4.45 ms**, and a re-read of an already-fetched region **1.20 s → 0.8 ms**. Both are pinned by `complete_file_needs_no_swarm`, which builds a torrent from a local file with `create_torrent`, seeds the cache and the folder by hand, and asserts the served bytes plus `state == "paused"` — **fully offline**, so it runs in an ordinary `cargo test` and catches a reordering of `select` that would quietly start the swarm. **Piece re-verification is skipped too, and that took measuring the fear rather than accepting it.** Without `fastresume` librqbit hashes the *whole torrent* on every open — holes included, since at the time the files were all created at full length — so reopening a 7.5 GB season with 46 MB fetched cost **3208 ms**, and that grows with the torrent rather than with what was watched (hashing measures ~2.3 GB/s here). `fastresume` needs `persistence`, which was refused on the grounds that it resumes torrents at startup; measured, three of the four worries were unfounded. The stored metadata is written as a separate `.torrent` file and read back, so restoring costs **no DHT lookup**. Data deleted behind our back is caught rather than trusted — librqbit reports 0 bytes held and a read blocks for pieces, instead of quietly serving the zeros a sparse file gives back. Session creation with a torrent in the store is 21 ms. The one real risk is that **a torrent recorded as running is restored running**, which would talk to peers for something nobody asked to watch — so `pause_restored` stops everything the session brought back, and it has to **wait out `Initializing` first**, because librqbit refuses to pause a torrent in that state and the moment initialization ends it would go live. Result on the same season: 3208 ms → **2.38 ms**. Two bugs fell out of enabling it, both of which would have bitten in the app: librqbit does **not** create the persistence folder, and without it every torrent fails its initial check with "error storing initial check bitfield"; and the DHT's own state file pins the port it bound and rebinds it next time, so tearing the session down and building another — which the **seeding switch does** — hit "address already in use" and left the player unable to open anything until a restart. `disable_dht_persistence` settles that and, as a bonus, stops librqbit writing to `com.rqbit.dht` in the OS cache root, outside the directory this feature can be cleared from.
- **Windows kills the stock DHT, and the tracker was never a backup — two librqbit bugs whose combination left Windows with no peer source at all.** The symptom read as a network problem (magnet never resolves; a `.torrent` lists its files but playback sits on "Connecting to the swarm… / No peers" while qBittorrent on the same machine finds 150 seeds in seconds) and the network was fine. Upstream librqbit-dht's UDP reader dies on the **first** `recv_from` error — permanently, for the life of the session, i.e. of the app — and Windows produces such errors in normal operation, which Unix never does: **WSAECONNRESET (10054)** when any of the thousands of DHT nodes contacted turns out dead and its ICMP "port unreachable" comes back (an error about one datagram, not the socket — libtorrent suppresses it with `SIO_UDP_CONNRESET`), and **WSAEMSGSIZE (10040)** when a node's datagram exceeds the 16 KB read buffer (Unix truncates silently). Both were caught live here; the stock DHT died 89 s into a session with `framer quit … os error 10054`, timing a lottery decided by the first dead node to answer. That alone should have degraded, not killed — except the fallback source was also broken: the HTTP announce **replaces** the URL's own query (`Url::set_query`), so a tracker announce path carrying its own query (`/ann?magnet`, a passkey) loses its marker and answers **403**, and with no listener the announce says `port=0`, which trackers refuse outright ("Port can't be 0"). macOS never noticed any of this because a live DHT carries a popular swarm by itself — which is why the fix is three-legged and the first leg is the only Windows-specific one: vendored `librqbit-dht` tolerates recv errors (log + continue, fatal only after 100 *consecutive* — the behavior librqbit's own UDP tracker client already has), vendored `librqbit-tracker-comms` re-appends the announce URL's original query, and `listen_port_range` gives announces a real port (which also lets NAT-ed home seeds connect inward; UPnP stays off on purpose). Verified with a probe on the failing machine: stock — resolve works only while the DHT happens to be alive, dead by 90 s; patched — two recv errors absorbed, and a fresh magnet still resolves in under a second 2.5 minutes into the session. Neither fix exists upstream in any 8.x-compatible release (the query fix is 9.0-rc-only, the recv fix nowhere as of 9.0.0-rc.0), hence `src-tauri/vendor/` + `[patch.crates-io]` — see vendor/README.md before touching those crates or bumping librqbit. Worth knowing while debugging any of this: peers from such swarms often cut plaintext BitTorrent handshakes mid-stream (DPI on Russian ISPs; the fix would be MSE encryption, which no rqbit version implements — that is what qBittorrent has and we do not), so expect some handshake noise in logs even when everything works.
- **The HTTP announce was dead on every platform, and the DHT hid it.** Two more vendored fixes, found together and each fatal on its own. **reqwest sends no `User-Agent` at all** by default, and the WAF trackers sit behind refuses such a request outright — measured against one such tracker with a byte-identical query, **403 without the header, 200 with it**, and the value is irrelevant (a single letter passes); presence is the whole requirement. And **`complete`/`incomplete` are required fields** in librqbit's `TrackerResponse` while real trackers omit them — one such tracker answers `d8:intervali3595e12:min intervali3595e5:peers180:…e` and nothing more — so even a 200 failed to deserialize and **every peer in it was discarded**. Both failures are invisible from outside: the announce is a clean HTTP exchange, the error is one level below it, and the torrent merely says "connecting to the swarm". What made them survive so long is that **the DHT covers for the tracker until it doesn't**: two releases of the same film from one tracker, one with 24 seeders that would not fetch a byte in five minutes and one at 3 MB/s, and the difference was entirely whose DHT records were fresh — the working one's peers all came from the DHT, and the broken one's DHT entries were the same IPs on stale ports (`66.56.80.137` at eight different ones, none of them the port the tracker gave). So the lesson is the diagnosis, not the fix: **a torrent that will not download is a question about where its peers came from**, which is what `swarm_probe` exists to answer — peers *seen* against peers *live* against bytes, plus per-peer attempt/error counters. Peers seen but never live means the addresses are wrong (i.e. no tracker), not that the swarm is dead. Verified end to end on the failing magnet: seen 22 → 44, live 0 → 5, and 0 B/s → ~800 KB/s with the first megabyte read in 8 s. **A third leg was hiding behind those two, and it is ours rather than the vendored client's**: a torrent is added *paused*, and upstream ties the announced **port** to whether the torrent is started (`make_peer_rx` passes `None` unless it is), so the announce that fetches a magnet's metadata goes out as `port=0` — which a tracker reads as "cannot accept connections" and answers accordingly. Measured on one info hash: **1 peer from port 0 against 26 from a real one**. Adding paused is not negotiable (it is what makes "what is in this torrent" cost no download), so metadata was left to the DHT alone, and a torrent whose DHT records have gone stale then never resolved at all — three fresh opens of that same 24-seeder release, three 90-second timeouts. Fixed without forking librqbit: `announce_peers` asks the magnet's own HTTP trackers once, directly, and hands the addresses over as `initial_peers`. Resolve went **90 s (timeout) → 0.9 s**. It is a head start and never a prerequisite — a tracker that fails, times out or is UDP-only costs nothing, since the DHT is running regardless (Sintel, whose magnet carries only UDP trackers, is unaffected and is the control for that). Its response is *scanned* for the `peers` field rather than deserialized, deliberately: a strict parser is precisely what caused the bug above, so the length being a non-zero multiple of six is the only check, and anything else degrades to "no peers" rather than to wrong addresses.
- **A torrent arrives three ways, and a `.torrent` file is not a file the player opens.** A magnet is pasted, a `.torrent` URL is pasted, and a `.torrent` **file** is dropped or picked — and only the first two fit a box that takes text, which is why torrent support was invisible in a dialog called "Открыть ссылку". Three things make the file first-class. `AddTorrent::Url` understands `http:`, `https:` and `magnet:` **and nothing else** (a local path reaches it as "provided path is not a valid magnet URL"), so `add` reads the bytes itself and goes through `AddTorrent::from_bytes` — and since a `.torrent` file *is* the metadata, `librqbit::torrent_from_bytes` gives the info hash locally, which means the hash-named folder, the metadata cache and the history all work exactly as for a magnet. A `.torrent` URL is now the only source left with no hash to read. Classification happens **in `loadFiles`**, where a drop is already sorted by extension, rather than at each of the four entry points (drop, picker, argv, the Apple Event) — reached through an `openTorrentFile` hook, because player.svelte.ts must not know that a torrent client exists; and only when nothing else in the drop is playable, since a folder holding both a film and its `.torrent` should play the film. **What gets remembered is a magnet built from the hash, never the path** (`magnetFor` in source.ts): a `.torrent` file is thrown away after use and a tracker page can go down, while the info hash plus the metadata cache reopens the torrent with no lookup at all — so a file opened once keeps working after it is deleted. One consequence worth keeping in mind: `openTorrent` is now reached with **no dialog open**, so its failure path raises one, or a corrupt file would fail in complete silence. The file association is deliberately **not** declared in tauri.conf — claiming `.torrent` system-wide would take it from whatever BitTorrent client the machine has, which is not a video player's to do. **The box surviving a close and the box being reopened are different events**, and conflating them is what left the previous link typed in it: the text and its error line are kept on purpose, because a link that fails reopens the dialog with both — that is what makes the yt-dlp button usable — but those paths raise the dialog themselves and never go through `openLinkDialog`, which is somebody choosing to open a link and therefore clears all three. Finding the last magnet still there is wrong twice over: it has to be deleted by hand before anything can be pasted, and **the recents list is hidden while the field is non-empty**, so the one place the previous links are offered disappears with it. A torrent that resolves into a file picker closes the box for the same reason a single-file one does (`playTorrentFile` always did); left open it sits *under* the picker and comes back when the picker is dismissed.
**A freshly added torrent is not ready to be touched, and the order of the three steps is load-bearing**: `add_torrent` returns while the torrent is still `Initializing` (checking and allocating files on disk, which scales with the size of the *torrent*, not of the file being watched), and in that state librqbit refuses `update_only_files` outright ("can't update initializing torrent") while `stream()` accepts only `Paused` or `Live`. So it is wait → select → unpause → wait again, with the lock dropped across each wait or every parallel connection ffmpeg opens serializes behind it. On Sintel (129 MB, one file) that window is too short to see; on a nine-episode 7.5 GB season it swallowed the whole of playback. It cost a diagnosis only because the handler answered a bare **404** for every failure, which reads as "no such file" — hence the reason is now logged and a not-ready answers **503**, since the two are different facts and a torrent that plays on small releases and dies on large ones is otherwise indistinguishable from a broken URL. Three things fell out for free because a stream is `http://127.0.0.1:…`: `isNetworkSource` already gated the storyboard (the collision the roadmap warned would be discovered late), the posters and the folder queue. What is **not** solved is the seek: a cold jump costs *downloading*, so the measured seek contract below does not apply, and there is no map of what is buffered — librqbit keeps the piece bitmap behind `pub(crate) with_chunk_tracker` and the finest public measure is `TorrentStats::file_progress`, a percentage. Measured against the live Sintel swarm (the analysis's spike #1, kept as `sintel_smoke`): magnet → file list **10.0 s**, first byte of a tail range **7.9 s**, a cold seek into the middle **1.3 s**, 13 peers at 664 KB/s. Which is why a torrent stall must say *why* — peers and rate under the label — since mpv's own answer is `paused-for-cache` and nothing more, and "no peers" and "slow swarm" are different problems that must not look the same.
- **Seeding is off by default, and the switch has to be able to stop it *now*.** In Germany and several other jurisdictions the exposure from uploading is categorically worse than from downloading, so a player must not opt anyone into it silently. The mechanism is librqbit's `disable-upload`, which is a **compile-time feature unlocking a runtime flag** — without the feature there is no way to stop seeding at all, since `LimitsConfig.upload_bps` is a `NonZeroU32` and cannot even express zero. What it does is thorough rather than a rate limit: no bitfield, no `have` messages (peers are never told what we hold), piece requests refused outright, peers dropped once the file is complete. What it does **not** do, and the settings hint says so, is make the client invisible — finding peers means announcing to trackers and the DHT, so membership of the swarm is still observable. The flag is baked into the session when it is built, so changing the preference **tears the session down and rebuilds it**, which costs the running torrent; that is the honest trade, because a switch reading "off" while pieces are still going out would be a lie about the one behavior here with legal weight attached.
- **Peer count has exactly one large lever, and it is not the one that suggests itself.** One private tracker's swarm was probed one address at a time, and the failures separate cleanly: of ~30 peers the tracker handed out, **20–22 never answered a SYN**, 5 completed a handshake, 2–3 refused the connection outright, and exactly **1** showed the mid-handshake cut that means DPI. So this is NAT, not filtering and not a dead swarm — those twenty can only ever be reached if *they* dial *us*. Four things that look like levers were measured and are worth nothing here, which is the more useful half of the result because each is the obvious next idea: **public trackers** know 0–1 extra peers for a tracker-exclusive release (opentrackr, demonii, torrent.eu.org, stealth.si, exodus, nyaa — so `SessionOptions.trackers` stays empty, and the privacy cost of announcing to strangers buys nothing); **`numwant`** changes nothing, the tracker caps at ~25–30 whatever is asked for; **IPv6** is moot, the tracker sends no `peers6` field at all; and **PEX** already runs (librqbit enables `ut_pex` for any non-`private` torrent — visible as `seen` growing past what the tracker gave). Hence `enable_upnp_port_forwarding`, **opt-in and off by default**, because it is the one setting here that changes the *machine* rather than the app: it makes a port reachable from the internet for as long as a torrent is open. It helps even with seeding off, which is the counter-intuitive part — a seed serves us whether or not we serve anyone, so reachability is about who can *start* a connection. The flag is baked into the session exactly like `disable_upload`, so both directions of the switch cost the running torrent (`rebuild_if` is the shared mechanism). **And the switch reports what the router said, not what it asked for**: librqbit's forwarder is a `run_forever` task that tells nobody whether it worked, and a router with UPnP disabled swallows the request in silence — so `upnp.rs` finds the gateway and asks it for the mapping, and "on" and "working" stay two different things on screen. Two traps in reading that answer: UPnP error **714 is the answer, not a failure** (`NoSuchEntryInArray` is how a gateway says "nothing is mapped there", and treating it as an error reports a working router as an absent one); and on macOS an empty search is **ambiguous** — a router without UPnP and a refused Local Network permission look identical from here — hence the log line, and hence the fact that this path cannot be tested from a CLI at all (multicast from a terminal process is dropped, the same reason `FP_DLNA_PROBE` has to run inside the app).
- **A finished episode leaves no trace, so the torrent store keeps its own record of them.** `frameplayer.positions` *deletes* an entry past `FINISHED_FRACTION` — which is what takes a film out of "continue watching" — so a watched file is indistinguishable from one never opened, and neither "delete the ones I have seen" nor a mark in the file picker can be built on it. Hence `watched: string[]` on the `frameplayer.torrents` entry, by **file name** rather than index (an uploader who inserts an episode renumbers everything after it, the same reason positions are re-keyed by name when a torrent is superseded). It is written from the **status poll** rather than from `persistPosition`, and that is the dependency direction rather than convenience: the position store must not know what a torrent is, while the poll already holds the info hash, the index and the playhead, and ticks once a second for exactly as long as a torrent is playing. `rememberTorrent` runs on *every* open, so it has to carry the list forward — dropping it would forget every watched episode each time the season was reopened, in silence. Deleting them is `torrent_forget_files`, which prunes rather than forgets: the folder, its `.meta` and the magnet all stay, so the torrent reopens for nothing and the kept episodes play at once. **It is safe only because of `validate_fastresume`** — librqbit verifies at least one piece of every file its resume data claims plus a random sample, and one failure throws the whole bitfield away, so a file removed behind its back cannot be served as zeros; the price is one re-check on the next open (~3.2 s for a 7.5 GB season). The order is load-bearing: the torrent leaves the session *before* anything is unlinked, since on Windows an open file cannot be deleted and on macOS it can, which is worse — librqbit keeps writing through a handle to a file with no name. Matching is by file name **against what is already inside the folder**, so nothing is joined onto a path and no name can escape. And the store itself joined `IDENTIFIED_STORES` in the process: it had never been in it, so "forget everything" left behind a magnet for every torrent ever opened — which names what was watched as plainly as a position does.
- **Once the viewer can choose where torrents are written, "the torrent directory" is three questions, and answering them with one path is how a video player deletes somebody's films.** `Dirs` keeps them apart. **`state`** is ours unconditionally — the metadata cache, librqbit's session store and the record of the roots — and stays in the app cache directory whatever is chosen, which keeps the chosen folder pure video, leaves `prune_orphaned_store` and the clear-cache button pointed where they always were, and means a removable drive going missing costs data and not the player's bookkeeping. **`root`** is where *new* torrents go. **`roots`** is everywhere data may already be — the current root, every root used before it, and `state` — because changing the setting must not orphan a season downloaded last week: lookups scan all of them and **nothing is ever moved by a change of setting**. The dangerous half is what may be *deleted*, and `is_ours` is the single rule: inside `state` the answer is yes for anything (the player owns that directory, and a folder from the older name-based layout has to stay deletable), anywhere else the folder name must parse back to an info hash. It is enforced in Rust in front of every destructive path rather than in the UI — `list` skips what it does not recognise (not even measuring it: walking somebody's media drive to print a number is its own kind of rude), `forget` takes a **path** and refuses one whose parent is not a known root, and `torrent_clear_cache` — which used to remove *every entry it found*, correct while the directory was ours alone — now removes only recognised folders, sweeping loose files in `state` and nowhere else. Roots are compared with `same_dir`, i.e. canonicalised, so a symlinked home (which macOS hands out routinely) is one directory rather than two, and a path that cannot be canonicalised is refused rather than guessed at. Two consequences elsewhere: `relocate` renames **beside the folder it replaces** rather than into the current root, since `fs::rename` does not cross a volume and the two may now be different ones; and the chosen root is recorded in a dot-file beside the state rather than in localStorage, because commands can arrive before the frontend has said anything and a preference that is only sometimes in effect would put files in two places. `a_chosen_root_protects_what_it_did_not_create` is the test that matters — it points every destructive path at a directory holding somebody's films and proves they survive.
- **The torrent's folder carries its info hash, and disk is the source of truth for storage.** `ManagedTorrentOptions.output_folder` is `pub(crate)`, so a folder named after the torrent alone could never be *read back* and the mapping from torrent to directory would have to be guessed — hence the name is ours to compose and it always ends in the hash: `<cache>/torrents/<Name> [<infohash>]`, parsed back by `folder_hash` and resolved by `folder_for`, which **prefers whatever folder already exists** so nothing on disk is moved by an upgrade. A side file mapping hash to directory would answer the same question and be a second source of truth to keep in step with the filesystem — a rename, a half-written index or a folder restored from a backup puts the two out of agreement, and the failure is either a torrent that cannot be found or a delete aimed at the wrong path. `sanitize_name` is what a torrent name has to survive first, and every rule in it is Windows': the forbidden characters, **reserved device names** (`AUX`, `com1.2026` — the *stem* is what makes a name reserved, so the escape goes at the end of the stem and not of the name, which is where it was first written and achieved nothing), a **trailing dot or space** (silently dropped by Win32 after the folder is created, so every path built afterwards misses it), and a length cap cut on a **character** boundary, since a byte-wise cut leaves a Cyrillic name invalid UTF-8. Brackets are stripped from the name too, or a release called `Show [1080p]` makes its own suffix unparseable. A folder that is a bare hash is renamed the first time `add` can read a name for it — one torrent at a time, at the moment it is opened, rather than a sweep over the whole cache at startup — and that rename **must not happen under a live torrent**: on Windows the files are open and it fails, on macOS it succeeds and leaves librqbit writing through handles to a path that no longer exists, so the torrent leaves the session first. It costs `fastresume` (the store entry goes with it) and therefore one re-hash of what is on disk, ~3.2 s for a 7.5 GB season, once per torrent ever; a failed rename costs nothing, since `folder_for` finds the old folder by hash regardless. **The name is only knowable before the add because the metadata is fetched first** — `list_only` resolves a magnet and returns before any storage is created, so `add` now goes: bytes (a `.torrent` file, our `.meta` cache, or one `list_only` lookup) → cache them → name the folder → add from those bytes, which reaches no network at all. The hash comes from `Magnet::parse` (no network) rather than a `list_only` resolve, which would double a ten-second DHT lookup. `torrent_list` reads the directory and never consults our records, so a folder from a previous run or the older layout is still visible and deletable — storage management keeps working with history off, and the remembered magnets only add the ability to *reopen*. **Size must be measured in allocated blocks, not `len()`**: librqbit creates every file at full size up front and APFS/ext4 make them sparse, so a nine-episode season with one episode part-fetched reports **7.45 GB** by length and **142 MB** by blocks (verified against `du` to the byte). Reporting the length would tell the viewer to delete something to reclaim space that was never taken. Windows keeps `len()` — NTFS needs an explicit `FSCTL_SET_SPARSE` that librqbit never asks for. **"In the session" is not "playing right now", and `torrent_list` must not answer the second.** It used to: the row's `active` flag was session membership, and since `release` *pauses* rather than removes (the pieces stay, so re-opening continues), a torrent stayed in the session for the rest of the run — so returning to the start screen found its delete button disabled and labeled "сейчас проигрывается", permanently, from the moment anything had been watched. Deleting a merely-loaded torrent is safe anyway, because `forget` takes it out of the session *before* removing the directory. So the flag left Rust entirely and became `torrentIsPlaying(row)`, read from `parseTorrentUrl(player.filePath)` — **not** from `torrent.info`, which is set when a magnet resolves and would still claim to be playing after the file picker was canceled — and it is a **function, not a field of the row**, because the list is fetched ~300 ms after the file is unloaded and a snapshot taken there is how a button gets stuck disabled. **A row also names itself from the disk, because our record of it is not where the truth lives.** The name and the magnet are in `frameplayer.torrents`, i.e. in *localStorage*, which is per webview, while the data directory is per identifier — so two builds of the player (a `.app` and an unbundled dev binary, which WKWebView files under the executable name) share every byte on disk and neither one's store, and a season downloaded by one showed up in the other as "Раздача без названия · ссылка не сохранена" with a dead button. The cure is that everything needed is already beside the data: `cached_name` reads the torrent's own name out of `.meta/<hash>.torrent` (measured warm on a 227 KB file: **0.16 ms**, and the parse borrows rather than copies), and `listTorrents` builds the magnet from the folder's own info hash when nothing was remembered — which reopens with **no lookup at all**, since that same metadata is what `add` resolves from. Opening such a row records it, so it is nameless once and never again. `start.torrent_unknown` now belongs to folders from the older name-based layout alone.
- **A deleted torrent used to come back, one per restart, as an empty copy of itself.** `torrent_forget` removed the directory and our record, but took the torrent out of librqbit's own store only when it was in `inner.torrents` — which `add` alone fills, so it covered a torrent opened *in that run* and nothing else. Everything else on disk is in the session only because it was **restored**, and a restore recreates the folder: `Initializing` calls `FileStorage::init`, which is `create_dir_all` plus `create(true)` on every file, with `ensure_file_length` giving the `only_files` entries their full length back. So the next session rebuilt the folder, the magnet was gone with the record, and the start screen grew a nameless 0 MB row — 0 MB because `dir_size` counts allocated blocks and nothing had been downloaded into the resurrection. Two halves, both needed: `forget` now deletes **by hash** (`Session::delete` resolves one against its own db, restored torrents included) and removes the cached metadata with it, and `prune_orphaned_store` drops entries whose `output_folder` is gone **before** the session is built — which is the only moment it can, and the half that also covers the common case where there is no session at all (it is lazy, and deleting from the start screen rarely follows opening something), plus `torrent_clear_cache` and a viewer emptying the folder in Finder. It reads the store as plain JSON, since librqbit's types are private, and leaves anything unparseable exactly as it is: the cost of skipping is a ghost row, the cost of guessing wrong is somebody's downloaded season. Both halves are pinned by tests that fail without them (`deleted_torrent_does_not_come_back`, `forget_removes_a_restored_torrent_from_the_store`), and both run offline against a torrent built on the spot.
- **Opening from the history must give back the queue as well as the file.** A local file gets it for free (`loadFiles` builds the folder queue through `filesOpened`), but a torrent episode did not: `resolveTorrentFile` handed back one URL and dropped the file list, so the same episode had a next episode when opened from the torrent list and none when opened from the history — one behavior per entry point, invisible from outside. It now returns the torrent with the URL and `openRecent` queues the season. Related and the reason the folder case can fail the same way silently: `samePath` is separator-insensitive as well as case-insensitive, because the two sides come from different places (a stored record or mpv's `path` against a directory read in Rust) and on Windows one mixed `E:/Videos\ep1.mkv` costs the whole queue — `findIndex` answers −1 and `queueAround` returns without a word. That return now logs what disagreed. **A torrent entry in the watch history cannot be reopened from what it stores.** Its `src` is a loopback URL and the port died with the session that issued it, so every torrent card led to a refused connection after a restart — the problem `sourceId` solves for the *key* showing up again one layer higher, in the thing you actually open. `RecentItem` therefore carries `id` beside `path`, and `openRecent` sends anything `torrent:`-shaped through `resolveTorrentFile`, which re-resolves the remembered magnet. That store (`frameplayer.torrents`, privacy-gated like positions — a magnet names what is being watched) is also what puts a **torrent list on the start screen**, and the unit there is deliberately the *torrent*, not the file: the grid above already holds individual episodes with positions, while a torrent's never-started episodes have no representation anywhere else, so one row per torrent is how you get back into a season without the magnet rather than a duplicate of the grid. It is styled as compact rows rather than poster cards for the same reason — a second grid would compete with the first and turn the start screen into a download manager, which the roadmap is explicit this player is not. **Clicking a row resumes rather than asking**: the row already prints "продолжить: S01E03 — осталось 23:14", and dropping the same nine-name file picker a fresh magnet gets, to hunt for the episode you were already watching, is the player forgetting something it plainly knows. The picker is what happens when there is nothing to continue. Its resume point comes from `positionsLoad()` directly, **not** `history.recent`, which holds only the twelve newest entries across everything — a torrent watched last week has fallen out of that long before its data has fallen off the disk. The picker itself marks which files have positions (brighter name, "осталось X"), since a season is nine names differing by two characters. It carries no progress *bar*, and that was tried: a full-width rule under the name reads as an underline rather than a value — at 91% it is indistinguishable from a border and a list of them turns the panel into stripes. The card grid needs one only because a poster leaves no room for words.
- **A torrent stalling mid-playback used to be completely silent.** `opening` is raised in `beforeLoad` and cleared on `file-loaded`, so the loading overlay — the one thing that reports peers and rate — is gone by the time playback starts. A swarm that dries up at minute twelve then froze the picture with nothing on screen to explain it, which is the difference between "give it a moment" and "this player is broken". Hence `.torchip`, a small readout below the top bar: rate, peers and how much of *this file* is on disk. It sits **outside `.topbar`** so it can survive the UI going idle, exactly like the skip button sits outside `.osc` and for the same reason — idle is precisely when a stall happens. The rest of the time it fades with the chrome, so the picture stays clean; it is suppressed while `opening` is up (the overlay is already saying all of it) and once the file is fully fetched. Its sentence comes from the same `torrentLabel` the overlay uses rather than a second copy of the logic. It goes **top-right**, and the left is not merely a worse choice but a broken one: `.osd` — the popup every volume change, seek and speed change raises — is `top: 60px; left: 18px`, two pixels from where this first sat, so the next volume nudge covered it outright. A status readout that vanishes exactly when a hand is on the keyboard is worse than none. The right is free below the bar on both platforms: the window buttons and the macOS logo end at 48px, and the skip button is bottom-right.
- **A torrent cannot gain an episode, so replacing one is a first-class action.** The info hash covers the file list and every piece hash — verified by building two torrents from the same folder and adding a file, which changes it — so an uploader who adds an episode publishes a *different* torrent with a different magnet. Left alone that costs a whole season re-downloaded and its watch history reset, which for an airing series is the common case rather than an edge one. The fix is **a rename done before the new torrent is added** (`torrent_relocate`): the data lands in the folder the new hash will ask for, `overwrite: true` makes librqbit verify it, and `add` needs no changes at all. Crucially the "folder name is the info hash" invariant survives, which is what keeps deletion unambiguous — the thing qBittorrent gives up by sharing one save path, and why cross-seeding there needs manual `Force recheck` and third-party tools to avoid deleting a neighbour's files. **Positions are re-keyed by file name, not index**, since one inserted episode renumbers everything after it; the name comes out of the URL each record already stores, so no new store was needed and entries written before this still migrate. The link box also *detects* the case (`findSupersededTorrent`), because pasting the new magnet where links go is the obvious move and would otherwise silently start a second copy — matched by **token overlap** rather than a prefix, since "Серии: 1-9 из 9" → "1-10 из 10" changes digits in the middle of a forty-word title. What none of this does is **discovery**: the player cannot learn that episode 10 exists. That needs RSS with auto-download rules, which means polling feeds in the background — the resident BitTorrent client this app refuses to be.
- **The buffer map needed no fork of librqbit, and finding that out was the whole job.** `with_chunk_tracker` is `pub(crate)`, which reads as "patch required" — but `Api::api_dump_haves` is public and hands out the same bitmap, as a `format!("{:?}")` of a `BitSlice`, evidently for debugging. Measured, the string is `BitSlice<u8, …> { addr: 0x…, head: 000, bits: 10 } [1, 0, 1, 1, …]`; only the bracketed tail matters, taken with `rfind` because the header has brackets of its own. Undignified rather than fragile: the format is pinned by Cargo.lock, `parse_haves` is tested against the real string, and a parse failure costs the map and nothing else. `file_ranges` then intersects the pieces with the file's own byte span — **the first and last piece of a file are shared with its neighbours**, so without that intersection the bar would draw buffer belonging to another episode. If this ever needs to be done properly the upstream PR is ten lines (`have_pieces()`), and vendoring is the fallback: `[patch.crates-io]` with a local path, **636 KB and 76 files** for the crate itself — the roadmap's "1.5M SLoC" was the whole dependency tree, not the thing that would be forked. What the map buys is two things, and the seekbar bands matter more than the previews: they answer "will a jump land or wait", which is what a torrent's bar is actually read for.
- **Previews before a file is complete are per-position, not per-file.** `thumb_get(exact)` opens its own decode session, so single frames need no storyboard — but the background grid pass walks a file start to end and would decode straight through a hole, so it still waits for the whole file (`thumbs.partial` is the distinction). The gate lives inside `issueThumb` rather than at the call sites, so no future caller can skip it, and it is fractional because the map is of *bytes*: for a variable-bitrate file bytes and seconds are not proportional, hence `BUFFER_MARGIN` keeping requests off the edge of a band where the estimate is worst. Expect previews to appear where they are least wanted — you have downloaded what you already watched, not what you are about to jump to — with the redeeming case being that rewinding is the common gesture on a file still arriving, and the past is always there.
- **Three things a torrent gains once its file is on disk, and one it cannot.** A torrent routinely **ships its own subtitles** (Sintel carries ten) — `sub-auto` finds nothing, since there is no local file to look beside, so they sat unreachable while the viewer searched OpenSubtitles for what was already downloaded. `sub-add` takes a URL, so each is a request to our own server; matched by name (same stem, stem plus a language tag, or a subfolder named after the episode) because a season carries one set per episode and attaching all ninety would make the menu useless, and `auto` rather than `select` so `slang` still decides. **The next episode is prefetched** once the current file is complete — one ahead and no further, which is the line between "the season does not stop between entries" and a background client filling the disk with what may never be watched; "next" is `torrentVideos` order, not mpv's playlist, which may hold a folder or a drop of loose files. And **the seekbar storyboard works**, which the network gate used to forbid for good reason that no longer applies: the data is an ordinary file here, so decoding costs nothing. `torrent_local_path` answers **only for a complete file**, and that is load-bearing rather than cautious — the files are sparse, so a stretch that has not arrived reads back as *zeros* rather than failing, and a storyboard over one would be black frames and mush with nothing to say it went wrong. Since a file completes *during* playback, `maybeStartThumbs` had to become retryable (`startedFor` is set only when a storyboard actually starts) and the status poll calls it on completion. **Start-screen posters now work too, and the obstacle that kept them off was the wrong one.** Completeness cannot be answered by `torrent_local_path` without the session — but it does not need to be: the cached `.torrent` beside the data names the file and its length, the info hash names the folder, and completeness is the allocated-blocks measure `torrent_list` already uses, so `torrent_offline_file` answers from the disk alone, with no session, no DHT and no peer. It answers only for a **complete** file, because the holes in an incomplete one read back as zeros and a poster decoded from one is a black rectangle presented as a frame of the film. (On Windows librqbit never marks the file sparse, so allocation cannot tell an empty file from a finished one there; a poster that fails to decode is treated as "none yet" rather than as an error.) **And an incomplete episode gets one too, captured while it plays** (`poster_capture`): that is the only window in which the data is on disk at all, so the picture is taken then and outlives both the download and the file. Two things distinguish it from the on-demand poster. Candidates come from the **buffered map**, spread across the bands rather than clustered at the playhead — a poster should be a scene, and three neighbouring frames are one scene — because asking for a second that has not arrived decodes zeros. And the winner is chosen **by content, not by position**: `rgb_score` is the mean absolute deviation of luma weighted by how far the mean sits from either extreme, which is near zero for a black frame, a white flash or a flat title card, and everything below `MIN_POSTER_SCORE` is refused outright — better no poster than a black one, and the next viewing tries again. Bounded like every other background decode: once per file, at most a handful of seeks, at the storyboard's QoS, and not before `POSTER_AFTER_S` of playback. It is written beside the thumbnail cache **with the source path inside the file**, for the same reason `CACHE_MAGIC` v4 carries it — an entry that cannot be attributed to a folder cannot honour a privacy root — and `forget_thumbs_under`/`clear_thumb_cache` clear both stores, or the second one is the leak nobody checks.
- **Casting (Google Cast) is a URL handoff, and while it runs the window is a remote control.** The TV fetches the file from a LAN HTTP server in cast.rs and decodes it itself; mpv stays **paused with the file loaded**, so tracks, chapters, duration and the hover storyboard keep feeding the UI, and disconnecting is a seek to the TV's position plus unpause — never a reopen. The rules that must not break, with the reasoning in `docs/casting.md`: **nothing opens at startup** — mDNS browses only while the picker is open (the `$effect` cleanup in +page.svelte covers every way it closes), the server binds when a device is picked, on the interface whose subnet contains the device (`pick_lan_ip`, if-addrs netmasks — never `127.0.0.1`, never `0.0.0.0`), and everything tears down on disconnect. **The server answers for exactly one file behind a random 128-bit token** — never a directory — and for a path under a private root the URL basename is the token itself plus the extension and the LOAD carries no title, which makes `cast_load` the **fifth** privacy enforcement point beside the four listed under "Watch history & privacy". **The CASTV2 protocol is spoken directly** (`wire::encode`/`decode`, a select! pump, a dedicated reader task because `read_exact` inside `select!` is not cancellation-safe): `rust_cast` was read and rejected — it holds its stream mutex across a blocking read with no timeout, so a command issued while its receive loop parks waits for up to the 5 s heartbeat, which is a broken remote. The TLS provider is **pinned to ring** (`builder_with_provider`): the tree compiles both ring and aws-lc-rs, and rustls' plain `builder()` panics with two providers enabled. **The remote seekbar is release-only** — no preview seeks, no probe, no drag settle (those are about local decode cost; every preview here would cost the TV seconds of buffering); Rust sets `cast.time` optimistically when SEEK is sent, which is what lets the page's `$effect` follow `cast.time` without a `seekSettling` twin and without the knob springing back. **Everything that moves the position has to be re-routed, and the ones that were missed all failed the same way.** The chapter *keys* were routed from the start; the chapter *list*, the skip button and the skip guard were not, and each of them talked to the paused local player instead — the knob jumped to the timestamp and the next status report dragged it back, the offer never appeared because `time-pos` is frozen while casting, and the guard that mutes a used skip never released for the same reason. The rule is one line: while `cast.remote`, read `cast.time`/`cast.duration` rather than mpv's, and act with `castSeek`/`castFollow`. The Windows **taskbar progress** was the fourth, and it adds a second half worth knowing: reading the right source is not enough when nothing is left to fire the update. It hangs off mpv's property observers, and with the local player parked `time-pos` never arrives — so the bar was written once, at the handoff, and held that position and its "paused" colour for the whole session while the television played through the film. Its driver while casting is therefore the cast poll (the same `$effect` that follows `cast.time`), and the call sits **inside** the `remote` guard: the local branch reads mpv's mirrors, so calling it there unconditionally would make that effect depend on `time-pos` and re-run ten times a second through ordinary playback. Anything else that only wakes on an mpv event inherits this bug by default. **Seeking while paused is refused by the measured renderer** — measured, UPnP 501 "Action Failed" — so `dlna_control` resumes, seeks and pauses again, which is the standard controller remedy and is verified end to end (the position moves, the state comes back paused, the TV fetches the new range); it costs a fraction of a second of playback, against a seekbar that would otherwise stop working exactly when a viewer reaches for it. It also needs a second guard the playing case does not: **a paused renderer keeps reporting the position it had before the seek** until playback resumes, so the target outranks its answer until a report lands near it (`seek_target`, bounded) — believing the renderer there is the same "jumps and returns" from the other end. **Keys and wheel are re-routed, not disabled silently**: `runCastAction` maps playback keys to the TV (chapter keys become remote seeks to the local chapter list's times — never mpv's `chapter` property, which would move the paused player out from under the session), the wheel is TV volume, and local-only concepts (frame step, zoom, speed, loops, screenshots, delays, mini) refuse with an OSD saying so. **A transport that fails must hand over, not stop.** `auto` can be wrong about DLNA in three ways that look identical from here — the container is listed but the codec inside is not decodable, the device advertises less than it can, or a renderer-only device simply cannot take this file — so the failure itself is the evidence: the session falls back to the Cast ladder, which names its own refusals, and the container is remembered as refused **for this device for this run** (not persisted: an under-declaring renderer deserves a fresh try next launch, but not one per episode of a season). Three detectors feed it, and the third is the one that matters: a `dlna_load` that errors, a renderer that stops before it ever played (its "ended" and "failed to start" are one state), and **fetched-but-never-playing past `START_TIMEOUT_MS`** — the failure that used to be perfectly silent, no error frame and no state change. That last one only became detectable once `load_url` stopped ending in an optimistic `playing`: claiming playback the renderer had not confirmed blinded every check downstream, so it now ends in `buffering` and the poll reports what the device actually says. Zero fetches is deliberately *not* a fallback case — nothing was read, so the file is not the problem and Chromecast would be served by the same blocked server; that stays the firewall message. **Discovery is not a one-shot question, and on macOS it cannot be.** The system asks for Local Network permission the first time something multicasts, a third-party firewall may ask again per destination, and both prompts are answered *after* the search has started — while the sockets refused in the meantime stay refused, so re-sending queries on them changes nothing. Two consequences, both learned from a real install: **discovery is torn down and rebuilt** after a few empty polls, which is what turns "allow" into devices appearing instead of the viewer having to close the panel and open it again; and the panel **never announces failure while it is still searching** — the first version said "no devices found" after six seconds, which is exactly when the prompt is still on screen waiting to be answered. It now says it is still looking, names the prompt, and only reaches "here is why a television is invisible" after a couple of rebuilds, by which time a granted permission would have taken effect. `NSLocalNetworkUsageDescription` and `NSBonjourServices` are in `src-tauri/Info.plist` so the prompt can say what it is for. **Errors are four different facts**: TCP/TLS connect failed, LAUNCH_ERROR, LOAD failed, and "LOAD accepted but zero fetches within 8 s" — that last one is the firewall signature (the CASTV2 channel worked, the media port is blocked) and gets the firewall message, which the picker also pre-empts by warning about the Defender prompt before the first bind. **The compatibility ladder is `castVerdict`** (cast.svelte.ts): direct play (MP4/M4V/WebM with receiver-decodable audio) → **prepare** (`cast_prepare` in cast.rs: the bundled ffmpeg CLI remuxes into a `+faststart` MP4 with video always stream-copied, `-tag:v hvc1` on HEVC only, audio copied when compatible and transcoded to E-AC-3 640k otherwise — `-ac 6` only above 6 channels, or a stereo source would be upmixed) → refuse, which only incompatible *video* earns now, named rather than generic. H.264/HEVC/VP9/AV1 and AC-3/E-AC-3 pass as *attempts* — device class and the HDMI passthrough chain are unknowable from the sender (E-AC-3 passthrough and 4K HEVC HDR10 are **measured working** on one real television). Prepared files live in `<app_cache>/cast/` keyed by path+size+mtime+track+rung, LRU-pruned to 20 GB; a private-root file's prepared copy is deleted with its session (`cast_forget_prepared`). **`cast.remote` vs `cast.active` is load-bearing**: during a prepare, local playback deliberately keeps running, so keys/wheel/seekbar/volume and the casting screen flip to the TV only on `remote` — gating them on `active` puts two writers on one seekbar. **The prepare rung spawns the ffmpeg CLI, and both platforms now ship one.** Windows: `ffmpeg.exe` from the BtbN SDK, a 0.5 MB shim over the bundled DLLs. macOS: Homebrew's `ffmpeg` binary relinked by `scripts/bundle-macos-libs.sh` — it is a shim over the very dylibs that script already bundles, so it joins the closure as a root (which is how libvmaf arrived), gets its load commands rewritten to `@rpath` and **one** rpath, `@executable_path/lib`. One is enough because the CLI is placed so that the relative position is identical in both layouts: `target/<profile>/ffmpeg` beside `target/<profile>/lib` in dev (build.rs copies it), and `Contents/Resources/ffmpeg` beside `Contents/Resources/lib` in the bundle. That is also why `ffmpeg_bin()` takes an `AppHandle` and probes the **resource dir**: on macOS the exe lives in `Contents/MacOS`, so "next to the exe" and "next to the resources" are different places, and the Windows-shaped lookup found nothing inside a `.app`. Consequence for a fresh macOS checkout: `bundle-macos-libs.sh` must run before the first build, because `ffmpeg-macos/bin/ffmpeg` is a declared bundle resource and **a resource pattern that matches no file fails tauri-build** — the same trap that broke the macOS build when `ffmpeg/bin/ffmpeg.*` was added to the base config without its `null` twin in `tauri.macos.conf.json` (a Windows-only resource needs that twin the day it is added; the platform config is merged even for a bare `cargo check`). **The transport is no longer a setting, and that is a conclusion.** The «ТВ» tab (two-character label on purpose: the nowrap tab row silently clips an eighth wide tab) held a `prepare`/`hls` pill; it is gone, because HLS was built to stream an incomplete torrent and both halves of that job went elsewhere — DLNA carries the release untouched, a direct-play file streams over Cast as it is — while measurement showed HLS carries only H.264 with stereo. As a choice it was worse on everything it could carry and unable to carry the rest: a menu entry whose every selection makes the result worse. The code path survives for the one case neither other reaches (a receiver with no DLNA, an incomplete torrent needing repacking — not yet wired) and as a debugging knob (`localStorage frameplayer.castMode = 'hls'`). What remains in the tab is the cache: its cap, the cache cap (0/5/20/50 ГБ — travels to `prune_cast_cache` as a parameter; zero also deletes the served copy at session end), the measured size and a clear button. **A per-device check lives in the picker instead** (`cast_diagnose`, the gear panel): our address on the device's subnet, the Chromecast port and handshake, the renderer's description, its accepted formats, whether it offers `Seek`, and what it says about volume — every one of them a question the normal flow already asks and throws away, written down here with a copy button, because on somebody else's television the difference between "the network cannot reach it", "the receiver refused the file" and "this device does not do that" is invisible from outside and decides everything. It deliberately stops short of `LAUNCH`: answering a diagnostic question by starting an app on someone's TV is a surprise. Three things about its shape. **Rust returns an id and data, never prose** — the report is shown in a localised window and Rust cannot reach the dictionary (the macOS menu's problem again), so a check names itself with a stable id the frontend translates, and `detail` carries only what this side knows: addresses, lists, the device's own error text. The frontend adds the sentence from `diag.<id>_<state>` **when there is one to add** — `t()` echoing an unknown key is the signal that the data speaks for itself. **The report is a dialog, not a panel inside the picker**: eight lines of prose in a 280px column that scrolls is a list of two-word fragments. And **the button is small and the row says what it is for** — `Не получается транслировать?` beside a link-sized `Проверить`, because a lone "check this device" is a button whose purpose the viewer has to guess, and a full `.btn-outline` there reads as the panel's main action rather than as a way out of a rare problem. `cast_hls_prepare` builds a full VOD rendition (TS segments) into a transient `cast/.hls/<rand>/` dir — removed at disconnect, on displacement by a track switch, and swept at the next HLS start minus the served dir; the server's directory mode validates the path after the token to one flat non-dot component. In HLS mode even direct-play files go through the segmenter (the mode is the transport) — **except HEVC, which cannot go over HLS at all and silently takes the progressive rung instead**. **The two transports have different codec ladders, and that is measured rather than assumed**: progressive reaches the TV's own decoder, so 4K HEVC HDR10 and E-AC-3 5.1 passthrough both work; HLS goes through the receiver's browser pipeline, which on the measured television takes **H.264 + AAC stereo and nothing else** — E-AC-3 refused in TS and in fMP4 and refused again when a master playlist merely *declares* `CODECS="ec-3"`, AC-3 refused, HEVC refused the same way with `hvc1` correct, and AAC **5.1** accepted and then killed the receiver app a few segments in. So `cast_hls_prepare` always transcodes audio to AAC stereo (`transcode_audio` describes the progressive rung and is deliberately ignored there), `hlsVariant()` answers `null` for anything but H.264, and the settings hint says the mode costs surround. **That fold-down must carry the LFE by hand, because a plain `-ac 2` deletes it** — measured on the rotating-tone file, the LFE second goes from −13.9 dB in the source to **−90.3 dB** in the downmix, which on a soundbar is the most audible thing about the mode; `lfe_mix_level` on the resampler does nothing, so a `pan` matrix (ITU coefficients normalized by 1/(1+2·0.707), LFE at the same weight as center and surround) puts it back at −16.8 dB with the file's peak *lower* than before. It is written in channel **indices** and applied only at exactly six channels: 5.1 and 5.1(side) share the order FL FR FC LFE S/BL S/BR, and a formula written with channel names silently fails on whichever of the two it was not written for. The progressive path is untouched by all this and is where surround actually lives — **E-AC-3 5.1 passthrough is confirmed by ear** (the LFE reaches the subwoofer, which a fold-down cannot fake). **The LOAD must carry `hlsVideoSegmentFormat` and never `hlsSegmentFormat`**: the latter is the format of an HLS *audio* segment, and sending it beside a muxed A/V stream made the TV reject the LOAD with a bare `LOAD_FAILED` — no `detailedErrorCode`, after it had already fetched the playlist, the init segment and segment zero. That one field cost fMP4 entirely and read as "the receiver cannot do fMP4", because fMP4 was only ever tried with HEVC, which fails for its own unrelated reason. Two properties of that receiver worth keeping in mind whenever a LOAD fails: **a bare `LOAD_FAILED` carries no reason at all** on that device, so the HTTP log is the diagnosis (nothing fetched = the request was refused; playlist only = it would not parse; init + a segment = the media was refused), and **a rejection by declared codec arrives before any segment is fetched**. `load_probe` in cast.rs is the tool that produced all of this — it drives a whole cast (bind, LAUNCH, LOAD, watch, stop) from `cargo test` against a rendition built by hand, so a receiver question costs one command instead of a GUI run and a copy-pasted log. **Complete torrent files cast** via `resolveCastSource` → `torrent_local_path` (complete only — sparse holes read as zeros). **An incomplete one streams, and only over DLNA**: `cast_serve_torrent` registers `(info hash, index)` in place of a path and the LAN server streams through `TorrentService::serve_file`, i.e. librqbit's blocking reads, so the television's Range requests become piece priority exactly as mpv's do — reading the sparse file instead would serve zeros silently. **Two doors, and neither is a preference.** A renderer that lists the container takes the release untouched — the wide one, since torrents are MKV. A Chromecast takes an incomplete torrent only when the verdict is `direct`, i.e. the file needs no repacking at all: it then fetches over HTTP with Range exactly as it fetches a prepared file, so "not finished" stops being a reason to refuse (`cast_load_url` LOADs a URL somebody else registered, the Cast twin of `dlna_load_url`). Anything that would need preparing still waits for the whole file, and that is not a limitation to lift later — half a film remuxed is half a film, so no amount of progress changes the answer; only completion does, which is why the picker re-reads the plan while a torrent source is open. A lead of `STREAM_LEAD_BYTES` is built before the LOAD, announced and capped, because the receiver's tolerance for a blocked read is the one thing about this rung that cannot be known from the sender side. **Every transport that borrows the LAN server must release it** — DLNA ends through its own disconnect and used to leave the server up, so the token outlived its session, which is the single promise that server makes. Known limit: `-c:v copy` cuts segments at keyframes only, so a file with minute-long GOPs degrades HLS to giant segments (real releases are 2–4 s). `docs/casting.md` carries the measured numbers behind all of this — the audio transcode at 276× realtime is why local-file seeking is solved by preparing the whole file rather than by segmenting it.
- **DLNA is the second way to a television, and the one that asks the least.** A UPnP MediaRenderer *is* the TV's own player, so a release it already decodes plays untouched — measured on the real set: a 6.3 GB 4K HEVC Main-10 HDR10 MKV with E-AC-3 5.1, no prepare, no remux, seeking included. It reuses the Cast half wholesale: the same Range server (`cast::serve_one_file`, which honours the private-root rule and is therefore the **sixth** privacy enforcement point), the same status shape, the same store, seekbar, keys and casting screen; the frontend only picks which command name to invoke (`dlna_*` against `cast_*`), which is why the transport cost the UI almost nothing. Four rules it added. **The picker is one row per television, merged by IP address** — the same set answers on both protocols and cannot be joined by identifier, measured: its Cast id and its renderer's UDN are different UUIDs. **The remembered profile is keyed differently from the merge** (`frameplayer.tv-devices`): an address is a DHCP lease, so a profile is filed under the most stable id the device has and matched by name+model as a fallback, because an LG renderer's UDN looks service-scoped and may not survive a reboot. **A row must not pass judgement on what it does not know yet**: SSDP sweeps for the first seconds, so a device whose DLNA half has not arrived is not a device without DLNA — for a torrent still downloading that difference *is* the answer, and a half-downloaded film was being told to finish first. The line says it is checking until the sweep settles, but only where the missing half could change the verdict (a file the Cast rung already plays untouched says so at once). **The picker reasons about the resolved source, never about `player.filePath`** — for a completed torrent those are different things (the player holds a loopback URL, the cast is pointed at the file on disk), and asking the URL made `isNetworkSource` true, so auto answered "Chromecast" for a file that in fact goes over DLNA: the row contradicting what clicking it does. The resolved path lives in `cast.plan.src` beside the verdict, computed once per picker opening. **The row states a consequence, not a protocol** ("играет как есть" / "подготовка перед стартом" / "поток · звук стерео"), computed once per picker opening from the file's verdict; auto prefers DLNA whenever the renderer's `GetProtocolInfo` lists the container — that Sink list is the capability API Cast never gave us. The protocol names live under a per-row gear, which **expands the row in place rather than opening a second floating panel**: a panel hoisted out of the picker would need the context menu's hover bridge, its click guards and its narrow-window drill-down, all for one control. And **seekability is declared in the DIDL metadata, not in HTTP headers** — with a bare `<res>` the TV grays out its own seek buttons before fetching a byte and answers a sender `Seek` with "not available"; with the DLNA flags in `protocolInfo`, `size` and `duration` (read from the container via libav) it reads the MKV's cues itself and range-requests the offset. Known device quirk, and the reason the volume slider stays disabled there: this TV answers `GetVolume` with a valid `0` while playing at almost full, and refuses the action outright to another client, so a level is trusted only once a non-zero one has been seen — and **mute is disabled with the slider**, because it is part of the same control rather than a capability of its own, and a device that ignores a volume ignores a mute too (the icon flipping back by itself is what that looks like; the keyboard path keeps the explanation). **Audio tracks cannot be switched over DLNA at all**, and that is read from the renderer rather than assumed: its AVTransport declares `SetAVTransportURI, GetMediaInfo, GetTransportInfo, GetPositionInfo, GetDeviceCapabilities, GetTransportSettings, Stop, Play, Pause, Seek, Next, Previous, GetCurrentTransportActions, SetNextAVTransportURI, X_LG_Seek` and its RenderingControl adds `X_GetSubtitle`/`X_SetSubtitle` and a 3D formatter — vendor extensions exist here, and none of them is about audio. So the file goes over with every track in it and the television chooses; the only alternatives would be its own remote or an explicit remux that copies the whole film to drop tracks, which would cost exactly what this transport exists to avoid. (`X_SetSubtitle` is the lead for subtitles over DLNA when phase 3 comes.) Because the choice cannot be read back either, the track menu **says so** while a DLNA session runs instead of showing a selection it cannot vouch for. **An optimistic state has to outlive the renderer's report, or play/pause looks broken**: this TV answers `Pause` properly and then keeps saying `PLAYING` for a poll or two — after a load it says `TRANSITIONING` six times — so the next status overwrote the optimism and the button sprang back, which is the seekbar's `seekSettling` problem in another costume and gets the same answer (a 2.5 s window in which a command's own state outranks the poll). Related, and the reason that bug hid: **a refused command must not vanish into an empty catch** — refusals here are meaningful (606 "not authorized", 701 "transition not available"), so they raise an OSD. Two more rules the same live session produced. **The optimistic state is armed before the round trip, never after**: a SOAP call takes a few hundred milliseconds and the frontend polls twice a second, so setting it afterwards leaves a gap for a poll to read the state mid-change — which is exactly the resume flicker (new icon, old icon, new icon again); armed first, the window does not exist, and a refusal rolls the value back. **`Stop` goes before every `SetAVTransportURI`**: a renderer that is already playing refuses a new URI with 701, and it will be playing more often than not — the previous session, a session that did not end cleanly, another sender on the same television. **A refused `Play`, on the other hand, is not a failed load** — and reading it as one is what made a perfectly good cast report that the television could not open the file. The measured renderer starts fetching on `SetAVTransportURI` alone, so it answers `Play` with 701 *while already doing the thing being asked of it*, and how long that lasts scales with the file rather than with our requests: on a 10 GB 2160p HDR MKV it stayed `TRANSITIONING` from the first poll to the last, served a HEAD, a read from byte 0, then the Matroska cues from the 10 GB mark ~18 s in — while a fixed six-attempt budget expired around seven seconds and tore the session down, and the same cast succeeded at once on a second try against a player that was by then already up. So the loop **asks `GetTransportInfo` rather than counting refusals**: `PLAYING` or `TRANSITIONING` both mean started, only "still neither when the wall-clock budget runs out" is a failure, and that budget stays inside the frontend's own `START_TIMEOUT_MS`, because judging whether a television that took the file ever shows anything is that detector's job. Every refusal is printed, since collapsing them all into `load_failed` is what made this indistinguishable from a file the set cannot decode — it took a `FP_CAST_DEBUG` wire log to tell apart. The resume `Seek` that follows stays best-effort: a renderer still `TRANSITIONING` has no index yet and cannot turn a time into an offset, and losing the resume point is a far smaller failure than refusing the load over it. And **click-to-pause inverts its trade while casting**: locally the toggle fires immediately because a double click cancels itself and half a second of delay on "resume" costs more than the artifact, but on a television a pause and a resume 100 ms apart is a decode restart rather than a frozen frame, while the delay is free next to the remote's own latency — so the cast path waits out the **system's** double-click interval (`double_click_time`, which had been registered and unused until now) and the double click cancels it. The casting screen carries the same handler, or the gesture the player is built around stops existing the moment a cast starts. `dlna.rs` also carries the two things that make a device answerable without the GUI — `FP_DLNA_PROBE=1` dumps what the network holds and what each renderer accepts, and `FP_DLNA_PLAY=<file>` drives a whole session *through the shipping commands*; both must run inside the app, because macOS silently drops multicast for a process without Local Network permission and a CLI probe reports an empty network whatever is on it.
- **Everything DLNA knows about a television has to be read off that television, because the next one is a different make.** Every rule above was measured against one set, and the failure mode of measuring against one device is that the code encodes it — silently, since a renderer that disagrees does not report an error, it declines. Six places where that had happened, and the shape each one takes. **The MIME spelling is the device's, not ours** — a container has several live names (Matroska is `video/x-matroska`, `video/x-mkv` and `video/mkv`; AVI has four), a strict renderer answers a name it did not list with UPnP 714, and `cast_mime` — written for the Cast ladder, where anything but MP4 and WebM is prepared first — returns `application/octet-stream` for exactly the containers only this transport carries. So `negotiate_mime` picks whatever the `GetProtocolInfo` Sink list advertises and falls back to our own first spelling, never to octet-stream. It is matched **case-insensitively on both sides**, and `mime_candidates` in dlna.rs and `DLNA_MIME` in cast.svelte.ts answer *different* questions — what to send, and whether to offer the device at all — so a spelling missing from the frontend copy is a television that reads as incapable with nothing on screen to say why. Keep them in step; a divergence now costs a worse guess rather than a failure, because Rust re-negotiates what the frontend chose. **`REL_TIME` is not the only seek unit** — `ABS_TIME` is all some renderers implement, so `seek_to` walks a ladder and remembers what worked; deliberately a runtime probe rather than a reading of the SCPD's `A_ARG_TYPE_SeekMode`, since a device that declares a mode may still refuse it, which is this very television's habit with `Seek` while paused. The resume seek after a load pointedly does **not** teach the ladder: a refusal there means "too early", not "wrong unit", and recording `ABS_TIME` from it would pin the session to the fallback. **`URLBase` outranks the LOCATION** for resolving control URLs — deprecated in UPnP 1.1 and still emitted, sometimes on a different port, in which case every control URL is silently wrong; and a path-relative URL resolves against the description's *directory*, not the origin, which is a fix to a test that had been asserting the bug. **A description may hold more than one device**: the spec lets a root device embed others, so a combined server+renderer box gave its MediaServer's ConnectionManager to a walk that took every `<service>` in the document — and where the root *is* the server, the renderer was dropped from the picker entirely. `renderer_device` narrows to the MediaRenderer's own subtree, and only on a positive identification, so an unrecognised device keeps the old whole-document reading rather than disappearing. **The opposite rule holds in upnp.rs** — an InternetGatewayDevice keeps its WAN services two levels down, so narrowing there would find nothing; the two modules read the same shape of document for opposite reasons, and the note at each end says so. **The DIDL is escaped twice, and one round was missing** — it is a document embedded as *text* inside `CurrentURIMetaData`, so the title is escaped for the DIDL and the whole DIDL escaped again for the envelope; escaping once means the receiver unescapes once and hands its parser a bare `&`, which any film with an ampersand in its name produces and a strict renderer rejects outright. **And reqwest sends no `User-Agent`** — the trap the tracker announce already paid for, now closed for every UPnP call by one shared client, which also keeps a connection pool alive across the poll's several SOAP actions a second. Two smaller ones in the same sweep: `RelTime` is optional and is answered `NOT_IMPLEMENTED` by real devices, so the position falls back to `AbsTime` or the seekbar sits at zero for the whole film; and `CurrentTransportStatus` reaching `ERROR_OCCURRED` **before the first `PLAYING`** is a load that died, which beats waiting out the frontend's eight-second "fetched and never played" detector — after a `PLAYING` it is ignored, since a device that stumbled and recovered must not have its session torn down.
- **The tolerance of the string-scanning XML lives in one function, and it is the price of not taking a parser.** `tag`/`chunks` compare a **local** name against everything up to the first whitespace, so an attribute (`<friendlyName xml:lang="en">`), a namespace prefix (`<av:CurrentTransportState>` — the schema says out-arguments are unqualified and not every renderer obeys) and an empty element all read correctly, while the delimiter check keeps `deviceType` from answering a search for `device`. Anything shown to a person goes through `unescape` as well, or a set called "Living Room &amp; Kitchen" is listed as its markup. The module header is no longer "recon-shaped, parsing gets a real dependency if the branch proves out" — the branch proved out and shipped, and the decision now is that a dozen leaf elements do not justify a crate plus its licensing entry. **If this ever needs a third special case, take the dependency instead.** What makes that affordable is that all of it is pure: `parse_description` is split from the fetch precisely so a device nobody here owns can be reproduced as a fixture, and the vendor shapes above are pinned that way. Nothing in the transport half is — `soap`, the poll, the play budget, the paused-seek workaround are covered only by `FP_DLNA_PLAY` against a real television, which must run inside the app.
- **Watching together is one shared timeline and nothing else, and the shape of the wire is the whole design.** What travels is a **snapshot of the state after a change** — `{content, paused, position, speed, at, rev, by}` — never the gesture. A replayed action is not idempotent, does not survive a dropped message, and cannot answer the only question a lagging or late-joining viewer has, which is where they should be *now*; a snapshot answers all three, which is why every guard in the reconciler can simply `return`: a moment when this player must not be touched is a moment it will be corrected a second later. `at` is the **relay's** clock and `rev` is the relay's to assign — a client that fills them in is overwritten, which is what keeps revisions monotonic when two people press space at once, and what lets each peer know only its own offset from one clock instead of everybody agreeing about wall time. **Ordering is by `rev`, never by `at`**: the relay is the only participant with one opinion about what happened first, while `at` is a clock *estimate* whose error bars are half a round trip — two clients ordering by timestamp could disagree about which change came last and both be right. So `at` answers "where should playback be" and `rev` answers "which of these do I believe". `shouldApply` is the guard, and two things in it look like mistakes and are not: **`>=` rather than `>`** (a refusal is answered by re-sending the *same* revision, and that message is the correction that pulls a guest back from where they optimistically moved — dropping it strands them there), and **a `welcome` applies unconditionally** (it describes the room as it is, and covers a room re-created from zero). Most of the ordering is not ours anyway: a WebSocket is TCP, so within one connection messages cannot arrive out of order at all, and the `socket !== sock` guards drop a previous socket's traffic after a reconnect. **Delay costs nothing** — a snapshot that arrives two seconds late still projects the right position, which is the deepest reason the wire carries state rather than actions. **Tracks are the one place the roadmap's "sync the timeline, not the presentation" is deliberately crossed**, and it is crossed by **a rule of the room rather than a preference of a viewer**: `shareAudio`/`shareSubs` live on the relay beside `hostOnly`, are set by the host in the room panel, and arrive in `welcome` and every `members` broadcast. All three are the host's for one reason — the host owns the room's rules, and a panel where one switch answers to a different person than the two beside it is unpredictable. Defaults are **audio on** (a room listens to one soundtrack) and **subtitles off** (one viewer needing them and another not is the ordinary case, and sharing the choice would turn them off for somebody who cannot follow the film). A per-viewer switch was built first and was wrong: a room where one person's audio choice reaches everybody and another's does not is a room whose own members disagree about what it does. They ride on the timeline (`tracks`) rather than in a message of their own, which gets last-writer-wins and handshake delivery for free; the cost is that **a publish must merge with what the room already holds**, since a snapshot carrying `{audio}` alone says "no subtitle preference" and would wipe the other kind for everybody who shares it. They travel as a **description resolved by `matchTrack`**, never an id: ids are positions inside one file, so the dub that is #2 in one rip is #3 in another. **Drift is corrected by bending the speed, never by seeking** (the roadmap decided this in advance and it is right): an exact seek costs decoding from the preceding keyframe — 1.9 s on a 4K60 VP9 file — so seeking to fix 300 ms stops for two seconds to correct a third of one and lands further out than it started, while ten seconds at 103 % fixes it inaudibly (`scaletempo2` preserves pitch). Three bands in `drift.ts`: inside the deadband nothing, ≤2 s a proportional nudge capped at ±10 % aiming to erase it over ten seconds, >2 s one seek. **The deadband is measured rather than chosen** (`deadbandFor`): twice the clock uncertainty, clamped to 40–150 ms — a flat 150 ms is what a viewer felt as a room that held to a tenth of a second and then stopped trying, and a tenth of a second is a guess about the network rather than a property of it. **And the local position must come from `positionNow()`, not the `time-pos` mirror**: the mirror is an event, so reading it is tens of milliseconds late — a systematic error in the one measurement whose job is to be small, and it sat inside the old band where nothing could see it — and while *paused* there is no speed to bend, so the tolerance drops to 0.25 s and it seeks. The correction is applied around the **room's** speed rather than around 1, or a room watching at 1.5× would silently lose it, and it is written straight to mpv rather than through the verb, because it is this machine catching up and publishing it would have every peer chasing every other peer. **Readiness is the relay's decision and it freezes the room with a real timeline** rather than a flag beside one — a paused snapshot at the position playback had reached — so every client's projection keeps working unmodified and somebody joining mid-wait sees the same state as everybody else. Three rules make that bearable: a pause a *person* asked for is never lifted by the relay, resuming while somebody loads means "resume when they are done", and a member who never reports counts as ready after 45 s, or one player that died mid-buffer holds an evening. Joining is itself not-ready, which is correct: the newcomer has a file to open. **The bus is the existing verbs**, which is the whole of "new features are shared by design": every button, menu row, hotkey and gesture already routes through `playback.svelte.ts`, so publishing from there covers a control added next year — and `SYNC_BEHAVIOR`, a `Record<ActionId, 'shared'|'personal'|'solo'>`, makes a new action a **compile error** until somebody classifies it, exactly as `CAST_BEHAVIOR` does and for the same failure (every casting bug that module exists for was an omission). Only the A–B loop is `solo`; frame stepping is `personal` because a frame is an order of magnitude below the deadband, and repeat mode is `personal` because a viewer whose file loops while the room moves on ends up on different content, which heals itself when the room's content is opened. Gestures publish **on release only** (`onSeekUp`, `endScrub` — the same rule the cast seekbar keeps), because a drag is a stream of positions and each would be a seek on somebody else's machine. **An arriving timeline is not a gesture**: it goes to mpv directly rather than through the verbs, or the OSD, the drag guard and — fatally — the publish would all fire, and every peer would re-broadcast every peer. **A torrent is the case this is good at and the reason the roadmap paired the two**: an info hash plus an index names a file exactly, the metadata is already cached beside the data, so a guest joining mid-season is a `torrent_add` of a few milliseconds and switching episode is the same hash with another index. A **local file cannot be sent**, so what travels is enough to recognise a copy — the OpenSubtitles release hash (reused from `opensubtitles.rs`, not rewritten), the duration and the size — and the panel says *the same release* / *a different rip* / *a different file* rather than refusing: a viewer who deliberately opened the director's cut is making a mistake worth mentioning, not correcting. Comparison is **identity, not equality** (a late title, a firmed-up duration or a magnet rebuilt from the hash must not read as a different film, or playback restarts for everybody). **The room code is Crockford's base32**: I, L, O and U are out of the alphabet *and* the ones people type anyway are folded onto their look-alikes rather than refused — an alphabet that merely excluded them would reject the code the viewer is looking at. `frameplayer://join/<code>` is **offered, never obeyed** — a custom scheme is a surface any page can aim at, and exactly one shape is parsed; anything else is ignored in silence. The relay is `relay.frameplayer.app` by default (`DEFAULT_RELAY` in `wire.svelte.ts`), and the address is a **field in the settings sheet** (Основные) rather than a build-time constant — self-hosting `services/relay/` is a setting, not a fork, and an empty field means the default rather than no relay. It is not in the room dialog, where it started: almost nobody runs their own, so it was a question with one answer in front of the two controls that matter. `socketUrl` **refuses plaintext off loopback**: the relay carries what everybody in the room is watching, and over `ws://` that failure would be invisible because it works. The relay never parses content (opaque JSON, size-bounded), so a new kind of source is a frontend change and never a redeploy, and `shared/sync-protocol.txt` is what keeps the two languages' field names in step — with the trap that **`go test` caches and the fixture lives outside the Go module**, hence the `t.Setenv` at the top of that test.
- **The catalog is two services and one rule about which answers what.** A metadata service says *what* to watch — posters, localised titles, descriptions, how many seasons a series has — and a Torznab-compatible indexer says *where from*. Neither can do the other's job, which is what decides the shape: an indexer holds no posters and no descriptions, so browsing one directly is a list of raw release names, i.e. precisely the experience a catalog exists to replace. **The player carries no TMDB key at all** — metadata goes through our own proxy, `services/tmdb`, and the key lives only there. That is a reading of the terms rather than caution, and the reasoning had to be corrected once: the first design baked a key in on the grounds that TMDB rate-limit **by IP rather than by key** (50 req/s and 20 connections per address), so a shared key creates no contention. True, and beside the point — that is a fact about *load*, not a permission. The licence is non-transferable and **non-sublicensable** (§1.A), and §1.C forbids attempting to "cloak or conceal Your identity, or the identity of any … application", which is exactly what one anonymous credential shared by every copy does. The OpenSubtitles analogy is weaker than it looks and inverted in one place: OpenSubtitles **bans** apps that make users register their own keys, so a shipped key is the required design there, while TMDB has no such rule. What *is* uncontroversial: the free licence is non-commercial (§2.A) and a free player satisfies it — there is no "personal use" tier and that is not the right frame — though GPL-3.0 lets anyone sell copies, so a fork that starts charging owes TMDB its own commercial licence. **Attribution is mandatory** (§3): the exact sentence in `catalog.tmdb_notice`, reproduced verbatim and deliberately **untranslated in both dictionaries** since a translation is a different sentence, plus their logo above it — referenced from `static/` rather than inlined, so nothing here can alter a trademark, and with **the aspect ratio stated in CSS** because the file carries a `viewBox` and no intrinsic dimensions, so `width: auto` collapses it (measured in a WKWebView harness: 13×13 with nothing painted, against 179.6×13.0 once the ratio is given). **Caching is bounded at six months** (§1.C), which is why every TTL in `services/tmdb` is pinned by a test rather than by a comment: a raised TTL is a terms violation that nothing else would report. **Posters are the whole of the bandwidth and therefore do not go through the proxy by default** — a grid of twenty at w342 is ~800 KB against ~25 KB of JSON — so Rust returns the poster *path* and the frontend composes it against TMDB's own CDN, falling back to `/img/…` on the proxy when images fail to load. **Trying is the measurement; an IP address is only a guess about it** — geolocating the client would need a database, would be wrong for anyone on a VPN, and would infer a fact the browser reports for free — **and a single failure is not the measurement either**: an `<img>` cannot tell a refused connection from a 404, and the live CDN does answer 404 for a stale path, so the verdict needs `CDN_STRIKES` failures with a success resetting the count, or one missing poster convicts a working CDN for good. The proxy passes a 404 through as a 404 for the same reason. **No indexer address is compiled in**: the player reads `catalog.json` from the update host on every panel opening — ordinary remote configuration, because a value built into the binary is a per-build constant rather than a default, and it lives beside `latest.json` rather than on the proxy so it does not inherit that service's availability. Four properties it depends on: a viewer's own setting always wins; any failure means "no configuration" and the player asks the viewer; **the client never persists what it reads**, or the answer is pinned to whatever it was the first time the panel opened; and how fast a change lands is a **CDN cache rule on that path**, not object metadata, because metadata is lost the first time somebody re-uploads without the flag — silently, since the file is correct and only the timing changes. **The indexer's own search is fuzzy and the filtering is ours**: a widely released title answers well over a thousand rows, most of them unrelated. Three things that filter must get right, all measured. It compares the indexer's *parsed* name fields, never the raw release title — that string carries the year, the codec and the dub list, so a substring test against it matches anything that merely mentions the film. It matches on **either** the local or the original name, because some sources fill the original-name field with the entire release line. And it **keeps rows whose year is 0**, since not every source fills the year in and a strict filter drops them all. `fold()` is what makes the comparison work across the alphabets: release names mix Latin and Cyrillic homoglyphs freely, so a title written with a Latin `a` is a different string and the same film. **Releases are ordered by quality with dynamic range inside it** — 4K HDR, 4K SDR, 1080p HDR, 1080p SDR — and seeders decide within a group; the first version sorted by seeders alone and put a live 480p rip above a 4K remux with a healthy swarm, which answers "what is busiest" rather than "what is the best copy I can get". The one departure from a pure quality order is that **a release nobody seeds sinks to the bottom**, measured rather than defensive: of 95 4K rows in one response, 13 had no seeders at all. `dynamic_rank` is deliberately two buckets and not a ladder — across 768 rows the field only ever held two values — and an unrecognised value is treated as high, because the indexer only fills it in when it found something. This is a selection order as well as a display one, **and the cap does bind on a popular title** (326 releases after filtering against a cap of 120), so the frontend's "by seeders" pill re-orders the best 120 *by quality*; if that ever matters the fix is to make the cap a property of the requested order rather than raising it. Off-switch, not off-by-default: this is the only surface in the player that tells a third party what somebody is *looking for* rather than acting on a file they already hold, which is an argument for a way out rather than for hiding the feature from everyone who never opens the settings. Both addresses refuse plaintext off loopback (`proxy_base`, the rule `socketUrl` already applies to the relay), because over `http://` that failure is invisible: it works. Nothing here is derived from a path, so there is no privacy root to gate against; **that stops being true the moment anything asks "which releases exist for the file I am watching"**, and such a feature needs the gate before it ships. A chosen release is a magnet and goes to `openTorrent`, so the resolve, the file picker, the history and the queue are not reimplemented. Details, and the measurements behind the numbers: `docs/catalog.md`.
- **A network source is not a file, and a surprising amount of the player assumes otherwise.** `isNetworkSource()` gates the three that matter: the thumbnail storyboard (it decodes the *whole* file in the background — over a stream that pulls the entire thing a second time, in an order unrelated to playback, while the player is trying to buffer), the folder queue (`folder_entries` would take a URL for a path), and "show in Finder" (nothing to show). Watch positions and remembered tracks work unchanged, since a URL is a perfectly good key. **yt-dlp is enabled explicitly** (`ytdl=yes`): the CLI turns the hook on by default, the manual is ambiguous about the client API, and a feature depending on which side of that line libmpv falls is not worth the saved line. Finding the binary is ours to do, because **a GUI process does not have the shell's PATH** — launched from Finder or Explorer it inherits the session's minimal environment, so a perfectly good `~/bin/yt-dlp` is invisible to mpv's own lookup. `ytdlp_path` probes the usual locations, *runs* the candidate (a file being present says nothing about it being runnable), hands mpv the absolute path through `ytdl_hook-ytdl_path` and puts its directory on PATH as well. Measured: the hook logs "No youtube-dl found … in config directories" — which is about mpv's config dir only — and then spawns exactly that absolute path. Expect the failure mode to be **staleness, not absence**: a September 2025 yt-dlp already fails on YouTube with "The page needs to be reloaded", so the error message names updating it rather than installing it.
- **File associations on macOS need UTIs, not extensions**: `bundle.fileAssociations[].contentTypes` → `LSItemContentTypes`. Without it only mp4/mov/avi worked, because modern LaunchServices matches by UTI and `CFBundleTypeExtensions` is a legacy fallback. `public.movie` is the supertype that covers formats declared by other apps (mkv); the explicit UTIs next to it are belt-and-braces. Tauri's association schema is `additionalProperties: false` — no comment keys.
- **Opening files ("Open with", associations)**: two delivery paths that must both work. Windows/Linux put the paths in `argv` (first launch) or route them through `tauri-plugin-single-instance` (already-running app); **macOS never puts them in `argv`** — Finder sends an Apple Event, surfaced as `RunEvent::Opened { urls }`, which is why `run()` is `.build(...)` + `.run(callback)` and not `.run(context)`. Both paths funnel into `deliver_files()`. **The event is a signal, not a transport**: the paths always go into a buffer first and the frontend fetches them with `take_pending_files` (argv is consumed once, via `argv_taken`). This matters because a single missed emit used to mean a silently lost file — the Apple Event lands long before `onMount`, mpv init takes hundreds of ms, and the webview may be inactive. There are therefore *two* independent triggers for draining: the event, and **window focus** — opening a file from Finder always activates the app, which makes focus a guaranteed backstop and is what fixed "opening a second file in an already-running player does nothing". `drainPendingFiles()` guards against re-entry so the two triggers cannot split one list between them.
- **Anything mpv keeps across a file change is a leak waiting to be noticed.** `video-rotate`, `video-aspect-override`, `panscan`, the A–B loop points and — measured — **`sub-delay` and `audio-delay`** all survive a `loadfile`, so a correction dialled in for one episode silently applies to the next. Every one of them is therefore given an explicit value on `file-loaded`: its own, or the default. The delays are stored per source in the track entry (the same store, because they answer the same question — how this file needs to be played — and outlive the position), and **never per folder**: a mux error belongs to one file, and applying one episode's correction to the next would be inventing a fault. The value written is read back from mpv rather than computed, since `nudgeDelay` uses `add` and mpv owns the result, and it is debounced because a delay is dialled in by repeated presses and only where it settles is worth keeping. Zero deletes the record instead of storing a zero, or resetting a delay would leave an entry behind for ever.
- **What a source *is* is not how the player reaches it.** Everything remembered about a video — position, chosen tracks, title — is filed under `sourceId()` (source.ts), not under the path. A path is a fine key for a file and a poor one for anything else: the same YouTube video arrives as `youtu.be/ID?si=<tracking>` from a share button and as `youtube.com/watch?v=ID` from the address bar, and a torrent stream (ROADMAP 21) is served from `http://127.0.0.1:<port>/…` where **the port changes every run**, so a key taken from the transport forgets the file every session. Local paths are their own identity, which is what makes this free: `sourceId('/a/b.mkv')` is `/a/b.mkv`, so every record ever written still reads and there is nothing to migrate. Records now carry `src` beside the key — the id answers "which video is this", `src` answers "how do I open it", and the two are only the same thing for local files. The resume snapshot deliberately keeps a path for that reason: it is not a lookup key. URL canonicalisation drops the fragment, lower-cases scheme and host but **not** the path (which is case-sensitive), removes tracking parameters and sorts the rest, and leaves `t`/`start`/`list` alone — dropping those would be a guess about what the viewer meant rather than a fact about the video. One consequence worth knowing: a network source gets **no folder scope** for remembered tracks, because a URL has no folder — taking one would put every video on a site into a single `youtube.com/watch` bucket deciding the dub for all of them.
- **A video's name is asked for only when it is not already free, and only from the site serving it.** mpv supplies `media-title` for anything that plays (yt-dlp resolves the page), so that is recorded into one cache keyed by `sourceId` and costs nothing. What it cannot cover is a link in the recents list that never played, or one whose title never arrived — there `oembed_title` asks **the provider's own oEmbed endpoint** (YouTube, Vimeo), never a third-party aggregator like noembed. The distinction is not fussiness: YouTube already knows you are watching the video because you are streaming it from them, while an aggregator learns it for the first time — the same objection that keeps subtitle search talking straight to OpenSubtitles. The cost is coverage, and it is the right trade because everything actually watched gets its name for free anyway. The lookup is skipped for private paths, runs one request at a time, and for the title bar waits a moment first to see whether mpv produces a title on its own.
- **The start screen shows the title the player showed, not the file name.** A path is written for sorting, not for reading, and for a link it is a video id with a tracking query attached — so `frameplayer.positions` carries the `media-title` mpv reported (the container's own metadata, or the name yt-dlp resolved) alongside the position. It is only ever overwritten by a real one: mpv reports `media-title` a beat after the file opens, and the null in between must not erase what an earlier viewing recorded. `displayName()` is the fallback for anything never watched long enough to be recorded — extension off, query and fragment off, dots to spaces *between non-space characters only*, so a name that already reads properly is left alone. It is also what the title bar falls back to, since mpv's `filename` for a shared YouTube link is `TfUP5fQcbCM?si=…`.
- **Start screen recents**: `RECENT_LIMIT` cards, candidates drawn from a pool 3× that size — a dead file (renamed, deleted, unplugged drive) is replaced by the next candidate rather than leaving a gap, and is *not* purged from the history, since an unplugged drive comes back and the record could not be rebuilt. **It is a rail, not a wrapping grid**, and that is a structural fix rather than a tuned number: a grid was the only part of the start screen that grew with its content, so once network entries stopped being dropped it went three rows deep and pushed the torrents section 220px below the fold at 1280x800 — measured, and a section nobody scrolls to may as well not exist. One row keeps the page a fixed height whatever the history holds. It needs **`justify-content: safe center`, never a bare `center`** — the same trap the start overlay already carries a note about: a centered flex container that overflows does so in *both* directions, and rendered with a bare `center` twelve cards began at the fifth with the first four unreachable off the left edge. The trackpad scrolls it with no work at all, because `.overlay` is in `WHEEL_SURFACES` and `onWheel` returns early there, handing wheel events straight to the browser. **The list is verified before it is published, and a missing poster is not evidence of a missing file.** It used to go on screen in full and then shed entries one at a time as `poster_frame` failed on them, which reads as the player briefly showing files that then vanish — a grid of black cards collapsing, including things renamed months ago. Worse, `poster_frame` opens a *path*, so it fails for every network source: a YouTube link or a torrent episode was dropped on that basis and could never stay in this list at all, which silently disabled resuming a torrent from a card. So existence is now settled up front by `paths_exist` (one batched `stat`, microseconds against a poster decode) for local files only — a URL does not rot the way a renamed file does — and the poster loop only decides whether there is a picture. A network entry keeps its place and shows the link mark, the same answer the end-of-file cards already give. The overlay scrolls, which needs two non-obvious things: `justify-content: safe center` (a centered flex container overflows in *both* directions, so the top of the content becomes unreachable — the scrollbar will not go there), and a wheel that scrolls rather than changing the volume, which is now one rule in `onWheel` (`WHEEL_SURFACES`) rather than a `stopPropagation` on each surface. The `::-webkit-scrollbar` rules in app.css are **universal, not opt-in** — Windows otherwise draws its native light-gray bar, which is wide and alien in a dark UI; declaring them also switches macOS off overlay scrollbars, so the two platforms stop diverging. They were a `.scrollable` class first, itself a replacement for a list of surface selectors, and both failed the same way: a surface that starts scrolling without anyone telling it to. The context-menu submenus inherited `overflow-y: auto` from the class they share with the menu and drew native bars on Windows — invisible on macOS, where the overlay bar is dark and nearly transparent. There is no page content here that should keep the platform's own bars, so the safe default is all of them. A horizontal bar also needs `height` — `width` alone styles the vertical one, which is why the horizontal bar came out two to three times thicker — and `::-webkit-scrollbar-corner` needs a color of its own, or the square where the two bars meet stays the platform's white. Related and easy to miss: **setting one overflow axis computes the other from `visible` to `auto`**, so a menu that only ever scrolls vertically still raised a horizontal bar (and lost a row's height to it) whenever a row was a fraction of a pixel too wide — `overflow-x: hidden` is part of making something scroll vertically, not an extra. The start overlay starts at `top: 48px` (title-bar content height) so the bar does not run into the window buttons, and mirrors its scrollbar reserve because its content is centered — holding space only on the right shifts it off-center relative to the title bar. That was `scrollbar-gutter: stable both-edges` and therefore did nothing on macOS (see the settings sheet above): measured, a centered child sat at 100/100 while the content fitted and at **90/110** once it scrolled, which is the whole shift the rule existed to prevent. It is now `overflow-y: scroll` plus a matching `padding-left`, measured at 100/100 in both engines and both states — and 10px wider than `both-edges` was on Chromium, which reserved a gutter on each side.
- **The start screen must be complete in its first frame.** `loadRecent` and `refreshTorrents` used to be fired un-awaited before `show()`, so the window appeared holding the panel and its two buttons and then grew a rail and a torrent list underneath them — a reflow on every launch, at the one moment the player has nothing else to do but be ready. Both are now awaited, which is affordable precisely because of where each one stops: the recents list settles after a single batched `paths_exist`, and its **posters keep filling in afterwards on their own** (`loadPosters`, fired and not awaited, guarded by the same `seq`). Awaiting the posters instead would hold the window for a dozen keyframe decodes, which is the trade this split exists to avoid — the cards are on screen at their final size with a placeholder, which is what stops the layout moving. `enterStartScreen` deliberately does *not* await: there the picker has to cover a stopped video immediately, and a list arriving a moment later is the lesser fault.
- **Start-screen layout must not depend on its own content.** `.overlay` is a `grid` with `place-items: center`, which sizes the column from content — so the recents grid was measured from the cards, and the cards changed as posters arrived, moving the whole page. `.overlay.start` overrides it to `flex` + `align-items: center` so widths flow container → children, plus a mirrored scrollbar reserve (`overflow-y: scroll` + `padding-left`; see the note above for why not `scrollbar-gutter`). Its padding lives on the inner `.start-inner`, never on the scroll container itself: a scroll container's `padding-bottom` is not part of its scrollable area, so the bottom gap vanished exactly at the height where the content was flush but no scrollbar had appeared yet. Separately, `restoreGeometry()` must `settleLayout()` before `show()`: the resize reaches the webview asynchronously, so the window was being shown with the layout of its previous size — the giveaway is the title-bar logo sitting too far from the right edge, since that is outside the overlay entirely.
- **A remembered track is a description, not an id, and its scope is the folder.** Track ids are positions inside one file — the Russian dub that is #2 in episode 1 is routinely #3 in episode 2 — so a choice is stored as `{lang, title, codec, forced, index}` and resolved against whatever the next file turns out to have. Resolution is **scored, not compared for equality**, because not one of those fields is guaranteed: releases exist with languages and no titles, with titles and no languages ("Rus"/"Jap" as names), and with two same-language tracks separated only by codec. Language +100, title +60, codec +12, a forced/full mismatch −50 (a forced track carries alien dialogue, not the script — never a silent substitute), position +5 as a tiebreak only; below a floor of 60 nothing is applied at all and mpv's own `alang`/`slang` stands, which is the right answer for an episode that simply has no Russian dub. Language codes are normalized through a 639-2→639-1 table rather than compared by prefix, because `jpn` and `ja` share one letter. The choice is written to **two** scopes: the file (what was playing here) and its **folder** (what to look for next door) — a folder is what a season is and what the play queue is already built from, where a global memory would carry an anime's Japanese track onto an unrelated film. A better match may still arrive after the first one is applied (external subtitles land a beat after `file-loaded`), so the pending restore keeps the score it acted on and re-applies only on a strictly better candidate, until its deadline or a manual pick clears it. Entries written before this carried plain ids; they are still read, exact in the one file they came from.
- **Restoring on resume has two traps.** The chosen tracks live in `frameplayer.tracks`, separate from `frameplayer.positions` because those entries are *deleted* past 97 % and a dub choice should outlive finishing an episode; only explicit picks are recorded, since mirroring mpv's own auto-selection would freeze it against later `alang`/`slang` changes. Applying the choice cannot be a one-shot on `file-loaded`: external subtitles found by `sub-auto` appear a beat later and setting `sid` to an id that does not exist yet silently selects nothing — hence the `$effect` that waits for the track to show up, with a deadline so it cannot hijack a manual pick made in the meantime. **But it must also run once immediately, and for two separate reasons.** The race: the pending restore is a plain `let`, so arming it triggers no effect — the effect next runs when a track list *changes*, and if this file's list finished loading before `file-loaded` reached us, no further change is coming and the restore silently never applies. The delay: mpv has already selected a track by its own `alang` and is decoding it, so every millisecond before the switch is a moment of the wrong dub, and there is nothing to wait for when the list is already there. Both halves call one `applyPending(audioList, subList)`, which takes the lists as **arguments rather than reading them inside** — a bare `void player.audioTracks` to register the dependency is the shape that has caught this project before, since an expression statement is what a compiler or minifier is entitled to drop. Separately, a resume seek must carry the knob with it, and that takes **both** halves of the fraction. `seekOnResume` sets `seekValue` optimistically and holds it with `seekSettling` (exactly as a drag release does), because otherwise it stays at zero until mpv reports the new position — a second on a 4K file — and then jumps across the bar in full view. But the knob is drawn as `seekValue / duration`, and `duration` only arrives once mpv has opened the file, which is *after* the OSC is on screen — so fixing only the numerator still leaves a visible frame at the far left. `primeResume` therefore fills both from the history record (the same numbers the "resuming" popup prints) at `beforeLoad` time, and `barDuration` hands over to mpv's own the moment it has one. Display only: seek maths must keep using `player.duration`, since you cannot seek in a file whose length is still a guess.
- **Watch history & privacy**: a file enters the history only once playback passes `min(15 s, 5 % of duration)` and leaves it again past 97 % — the relative half of that floor is not optional, a flat 15 s made anything shorter than ~15.5 s permanently unrecordable (a 17 s clip had a two-second window between "not started" and "already finished"). Writes happen on pause, on file change, on unload, and every ~5 s from `resyncState`. The start screen lists unfinished videos from `frameplayer.positions` with posters from `poster_frame` (reads a ready frame out of the storyboard cache when there is one, decodes a single keyframe otherwise; deliberately a throwaway session so it does not reset the live `ThumbState`, and loaded one at a time rather than eight decoders at once). Privacy has to be enforced in **seven** places or it leaks: `persistPosition`, `saveResumeSnapshot` (a plain-text snapshot that auto-restores after an update), the on-disk thumbnail cache, `subs_search` — those two live in Rust, hence `set_private_paths` and `thumb_service::is_private` — and `cast_load` (the frontend passes `hidden` from `isPrivatePath`, and cast.rs then names the URL after the token and sends no title to the TV). Seven is today's count, not a property of the design: **every new path by which something about a file leaves this machine is another enforcement point**, and the check is easy to forget precisely because such a path is usually being added for an unrelated reason. Subtitle search was predicted as the fourth and duly became it — a file hash sent to OpenSubtitles names what is being watched as surely as a stored position does; casting became the fifth the same way, a LAN URL and a LOAD title naming the file to the network and the TV; DLNA the sixth, and **watching together the seventh — and the most direct of them, because the other six speak to a service or to a device on the same network while this one names the file to other people**. That last one is `contentOf` in `sync/content.ts`, which is deliberately the only place a `ContentRef` is ever built: a private-root file publishes `{kind:'hidden'}` and the room is told nothing but that something is playing. Path matching is on a component boundary (`/Movies` must not swallow `/Movies2`), case-insensitive and separator-insensitive **on both sides**, and it is mirrored in JS (`pathUnder`, now in `format.ts` beside `samePath` and `normalizePath` — there had been three copies of "compare two paths" and the privacy one was the laxest) and Rust (`path_under`). "Change one, change the other" is no longer a note: the cases live in **`shared/path-under.txt` and both test suites read that file**, so a vector added there fails on whichever side does not already agree. Verified by adding a contradictory case and watching both go red. Each side also asserts a floor on how many vectors parsed — a file that moved, or was reformatted so every line reads as a comment, would otherwise pass in silence, which is the one way a shared contract quietly stops being one. **Excluding a folder also erases what is already recorded for it**, and that is a correction rather than a refinement: filtering on read (which is all it used to do) left the entries in localStorage and the frames in the thumbnail cache, so the start screen was clean while the disk was not — and removing the folder from the list brought everything back, which is how the gap was found. **Which stores those are is a list, `IDENTIFIED_STORES`, not three lists.** Three operations walk the same set — excluding a folder, forgetting a torrent, clearing the history — and each used to enumerate it by hand, which is one copy too many before they even disagree. They did: **`clearHistory` named three keys and cleared three of six**, so asking for everything to go left the remembered titles (keyed by source id, which for a local file *is* the path — that store on its own is a list of everything ever watched), the per-folder track memory, and the path of every subtitle the player had downloaded. Now one list, three predicates: a folder asks a path-shaped question (`pathUnder`), a torrent an id-shaped one (`torrent:<hash>/` prefix), and clearing asks for the key itself — a store the predicate has nothing to say about simply matches none of its entries, which is why the path-keyed stores need no special case when a torrent is forgotten. The identity is not always the key: positions carry `src` beside it, because the id answers "which video" and `src` answers "how do I open it", and the two only coincide for a local file. `frameplayer.links` is deliberately outside the list (a URL has no folder, so nothing in it can belong to one) and is cleared by name. Thumbnails are handed to Rust. The tests restate the store list rather than importing it, on purpose: a test walking the same registry the code walks would pass for a store the registry has forgotten, which is the only failure worth catching. The folder is added to the list **before** the purge runs, so a write racing it — the position timer fires every ~5 s — is already refused rather than landing behind the deletion. Purging thumbnails is what forced `CACHE_MAGIC` to v4: the cache file name is a hash of path + size + mtime, so without the source path *inside* the file an entry cannot be attributed to a folder at all. Entries in an older format are deleted too, since they cannot be attributed either and are unreadable to the current build anyway. Because this deletes data irreversibly, the settings hint says so before the folder picker opens. "History off" is a separate `all` flag, **not** a synthetic `/` root: roots get their trailing separators trimmed, so `/` collapses to an empty string and would match nothing.
- **The mini player is a window mode, and every other size mode has to know about it.** With `wid` embedding there is no true picture-in-picture to reach for — the video is a child view of our own window — so it is a small always-on-top window with the chrome out of the way, which is 80 % of the value out of parts that already existed. What it cost was the interactions, and each one is a trap someone would otherwise find later: **the minimum window size has to be lifted first** (`minWidth`/`minHeight` are 480×320 in tauri.conf and a smaller request is silently clamped — the window simply would not shrink, with nothing to say why), and put back on the way out; **geometry must not be captured while mini**, exactly as it is not while fullscreen or maximized, or the next launch opens a thumbnail in the corner; **fit-to-video stands down**, or the next file's aspect undoes a size the viewer chose; **always-on-top is owned by the mode** and the pref restored on exit; **fullscreen and mini each leave the other** on the way in; on macOS the mode also **floats over other applications' fullscreen spaces** (see below); on macOS the **traffic lights are hidden outright**, since in a 420 px window they sit on the picture; and going back to the start screen leaves mini, because the button that leaves it is drawn over the video. Dragging still works without the title bar: dragging the video area moves the window, which it already did — and the window is **magnetic** there (`snapMini`, on by default, in the window submenu): dragged within `SNAP_DIST` of a resting place it goes the rest of the way, to the same padded corner it opened in. Snapping and clamping answer different questions and both are needed — snapping owns the band near an edge, clamping owns everything outside the work area, since a mini window hanging off the screen has no title bar to grab it back by. The constraint that shapes it: **a native drag runs its own event loop and never says when it ends**, so "stopped moving for `SNAP_SETTLE_MS`" is the only signal there is, and the number is a compromise — long enough that a pause mid-drag rarely reaches it, short enough to read as the window settling rather than moving on its own later. The move itself is **animated from the frontend** — one `setPosition` per frame over `GLIDE_MS`, eased out, driven by elapsed time rather than a frame count so a slow round trip stretches the steps and not the animation. There is no animated `setPosition` to call instead, and a window that teleports reads as a glitch: the eye has nothing to attribute the new position to. Its exit button is **round**, and that is not a style choice — a rounded rectangle inset from the window's own rounded corner has to obey the concentric rule (inner radius = outer minus the gap), and the outer radius is not ours to know: macOS picks one, Windows 11 another, and either can change with the OS. A circle has no corner to disagree with, which is why the system's own corner controls are circles. Two things this cost that are worth stating on their own, because neither announces itself: **a window API the frontend has never called before needs its capability added** — `setMinSize` was not in `capabilities/default.json`, so the call *rejected*, and with the geometry work sitting behind a bare `catch {}` the feature entered mini chrome on a window that had not moved or resized at all. Hence the mode flag now flips **after** the geometry lands, and failures are logged: "P does nothing" is a far better bug than a mode that half-applied. And **hiding a grid item does not re-center the rest** — `.controls` is `1fr auto 1fr`, so dropping the two side clusters left the remaining one auto-placed in the first column, i.e. the mini controls sat against the left edge; `justify-content` on a grid whose columns are `1fr` changes nothing.
- **Floating over another app's fullscreen is decided by the window's class, not by its level — and every plausible guess about it is wrong.** "Always on top" only lifts a window above the others *on its own space*, and a fullscreen app is a space of its own, so the mini player vanished exactly when a small player on top is wanted; it is the one thing a system PiP panel does that an always-on-top window does not. Everything below was measured with a probe app that put labeled windows in each configuration and screenshotted them over a fullscreen TextEdit, because three rounds of reasoning got it wrong first. **The level is irrelevant**: a plain `NSWindow` does not reach the space at floating (3), modal (8), main-menu (24), status (25), pop-up (101) *or* `CGShieldingWindowLevel`, which is above everything the system itself draws. **`CanJoinAllSpaces | FullScreenAuxiliary` is necessary but not sufficient** — every probe window had it. What decides it is **an `NSPanel` whose style mask carries `NonactivatingPanel`**, and it then works at level 3; either half alone fails (a plain window with the bit does not float, a panel without it does not float). Since the window is tao's `TaoWindow` and we never get to ask for a panel, it is **promoted in place with `object_setClass`** and put back on exit — verified in both directions over a fullscreen app. That is only sound because **`NSPanel` adds nothing to `NSWindow`** (measured: `class_getInstanceSize` 520 for both, zero own ivars), so only the method table changes; the size is re-checked at runtime anyway, and a future macOS that grew NSPanel would get a no-op rather than a corrupted window. Three consequences. `TaoWindow`'s overrides are gone while promoted — `canBecomeKeyWindow`/`canBecomeMainWindow` fall back to NSPanel's defaults (**key yes, main no**) and `sendEvent:` (tao's `movableByWindowBackground` drag) is not in use here anyway. **Nothing may call `set_focusable` while mini is on**: tao looks its `focusable` ivar up by name and NSPanel does not have it, so that panics inside tao rather than failing quietly. And `hidesOnDeactivate` must be forced off, because panels hide themselves when the app deactivates and switching to the fullscreen app *is* a deactivation. The restore has its own trap: **`FullScreenPrimary`, the flag that makes a window fullscreen-capable at all, shares an exclusivity group with `FullScreenAuxiliary`** (AppKit takes at most one from each group), so it comes off while mini is on and forgetting to put it back leaves `setFullscreen` silently doing nothing — hence the whole previous state is saved and written back verbatim rather than recomputed, and restored **first** on the way out, where the awaited window calls after it travel the same main-thread queue and act as a barrier for `toggleFullscreen`, which leaves mini on its way in. What this does *not* buy is corner tucking and pinch resize; those need the private `PIPViewController` route IINA takes, which would additionally mean reparenting mpv's `wid` view into a system panel — leaving gotcha 10's hole in our own window — and giving up the HTML overlay with it.
- **Placing a floating box is three rules, and they belong in one place.** Flip to the other side of the anchor when the preferred one has no room, shift along the other axis to stay inside, cap the size when the box is simply bigger than the space. `floating.ts` is those rules as two functions (`flipAxis`, `shiftAxis`) with unit-tested arithmetic; tooltips, the context menu and its submenu all placed themselves before, which is exactly why each of them was wrong in a different way. Floating UI would be this plus scroll containers, virtual anchors and auto-update — none of which exists here (one non-scrolling viewport, every anchor a real element), so the dependency buys nothing the 40 lines do not. Three findings are baked into the call sites. **A box laid out at `left: x` may only use the width to its right**, so a tooltip near the right edge wrapped to one word per line — and the measure-then-clamp pass that followed read the *wrapped* width and called it a fit, which is why it never recovered. The tip is therefore laid out at the window origin and moved with a `transform`, which happens after layout instead of deciding it. **A cap is not a clamp**: in the mini player the context menu is taller than the whole window, so no position shows all of it and it has to scroll — hence `max-height` from the placement's `room`. And **a panel must not be rendered inside a scroll container it is meant to escape.** The moment the context menu got a `max-height`, its submenus were cut off at its edge — only the sliver overlapping the menu's own box was left. `position: fixed` in viewport coordinates is supposed to be the escape, and it measures as one: a fixed box inside an `overflow: auto` parent lays out *and hit-tests* at full size in both engines (checked in headless Chrome and in a WKWebView harness built for this, since macOS is WebKit and Windows is Blink). It was still cut off on screen. Rather than argue with the screen, the submenus are now rendered as **siblings of the menu** instead of children of the item that opens them — nothing about the placement changed, since it was already in viewport coordinates, and the hover bridge is geometric so it did not care either. The parent still closes them on scroll: fixed panels do not travel with the content underneath. The general rule that came out of it: when a floating panel has to leave its parent's box, take it out of the parent, and keep `overflow` for things that are genuinely inside. Two more traps live in the same code. **A cap only means what the placement measured because every box is a border box** — the reset in app.css is what makes `max-height` cover padding and border, and before it existed the menu rendered 14px taller than it was told, ate the 8px margin it was meant to keep and ended up past the window edge, which read as "the placement has no padding". Anything new that hands a floating box a size inherits that guarantee and must not opt out of it with a local `box-sizing`. And **a submenu needs a plan for having no room at all**: in the mini player the window is narrower than two menus side by side, and flipping to "the roomier side" then half-overlaps the parent, which reads as a menu growing out of its own middle and being clipped by it. When the chosen side cannot fit the box (`room < size`), it is placed *over* the parent and aligned to it instead — the drill-down every small-screen menu uses. **That changes how submenus open, not only where they land**, which is the half that is easy to miss: a submenu covering its parent must not open on *hover*, or the parent stops being usable — every pointer move across it lands on another submenu head, and it cannot even be scrolled, so reaching an item means aiming at the corners of the ones that are not submenus. Below `SIDE_BY_SIDE_MIN` (the two menus' widths plus their margins) hover is therefore inert, the parent is hidden behind the panel (`visibility`, so the placement can still measure it — which works only because the panel is no longer its descendant), and the panel carries a back row, since otherwise the only way out is closing the menu and opening it again.
- **The player's wheel gestures stop at the edge of any floating surface.** Vertical is volume and horizontal is a scrub, which is right over the video and wrong over a list — scrolling the queue was changing the volume. The rule lives once in `onWheel` (`WHEEL_SURFACES`, matched with `closest`), not as a `stopPropagation` per surface: that list is invisible until the one surface missing from it is found by hand, which is how the queue, the chapter list and the context menu all ended up missing. Ctrl+wheel still calls `preventDefault` everywhere, surface or not — without it the webview zooms the whole UI and there is no way back.
- **The HTML resize edges are Windows-only, and on macOS they were actively harmful.** `startResizeDragging` reaches `drag_resize_window`, which on macOS is a stub returning `NotSupported` — and Tauri discards the error (`let _ = ...`), so nothing anywhere reports that the call did nothing. The eight `.rz` strips are 5px wide, sit *inside* the window at `z-index: 50` and set their own `n-resize`/`e-resize` cursors, so on macOS they took the band AppKit uses for edge resizing and turned it into a dead zone that still looked live: the arrows appeared, the press was swallowed, and the window only resized when the pointer happened to land in the system's band **outside** the frame — which reads as "resizing works sometimes". They are needed on Windows, where the window is `decorations: false` and there are no system edges at all; on macOS the window is `Titled | Resizable` and AppKit handles edges and corners, including the outside band no DOM element can reach. General shape of the trap: a platform-stubbed API plus a discarded error means a control that is present, styled and inert.
- **Window prefs & the macOS menu bar**: settings live in `localStorage` (`frameplayer.window`: remember geometry / fit to video / always-on-top), restored **before** `show()` — restoring a visible window reads as a jump. `window_guard::clamp_to_visible_area` was written for this and was inert until now (the window was always `center: true`). Geometry is never captured while fullscreen or maximized, or it would restore as a monitor-sized window with no maximized flag. `fitWindowToVideo` must fix the **position** too, not just the size: a window grows from its top-left corner, so one near the right/bottom edge grows off-screen. Bounds come from `Monitor.workArea` (already excludes Dock and taskbar — the old `size * 0.95` guesswork was wrong in both directions), inset by `SCREEN_PADDING`. If the requested size fit, the window keeps its place and is only pulled back inside; if it had to shrink, the old position is meaningless and it is centered. The macOS menu (`macos_menu.rs`) owns no state: items emit their id to the frontend, which runs the *same* functions as the context menu, and `sync_window_menu` pushes checkmarks back. **Accelerator rule**: only Cmd-combinations may be used. A menu accelerator makes the OS swallow the key before the webview sees it, so any single-key accelerator would silently replace the `e.code` hotkey rather than complement it. **The menu bar is also load-bearing for text editing**: replacing Tauri's default menu removed its Edit submenu, and without those items AppKit never delivers ⌘V, ⌘X or ⌘A to a focused field — the link dialog simply could not be pasted into. The Edit menu is back, deliberately **without Copy**, because ⌘C is this player's "copy the current frame" and a menu item would swallow it; copying text works through the right-click menu instead, which is why `onContextMenu` and the dialog backdrops leave editable elements to the system rather than calling `preventDefault` on everything.
- **A link promises navigation; an action gets a button.** `.settings-link` is for "show mpv.conf in Finder" and nothing else. Destructive actions are `.btn-danger`, and secondary actions next to a `.primary` — "open a link", "install yt-dlp" — are `.btn-outline`: they open a dialog or download a binary, which is not navigating anywhere.
- **Hiding the cursor must trail the native button hide, never race it.** `set_buttons_visible` hides the traffic lights with `setHidden`, which asks AppKit for a title-bar relayout — and a relayout resets the window's cursor rectangles, putting the arrow back. With `cursor: none` applied at the same moment as `idle`, it was undone ~40 ms later, and with the pointer standing still nothing re-applied it (WebKit updates the cursor from mouse events), so it blinked once and stayed. The tell is that it looks like a windowed-only bug while nothing in the cursor code mentions fullscreen: in fullscreen `set_buttons_visible` returns early, so there is no relayout to undo it. Hence `CURSOR_HIDE_MS`, a margin covering the button timer, the command round-trip, the main-thread hop and the relayout. Only the hiding is delayed — showing the cursor again answers the pointer moving, where any lag is felt at once.
- **Hiding the cursor on idle has exactly one exception, and it is a corner, not a band.** `.player.nocursor` applies in windowed mode too — there is no fullscreen condition. The exception is the macOS traffic lights: hovering them stops the webview from receiving mousemove, so the cursor sticks there, the idle timer fires anyway, and hiding it would be wrong because the user is working with the native popup on the green button and we cannot see it. That exception was originally the whole 48 px band across the full width on both platforms, which reads in use as "the cursor never hides in a window" — the pointer lands in that band constantly after dragging the window or using the buttons, while in fullscreen it rarely does, so the behavior looked like a windowed-vs-fullscreen difference that does not exist in the code. It is now `IS_MAC && y <= 48 && x <= 110`; Windows needs none of it, because the window buttons there are our own HTML and stop being hit-testable once the bar fades. Worth knowing when this comes up again: `cursor: none` cannot leak outside the window — it is a property of our document and only applies while the pointer is over our content, and re-entering the window fires mousemove, which restores it.
- **A `$derived` re-evaluates the moment it is read again, not at the end of the tick.** So an event handler must read the derived object it is acting on *once*, before it touches anything that derived depends on. The skip button got this wrong — `skipUsed = skipHint.from; seekChapter(skipHint.next.index)` — and the second read returned `null`, threw, and left a control that visibly disappeared (its block had already unmounted) while doing nothing at all. Verified against the real compiler and runtime rather than guessed: compile a runes module with `compileModule`, read a derived, mutate its dependency, read it again — it is already the new value. Destructure first (`const { from, next } = skipHint`) and the whole class of bug goes away. Worth knowing that the symptom is silent: the exception dies in the handler, so what the user sees is a button that vanishes on click.
- **State lives in `.svelte.ts` modules, not in a store library.** Runes work outside components, so a module exporting a class instance with `$state` fields *is* the store — with per-field reactivity a subscription-based store cannot match. Three rules: never export a `let` that gets reassigned (the importer gets a snapshot — use a class field or a getter function, as `osd()`/`locale()` do); keep the dependency direction one-way (`history`/`window-prefs`/`zoom` → `player` → nothing); and **never write a `$effect` at the top level of one**. That last rule is the only one in this list whose violation is completely silent: `svelte-check` reports nothing, `npm run build` succeeds, and the app throws `effect_orphan` the moment the module is imported — which for a module the page imports means a window that never paints. Measured against the real compiler rather than reasoned about: `compileModule` on a two-line probe emits a bare `$.user_effect(…)` at module scope, and importing the output throws. The shape that works is an exported `initX()` called during a component's initialization (`trackTorrentPlayback`, `initChrome`, `initEndScreen`), and it must be a **block** body — `const f = () => $effect(…)` is rejected outright by the compiler with "`$effect()` can only be used as an expression statement", which is the one form of this mistake the build does catch. `npm run check-runes` is the gate; it reports a `$effect` *statement* at brace depth zero and deliberately ignores one inside any function, since an arrow body does not run until it is called. The page is where they meet: `initPlayer` takes hooks rather than the module reaching back into the page, because that observer callback used to be where every concern in the app collided. **A `$effect` is not a substitute** for the `property` hook: the seekbar guard (`!dragging && !seekSettling && …`) has to run *only* on a time-pos report, whereas an effect would also re-run when the guards themselves flip — which is precisely the "knob jumps back on release" bug the guard exists to prevent.
- **Splitting further.** The page went from 11 727 lines to ~1 600 — twenty-four components and twenty-two `.svelte.ts` modules — of which ~1 100 is script. Four traps came out of doing it, and all four are silent. **A rule whose markup moved into a child stops matching** and the compiler does not say so — `.overlay.start` cost the start screen its flex layout with a clean build, which is why `scripts/css-orphans.mjs` exists; it reads class *and* element selectors, since `input[type='range']` was left behind the same way and the sliders reverted to the platform's. **`@keyframes` is scoped too**, and the `animation` shorthand is only rewritten inside the same component — a keyframe block left behind points the rule at a name that no longer exists, which happened four times (`spin`, `torchip-pulse`, `osd-in`/`skip-in`, `end-advance`) and now has its own check. **A state written as an ancestor cannot cross the boundary**: `.player.mini .topbar` and `.player.no-video .topbar::before` became props on the bar's own element. And **moving a rule between files changes the cascade order**, which decides equal-specificity conflicts; while the split was under way that was watched by diffing the built stylesheet against the previous tree, which is the only place the compiled order is visible. Reusing a class still means beating it: write `.menu-item.chapter-item`, never a lone modifier. The seekbar and scrub were the riskiest part and moved last, as a unit, into `seek.svelte.ts`; their invariants are in architecture.md and still no test covers them.

  **Shared vocabulary is the half of the CSS split that the first sweep missed entirely.** Moving markup out is visible; leaving a class's base rule behind while *another* component keeps using it is not, because the rule is still used where it is declared. `.speedopt` styled both the speed presets and the delay stepper while they lived in one file; afterwards the presets kept the rule and the stepper got only its own `.delayrow .speedopt` override, so its −/+ rendered as macOS push buttons — reported as "the symbol sits a pixel or two above center", which is what a native pill looks like when you take it for the intended design. The same sweep found four more (`.link-actions` in two dialogs, `.cast-hint` in the track menu, `.queue-row`/`.queue-remove` in the external-subtitle rows). The rule that follows: **a class two components draw belongs in `app.css`**, and only the part that is genuinely one component's stays behind — `.queue-row.dragging` did, since nothing else drags. Two things about detecting it, both learned by watching the check stay silent on a bug that was in front of it: a base rule is the **whole** selector `.C`, not merely a selector *ending* in `.C` (`.delayrow .speedopt` ends in one and is exactly the override that presumes a base), and `.C:hover` is not a base rule either (`.speedopt:hover` had stayed behind in `app.css` and stood in for the rule that had not).

  **`src/` has no import cycles, and now something says so.** "Keep the dependency direction one-way" had been a rule since the state modules were introduced and nothing enforced it: a cycle costs no error, no warning and no build failure, because the bundler resolves it — what it costs is a module-evaluation order nobody chose, where whichever file is imported first wins and the other reads `undefined` for anything at module scope. One had been alive for months (`thumbs` ⇄ `torrent`), and only the *notification* half was wrong: `thumbs` asking the torrent client where the data is (`positionBuffered`) is a fair question about its state, while the torrent client telling the thumbnail service to start is knowledge it has no business having. The general fix is to turn the notification into a **callback the composition root supplies** — `trackTorrentPlayback(maybeStartThumbs)` — not to invent a third module for the pair to share. `npm run check-imports` is the gate.

  **A hook is a debt, and a second borrower is when it comes due.** The file-dialog dimming flag started as a hook on `open.svelte.ts` — the page owned `chrome.fileDialogOpen`, so the module was handed a setter. The moment the track pickers needed the same flag that would have been two hooks for one boolean, which is the point at which the indirection stops paying: it is now `withFileDialog` on `chrome`, and both modules borrow it. The rule that came out of it is narrower than "avoid hooks": a hook is right when the page holds something the module genuinely must not know about (`chrome.overlayOpen` — the shell must not import a dialog), and wrong when it is only routing a value that has an owner already.

  **What is left in the page is the composition root, and that is the destination rather than a leftover.** `onPlayerProperty` and `onFileLoaded` stayed: they are the place the modules meet, which is exactly what `initPlayer` taking hooks is for — that observer callback used to be where every concern in the app collided, and the fix was never to move it somewhere else but to make every line of it a delegation. `onFileLoaded` is now twenty lines of calls into eight modules and nothing else, and a line that starts doing work in place instead of naming who does it is the signal that a module is missing.

  Splitting the *script* added four traps of its own, and they rhyme with the CSS ones: what moves is easy to see, what is left pointing at nothing is not. **A blanket rename does not know what is a name** — renaming `fullscreen` → `chrome.fullscreen` across the page also rewrote `case 'fullscreen':`, which is an `ActionId` string and had nothing to do with the variable (TypeScript caught that one only because the literal became an unknown member of the union), and it rewrote every mention inside prose, leaving twenty comments reading "while chrome.fullscreen" and "the chrome.idle timer". **A state the extracted module now takes as an input has to be given to it** — `chrome.overlayOpen` replaced `openMenu !== null || settingsOpen`, and nothing assigned it, so the chrome faded out from under an open menu with a clean build and no error anywhere. And **the copy left behind is worse than no copy**: the window-buttons effect ended up in both files, one of them with the `settingsOpen` term rewritten to a literal `false`, so two effects called `syncWindowButtons` with different answers and the winner was whichever ran last. And **a `bind:this` does not travel with its markup unless somebody carries it**: the torrent update dialog's input kept its declaration and its `?.focus()` in the page while the binding stayed behind in the markup that became a component, so the field silently stopped being focused — an optional chain on `undefined` is not an error. That one shares its shape with the `overlayOpen` bug, which is why `npm run check-runes` also reports a `$state` that its own file never writes; it found the dialog immediately, and one dead `let ctxEl` beside it. The lesson under all four: after moving something, grep for what used to *write* to it, not only for what reads it.
- **A hotkey is a row in a table, and three things move with it.** `ACTIONS` in [keys.svelte.ts](src/lib/keys.svelte.ts) is the only place a default binding is written; `onKeydown` normalizes the event to a chord (`ctrl+alt+shift+meta+<code>`, modifiers in that fixed order so the string is comparable) and dispatches. Overrides go to `frameplayer.keys` **sparsely — only what the user changed**, so a default corrected in a later version still reaches anyone who has opened the editor. Three consequences that are not obvious until something breaks. **Modifier overloads had to become separate actions**: `KeyS` was `saveScreenshot(e.shiftKey)` and the arrows were three things each, which an editor cannot express — "rebind screenshot" would mean rebinding a key *and* a modifier convention. **`noRepeat` and `quiet` are fields of the action**, since "holding this must not re-fire it" and "this already raises a popup" are facts about what happens, not about which button was pressed; as key-code lists they silently followed the old key after a rebind. And **a bound chord now gets `preventDefault` unconditionally** — per-case was fine while `Ctrl+=` was always the audio delay, and wrong the moment a viewer can put anything there while it stays the webview's zoom. **Escape needs it too, and was the one reserved key that skipped it.** In a fullscreen window AppKit answers `cancelOperation:` by leaving fullscreen, so Escape was being handled twice: `closeTopmost` shut the settings sheet and the system dropped the window out of fullscreen in the same keystroke. Nothing showed on Windows, where the window is undecorated and Escape means nothing to the system. Consuming it also keeps the no-dialog case ours, which matters because `exitFullscreen` is what keeps the mirror honest — letting AppKit do it is the path that leaves `isFullscreen()` disagreeing with the button (see 15). What the editor refuses is as load-bearing as what it accepts: bare 0–9 (one parameterised action across ten keys), Escape and Enter (contextual — they unwind dialogs and take whatever is being offered), and on macOS **every accelerator the menu bar owns**, because the system swallows those before the webview sees a keydown and the binding would look accepted and never fire (`MAC_MENU_ACCELERATORS`, kept in sync with `macos_menu.rs` by a note at each end). Recording runs a **capture-phase** listener on the window — the player's own handler is a bubble listener on that same window, so stopping propagation on the way down is what keeps recording a binding for "полный экран" from going fullscreen while recording it. Labels are **US-QWERTY on both platforms**: `navigator.keyboard.getLayoutMap()` would give the active layout's label (Я for `KeyZ`) but it is Blink-only with no WebKit implementation, so using it would make one build print different badges on Windows and macOS; mpv, IINA and VLC all print the US name. Twenty-two places used to spell a key out — twelve in markup and eight inside a translated sentence (`'Играть/пауза (пробел)'`, `'Звук (M)'`) — and all of them now read `hint()`. A translation carrying a key in its text is the regression to watch for, and the sweep that finds them is a grep for a parenthesised key name in [i18n.svelte.ts](src/lib/i18n.svelte.ts); the two remaining `(Esc)` are deliberate, since Esc is reserved and cannot move.
- **Localisation**: user-facing strings live only in `src/lib/i18n.svelte.ts` and reach the UI through `t('key')` / `t('key', { param })`. `t()` reads reactive state, so switching the language re-renders everything — including the `SETTINGS` array, which is `$derived` for exactly that reason. Two things do not follow that path and are easy to miss. **The macOS menu is built natively in Rust** (`macos_menu.rs`) and cannot reach the dictionary: it carries its own `EN`/`RU` tables, is built in English at startup, and the frontend corrects it from `onMount` via `set_menu_locale` — a new menu item means editing both tables. Rebuilding the menu also replaces the check-mark items, hence `MenuChecksState` behind a mutex (`manage` keeps the *first* value it is given) and a `Once` around `on_menu_event` (handlers stack, so re-registering would fire every action twice). **Platform wording gets separate keys** (`ctx.reveal_win`/`ctx.reveal_mac`, `set.hdr_off_win`/`set.hdr_off_mac`), never a branch inside one string — the two sentences differ by more than a word in at least one language. Note `t` is now a module-scope binding: don't shadow it with a loop variable.
- **The language of the interface and the language of the film are different questions, and conflating them was a bug with a name.** Every language choice in the player used to offer exactly two — `alang`/`slang` in the settings, and the subtitle-search filter — which was never a decision about languages: it was the *translation set* leaking into content preferences. There are two translations because there are two; what is being watched has nothing to do with that, and anyone with Japanese audio and Polish subtitles was simply not served. `languages.ts` is the fix and is **one table**: 639-1 code, the language named in itself, and the 639-2 spellings. Everything else is derived from it — `LANG_ALIASES` (which the remembered-track scoring uses to know `jpn` and `ja` are one language), `mpvLangValue`, `parseLangList`, `searchLanguages` — rather than kept as a second copy that drifts, which is exactly what the old alias map beside it had become. Four rules the code depends on. **Each language is named in itself**: someone hunting for Polish subtitles is looking for "Polski", and that also keeps 60-odd languages out of the `t()` dictionary, where they would be 120 strings saying the same thing and where the one entry a viewer needs is the one nobody translated. **A chosen language expands to all of its spellings, adjacent** — `--alang` is an ordered priority list, so `ja,jpn,en,eng` means "Japanese however it is tagged, else English", while grouping by spelling would let an `eng` track beat a `jpn` one. **The list is derived from the mpv.conf line, never stored beside it**, which is what makes a value someone typed by hand show up correctly and why nothing needed migrating: the two values this dialog used to write, `rus,ru` and `eng,en`, parse back to exactly `[ru]` and `[en]` (tested, along with the round trip, the B/T collapse `ger,deu,fre` → `[de, fr]`, and unknown tags being *kept* — the line is theirs and silently dropping an entry would change what mpv selects). And **search is ranked, not filtered in table order**: prefix-matching codes puts near-misses first — measured, typing `ru` matched Romanian ahead of Russian through its own `rum`. The control is a new `SettingDef` kind (`langs`) rather than a pill row, because `.segmented` picks one of a few *named* values and this is an ordered list drawn from sixty; chips carry the order, clicking one promotes it to preferred (order is priority, and without that the only way to change it is to remove everything above and re-add, which appends and therefore does not even work). The subtitle-search filter is those same preferences plus "любые", and it reads them from **mpv**, not from `settingsValues` — that map is filled when the settings dialog opens and is empty until then, so the filter would have depended on whether the viewer had been into settings this session.
- **"No subtitles in a language I am already hearing" is mpv's option, not ours, and its rule is not the obvious one.** `subs-with-matching-audio` — choices `no`/`forced`/`yes`, default **`yes`** on mpv 0.41 (read out of `options.c`, not assumed, which is why `null` is the "показывать" pill). Building this ourselves would mean reimplementing `select_default_track` and then fighting it *and* the remembered-track restore. Two things about the semantics, both from the source and both different from what one would design by hand. It gates on `mp_match_lang(langs, audio_lang)` — **the whole `slang` list against the selected audio track**, not the candidate subtitle's language — so with Russian audio and `slang=[ru,en]` the answer is *no subtitles at all*, not "skip Russian and fall through to English". That is the better rule: someone watching a Russian dub does not want English subtitles, they want none. And the consequence that follows from the same line, which the hint has to say out loud: because it tests the whole list, having `en` in your **subtitle** languages means an English-audio film gets no automatic subtitles either. That is what makes `forced` the sane middle rather than a curiosity — a forced track is alien dialogue and signage, exactly what you still want in a film you understand, and it matches what the track scoring already believes (`-50` for a forced/full mismatch). One more consequence worth knowing before it is reported as a bug: an external subtitle found by `sub-auto` is gated too, so with `no` a `.srt` sitting beside the video is not auto-selected when the audio matches. A subtitle downloaded through the OpenSubtitles panel is unaffected *that* session — `attachTrack` uses `sub-add … select`, which is an explicit pick — and only meets this rule on the next playthrough.
- **Focusing an input scrolls it into view, and that silently undoes whatever scrolling you just arranged.** The subtitle panel's sign-in form unfolds at the bottom of a box that already scrolls (`.settings` is `max-height: 100%; overflow-y: auto`), so opening it has to bring the form into view or the button reads as doing nothing. Scrolling there and *then* focusing the first field looks correct and is not: the browser's own scroll-on-focus runs afterwards, is instant where ours is smooth, and lands the field near the top — leaving the form's buttons under the fold, which is the half that mattered. `focus({ preventScroll: true })` is half the fix, and the scroll is aimed at the form with `scrollIntoView({ block: 'end' })` rather than at the container's `scrollHeight`, so it stays correct whatever else the panel is showing. The other half came from a WKWebView harness built against this exact structure, because two plausible causes had to be ruled out rather than argued about: **a nested scroll container is not the problem** (every API — `scrollIntoView`, `scrollTo`, `scrollTop`, smooth or instant — reaches the bottom of a `max-height` box), and **neither is the form being inserted on click** (it works with no waiting at all, `tick` or `requestAnimationFrame` notwithstanding). What does fail is the combination: with a `focus()` call nearby, a **smooth** scroll stops 710 px short of 717 — *and `preventScroll: true` does not save it*. So the scroll is instant, which lands exactly, and runs a second time on the next frame to cover the box still settling as the form unfolds. General rule: when a scroll "does nothing", suspect a focus call before suspecting the scroller.
- **Every box is its border box, and every size written down is an outer size.** The reset (`*, *::before, *::after`) lives in app.css. The project went without it for a long time and the cost was never legible as a box-sizing problem: the symptom is always "something is a pixel or two off", found by measuring, and the cause is always a border or a padding sitting outside the number somebody wrote. Four in one session — the mini player's exit button breaking the concentric-corner arithmetic, the preview's crossfade layer 4px too big over a `height: 100%`, the context menu 14px taller than the cap the placement gave it, and the carousel arrow a 34px circle in a 32px button — each fixed by a local `box-sizing: border-box`, nine of which had accumulated. That is the reset written one element at a time, and only where somebody had already been bitten. The one thing the reset does **not** change is `<button>` and `<select>`: both engines already make those border-box in their own stylesheets (measured in headless Chrome and in a WKWebView harness), which is why all nine local declarations sat on a div, a span, an img or an input, and why a `<button>` with `width: 100%` and padding never overhung its parent. Do not "compensate" a button's size for the reset — it was already outer. Everything else was adjusted so the pixels did not move: 43 of the 44 boxes measured before and after are identical in both engines, and the exception is the hover preview's height, where `aspect-ratio` follows box-sizing and so now shapes the outlined frame rather than the picture inside it (1.75px, documented at the rule). Two latent bugs the reset fixed rather than preserved, both in the settings sheet, both from `100%` meaning "the container plus my own 38px": at full height it stood 32px taller than the backdrop's padded grid area and reached 39px from the top of the window, *under* the 48px title bar the 56px of padding exists to clear; and in a narrow window it escaped the 24px side inset entirely, sitting 5px from each window edge. It now fits exactly, which below ~646px of window width also means it is 38px narrower than it used to be and the tab row scrolls sooner — the row is built to scroll, and the alternative was a dialog that keeps its width by ignoring its own margins.
- **A flex item does not shrink below its content unless told to.** `min-width: auto` is the default, so `overflow: hidden; text-overflow: ellipsis` on a label inside a flex row never gets the chance to fire: the row grows instead, and the panel around it grows a horizontal scrollbar. Every ellipsizing label in a flex row needs `min-width: 0` on itself *and* on each flex ancestor between it and the fixed-width box — in the queue that is the name, the row button and the row. **And all of that is worth nothing if the row is not actually a flex container**, which is how the queue spent a while with names running past the button and under the × with no way to read them. The button carries two classes, `.menu-item` (`display: block`) and `.chapter-item` (`display: flex`); they weigh exactly the same, so the winner was whichever came later in the file — and it was `block`. Measured in the compiled bundle rather than argued about: `display:flex` at byte 27352, `display:block` at 27753. With the parent not a flex container the `flex`/`min-width` pair is inert and the name stays an **inline** span, where `overflow: hidden` does not apply at all. Hence `.menu-item.chapter-item`: a rule that has to beat another is written to win rather than left to source order. Two traps around it worth naming. Reconstructing a panel's CSS by hand to test it is how this was missed twice — the harness had the two rules in the opposite order and "proved" the layout was fine; building the real bundle and feeding *that* into the harness is the only version of this test worth trusting. And the panel is positioned by its right edge with `left: auto`, so it grows leftwards without bound: a long name made it 972px wide inside a 700px window at `offsetLeft: -297`, clipped and unreachable. Menus therefore carry a `max-width` with a viewport term (`min(520px, calc(100vw - 48px))`), which is also what keeps them inside the mini player.
- **Reusing a class means beating it, and equal weight is decided by source order — this has now cost two bugs.** The queue rows lost `display: flex` to `.menu-item`'s `display: block` that way; the torrent list's delete button then lost `position: static` to `.card-forget`'s `position: absolute` the same way, and with no positioned ancestor in the row it flew to `top: 4px; right: 4px` of the overlay and sat under the title-bar logo — invisible as well, since `.card-forget` also carries `opacity: 0` until a `.card` is hovered. Both times the override was written as a bare second class of equal specificity, and both times the borrowed rule happened to sit later in the file. So: **write the winning selector** (`.menu-item.torrent-file`, `.card-forget.torrow-forget`), never a lone modifier class. Measure it in the **built bundle**, not a hand-written copy: `npm run build`, then read the rule offsets out of `build/_app/immutable/assets/*.css` — the compiled order is the thing that decides. The bug reproduces exactly by `sed`-ing the winning selector back down to one class in that same file and re-measuring in a browser, which is the cheapest possible proof that the diagnosis is right rather than plausible. **The same arithmetic decides a control's own hover against its container's**, and there source order does not save you: Svelte scopes a descendant selector as `.a.svelte-x .b:where(.svelte-x)` — the `:where()` is free, so `.row:hover .cross` weighs (0,4,0) against a bare `.cross:hover`'s (0,3,0) and the container wins. A three-strength control (resting / row hovered / itself hovered) therefore needs its top state written as `.row:hover .cross:hover`, or the glyph never reaches full strength under the pointer.
- **Animating `opacity` on a small glyph makes it twitch, and no amount of measuring geometry will find it.** The torrent list's delete cross was reported "jumping and coming back" on hover. Geometry was identical across rest / row-hover / cross-hover — same row height, same offset inside the row, to the hundredth of a pixel, measured both standalone and in the real page nesting with transitions disabled. Nothing in the box model moves. The cause is that taking a layer off full opacity makes the engine re-rasterise it and switch how it antialiases, which on a **1.4px stroke** is visible as a wobble; Chrome does not reproduce it, WKWebView does. So the three strengths (resting / row hovered / hovered) are **color**, and `opacity` is pinned at 1 and never transitioned. Worth knowing generally: opacity is the wrong lever for a control that is always on screen — it is for things that appear and disappear, where the rasterisation switch is hidden by the fade itself.
- **The hover preview keeps the video's own aspect, not 16:9.** mpv reports `dwidth`/`dheight` — the size with the aspect already applied — the moment a file opens, so the box can be shaped correctly before any frame exists. It used to be a hardcoded `aspect-ratio: 16 / 9` on the placeholder, which meant the first real frame resized the whole popup: invisible on a 16:9 film and a jump on every hover for a 4:3 one, a phone clip, or a 2.39:1 scope transfer. Torrents merely made it obvious, since there the placeholder is on screen for much longer. The **crossfade layer** was the other half of that blink and a separate bug: `.thumb.fading` inherits `.thumb`'s `width` and 16:9 `aspect-ratio`, while the inline aspect that corrects them sits only on the in-flow frame — so on anything wider than 16:9 (a 1920x816 rip is ordinary) it computed 105px over an 80px box and overflowed onto the timestamp for the length of the fade. The tell was that arriving from an un-downloaded position never blinked: there is no outgoing frame there, so the element is never created. An overlay must take its size from the box it covers — `width/height: 100%` and **not** `auto`, because an `<img>` is a replaced element whose `auto` means its intrinsic size rather than the insets (measured: 484px), and the global border-box reset is what stops its own 2px border landing on top of that 100%. The frame is **184px** including that border, which is the figure `.hover-chapter` and `onSeekHover`'s 92px clamp are both written against; one consequence of the border box is that `aspect-ratio` now shapes the outlined frame rather than the picture inside it, so the video's shape is exact at the outline and off by the 2px inset (under 2%, absorbed by `object-fit: cover`) at the image. **And the shape must only ever move to a real value.** `dwidth`/`dheight` are observed with `none`, so mpv reports them *unavailable* whenever the VO reconfigures — which on a torrent is every stall for pieces. Read directly, the box fell back to 16:9 for those frames and snapped back, a visible blink while hovering; the swap of one frame for another was measured stable at 139px throughout, so the flicker was never the image. Same rule as `media-title`: a transient null must not erase what is already known. Related: a position of a torrent that has not downloaded gets a **distinct** state, not an empty box — the arrow the download readout already uses — because an empty outlined rectangle reads as a preview that broke rather than one that was never coming, which is the same mistake the end-of-file cards were fixed for.
- **A scrolling box says it has more below it, and the shape of that is forced rather than chosen.** `ScrollFade` is a bottom gradient with a chevron, rendered as the **last child of the container that scrolls** — one line per list and no wrapper, which is what made it affordable in five places at once: the dialog shell (so every sheet gets it, and the ones that fit never show it), the subtitle results, the torrent file picker, the link recents and the language list. Three things it cannot be, each measured in a WKWebView harness against the built stylesheet rather than reasoned about. It cannot be `position: absolute`: inside a scroll container that resolves against the *content* box, whose bottom is the end of the content, so `bottom: 0` sits under the last row and scrolls out of view — precisely backwards, and the alternative is a positioned wrapper around all five. The paint cannot be a negative offset on the sticky box either, because a sticky box is clamped to its containing block: on the settings sheet (`padding: 16px 8px 14px 18px`) `bottom: -14px` lands in exactly the same place as `bottom: 0`, 15px above the sheet's outer edge — and content scrolls *through* that 14px band, so the fade would leave a sharp strip of half-cut text under a faded one. An absolutely positioned **child** of the sticky box is not clamped, only clipped, and a scroll container clips at its **padding** box, so the paint reaches the border with a negative `bottom` of the container's own padding (measured flush: 1px from the outer edge, which is the border). And the two numbers it needs — that padding and the container's `row-gap` — are read off the container rather than passed in as props: a prop per call site is a number that drifts the day the sheet's padding changes, and a zero-height child of a flex column still takes a gap before it (12px in the diagnosis dialog), which a fade adding space to the box it describes cannot afford. Measured with the compensation in place, the layout cost is 0 and a box that fits does not begin to scroll. Detection is `scroll` + `ResizeObserver` + **`MutationObserver`**, and the third is not belt-and-braces: subtitle results arrive into a box with a `max-height`, so the content grows while the container's own size never changes and nothing else fires — measured, that case turns the fade on and no resize is involved. It is `pointer-events: none` and `aria-hidden`: a caption on the scroll position rather than a control (a click there is a click on the row underneath, the rule the bars' gradient tails already carry), and "there is more below" is something a screen reader already has from the scroll container itself. **Only a scroll earns the transition.** Growing in over 140ms is right when the fade answers the viewer's own gesture and wrong for everything else: switching from a settings tab that fits to one that scrolls left a shadow creeping up from the bottom edge a beat after the content had landed, which reads as a flicker rather than as an answer, and opening the sheet on such a tab is the same thing at mount. So a mount, a content change and a resize land at their final value in the frame the content itself paints (`instant`, a class that sets `transition: none`), and only scrolling is animated. Two things that has to get right: the flag and the state must be written in **one synchronous block** so they reach the DOM in one flush — a `transition: none` arriving a flush later would animate the very change it exists to suppress — and the flag is given back on the next frame, where the value is already committed and restoring a transition animates nothing retroactively. **The way that first went wrong is worth more than the feature**: deciding on `if (instant)` rather than on the local it had just been assigned from made the effect *read* a `$state` it writes, so it re-ran, re-registered its observers, took the `ResizeObserver`'s initial callback again — which re-armed the flag — and did it again the next frame. Writing state from an effect is fine; reading it back subscribes the effect to itself. Nothing reports it: no error, no warning, and the only symptom is a flag that never clears, i.e. a transition silently dead everywhere rather than a loop anybody notices. Measured on an idle probe: **95 class writes in 1.5s against zero mutations in the container**, and zero after the fix. Two traps in *testing* any of this. `requestAnimationFrame` does not tick in a webview that is in no window or in a window parked off every display, so the harness reads the initial state and every later one as identical — the first run said the fade never turns off, and the only thing wrong was the harness. And **`getComputedStyle().opacity` is not evidence in WebKit**: opacity is an accelerated property and reads back as its *final* value while a transition runs, so a fade mid-flight measures as 1 and every case looks instant. `Element.getAnimations()` is what actually answers — a running `CSSTransition` is listed there — and it is what separates the three cases above.
- **Tooltips**: put `data-tip="..."` (+ matching `aria-label`) on any element — a delegated handler renders the custom tooltip. Don't use `title`. **A tooltip is cleared by the pointer not being over an anchor, never by being told it left one.** Two measured browser facts make the obvious implementation leak: **`pointerout` is not delivered when the hovered node is removed**, and **a detached element's `getBoundingClientRect()` is all zeros** — which `flipAxis`/`shiftAxis` faithfully place in the top-left corner of the window. Going from the start screen into playback removes anchors under a stationary cursor by the handful (the torrent file picker is the one that gets noticed), so a tip whose 450 ms timer outlived its anchor rendered in the corner with nothing left to dismiss it: moving the mouse onto the video hit `onTipOver`'s early return, so only a click — which clears it in the pointerdown capture handler — or landing on another anchor took it away. Hence `el.isConnected` is checked **on both sides of the `await tick()`**, since a tick is exactly when a pending unmount flushes, and `onTipOver` over a non-anchor now *clears* rather than returning. Note `closest('[data-tip]')` still matches on a detached node, so guarding on the selector alone proves nothing. Tips go **above** their anchor by default, which is right for anything in a bar; `data-tip-below` beside the `data-tip` flips the preference for the case where what the tip explains sits *above* it and would be covered. Only the preference moves — `flipAxis` still takes whichever side has the room, so a card near the bottom of the window gets its tip above anyway. **The tip belongs on the part it answers, not on the whole control.** A recents card had it on the entire button, so pointing at the poster raised a path over the poster — the frame is the one thing on that card that needs no caption, and the tip covered it to say so. It now hangs on `.card-meta`, the wrapper around the name and the remaining time, which is where the truncated name that prompts the question actually is. That wrapper is deliberately boxless: `.card-name`'s top margin collapses through it, so it covers the two lines and not the gap above them, and the card's height is unchanged. **A raw source string is not a tooltip** (`readableLink` in format.ts): a URL is percent-encoded, so a Cyrillic path arrives as a run of `%D0%B1` and the one thing meant to answer "which link is this" became the least readable text in the dialog; and a magnet is long not because it says a lot but because it carries a *tracker list*, which is how a client finds peers and not how a person tells two magnets apart. So trackers are dropped and what is left is the name and the hash — and deliberately **not** the row's own label, which is the name alone: a tooltip that repeats what it is pointing at is noise.
- **OSD**: `showOsd(text, icon)` with icons `info|volume|mute|speed|loop|zoom` — icon + value only, no progress bars.
- **Tests cover the pure end of the codebase, and the choice of what to cover is the point.** `vitest.config.ts` is separate from the app's Vite config because `sveltekit()` brings routing and the `$app/*` virtuals with it; the plain `svelte()` plugin is what compiles a `.svelte.ts` so its runes work under node. `src/lib/test-setup.ts` stubs the three browser globals this codebase touches at *module scope* — `localStorage`, `navigator.language` and `<html lang>`, all read by `i18n.svelte.ts` when it loads, which every module reaching `t()` drags in. Hand-written rather than jsdom on purpose: anything beyond those three has to be stubbed in the test that needs it, where a reader can see it. What is worth testing is where a wrong answer is **silent and permanent** — `sourceId` (a changed key forgets every position ever recorded), `matchTrack` (the wrong dub for a season), `skipKind` (a skip button over the film), `parseEpisode` (a subtitle search that reaches the 1973 film instead of the 2024 series), `parseLangList` (an entry dropped from someone's own mpv.conf changes what mpv selects), `flipAxis`/`shiftAxis` (only wrong at a window edge, which is where nobody clicks by hand), `latest` (an attempt guard that stops guarding is invisible until two reads finish out of order), `pathUnder` and the purges (what a purge leaves behind is invisible by construction — the start screen looks identical either way). None of that is visible in a screenshot, which is why it is here and the rest is not. Two disciplines to keep. The first: **a test is verified by breaking the code**, not by passing — change the thing it claims to guard, confirm it fails, put it back. That was done deliberately over these tests once, by hand, against 33 plausible mistakes (a dropped guard, an inverted comparison, a boundary moved by one), and the four holes it found say what to watch for. Two of them were interesting rather than lazy. The `skipKind` word cap was "covered" by a title long enough to trip the pattern's own *character* budget instead, so the cap itself was pinned by nothing — a test can exercise a line and still assert nothing about it. And `rememberTrack`'s network-source guard exists on **both** sides, the write not creating a folder entry and the read not consulting one, so a test that only exercised the read let the write guard be removed silently: each side of a defense in depth needs its own assertion. That pass was a one-off and the script for it is gone — it earned its keep while these tests were being written and would have earned little afterwards. Repeat it by hand when changing one of the functions above or its tests; reach for Stryker if it is ever wanted properly.

  The second discipline: **a test that documents current behavior is not automatically right.** Twice now. The first `torrentResume` case asserted that an upper-case info hash matches nothing, which was a real bug — the prefix was not lower-cased where the ids were, so a torrent whose folder came from the older layout lost its "continue watching" line and dropped the file picker instead of resuming. And the `isPrivatePath` case asserted that separators are normalized, which they were not: `pathUnder` was case-insensitive but took the slash direction literally, so a root spelled `E:\Films` failed to match `E:/Films/a.mkv` — a privacy root that does not match is a leak, and the queue's own `samePath` had been normalizing all along for the identical reason with a far smaller cost. Fixed in **both** copies (`history.svelte.ts` and `thumb_service.rs`), with the boundary cases pinned on each side.

  A mutation that survives is not always a hole in the tests, either: reversing the skip patterns' order survived, and the investigation found the *mutation* invalid — the patterns are anchored, therefore disjoint, and the ordering has been inert since. It is documented as such and deliberately absent from the list.

Node only — the Rust half needs libmpv and the FFmpeg SDK, which the release job downloads or builds from source, so **`cargo check` and `clippy` are not covered by CI** and stay a local step. - **The application is GPL-3.0-or-later, and that is the conclusion the LGPL work was for.** Keeping every bundled library strictly LGPL bought exactly one thing: the freedom to make this player closed or paid. MIT — which the project carried by default — handed that same freedom to anyone who wanted to close a fork and sell it, which for an *application* buys nothing back: permissive licensing pays off for a library, where the win is being embedded, and users of a player install a binary. Copyleft costs the sole copyright holder nothing (dual licensing stays available) and costs a closed fork everything. **3.0 rather than 2.0** because 306 crates in the graph are Apache-2.0, which is incompatible with GPL-2.0-only; the whole graph was checked and is GPL-3-compatible, including the odd ones (`webpki-roots` is CDLA-Permissive-2.0, a certificate dataset with no copyleft). The App Store argument does *not* apply here and should not be reached for — that channel is already closed by the private API the embedding depends on (`distribution.md`). GPL §4 also means `LICENSE` itself is now a bundle resource, and `gen-notices.mjs` embeds it as the last section of the notices, read from the file rather than restated — so editing one without the other leaves the committed notices stale and the gate fires.
- **Licensing is a build output, not a document somebody remembers to update.** The player links libmpv, FFmpeg, libplacebo, GLib, FriBidi, Graphite2 and the gettext runtime — all LGPL-2.1 — which a proprietary application may do under §6, but only against three obligations the bundle carried *none* of until this existed: a prominent notice naming the libraries, a copy of the license, and a route to the source. `THIRD-PARTY-NOTICES.md` is all three, it is a bundle resource on both platforms (`"../THIRD-PARTY-NOTICES.md": "./"` — traced through `tauri-utils::resources`: a pattern **without a `*`** is a plain file, and for a plain file a *non-empty* destination becomes the target path itself, so `{"x.md": "./folder/"}` writes a file literally named `folder`; `"./"` normalises to empty, which is the branch that keeps the file name), and `build.rs` copies it beside the dev exe so the settings-footer link works while developing rather than only in a release nobody clicks. What keeps it true is the coverage check: **every dylib in `src-tauri/lib` must be named by the manifest**, or rendering fails. That check must match by declared name plus a version suffix and never by stripping digits — the digits in `libX11`, `liblcms2`, `libpng16` and `libpcre2-8` are part of the name, and the first version of it reported three covered libraries as missing, which is the failure mode that gets a gate weakened instead of fixed. Three traps in the data itself, all found by looking rather than trusting: a keg's `COPYING` is often a **pointer** (pcre2's says "see LICENCE", FreeType's describes two licenses and ships neither), **gettext's `COPYING` is GPL-3.0** because it covers the tools while we ship only the LGPL runtime, and **Homebrew's `license` field describes Homebrew's build** — its `ffmpeg` is GPL-3.0 and its `mpv` is GPL-2.0, so copying that field would have labelled our own `--disable-gpl` builds as GPL. Hence `license` in the manifest means *the artifact we ship*, with `note` recording which option was taken where a project is multi-licensed. Windows was audited the same way and is LGPL too, proven from mpv's own configuration string embedded in `libmpv-2.dll` (`-Dgpl=false -Drubberband=disabled`): the alarming strings there are innocent — `x264` is libavcodec's SEI **decoder**-side encoder detection (zero encoder symbols), `modplug` is libopenmpt, `xvid` is the MPEG-4 decoder's quirk table. Its component list is deliberately *over*-inclusive and carries no `libs`: `fetch-libs.ps1` takes the **latest** upstream release, so a list read out of today's DLL would be stale within a week, and listing a component the current build lacks costs nothing while omitting one it has is the actual violation. **The rendered file has to be byte-identical on every machine, and the first version was not.** `--check` compares a fresh render against the committed copy, so anything that varies by platform makes the gate fail somewhere and only somewhere: one upstream text (libopenmpt's) ships with **CRLF**, git normalised it to LF in the blob while leaving the working copy alone, so the machine that fetched it embedded CRLF into the notices — and the Windows runner, checking *everything* out as CRLF against `\n` joins, produced a third string again. The CI failure reproduces exactly by CRLF-ing a copy of the tree and running the old script: same two digests. Fixed at the read — every input is normalised to LF, so the output depends on content and not on anybody's `core.autocrlf` — with a scoped `.gitattributes` (`LICENSE`, the notices, `licenses/**` → `eol=lf`) keeping the working copies matching their blobs. Both are kept deliberately: the script guarantees the comparison, the attributes guarantee the files, and neither substitutes for the other. **Showing them is a surface of its own**, because pointing at the file is not showing it: `revealItemInDir` gives a location, `open-path` is not in the capabilities (its permission needs a scope), and a `.md` has no reliable handler on Windows. So `third_party_notices` reads the resource in Rust — a filesystem plugin to read one read-only document we ship ourselves would be a far wider permission than the job needs — and `LicensesDialog` renders it as selectable text (the page sets `user-select: none`, which every child inherits, and WebKit still needs the prefixed property). Measured in a WKWebView harness rather than feared: 560 KB is **171 075 px** of `pre-wrap`, 52 ms of forced layout, 263 ms from load to ready and instant scrolling — no reason to split it. It is a layer *above* the settings sheet in `closeTopmost`, so Escape gives the settings back. **On macOS the About panel takes `credits`, never `license`**: `orderFrontStandardAboutPanel` has a fixed key set and muda passes only ApplicationName, ApplicationVersion, Version, Copyright, ApplicationIcon and Credits — `AboutMetadata.license` is for the Windows and Linux dialogs and is dropped in silence here, which is how the first attempt shipped a panel showing nothing but a name and a copyright line. And **`licenseFile` is deliberately unset**: traced to `!insertmacro MUI_PAGE_LICENSE` in the NSIS template, it adds an "I agree" page to the Windows installer and is not read for `.app` or `.dmg` at all — so it buys no part of the obligation and would make the two platforms' installs differ.
- **Releases**: `npm run set-version 0.21.0` (or `patch`/`minor`/`major`), then push to main. **Five files carry the version** — package.json, package-lock.json, tauri.conf.json, Cargo.toml, Cargo.lock — and they cannot be collapsed into one: `tauri.conf.json`'s `version` accepts a path to a package.json instead of a literal, but the release workflow reads that literal with `jq` to decide whether a push *is* a release, so making it indirect would leave the gate with nothing to compare; and Cargo cannot read a version out of JSON at all. So `scripts/set-version.mjs` writes them, with one anchored line per file rather than a JSON round-trip (which reformats tauri.conf.json's hand-written inline arrays — measured on the `endpoints` array) and with **every anchor required to match exactly once**, since a bump that silently skipped a file is the whole failure being prevented. Run with **no argument** it reports instead of writing and exits non-zero on disagreement: worth doing before a release, because this drift is invisible — `package-lock.json` had been sitting at **0.1.0** since the first commit, which is exactly what the script found on its first run. `src-tauri/tauri.conf.json` remains the authority: a `patch`/`minor`/`major` bump is measured from what *it* says, whatever the others have drifted to. CI needs repo **secrets** `TAURI_SIGNING_PRIVATE_KEY` (passwordless), `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ACCOUNT_ID` and `FP_OPENSUBTITLES_KEY`; six more for macOS signing — `APPLE_SIGNING_IDENTITY` (the whole `Developer ID Application: … (TEAMID)` string), `APPLE_CERTIFICATE` (base64 of a `.p12` exported from **My Certificates**, which is the view that carries the private key with it) and `APPLE_CERTIFICATE_PASSWORD` for the certificate, plus `APPLE_API_KEY`, `APPLE_API_ISSUER` and `APPLE_API_KEY_P8` for notarisation. **Every one of those six is optional**: without them the build is ad-hoc and the notarisation steps skip themselves, saying so in the job summary — a fork can still cut a release. Plus repo **variables** `R2_BUCKET_UPDATES`, `R2_BUCKET_LIBS`, `R2_PUBLIC_URL_UPDATES`, `R2_PUBLIC_URL_LIBS` — bucket names and public URLs are not secrets, and as variables they are readable in a failed log instead of appearing as `***`, which is the difference between diagnosing a 404 and guessing at one. Each is guarded against being empty, because an unset variable expands to nothing and would otherwise upload to `s3:///` — the OpenSubtitles *application* key, baked in with `option_env!` at build time. Two things about that one. It is not really a secret (it identifies the app, not the user, and cannot be hidden inside a desktop binary); what a leak costs is **availability**, since abuse gets it revoked and subtitle search then breaks for everyone at once — which is why `opensubtitles.rs` looks in `<app_data>/opensubtitles.key` *before* the compiled-in value, so a revoked key can be replaced without a release. **Nothing delivers that file yet**: today it is a manual escape hatch, and wiring it to the signed R2 channel next to `latest.json` is the piece still missing. And `option_env!` is read at compile time **without** registering a dependency on the variable, so `build.rs` carries `rerun-if-env-changed=FP_OPENSUBTITLES_KEY` — without it a warm target directory keeps baking in the previous key. An absent secret is not a build failure: the feature simply reports that this build has no key. Updater pubkey lives in tauri.conf.json. **The `publish` job needs its own checkout, and it has to be the first step**: the job began life as downloaded artifacts and nothing else, so it had none — and the moment it called a script from the repository it died with a 127 *after* every artifact and `latest.json` were already uploaded, leaving the update channel live and no GitHub Release at all. Order matters because `actions/checkout` clears the workspace before cloning, so placed after the download it would delete `dist` and the failure would read as the build producing nothing. The same incident moved the retention sweep **after** `Create Release` and into a step of its own: it had been the tail of the upload step, which put the least important thing in the job in front of the most important one. It still fails loudly rather than being swallowed — pruning that quietly stopped working is how the bucket reached nine gigabytes.

- **Accent colors**: indigo `#6366f1` (fills) / `#818cf8` (hover/active/focus); white text on accent surfaces. Indigo means **one** thing — selected / on / primary / focused (`.segopt.sel`, `.tab.sel`, `.switch.on`, `.updbtn`, focus rings). Passive readouts stay white, like `.seekfill`: the OSD bar used to be indigo, which inverted the logic — the control you drag was white while the thing that merely reports a value wore the accent. The exception is `.card-progress`, indigo on purpose because it sits over arbitrary video frames where white would disappear. Floating surfaces come from one scale (`rgba(16,16,22,~0.96)`), not per-component values — **and that fill is half of the recipe**: it is also the start screen's own color, so a surface without the hairline border beside it is invisible there, and one without the shadow is lost over a bright video frame. Taking the fill and leaving the rest is the mistake to watch for. **One deliberate exception, and it is a different token rather than a loosening of the rule**: `.btn-catalog` on the start screen wears a 1px *gradient hairline* (`#818cf8` → `#6366f1` → `#a855f7`), which is the only place a second hue appears. A flat indigo fill beside `Открыть файл` would have been two primaries, i.e. none; a gradient ring is not a fill and can carry its own meaning — *this one is worth knowing about* — and the violet end is what makes it legible as a gradient at all, since indigo shading into indigo is invisible at a hairline. Drawn with a masked `::before` rather than the usual padding-box/border-box double background, because that trick needs an opaque interior and this button's fill is transparent and changes on hover. Two things measured in a WKWebView harness against the built stylesheet, both of which a hand-written copy would have got wrong. `mask-composite: exclude` **is** honoured there (with `-webkit-mask-composite: xor` beside it), so the label is not covered — the failure mode had it been ignored is the whole button painted over. And **`inset: 0` is one pixel wrong**: an absolutely positioned box resolves its insets against the containing block's *padding* box, so the ring landed 1px inside the button's own border and therefore 1px in from the plain border of the button standing next to it; `inset: -1px` puts it on the border box. Measured: gradient at +1.0px before, at 0.0px after, with the button's height unchanged at 38px either way.
