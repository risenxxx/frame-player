# CLAUDE.md — Frame Player

Windows and macOS video player: **Tauri 2 + Svelte 5 (SvelteKit static) + in-process libmpv** via `tauri-plugin-libmpv` (wid embedding: mpv renders into a child HWND / NSView *behind* the transparent webview; the entire UI is HTML on top). On macOS that needs a patched libmpv — stock mpv does not implement `--wid` there at all; see `patches/` and `scripts/build-libmpv-macos.sh`.

The UI is **localised (ru/en)** — every user-facing string goes through `t()`, see "Localisation" below. Code comments and docs are **English**.

The reasoning behind it — measurements, dead ends, options tried and rejected — lives in **`private-docs/`**, a folder kept out of the repository (it is in `.gitignore`). ## Commands

```bash
npm install
npm run fetch-libs        # one-time: downloads libmpv, FFmpeg SDK, libclang into src-tauri/{lib,ffmpeg,tools}
npm run tauri dev         # dev run (vite on :1420 + cargo)
npm run check             # svelte-check — run after ANY frontend change (expect 0 errors; a few known a11y warnings are OK)
npm run tauri build       # NSIS installer (unsigned locally unless TAURI_SIGNING_PRIVATE_KEY is set)
npm run set-version       # report the version in all five files; exits 1 if they disagree
npm run set-version 0.21.0   # …or `patch` / `minor` / `major`. See "Releases" below
```

Rust validation while the user's dev instance may be running (target/ is locked by the running exe):

```bash
cd src-tauri && CARGO_TARGET_DIR=/some/tmp/target-check cargo check
```

Sidecar smoke tests (both engines: stepping + thumbnails). Generate the fixture with the bundled ffmpeg:

```bash
src-tauri/ffmpeg/bin/ffmpeg.exe -f lavfi -i testsrc2=duration=60:size=1280x720:rate=30 -c:v mpeg4 -q:v 5 test.mp4
cd src-tauri && FP_TEST_VIDEO=<abs path to test.mp4> cargo test --lib -- --nocapture
```

(The LGPL ffmpeg build has **no GPL encoders** — use `mpeg4`, not libx264.)

Torrent streaming against a real swarm (ROADMAP 21's spike, kept as a test — off
by default because it needs the network, live seeders and up to a minute):

```bash
cd src-tauri && FP_TEST_MAGNET=1 cargo test --lib torrent::tests::sintel_smoke -- --nocapture
```

On macOS a test binary in a custom target dir cannot find the bundled dylibs
(`@executable_path/lib` resolves next to `deps/`, where build.rs did not copy
them), so any `cargo test` there also needs `DYLD_FALLBACK_LIBRARY_PATH=$PWD/lib`.

## Critical gotchas (violating these causes crashes or subtle breakage)

1. **libmpv-wrapper bugs (upstream, unfixed)** — see architecture.md for details:
   - Never `getProperty(..., 'node')` and never observe properties in `node` format → stack corruption crash. Use string/flag/int64/double; read track-list via `track-list/N/...` sub-properties — and observe `track-list/count` (int64) to know *when* to re-read it, because tracks keep appearing after `file-loaded` (external subs via `sub-auto`, lazily parsed containers): reading once on that event left the subtitles button missing until something else happened to refresh the list. `loadTracks()` is a long chain of sequential reads with several possible triggers, so it needs a sequence guard or a slow earlier run finishes last and overwrites the fresh list.
   - Never send broadcast `script-message` → AV crash in the wrapper's client-message serializer. Only targeted `script-message-to <script> ...`.
2. **ffmpeg-the-third seeking**: always `ictx.seek(ts, ..=ts)` (inclusive). `..ts` silently fails with EPERM.
3. **mpv state mirrors go stale** (event queue overflow drops property-change events). Toggles must use `command('cycle', [prop])`, never `setProperty(prop, !mirror)`. Mirrors are resynced every 1 s and on `queue-overflow` in `resyncState()`.
4. **Multiple mpv properties are never visually atomic** from outside — even back-to-back Rust `set_property` calls let the VO redraw in between. If several properties must land in one frame (zoom+pan), go through `zoompan.lua`-style script handlers.
5. **Seekbar**: the original rule was "click = one `absolute+exact`; drag = `absolute+keyframes` only, *including the final one*", because a trailing exact seek after keyframe previews caused a frame-blink. That has since been deliberately narrowed — see "Seek flags are a performance contract" below for what replaced it and why. If the blink ever returns, `onSeekUp` is the first place to look.
6. **Fullscreen transitions**: order matters — set veil state → wait double-rAF + ~30 ms (frame must be presented) → show shutter window → `setFullscreen`. Do not "simplify" this sequence; each step masks a distinct Windows artifact.
7. **Hidden `veil` window keeps the app alive** — main-window `Destroyed` explicitly calls `app.exit(0)` in lib.rs. Removing that resurrects zombie processes that swallow Explorer "open with" requests via single-instance.
8. **Hotkeys use `e.code`** (physical keys) so they work in any keyboard layout. Keep it that way — the editor stores codes for the same reason. They live in `ACTIONS` in [keys.svelte.ts](src/lib/keys.svelte.ts), not in a `switch`: `onKeydown` resolves a chord to an action and calls `runAction`, and every place that *shows* a key reads `hint()` from the same table. Two defaults worth knowing: `L` is seek-forward (the J/K/L trio) and **loop is `Shift+L`** — mpv's own binding; the A–B loop that would have taken mpv's plain `l` therefore lives on `A` (`Shift+A` clears it). `noRepeat` and `quiet` are fields of the *action*, not lists of key codes, because neither is a property of a key once the key can be moved.
9. **A bar's gradient tail must not be part of its hit area.** `.topbar` and `.osc` extend well past their controls to fade the scrim (76 px vs 48 px of content; 44 px of top padding on the OSC). While that padding belonged to the element, clicks in it were swallowed by the bar — the user is visibly clicking video and the player ignores them. The gradients live in `::before` with `pointer-events: none`, and the elements themselves are sized to their content. **An absolutely-positioned `::before` paints *above* in-flow children**, so `.osc::before` needs `z-index: -1` plus `isolation: isolate` on `.osc` — without it the gradient covered the control row and every button looked disabled. `.topbar` survives without it only because its children are themselves absolutely positioned and come later in DOM order; do not rely on that when adding children. Anything targeting the scrim must therefore target `::before` (e.g. `.player.no-video .topbar::before`), and `data-tauri-drag-region` still needs the bar itself to receive events, which is why `pointer-events: none` on the whole bar is *not* the fix.
10. **The window is transparent, so "nothing painted" means "desktop visible"** — `.player` is transparent on purpose (mpv renders *behind* the webview), which makes any moment when neither party paints a hole through the window. Hiding the start screen (`showEmpty = false`) must therefore never be conflated with dropping the background: at launch with a file that flag flips before `init(mpvConfig)`, so the window was shown see-through until mpv's VO came up. `videoReady`/`.player.backdrop` keeps a dark fill until mpv paints. Erring long is free (mpv's own field is black underneath); erring short shows the desktop. The same hole exists one layer lower and *before* any of our code runs: on macOS the frame view draws the traffic lights the instant the window is ordered in, while the webview's first composite is a frame or two behind — so the buttons appear over bare desktop. Fixed natively in `macos_chrome::apply` by giving the NSWindow an opaque `#101016` `backgroundColor` (it sits below both the mpv view and the webview, so it only shows where nobody painted). Do **not** pair it with `setOpaque(true)` — that costs the system's rounded corners and edge shadow. Related: the window-appear animation is disabled via `setAnimationBehavior(None)`, which dates from when traffic-light placement lagged AppKit by a frame; that is fixed (see 15), so the line is now a taste choice rather than a workaround.
11. **Buttons/inputs get `font-family: inherit`** via a reset in +page.svelte — form controls don't inherit fonts by default and silently fall back to the system font.
12. **HMR resets JS mirrors** (videoW/videoH etc.) while mpv keeps state and won't re-fire unchanged property events — after editing +page.svelte, reproduce bugs with a full dev restart, not just HMR.
13. **tauri.conf.json / capabilities / icons changes need a dev restart** (and icons are tracked by build.rs `rerun-if-changed`); frontend-only changes hot-reload.
14. **Code after `updater.downloadAndInstall()` never runs on Windows** — the NSIS installer kills the process inside that call. Anything that must survive the update (e.g. the `frameplayer.resume` snapshot) has to be persisted *before* install starts (see `saveResumeSnapshot()`); `relaunch()` after it is effectively dead code on Windows.
15. **Never move the macOS traffic lights by hand — grow the title bar instead.** There is no positioning API (the buttons belong to the private frame view), so the obvious approach is to set their frames and re-set them whenever AppKit puts them back. That was built, in full, and it is a dead end. Three measured reasons, worth keeping because each one costs a day to rediscover: AppKit resets the buttons on every title-bar relayout and the causes cannot be enumerated (`setTitle` alone does it every time, and a container view of our own does not stop it); **position is only half of moving a button** — the ×/−/+ glyphs come from `NSTrackingArea`s AppKit lays out from its own model of where the traffic light is, never from the buttons' frames, so moved buttons keep the hover region of unmoved ones (glyphs lighting up 7.2 pt above and left, and the zoom button, past the stale rect's right edge, not responding at all); and **that cannot be repaired** — replacing the tracking area with a correctly positioned copy of itself (rect/options/owner/userInfo are all public) fixes the geometry and kills hover completely, because AppKit keys on the identity of the area *it* created, leaving glyphs that appear only while a button is held. What works instead is to change the title bar and let AppKit do the rest: an empty `NSToolbar` + `NSWindowToolbarStyle::Unified` grows it 28 → 66 pt, and AppKit itself places the buttons at (19, 33) with tracking rects to match — measured stable in the window, across resizes, after `setTitle`, and in fullscreen, where they keep the system's own placement and hover (which is exactly how Spotify behaves). It needs no per-relayout maintenance at all: `macos_chrome.rs` lost ~185 lines, a `CFRunLoopObserver`, a custom `NSView` subclass and a Tauri command to it. **The one thing the toolbar costs is fullscreen**: a window that has one shows it there *permanently*, as a tall opaque band whose buttons only appear once the system menu bar is revealed — instead of the thin strip that slides down on hover. So the toolbar is removed on `WillEnterFullScreen` and put back on `DidExitFullScreen` (measured: title-bar host 66 pt → 32 pt, buttons to the standard (9, 9) with their tracking rect). Restoring must wait for **Did**, not `WillExitFullScreen` — measured, a toolbar set there has no effect at all: AppKit ignores it while the transition is in flight, and the window animates back and sits for several frames with the short title bar. That gap is visible as the buttons sitting at the system position and then jumping to ours, and there is no earlier hook to close it — so it is masked instead: hide the buttons on `WillExitFullScreen`, unhide right after the toolbar is back, and they appear already in the right place. What comes back must be the frontend's last instruction (`BUTTONS_VISIBLE`, recorded by `set_buttons_visible`), **not** the button's own `isHidden`: AppKit shows the buttons itself in the fullscreen strip, so reading them back returned an idle-faded UI with its traffic lights on, which the next idle pass then blinked away. **Recording that intent and acting on it are two different things**, and both halves are load-bearing. The frontend reports the idle state in fullscreen as well — excluding it (the rule once read `idle && !fullscreen`) left the record saying "visible" the whole time, so leaving fullscreen while idle flashed the traffic lights on and the idle effect hid them a frame later. But `set_buttons_visible` then declines to *apply* a hide while the window is fullscreen: there the buttons belong to the strip that slides down from the top edge, and the idle timer emptied a strip the user had just pulled down — including while the pointer rested on a control they were about to click. Separately: **force `darkAqua` on the window**. The frame view draws itself to match the appearance, not the background colour, so under the light system theme it put a bright highlight along the window's **top edge** — far stronger than the shadow on the other three sides and obvious against the dark fill. Screenshots settled the cause: the line is identical with and without the toolbar (so not the toolbar's doing), `titlebarSeparatorStyle = .none` changes it by not one pixel, and it all but disappears under the dark appearance. Two properties it quietly depends on, both verified, both worth re-checking if the chrome changes: the 66 pt system title bar **does not swallow clicks** (anything below 10 pt from the top hit-tests to the content view, so `data-tauri-drag-region` and the HTML top bar keep working) — that follows from `FullSizeContentView` plus a transparent, item-less toolbar, and giving the toolbar items would end it; and **window geometry is unchanged** (frame == content == `contentRectForFrameRect`), so size persistence and fit-to-video do not drift by the title-bar height.

## Conventions & flows

- **mpv option surface**: defaults are set in `initialOptions` in +page.svelte; user overrides come from `%APPDATA%/<identifier>/mpv.conf` (command `user_mpv_conf`, template in lib.rs, `wid` filtered out). The interactive editor (`SETTINGS` array in +page.svelte) persists via `mpv_conf_set` (surgical line edit: comments/unknown keys survive) and live-applies via `command('set', ...)`. To add a setting: one `SettingDef` entry. The dialog was once split by **who owns the setting** — one tab for exactly what ends up in mpv.conf, one for state the player keeps itself. That boundary is real and still shapes the code (`SettingDef` covers only the mpv.conf half; volume levelling and the queue options are localStorage), but it turned out to be a poor map for someone hunting for "subtitle size", which is how a settings dialog is actually read. It is now topical sections — Основные / Видео / Проигрывание / Аудио / Субтитры / Раздачи / Клавиши — with each `SettingDef` naming its own `tab`. What the ownership boundary still owns is the footer: it says mpv's settings live in mpv.conf rather than claiming everything on the page does, because the Audio section deliberately mixes both. **Adding a section means re-measuring the dialog's width**, and skipping that is invisible rather than ugly: `.tabs` is `nowrap` with `overflow-x: auto` and `scrollbar-width: none`, so a tab past the right edge is simply *gone* — the six-tab row had quietly been overflowing a 428px sheet and clipping "Клавиши" before anyone added a seventh. Measured against the built stylesheet (a hand-written copy of the rules is how this class of bug gets missed twice): seven Russian labels are **510px** at 13px with a 13px gap, English 408, so the sheet is 560 — a content-box number, since there is no global `box-sizing` reset and the 36px of padding sit outside it. Torrents earned a tab of their own for the reason the topical split exists at all: seeding and the piece cache were correctly filed under privacy and storage, and a viewer looking for anything about torrents still had to read "Основные" to the bottom to find them. Destructive actions there are real buttons (`.btn-danger`), never `.settings-link` — a link promises navigation, not deletion. The context menu is **grouped, not listed**: anything with more than two related entries (file, frame, playback, picture, window) is a submenu, which took it from ~19 rows to 11 — a menu that had to scroll in an ordinary window was the sign it had outgrown a flat list. What stays at the top level is what has no group and is reached often. Two things the grouping cost, both worth knowing before moving a panel again. **A panel moved out of its parent loses the parent's event guards** — the menu stops clicks with `onclick={e => e.stopPropagation()}` so they do not reach the handler that closes it, and a hoisted panel is no longer covered by it: every click inside a submenu, the back row included, closed the whole menu. And **five submenus need one implementation, not five** — `submenuHead`/`submenuPanel` snippets keyed by a `CtxSub`, with the anchors in a `Record` rather than a ref each, or the fifth copy is where the divergence starts. The context-menu submenu needs **both** a hover bridge (`.ctxmenu.submenu::before`, `inset: 0 -10px`, `z-index: -1` so it does not eat clicks) and a delayed close: the diagonal path from the parent item to the submenu crosses the gap between them, which belongs to neither element, so `mouseleave` fires and the menu collapses under the cursor. Reset it with `closeSubmenuNow()`, never a bare flag, or a pending timer from the previous menu closes a freshly opened one. **One control shape per job**, or the UI stops being readable: underlined `.tabs` switch sections, pill `.segmented` picks one of several named values, `.switch` is boolean on/off. Reusing the pill for a Да/Нет pair made a setting look like navigation. A switch is **two** classes and the inner one is `.switch-knob`: the seeding toggle was written with a bare `.knob`, which has no rule anywhere in the project, so it rendered as a track with nothing sliding in it and on/off could only be told apart by the background colour. Nothing catches that — an unknown class is not an error and Svelte's unused-selector warning fires on the CSS, not on the markup.
- **The end of a file is a moment the player owns, and that is a deliberate inversion.** `keep-open=always` (not mpv's `yes`, which stops only on the LAST playlist entry and advances silently everywhere else) parks mpv on the final frame of every entry, so advancing is ours: the end screen with previous/replay/next, a cancellable countdown, and the wrap of a repeating queue — `loop-playlist` can no longer fire it, because mpv never advances at all. Measured on a three-entry playlist: at the end of entry 1 of 3, `eof-reached=yes`, `pause=yes`, `playlist-pos` stays put. **That `pause=yes` survives a file change**, so anything that moves to another entry must unpause explicitly or the next episode opens on a still frame. Repeat-one never reaches any of this (mpv loops the file internally). The repeat control is three-state as on music services — off / all / one — mapping to `loop-playlist=inf` and `loop-file=inf`; `all` on a one-entry playlist already means "repeat this video", so no special case is needed. **The mode is our state, written to mpv and never read back**: reading it back would make `all` look like `one` wherever both properties end up set, and the value is re-asserted after `init()` because the user's mpv.conf is merged over `initialOptions` and would otherwise leave the button lying about what the player is doing. The old default was `loop-file=inf` for anyone who never touched the toggle — which meant a file repeated forever and a queue could never advance past its first entry; the migration reads a stored `inf` as `one` (a deliberate choice) and an absent key as `off`.
- **A file's name in the queue comes from three places, and only the third costs anything.** mpv fills `playlist/N/title` from `media-title`, but **only for entries it has actually opened** — so everything ahead of the playhead was showing a bare file name until it played. The first fix is free: the fallback is `displayName()` (extension off, dots to spaces), the same one the start screen uses, rather than a raw basename. The second is `container_titles`, which opens each file's header and reads the `title` tag — `avformat_open_input` **without** `avformat_find_stream_info`, because a title lives in the header while the probe exists to identify streams. Measured on an MKV, warm: **0.10 ms** per file that way against **0.27 ms** with the probe, and a cold file is dominated by the disk either way; so naming a 300-entry folder is a fraction of a second, done once, 1.2 s after the playlist changes and never for a queue of one. Opening the queue panel reads immediately instead of waiting out that delay, which is why `openQueueMenu` now *awaits* `loadPlaylist`: fired against the previous list, the read would find nothing to do and the panel would sit on the timer it was meant to skip. What the measurement also said, and what decides the feature's worth: **most files have no title tag** — an ordinary rip held only `encoder` and `creation_time` — so this improves the minority that were authored with one, and `displayName()` is what carries the rest. Results are session-only (a Map, not a store: nothing persisted is one less place the privacy rules must be enforced) and each path is tried once, so a file without a tag is not reopened on every playlist change.
- **A queue is built from one opened file, never from several.** Dropping five files is an explicit selection and stays exactly what was given; opening a single episode is the case where the rest of the folder is wanted. `folder_entries` returns every plain file unfiltered and unsorted on purpose — what counts as a video (`VIDEO_EXTENSIONS`) and what natural order means (`Intl.Collator({numeric: true})`, which knows "ep2" precedes "ep10") both live in the frontend already, and a second copy in Rust is the kind that drifts. The opened file keeps its natural position rather than becoming entry zero: the files sorting before it go in with `loadfile … insert-at N` (mpv 0.38+; older builds throw and the queue is simply forward-only). Verified rather than assumed — `insert-at 0` on a playing file shifts `playlist-pos` 0 → 1 by itself, so what is playing keeps playing. Long folders are truncated *around* the opened file, not from the end: in a folder of thousands, the episodes that matter are its neighbours.
- **Whether the sidecar shares mpv's FFmpeg depends on the platform, and the prefix on a log line tells you who is talking.** On macOS `src-tauri/ffmpeg-macos/lib/*.dylib` are **symlinks into `src-tauri/lib/`** (verified with `otool -D`: both carry the install name `@rpath/libavcodec.62.dylib`) — mpv and the thumbnail service load one and the same library. On Windows they are separate DLLs: `libmpv-2.dll` against `ffmpeg/bin/*.dll`. What is constant is the logging: mpv installs an `av_log` callback and its lines read `[ffmpeg/video] hevc: …`, so **a bare `[hevc @ 0x…] …` is libavcodec's default callback** and did not come through mpv — in practice the sidecar decoding a file in software, not playback. Hence `log::set_level(Error)` next to `ffmpeg_the_third::init()`: a chatty file (Dolby Vision RPU notices on a DV remux, for one) otherwise buries everything else in the dev console. Note the asymmetry it inherits: the log level is global to a library, so on macOS that call also caps mpv's own libav messages, while on Windows it only affects ours. If mpv-side FFmpeg warnings are ever needed for debugging, that line is where they went.
- **Background decoding competes with playback — budget it explicitly.** The thumbnail storyboard decodes in *software*, so it degrades the player identically whether mpv's hwdec is on or off; that symmetry is the tell. Measured on a 197 s 4K60 VP9 file: an unbudgeted storyboard (`threads = ncpu`, 5 ms sleep) took ~3 cores for ~35 s right after the file opened, and made seeking feel broken. Now bounded three ways: `DECODE_THREADS` (capped, not `ncpu` — 292 % → ~150 % CPU), a duty cycle sleeping `1/YIELD_RATIO` of the time the last cell took, and `background_qos()` (ffmpeg's frame-thread workers inherit the creator's QoS, so one call at thread start is enough). **Both knobs have a floor as well as a ceiling**: the first attempt (`QOS_CLASS_BACKGROUND` + 1:1 duty) was over-corrected — BACKGROUND pins the work to efficiency cores and a 3-minute 4K60 storyboard then took minutes, so thumbnails were not ready when the user reached for them. `QOS_CLASS_UTILITY` is the right class: P-cores stay available, but the player preempts the storyboard rather than the reverse. Keep any future background work under the same three constraints.
- **Seek flags are a performance contract, not a detail**: `hr-seek=yes` in `initialOptions` makes any seek without an explicit flag *exact*, and an exact seek costs decoding from the preceding keyframe. Measured on a 4K60 VP9 file with a 5 s GOP (mpv IPC, hwdec on): a far `absolute+exact` jump ≈ **1.9 s**, the same jump `absolute+keyframes` ≈ **0.05 s**; a nearby `relative` (still exact) ≈ 0.13 s. Crucially, that cost is a property of the **file**, not of the flag or the jump distance. Measured via mpv IPC, 30 steps of 2 s:

| file | exact | keyframes |
|---|---|---|
| HEVC 4K 25 fps, GOP 2 s | 25 ms | 25 ms |
| h264 4K 60 fps, GOP 2 s | 36 ms | 37 ms |
| VP9 4K 60 fps, GOP 5 s | 1219 ms | 50 ms |

On a normal file keyframe seeking buys **nothing**, while *switching modes mid-gesture* is plainly visible as a jerk (previews sit on a keyframe, the final frame lands on the exact position). So the mode is probed once per file — `issueSeek()` times the first exact seek, `fileSlowSeek`/`wantExact()` decide from then on, `resetSeekProbe()` on `path` change (IINA does the same via `useExactSeekForCurrentFile` with a 0.05 s threshold). Fast file → exact everywhere, no mode changes at all. Slow file → keyframe previews, exact only where a frame is actually being asked for. Notes: hwdec **halves keyframe seek time but doubles exact seek time**, so "turn hwdec off" is not a win either way; `vd-lavc-fast`/`skiploopfilter` change nothing for VP9; `demuxer-max-back-bytes` is not implicated.

The two gestures deliberately differ on pausing. **The seekbar drag pauses** (from the first move, not from pointer-down, so a plain click never touches playback): playing video drifts forward between throttled preview seeks and the next preview yanks it back — visible as forward/backward judder. **The wheel scrub does not pause** — it self-terminates after 180 ms, and with only ~12 keyframes in a 60 s span a paused scrub degenerates into a slideshow, which is what "less responsive than IINA" actually meant; it mutes instead, so frames keep moving between landings without machine-gunning the audio. While either gesture owns the position, `time-pos` must not write `seekValue` — and that block must extend past pointer-up (`seekSettling`) until the final seek lands, or the knob snaps back to the preview position and then forward again. Drag previews run on the same one-in-flight pump, **never a time throttle**: a seekbar is a brutal magnifier (a 57-minute film across ~900 px is 3.8 s *per pixel*), so an 80 ms throttle leaves the shown frame seconds behind the cursor and releasing then visibly jumps by that gap. `scheduleDragSettle()` closes the rest: 120 ms after motion stops it re-seeks *exactly* to where the cursor rests — that is the frame the user is actually aiming at — and `onSeekUp` skips its own seek when that already landed (`dragShownAt`/`dragShownExact`), so a considered release changes nothing at all. **The arrows follow that same verdict**, which they did not always do: the coarse step went by keyframes *unconditionally*, and a keyframe landing is up to a GOP away — so a 5 s arrow actually moved 6 s on an ordinary file and 10 s on a network stream with long fragments. It had always done that; only the popup hid it, by reporting the promise rather than the landing. They also carry the probe themselves (`noteSeekCost`), because an arrow is often the first seek on a file and a slow one would otherwise go undiagnosed until the bar was touched. Shift+arrow stays exact regardless. Beating the keyframe ceiling on pathological files needs our own decoded-frame source (StepEngine), not a different flag; IINA has no such thing (its `FFThumbnail` cache is the seekbar hover popup, same as ours). Two more rules the gestures depend on: keep **exactly one seek in flight** (`pumpScrubSeek`) rather than firing on a timer — a fixed interval builds a queue that keeps "playing out" after the fingers stop; and while a gesture owns the position, `time-pos` must not write `seekValue` (`!scrubbing`/`!dragging` in the observer) or the knob jitters between the finger and mpv's lagging report. Note `onSeekUp` now ends a drag with an exact seek when it is near — a *deliberate, narrowed* rollback of the architecture.md "drag is keyframes-only, including the final one" rule, because keyframe landing made the knob visibly snap backwards on release. If the frame-blink ever returns, revert there first. When a seek lands on a keyframe, the optimistic OSD position is wrong — refresh it from `time-pos` afterwards (`refineSeekOsd`), but **not when the seek command resolves**: `command('seek', …)` returns when mpv *accepts* the command, and `time-pos` there is still the position before the jump. Reading it then showed the target, flicked back to the starting point and stayed — three figures for one key press. `playback-restart` is the event that means the seek is done; the timeout beside it exists so a seek that never completes cannot leave the popup waiting on a promise.
- **The preview must show the frame you land on, and both halves of that were wrong.** The hover thumbnail comes from a grid whose step is `clamp(duration/240, 0.25, 10)` — 10 s for anything longer than 40 minutes. The position was mapped to its cell by *truncation*, so the preview sat up to a full step **earlier** than the cursor, while the seek that follows is exact: the two errors added instead of cancelling, which is why the played frame was reliably *ahead* of the previewed one. Measured on a 24-minute file, 30 hover positions, "different scene" = PSNR < 18 dB between the previewed frame and the one playback starts on: **60 %** with truncation, **37 %** with rounding to the nearest cell, 30 % at a 3 s step, 20 % at 2 s, 0 % at 1 s. Rounding is free (cell N still holds the frame at `N*interval`, so existing caches stay valid — no `CACHE_MAGIC` bump) but it only halves the error; what removes it is fetching the **exact** frame when the cursor comes to rest, the same trade `scheduleDragSettle()` makes with the video. Two consequences worth keeping: that refinement visibly *replaces* the thumbnail in roughly 40 % of hovers — inherent, since those are exactly the cases where the grid frame was a different scene — and its cost is one GOP of software decode, measured worst-case **120 ms** on 1080p h264, **1330 ms** on 4K30 HEVC 10-bit, **1940 ms** on 4K60 VP9 (GOP 5 s). So on 1080p it reads as the preview sharpening ~200 ms after you stop; on 4K it is a late, visible flip that also burns three decode threads next to playback. **The decode itself cannot be made cheaper** — measured per GOP against the baselines above, `skip_loop_filter=all` gives 4K60 VP9 nothing at all (1950 vs 2010 ms, noise), 4K30 HEVC ~10 %, 1080p h264 ~8 %, and `skip_frame=bidir` ~18 % on h264 while costing a landing a few frames off — so the latency budget that *is* controllable is the scheduling: `SETTLE_MS` is 70 ms rather than `scheduleDragSettle()`'s 120 (this gates a 320px thumbnail, not a seek of the video), armed from the **pointer move** and not from every request (the throttle's trailing call re-enters up to 85 ms later, and re-arming there delayed the exact frame by that much for nothing the user did), with **one exact request in flight at a time** — a slow sweep would otherwise queue seconds of GOP decoding whose results are all stale on arrival. Firing an exact request also cancels the pending trailing grid request: it is for the same resting position, and it is the only way a grid frame could land *after* the exact one and overwrite it. If the 4K case becomes a problem, the fix is a probe in the shape of `fileSlowSeek`/`wantExact()` — time the first refinement and stop refining that file past a threshold — or a decode session of its own for hover requests, so they stop re-seeking the storyboard's; *not* a finer grid, which needs a 1–2 s step and therefore decodes the whole file in the background. The replacement **crosses over rather than cuts** (`.thumb.fading`, 140 ms), and the layer on top is the **outgoing** frame, never the incoming one: an `<img>` keeps showing its previous content until a new `src` decodes, so putting the new frame on top would let the pre-refinement frame show through underneath for a frame — with the outgoing frame on top, whatever is beneath it is always the newest. Grid frames are swapped with no animation at all, since those track a moving cursor. `frame_exact_at` must never touch `refine_mode`: that flag is the storyboard's verdict about the file, and one hover request must not push the whole background pass into linear decoding.
- **Frame export and external tracks go through mpv, not around it.** `screenshot-to-file` keeps exactly what the VO decoded, HDR tone mapping included — which is precisely what the StepEngine canvas path got wrong, so do not reintroduce a canvas-based grab. `screenshot-raw` is not an option either: it returns a node, and node reads crash the wrapper. Clipboard copy therefore round-trips through a temp PNG decoded in Rust — and **mpv's PNG defaults are a latency trap**: zlib level 7 is a size-first choice that buys nothing here. Measured on a 4K frame of photographic content (libavcodec's PNG encoder, the one mpv screenshots go through): level 7 = 1.46 s / 16.4 MB, level 3 = 0.73 s / 16.4 MB, level 0 = 0.21 s / 23.8 MB. A 10-bit source doubles every figure, because `screenshot-high-bit-depth` defaults to yes and writes 16-bit PNG. Hence level 3 globally, and level 0 + no row filter + 8-bit for the throwaway clipboard file, which reaches the clipboard as 8-bit RGBA no matter what. `withFastScreenshot()` restores the previous values in a `finally` — leaving compression off would silently bloat every frame saved afterwards. This encode runs on mpv's core thread, so getting it wrong stutters playback as well as making the user wait. Dropped files are split by extension in `loadFiles`: subtitle/audio files become `sub-add`/`audio-add` (an `.srt` handed to `loadfile` used to be *played*), and when they arrive together with a video they wait in `pendingAttach` until `file-loaded` — `sub-add` before that fails. Track delays use `add`, never `set` from the mirror, for the same reason toggles use `cycle`.
- **A subtitle found by the file's hash and one found by its title are different results, and the panel says which.** The hash (size + every 64-bit word of the first and last 64 KiB) identifies a *release*, so what comes back is already in sync; a title match is a guess about which rip you have and may be off by seconds. Conflating the two is what makes subtitle search disappointing elsewhere, so which one produced the list is reported and shown as a sentence. **The two searches must therefore be separate requests, and the verdict must come from the results rather than from the request** — this is the bug the first version shipped with. Sent together, the API answers with the **union**: measured, a hash alone returned 11 subtitles all flagged `moviehash_match`, the same hash plus an unrelated query returned 50 with still only those 11 flagged. The panel then announced "matched by the file itself" over a list of unrelated films — a file called `master.mkv` (an episode of a series) was offered *Master and Commander* under that heading. So: hash first, alone, with `moviehash_match=only`; the typed title only if that came back empty; and `match_kind` derived by looking at what arrived. The empty hash result is itself worth saying — "OpenSubtitles has nothing for this exact file" is a fact about the file, and it is what the viewer needs in order to stop trusting the list below it. Measured against the live API on 2026-08-03, and three of the four facts contradict what our own research assumed: **the rate limit is 5 requests per second**, not 1; **searching is not quota'd at all** while downloading is; **downloading works with no user account** (5/day per IP, and 100/day for a consumer marked *Under Development* — an anonymous `POST /download` returned `remaining: 99`), so signing in raises the ceiling rather than unlocking the feature. **Which bucket is being charged is in the response**: `uk` reads `app_ud_<consumer>` for a key in development — one allowance shared by everyone using that build — and `app_<consumer>_<ip>` for a released one, which is the per-IP allowance. Running a production key dry confirmed both the model and the refusal: five downloads answer 200 with `remaining` counting down, the sixth returns **HTTP 406** with `remaining: -1`, a human-readable `message` and `reset_time`. 406 is the daily quota and 429 is the rate limit — collapsing the two into "request failed" throws away the only thing worth telling the viewer, which is when it comes back and that signing in moves the ceiling; and the API's own relevance sort is not usable — searching "interstellar" put a documentary *about* the film first, hence the client-side sort of hash matches before download count. Two consequences in the code. A hash that matches nothing is the normal case for anything but a well-known release, so an empty hash search silently retries by title — free against a 5/s limit, and the difference between an empty panel and a usable list. And the key is the *application's*: OpenSubtitles bans apps that make their users register their own, so it ships with the binary, cannot be a secret, and is looked up in an order (`app_data` file → dev file → compiled-in) whose only purpose is that a revoked key can be replaced through the signed R2 channel without a release — the real cost of a leak is availability, not privacy. **There is no duration anywhere in the API** — verified by dumping a whole result and walking every key of the subtitle, its `files[]`, its `feature_details` and the `/features` record — so "will this one fit" is answered by `fps` instead, flagged when it differs from `container-fps` by more than 0.1: a 25 fps subtitle on a 23.976 fps file does not start late, it drifts further out the longer you watch, which is the failure viewers hit and cannot diagnose. An episode's own `title` is usually the literal "Episode 3", so episodes are labelled from `parent_title` + `season_number`/`episode_number` or a list of them says nothing. **Those two numbers are also what reaches a series at all**, and without them the feature simply misses: measured, `query=the day of the jackal` returns the **1973 film**, the same query with `season_number=1&episode_number=3` returns **122 subtitles for the 2024 series**, and `year=2024` is not a substitute — it answered with 10 000 results of "Empty Movie (SubScene)". They come from the file name (`parseEpisode` in format.ts), which also yields a far better query than the whole name. Only unambiguous markers are read — `S01E03` and its spacings, the spelled-out forms in both languages, and `1x03` bounded by non-digits so `1920x1080` cannot become "season 20, episode 10" — because a bare number in a release name is never an episode: `1080p`, `2024`, `x264` and `5.1` all sit exactly where a naive parser would read one. The panel says which season and episode it took, or a list of episodes appearing for a two-word query reads as the search guessing. **Removing a subtitle is two different actions, and which one applies is not a preference.** An embedded track cannot be removed at all — it lives in the container, taking it out would mean rewriting the video, and mpv's `sub-remove` refuses it anyway — so the × appears for external tracks only (`track-list/N/external`, with `external-filename` beside it). For an external one, detaching is the queue's gesture and would be enough, except for a consequence of our own naming: a subtitle we downloaded is called `<video>.<lang>.srt` *so that* `sub-auto=fuzzy` finds it next time, so detaching without deleting means it is back at the next launch and the removal reads as broken. Hence the file is deleted too — **but only for files we created**, recorded in `frameplayer.subs` (privacy-gated like the positions, since the path is named after the video). A subtitle the viewer made, corrected or dragged in is only ever detached; an unrecorded path is treated as theirs, which is the safe direction to be wrong in. `subs_delete_file` checks the extension as a second lock: a delete-by-path command that accepts any path is one wrong argument away from removing the video. **Signing in is an upgrade, never a gate**, and the code is shaped that way: downloading works signed out, so nothing checks for an account before trying, and what an account buys is the ceiling (5 a day per IP → 10–1000). What is stored follows from what losing it costs — the **token** goes into the OS keychain by default (it expires by itself, is revocable from the site, and lasts 24 h with no refresh endpoint, so without keeping it the viewer signs in again for practically every film), while the **password** is stored only behind an explicit opt-in, because it is the most sensitive thing this app will ever hold and is probably reused elsewhere; what it buys is silent renewal. Neither ever touches localStorage. Three details that are easy to get wrong: `/login` has its own rate limit of **1 request per second** where search allows 5, so nothing may retry in a loop; a **VIP account is answered by a different host**, handed over as `base_url` at login and used for everything afterwards, or a 1000-download account quietly behaves like a 20-download one; and a keychain refusal is **reported rather than swallowed** (`keychain_failed`) — on macOS the ACL is bound to the code signature, so dev builds re-prompt whenever the signature changes, and a session that silently lasts only until quit is worse than one that says so. The downloaded file goes beside the video as `<name>.<lang>.srt` so mpv's `sub-auto=fuzzy` finds it by itself next time, with nothing remembered on our side; a read-only folder falls back to the cache directory, and an existing file is never overwritten.
- **Closed captions are a subtitle track that isn't in the container.** `eia_608`/`eia_708` captions ride inside the video stream (SEI), so `ffprobe -select_streams s` shows nothing while mpv lists `--sid=1 (eia_608)` — do not conclude from ffprobe that a file has no subtitles. Two consequences the player has to live with, both inherent to the format rather than bugs in our code: captions are positioned on a 15×32 character grid, so the text is indented and off-centre by design (the decoder literally emits leading spaces); and the decoder is stateful — roll-up/paint-on modes build the screen over many packets — so seeking into the middle of a caption leaves residue. This player seeks harder than stock mpv, which compounds that residue into captions from several scenes stacked on top of each other, hence `sub-clear-on-seek=yes` in `initialOptions`. IINA shows the same smear on the same file, so do not go looking for the cause in our render path. Such a track carries no title and no language, so `loadTracks()` names it from the codec — otherwise the menu offers a bare "Track 1" with no hint of what it is.
- **Every list property is read through sub-properties, and they do not all behave alike.** `track-list`, `chapter-list`, `playlist` and `audio-device-list` are all implemented on mpv's side by the same helper, which exposes `<prop>/count` plus `<prop>/N/<field>` in simple formats — so none of them needs the `node` format that crashes the wrapper, and none of them needs native code either (the roadmap's worry about `audio-device-list` is unfounded). `readList()` in player.svelte.ts is that pattern; the sequence guard stays at the call site, because a read is dozens of sequential round-trips and there are several reasons to start one. What is *not* shared is how a missing field reports itself, and copying the track code blindly gets it wrong: measured on mpv 0.41, `track-list/N/title` of an untitled track is **unavailable** (the read fails, `.catch(() => null)` produces the fallback), while `chapter-list/N/title` of an untitled chapter is **available and reads back as the literal `(unnamed)`** — which would put an English placeholder into a Russian chapter list. Hence `MPV_UNNAMED`. Two more measured facts behind the chapter code: a file without chapters has `chapter-list/count` = 0 (available, not an error) while the `chapter` property is *unavailable*, so the current-chapter mirror needs its own fallback; and chapter navigation goes through the `chapter` property rather than a seek to the chapter's `time`, because with ordered chapters (MKV) the content can live in another file entirely and only mpv's own chapter seek follows that. It is also clamped at both ends — mpv's `add chapter ±1` walks off into the neighbouring playlist entry, and "previous chapter" opening the previous episode is not what the key says. **An arrow-key accelerator on an NSMenuItem does not fire** — measured: ⌘⇧←/→ on the View items did nothing at all, while the same keystrokes reach the webview normally, so chapter navigation is a frontend binding (`isChapterKey`) and those menu items carry no accelerator. On macOS it needs a modifier beyond Ctrl, since plain Ctrl+arrow is Mission Control and never arrives; hence ⌃⌘←/→ there against plain Ctrl+arrow on Windows. Testing `e.ctrlKey` alone is the trap that hides all of this: it silently accepts ⌃⌘, ⌃⇧ and every other Ctrl+arrow as the same gesture, so the binding *appears* to work on macOS while Ctrl+Shift+arrow quietly stops being the 1 s exact seek it looks like.
- **"Skip intro" matches the whole chapter title, never a substring.** `skipKind()` offers a skip button for the first `SKIP_WINDOW` seconds of a chapter that names itself an opening, a recap, a preview, the credits or an ad. The obvious implementation — search for "intro"/"ending"/"credits" inside the title — is wrong in the common case, not a rare one: those are ordinary English words, so "Ending the war for good" becomes the closing credits and "Opening the vault" becomes a title sequence. Announcement chapters name themselves and stop, so the patterns are anchored to the entire title (with only the decorations rips actually use: a leading "01. " and trailing "…"), plus a five-word cap as the outer bound for the open-ended tails like "Previously on <show>". Anchoring also settles "субтитры" contains "титры" for free, and it puts the failure on the harmless side: an unusual name simply offers no button. Two traps inside the patterns: **`\b` is ASCII-only in JS**, so `ранее в\b` never matched anything at all — Cyrillic alternatives need an explicit `\s`; and order matters, because "Opening credits" is an intro rather than credits. The window is measured from `chapterAt(timePos)`, not from the `chapter` mirror, so the elapsed time and the chapter it belongs to cannot disagree after a seek; and the button lives **outside `.osc`** on purpose — it has to stay up while the UI is idle, which is the entire point of it. Which costs it a `z-index`: `.osc` comes later in DOM order and its scrim reaches 44 px above the controls, so an unlayered button gets the gradient washed over its top half. **How long it stays is `min(chapter length, SKIP_MAX_WINDOW)`**, bounded at both ends and never a bare constant. Longer than the few seconds it started at, because the decision to skip lands when you recognise the music rather than at the first frame, and a short window took the offer away while its reason was still on screen. Shorter than the chapter, because an offer sitting over the picture for a whole minute stops reading as an offer. And never longer than the chapter itself, so a five-second bumper cannot leave a button hanging for three times as long as the thing it offers to skip — which is also what keeps a misread title ("Introduction" on a two-hour lecture) down to a brief button rather than a permanent one. Everything the button shows about time therefore comes from the position, not from a CSS clock — the draining wash is `background-size` driven by `--skip-left`, and the tail fade is an inline `opacity`, both smoothed by a transition because `time-pos` arrives in steps. That is what lets it survive a seek into the middle of an opening (a from-mount animation would show a full bar with ten seconds left) and what makes a paused film freeze the countdown with nobody arranging it. Two shapes that were tried and are wrong: a `::before` scaled with `transform` (a transform distorts what it scales — the wash's corners flattened and its square left edge crept out from under the pill's rounded one, and it dragged in the `z-index: -1` + `isolation` pair from gotcha 9), and percentage keyframes over the whole lifetime (fine at 5 s, but they stretch a 0.2 s entrance into three seconds on a minute-long opening).
- **The media info panel is a live readout, not a snapshot, and half of it is legitimately missing.** Every field comes from a plain `getProperty` — measured on a 4K HEVC file, `video-codec` gives the readable name ("H.265 / HEVC…") while `video-format` gives "hevc", `audio-params/channels` gives "5.1(side)" where `channel-count` gives 6, and `current-tracks/audio/lang` names the dub. **`video-bitrate` is a rolling average of recent packets**, so it is simply absent for the first seconds of a file (measured: audio had a figure while video still had none) and drifts afterwards — hence the 1 s refresh while the panel is open, and hence the average computed from `file-size / duration` next to it, which is exact and available immediately. Rows with no value are not rendered at all: which properties exist depends on the container, the codec and how long playback has run, and a column of "—" reads as breakage. Values are stored raw and formatted at render time, so a language switch relabels the units without waiting for the next refresh.
- **Picture geometry is per file, and reset only if we touched it.** `video-rotate`, `video-aspect-override` and `panscan` are global mpv options: a phone clip turned upright stays turned for the next episode, so they are reset on `file-loaded`. But only when the viewer actually used the menu (`pictureTouched`) — an unconditional reset would overwrite a `video-aspect-override` line in the user's own mpv.conf on every file. Two measured facts the menu depends on: **`video-rotate` does not change `dwidth`/`dheight`** (it is a VO-level transform, so rotating does *not* trigger `maybeFitWindow` or disturb the zoom clamp — the obvious worry is unfounded), and **an aspect override is reported as a decimal**, so `4:3` reads back as 1.333333 and the menu has to compare numerically rather than against the string it sent. Auto is any negative value; mpv's own default is -2.
- **The A–B loop is mpv's to run; ours only to mark.** Both points set means mpv loops the segment by itself — measured, playback stays inside the range and wraps without anything watching the position. Two things the marks need on our side: they read back as the **literal string `no`** when unset (asking for a double gives nothing at all), so the mirrors parse rather than cast — `Number('no')` is NaN and would read as a position; and they survive a file change, so they are cleared on load, or a segment measured in the previous episode traps playback in an unrelated stretch of the next one with no visible cause. B before A is refused rather than sent: mpv accepts the pair and then simply never loops, which reads as the feature being broken instead of the marks being the wrong way round. **mpv disarms the loop while the position is past B** and re-arms it when playback is inside the segment again, keeping the marks throughout — measured, and it is the right call for a destination but wrong for a nudge, so a *relative* seek wraps inside the segment (`wrapInAbLoop`, modulo rather than a clamp, because a loop is a circle and five seconds forward should stay five seconds). The wheel scrub is **clamped** to the segment instead, and the split is the nature of the two gestures rather than taste: fingers travelling right mean "later", so wrapping would break that correspondence and spin the picture around a short loop under a steady swipe, while a key press has no such correspondence to keep and would go dead at the edge if it clamped. Clamping is also what the scrub already does at the ends of the file, so a segment is tighter bounds rather than a new rule. Its upper bound stops a frame short of B, because landing exactly on B disarms the loop and the gesture would end by silently switching it off. Absolute gestures — a seekbar click or drag, a digit jump — deliberately keep mpv's behaviour and leave; the band on the bar then goes faint, because a control that keeps drawing a loop while nothing loops is the actual bug in that situation.
- **The settings dialog has two control shapes, and the choice between them is about the value, not the layout.** A pill (`.segmented`) picks one of several *named* values; a slider covers a continuous range. Subtitle size is the case that forced the second one — the useful adjustment is "a bit bigger than that", which three pills cannot express. A slider fires on every pixel of the drag, so applying live is immediate while the mpv.conf write is debounced (`CONF_WRITE_MS`), with **one timer per key**: a single shared one lets a second slider cancel the first one's write. Landing exactly on mpv's own default clears the line from mpv.conf rather than pinning the default in writing, which is what "по умолчанию" means for every pill above — so the step has to divide the distance from `min` to the default exactly, or the default is unreachable and the line never clears. Values are snapped to the declared precision before being written, because a range input hands back 1.2000000000000002. Subtitle defaults worth knowing, measured on mpv 0.41 and different from what older documentation says: `sub-border-size` is **1.65**, `sub-border-style` is `outline-and-shadow` (`background-box` is the readable-on-bright-frames alternative), and **`sub-ass-override` already defaults to `scale`** — so `sub-scale` and `sub-pos` reach ASS subtitles without forcing anything, which is the usual reason this feature disappoints in other players.
- **Volume levelling is a labelled `af` filter, and its state is ours.** `af add @fpnorm:lavfi=[dynaudnorm=…]` / `af remove @fpnorm` — the label is what lets it be removed again without touching an `af` line from the user's own mpv.conf, and it is also why this setting is the one playback option kept in localStorage instead of written there: `mpv_conf_set` replaces the last uncommented line of a key, and for `af` that would silently eat someone's filter chain. Reading the state back is not an option either — measured, `af` answers with its own escaping (`@fpnorm:lavfi=graph=%27%dynaudnorm=f=250:g=15:p=0.9`), so ours is the record, exactly as with the repeat mode. It is disabled while `audio-spdif` is on and says so: bitstreaming hands the receiver an undecoded stream and a filter has nothing to attach to, so the honest thing is to explain rather than quietly do nothing. **mpv lists a device once per audio output that can reach it**, so the picker showed every speaker two or three times with nothing to tell the copies apart: the macOS build carries `coreaudio`, `coreaudio_exclusive` and `avfoundation` (verified in the bundled libmpv), and only the `name` prefix differs — the `description` is identical. Deduplicated by description, first entry wins, which is mpv's preferred output; the cost is exclusive mode, which cannot be labelled here without inventing jargon and belongs in mpv.conf anyway. Worth knowing when a device's name looks wrong rather than duplicated: **the description is CoreAudio's, not the speaker's**. macOS exposes AirPlay as a single virtual device literally called "AirPlay", and which speaker it streams to is chosen above that layer, in the system output menu — so a JBL on AirPlay legitimately appears as "AirPlay" here and in every other app that enumerates CoreAudio devices. **`audio-device-list` needs no native code**, contrary to what the roadmap assumed — like every list in mpv it answers to `count` and `N/name`, `N/description`, so `readList()` covers it; the list is read when the dialog opens, since mpv builds it lazily on first read and there is nothing to keep fresh while the dialog is shut. Its first entry is `auto`, which is also mpv's default, so it maps to `null` and choosing it clears the mpv.conf line.
- **`hwdec-current` is shown in the settings footer** — a silent fallback to software decoding is otherwise invisible and is the first thing to check when seeking feels slow.
- **Everything the player needs at runtime is bundled; yt-dlp is the single exception.** `src-tauri/lib` carries libmpv, the wrapper and every transitive dependency (~65 MB and ~50 dylibs on macOS: FFmpeg, libass, libplacebo, MoltenVK, LuaJIT, x264/x265, OpenSSL…; on Windows `libmpv-2.dll` plus the FFmpeg SDK in `src-tauri/ffmpeg`, both fetched by `scripts/fetch-libs.ps1`). `build.rs` lays them out next to the dev exe and declares two rpaths — `@executable_path/lib` for dev and `@executable_path/../Resources/lib` for inside a `.app` — and `bundle.resources` puts them in the installer. So nothing is taken from the user's system: a machine with no Homebrew and no FFmpeg runs the player. **Nothing may block `init(mpvConfig)`** — whatever waits there holds up the whole window, and until mpv is up a click on a file does nothing at all, which reads as a dead player rather than a slow one. The lesson cost a session: the yt-dlp probe ran `yt-dlp --version` to prove the binary worked, and that call takes **11 seconds** on a macOS universal build (a 36 MB PyInstaller bundle that unpacks itself and is re-verified by the system on every exec) — twice over, before init, so the player ignored roughly the first twenty seconds of clicks. The probe now only *looks* (file present, executable bit set) and is not awaited; a broken binary is caught where it matters, when a link fails and the dialog offers to install or update. **yt-dlp alone is looked up at runtime** and is optional by design — without it, local files and direct links still work and only websites do not, which the link dialog says. It can also be installed from that dialog, into `<app_data>/bin` — the only place we may overwrite afterwards, since Program Files needs administrator rights and a binary inside a `.app` cannot be replaced without invalidating the signature. **Keeping it current is yt-dlp's own job, not ours**: `-U` fetches the release, checks it against the signed checksums published with it and replaces the binary in place, so writing a downloader would mean reimplementing verification that already exists and is maintained by people shipping it every few weeks. We only fetch the *first* copy. The update button appears **only for the copy we installed** (`managed`) — a Homebrew or pip install belongs to its package manager, where `-U` either refuses or starts a fight. Expect staleness rather than absence to be the failure: a September 2025 build already fails on YouTube, so a failed link reopens the dialog with that explanation and the button, instead of a popup that fades before it can be acted on. Note `bundle.targets` is `["nsis"]` and there is no macOS signing section: **the macOS build is a dev configuration, not a distributable one** — the dylibs would need signing and notarisation before anyone but a developer could run it.
- **A slow operation must say so before it starts, not after it finishes.** Two places had the same silence. Opening a URL sits on a black window for as long as yt-dlp takes to resolve the page and the stream takes to buffer, with nothing to show it is alive — hence the `opening` indicator, raised in `beforeLoad` for a network source only (a local file opens faster than it would fade in) and dropped on `file-loaded`. It reports a real figure rather than a guess: mpv's `cache-buffering-state` is the cache fill, and it is **absent while there is no cache yet**, which means "still resolving" and not "0 %"; `paused-for-cache` is playback stalled on the network as opposed to on the viewer. And saving or copying a frame is a second of PNG encoding on mpv's own thread on a 4K file, which used to pass in silence — the menu closed and nothing happened, which reads as a click that missed. Both now announce first, which is what `sticky` on `showOsd` is for: a popup that fades halfway through says the work finished, and finishing is the one thing that has not happened. Anything raising a sticky popup owes it a replacement on every exit path.
- **An `end-file` error is not a failed attempt.** mpv's ytdl hook raises one on the way to succeeding — it opens the URL, gives up on it and loads what yt-dlp resolved instead — and playlist transitions do the same. Reporting on the event threw an error dialog over videos that were about to play, which is worse than saying nothing. The verdict now waits `LOAD_FAIL_GRACE` and `onFileLoaded` cancels it: if anything opened, whatever failed on the way was a step and not an outcome.
- **No storyboard means no space for one.** With thumbnails gated for streams the hover popup was still reserving its 180px frame and filling it grey, which reads as a preview that broke rather than one that was never coming. The popup drops the frame entirely for a network source and shows the timestamp alone (and the end-of-file cards, which cannot decode a poster out of a URL either, put a link mark where the frame would be rather than an empty outlined rectangle) — and `hoverX`, whose clamp is half the popup's width, has to narrow with it or a bare timestamp stops following the cursor well before either end of the bar. What could bring previews back for YouTube specifically is its own storyboard sprites, which yt-dlp exposes as `sb0`/`sb1` formats; that is a feature, not a fix. The other half of the complaint — slow seeking — has one real lever, and it is `ytdl-format`: the hook's default takes the best available stream, so a 4K one is what every seek then pays for. Hence the quality setting.
- **A torrent is a network source that steers itself, and both halves of that are the design.** A magnet becomes a list of files, each served from our own loopback HTTP server at `/t/<infohash>/<index>/<name>`; mpv opens that URL and its Range requests are the "the viewer is here" signal librqbit turns into piece priority. **The identity lives in the path, never the port** — `sourceId()` reads `torrent:<hash>/<index>` straight back out (`parseTorrentUrl` in source.ts, matched to `stream_url` in torrent.rs by a test at each end), because the port is ephemeral and a key taken from the transport forgets the film every session. The trailing file name is load-bearing too: it gives ffmpeg an extension to probe by, and it is why `displayName` now percent-decodes — without that an ordinary film reads as `The%20Movie%202024`. **Nothing is downloaded until it is read**: the torrent is added *paused with nothing selected* and the HTTP handler itself puts a file into `only_files` and unpauses when a request for it arrives, which is the same principle as piece priority one level up. That is what makes a twelve-episode torrent a twelve-entry queue costing nothing but the episode playing — `queueTorrent` hands mpv every video's URL, and a URL is only a string. The session is **lazy** for the same reason the yt-dlp probe stopped blocking init: a player that joins the DHT on startup is not one people keep. **Opening an episode already on disk costs nothing, and getting there took two separate fixes.** First, `select` returns early when `file_complete` — initialization has just verified the pieces, and `stream()` reads from a *paused* torrent perfectly well (it only blocks on a missing piece), so a rewatch makes **zero peer connections**; librqbit's own `maybe_reconnect_needed_peers_for_file` already declines to reconnect for a finished file, so nothing fights this. Second, and bigger: **a magnet opened once is never resolved again.** `persistence: None` means librqbit forgets the torrent between runs and would go back to the DHT every time — measured at 1.5–10 s — even to reopen a season sitting on disk. The metadata *is* the torrent file, so it is cached at `<cache>/torrents/.meta/<infohash>.torrent` and replayed through `AddTorrent::from_bytes`; a corrupt or stale one falls back to the magnet rather than making the torrent unopenable. Measured on the same torrent back to back: resolve **1.52 s → 4.45 ms**, and a re-read of an already-fetched region **1.20 s → 0.8 ms**. Both are pinned by `complete_file_needs_no_swarm`, which builds a torrent from a local file with `create_torrent`, seeds the cache and the folder by hand, and asserts the served bytes plus `state == "paused"` — **fully offline**, so it runs in an ordinary `cargo test` and catches a reordering of `select` that would quietly start the swarm. What is *not* solved is the piece re-verification on every open: skipping that needs `fastresume`, which in librqbit 8.1.1 only works with `persistence` enabled — and that would resume torrents at startup, i.e. exactly the background BitTorrent client this app refuses to be.
- **A torrent arrives three ways, and a `.torrent` file is not a file the player opens.** A magnet is pasted, a `.torrent` URL is pasted, and a `.torrent` **file** is dropped or picked — and only the first two fit a box that takes text, which is why torrent support was invisible in a dialog called "Открыть ссылку". Three things make the file first-class. `AddTorrent::Url` understands `http:`, `https:` and `magnet:` **and nothing else** (a local path reaches it as "provided path is not a valid magnet URL"), so `add` reads the bytes itself and goes through `AddTorrent::from_bytes` — and since a `.torrent` file *is* the metadata, `librqbit::torrent_from_bytes` gives the info hash locally, which means the hash-named folder, the metadata cache and the history all work exactly as for a magnet. A `.torrent` URL is now the only source left with no hash to read. Classification happens **in `loadFiles`**, where a drop is already sorted by extension, rather than at each of the four entry points (drop, picker, argv, the Apple Event) — reached through an `openTorrentFile` hook, because player.svelte.ts must not know that a torrent client exists; and only when nothing else in the drop is playable, since a folder holding both a film and its `.torrent` should play the film. **What gets remembered is a magnet built from the hash, never the path** (`magnetFor` in source.ts): a `.torrent` file is thrown away after use and a tracker page can go down, while the info hash plus the metadata cache reopens the torrent with no lookup at all — so a file opened once keeps working after it is deleted. One consequence worth keeping in mind: `openTorrent` is now reached with **no dialog open**, so its failure path raises one, or a corrupt file would fail in complete silence. The file association is deliberately **not** declared in tauri.conf — claiming `.torrent` system-wide would take it from whatever BitTorrent client the machine has, which is not a video player's to do.
**A freshly added torrent is not ready to be touched, and the order of the three steps is load-bearing**: `add_torrent` returns while the torrent is still `Initializing` (checking and allocating files on disk, which scales with the size of the *torrent*, not of the file being watched), and in that state librqbit refuses `update_only_files` outright ("can't update initializing torrent") while `stream()` accepts only `Paused` or `Live`. So it is wait → select → unpause → wait again, with the lock dropped across each wait or every parallel connection ffmpeg opens serialises behind it. On Sintel (129 MB, one file) that window is too short to see; on a nine-episode 7.5 GB season it swallowed the whole of playback. It cost a diagnosis only because the handler answered a bare **404** for every failure, which reads as "no such file" — hence the reason is now logged and a not-ready answers **503**, since the two are different facts and a torrent that plays on small releases and dies on large ones is otherwise indistinguishable from a broken URL. Three things fell out for free because a stream is `http://127.0.0.1:…`: `isNetworkSource` already gated the storyboard (the collision the roadmap warned would be discovered late), the posters and the folder queue. What is **not** solved is the seek: a cold jump costs *downloading*, so the measured seek contract below does not apply, and there is no map of what is buffered — librqbit keeps the piece bitmap behind `pub(crate) with_chunk_tracker` and the finest public measure is `TorrentStats::file_progress`, a percentage. Measured against the live Sintel swarm (the analysis's spike #1, kept as `sintel_smoke`): magnet → file list **10.0 s**, first byte of a tail range **7.9 s**, a cold seek into the middle **1.3 s**, 13 peers at 664 KB/s. Which is why a torrent stall must say *why* — peers and rate under the label — since mpv's own answer is `paused-for-cache` and nothing more, and "no peers" and "slow swarm" are different problems that must not look the same.
- **Seeding is off by default, and the switch has to be able to stop it *now*.** In Germany and several other jurisdictions the exposure from uploading is categorically worse than from downloading, so a player must not opt anyone into it silently. The mechanism is librqbit's `disable-upload`, which is a **compile-time feature unlocking a runtime flag** — without the feature there is no way to stop seeding at all, since `LimitsConfig.upload_bps` is a `NonZeroU32` and cannot even express zero. What it does is thorough rather than a rate limit: no bitfield, no `have` messages (peers are never told what we hold), piece requests refused outright, peers dropped once the file is complete. What it does **not** do, and the settings hint says so, is make the client invisible — finding peers means announcing to trackers and the DHT, so membership of the swarm is still observable. The flag is baked into the session when it is built, so changing the preference **tears the session down and rebuilds it**, which costs the running torrent; that is the honest trade, because a switch reading "off" while pieces are still going out would be a lie about the one behaviour here with legal weight attached.
- **The torrent's folder is its info hash, and disk is the source of truth for storage.** `ManagedTorrentOptions.output_folder` is `pub(crate)`, so a folder named after the torrent could never be *read back* and the mapping from torrent to directory would have to be guessed — hence `output_folder` is set explicitly to `<cache>/torrents/<infohash>`, which also removes every question a torrent name raises as a path (length, `/`, two releases sharing one) and makes `torrent_forget` cheap to validate: a legal folder is exactly 40 hex characters. The hash comes from `Magnet::parse` (no network) rather than a `list_only` resolve, which would double a ten-second DHT lookup. `torrent_list` reads the directory and never consults our records, so a folder from a previous run or the older layout is still visible and deletable — storage management keeps working with history off, and the remembered magnets only add the ability to *reopen*. **Size must be measured in allocated blocks, not `len()`**: librqbit creates every file at full size up front and APFS/ext4 make them sparse, so a nine-episode season with one episode part-fetched reports **7.45 GB** by length and **142 MB** by blocks (verified against `du` to the byte). Reporting the length would tell the viewer to delete something to reclaim space that was never taken. Windows keeps `len()` — NTFS needs an explicit `FSCTL_SET_SPARSE` that librqbit never asks for. **"In the session" is not "playing right now", and `torrent_list` must not answer the second.** It used to: the row's `active` flag was session membership, and since `release` *pauses* rather than removes (the pieces stay, so re-opening continues), a torrent stayed in the session for the rest of the run — so returning to the start screen found its delete button disabled and labelled "сейчас проигрывается", permanently, from the moment anything had been watched. Deleting a merely-loaded torrent is safe anyway, because `forget` takes it out of the session *before* removing the directory. So the flag left Rust entirely and became `torrentIsPlaying(row)`, read from `parseTorrentUrl(player.filePath)` — **not** from `torrent.info`, which is set when a magnet resolves and would still claim to be playing after the file picker was cancelled — and it is a **function, not a field of the row**, because the list is fetched ~300 ms after the file is unloaded and a snapshot taken there is how a button gets stuck disabled.
- **A torrent entry in the watch history cannot be reopened from what it stores.** Its `src` is a loopback URL and the port died with the session that issued it, so every torrent card led to a refused connection after a restart — the problem `sourceId` solves for the *key* showing up again one layer higher, in the thing you actually open. `RecentItem` therefore carries `id` beside `path`, and `openRecent` sends anything `torrent:`-shaped through `resolveTorrentFile`, which re-resolves the remembered magnet. That store (`frameplayer.torrents`, privacy-gated like positions — a magnet names what is being watched) is also what puts a **torrent list on the start screen**, and the unit there is deliberately the *torrent*, not the file: the grid above already holds individual episodes with positions, while a torrent's never-started episodes have no representation anywhere else, so one row per torrent is how you get back into a season without the magnet rather than a duplicate of the grid. It is styled as compact rows rather than poster cards for the same reason — a second grid would compete with the first and turn the start screen into a download manager, which the roadmap is explicit this player is not. **Clicking a row resumes rather than asking**: the row already prints "продолжить: S01E03 — осталось 23:14", and dropping the same nine-name file picker a fresh magnet gets, to hunt for the episode you were already watching, is the player forgetting something it plainly knows. The picker is what happens when there is nothing to continue. Its resume point comes from `positionsLoad()` directly, **not** `history.recent`, which holds only the twelve newest entries across everything — a torrent watched last week has fallen out of that long before its data has fallen off the disk. The picker itself marks which files have positions (brighter name, "осталось X"), since a season is nine names differing by two characters. It carries no progress *bar*, and that was tried: a full-width rule under the name reads as an underline rather than a value — at 91% it is indistinguishable from a border and a list of them turns the panel into stripes. The card grid needs one only because a poster leaves no room for words.
- **A torrent stalling mid-playback used to be completely silent.** `opening` is raised in `beforeLoad` and cleared on `file-loaded`, so the loading overlay — the one thing that reports peers and rate — is gone by the time playback starts. A swarm that dries up at minute twelve then froze the picture with nothing on screen to explain it, which is the difference between "give it a moment" and "this player is broken". Hence `.torchip`, a small readout below the top bar: rate, peers and how much of *this file* is on disk. It sits **outside `.topbar`** so it can survive the UI going idle, exactly like the skip button sits outside `.osc` and for the same reason — idle is precisely when a stall happens. The rest of the time it fades with the chrome, so the picture stays clean; it is suppressed while `opening` is up (the overlay is already saying all of it) and once the file is fully fetched. Its sentence comes from the same `torrentLabel` the overlay uses rather than a second copy of the logic. It goes **top-right**, and the left is not merely a worse choice but a broken one: `.osd` — the popup every volume change, seek and speed change raises — is `top: 60px; left: 18px`, two pixels from where this first sat, so the next volume nudge covered it outright. A status readout that vanishes exactly when a hand is on the keyboard is worse than none. The right is free below the bar on both platforms: the window buttons and the macOS logo end at 48px, and the skip button is bottom-right.
- **A torrent cannot gain an episode, so replacing one is a first-class action.** The info hash covers the file list and every piece hash — verified by building two torrents from the same folder and adding a file, which changes it — so an uploader who adds an episode publishes a *different* torrent with a different magnet. Left alone that costs a whole season re-downloaded and its watch history reset, which for an airing series is the common case rather than an edge one. The fix is **a rename done before the new torrent is added** (`torrent_relocate`): the data lands in the folder the new hash will ask for, `overwrite: true` makes librqbit verify it, and `add` needs no changes at all. Crucially the "folder name is the info hash" invariant survives, which is what keeps deletion unambiguous — the thing qBittorrent gives up by sharing one save path, and why cross-seeding there needs manual `Force recheck` and third-party tools to avoid deleting a neighbour's files. **Positions are re-keyed by file name, not index**, since one inserted episode renumbers everything after it; the name comes out of the URL each record already stores, so no new store was needed and entries written before this still migrate. The link box also *detects* the case (`findSupersededTorrent`), because pasting the new magnet where links go is the obvious move and would otherwise silently start a second copy — matched by **token overlap** rather than a prefix, since "Серии: 1-9 из 9" → "1-10 из 10" changes digits in the middle of a forty-word title. What none of this does is **discovery**: the player cannot learn that episode 10 exists. That needs RSS with auto-download rules, which means polling feeds in the background — the resident BitTorrent client this app refuses to be.
- **The buffer map needed no fork of librqbit, and finding that out was the whole job.** `with_chunk_tracker` is `pub(crate)`, which reads as "patch required" — but `Api::api_dump_haves` is public and hands out the same bitmap, as a `format!("{:?}")` of a `BitSlice`, evidently for debugging. Measured, the string is `BitSlice<u8, …> { addr: 0x…, head: 000, bits: 10 } [1, 0, 1, 1, …]`; only the bracketed tail matters, taken with `rfind` because the header has brackets of its own. Undignified rather than fragile: the format is pinned by Cargo.lock, `parse_haves` is tested against the real string, and a parse failure costs the map and nothing else. `file_ranges` then intersects the pieces with the file's own byte span — **the first and last piece of a file are shared with its neighbours**, so without that intersection the bar would draw buffer belonging to another episode. If this ever needs to be done properly the upstream PR is ten lines (`have_pieces()`), and vendoring is the fallback: `[patch.crates-io]` with a local path, **636 KB and 76 files** for the crate itself — the roadmap's "1.5M SLoC" was the whole dependency tree, not the thing that would be forked. What the map buys is two things, and the seekbar bands matter more than the previews: they answer "will a jump land or wait", which is what a torrent's bar is actually read for.
- **Previews before a file is complete are per-position, not per-file.** `thumb_get(exact)` opens its own decode session, so single frames need no storyboard — but the background grid pass walks a file start to end and would decode straight through a hole, so it still waits for the whole file (`thumbs.partial` is the distinction). The gate lives inside `issueThumb` rather than at the call sites, so no future caller can skip it, and it is fractional because the map is of *bytes*: for a variable-bitrate file bytes and seconds are not proportional, hence `BUFFER_MARGIN` keeping requests off the edge of a band where the estimate is worst. Expect previews to appear where they are least wanted — you have downloaded what you already watched, not what you are about to jump to — with the redeeming case being that rewinding is the common gesture on a file still arriving, and the past is always there.
- **Three things a torrent gains once its file is on disk, and one it cannot.** A torrent routinely **ships its own subtitles** (Sintel carries ten) — `sub-auto` finds nothing, since there is no local file to look beside, so they sat unreachable while the viewer searched OpenSubtitles for what was already downloaded. `sub-add` takes a URL, so each is a request to our own server; matched by name (same stem, stem plus a language tag, or a subfolder named after the episode) because a season carries one set per episode and attaching all ninety would make the menu useless, and `auto` rather than `select` so `slang` still decides. **The next episode is prefetched** once the current file is complete — one ahead and no further, which is the line between "the season does not stop between entries" and a background client filling the disk with what may never be watched; "next" is `torrentVideos` order, not mpv's playlist, which may hold a folder or a drop of loose files. And **the seekbar storyboard works**, which the network gate used to forbid for good reason that no longer applies: the data is an ordinary file here, so decoding costs nothing. `torrent_local_path` answers **only for a complete file**, and that is load-bearing rather than cautious — the files are sparse, so a stretch that has not arrived reads back as *zeros* rather than failing, and a storyboard over one would be black frames and mush with nothing to say it went wrong. Since a file completes *during* playback, `maybeStartThumbs` had to become retryable (`startedFor` is set only when a storyboard actually starts) and the status poll calls it on completion. What stays off is **start-screen posters**: those are wanted when the torrent is not loaded, and completeness cannot be answered without the session.
- **A network source is not a file, and a surprising amount of the player assumes otherwise.** `isNetworkSource()` gates the three that matter: the thumbnail storyboard (it decodes the *whole* file in the background — over a stream that pulls the entire thing a second time, in an order unrelated to playback, while the player is trying to buffer), the folder queue (`folder_entries` would take a URL for a path), and "show in Finder" (nothing to show). Watch positions and remembered tracks work unchanged, since a URL is a perfectly good key. **yt-dlp is enabled explicitly** (`ytdl=yes`): the CLI turns the hook on by default, the manual is ambiguous about the client API, and a feature depending on which side of that line libmpv falls is not worth the saved line. Finding the binary is ours to do, because **a GUI process does not have the shell's PATH** — launched from Finder or Explorer it inherits the session's minimal environment, so a perfectly good `~/bin/yt-dlp` is invisible to mpv's own lookup. `ytdlp_path` probes the usual locations, *runs* the candidate (a file being present says nothing about it being runnable), hands mpv the absolute path through `ytdl_hook-ytdl_path` and puts its directory on PATH as well. Measured: the hook logs "No youtube-dl found … in config directories" — which is about mpv's config dir only — and then spawns exactly that absolute path. Expect the failure mode to be **staleness, not absence**: a September 2025 yt-dlp already fails on YouTube with "The page needs to be reloaded", so the error message names updating it rather than installing it.
- **File associations on macOS need UTIs, not extensions**: `bundle.fileAssociations[].contentTypes` → `LSItemContentTypes`. Without it only mp4/mov/avi worked, because modern LaunchServices matches by UTI and `CFBundleTypeExtensions` is a legacy fallback. `public.movie` is the supertype that covers formats declared by other apps (mkv); the explicit UTIs next to it are belt-and-braces. Tauri's association schema is `additionalProperties: false` — no comment keys.
- **Opening files ("Open with", associations)**: two delivery paths that must both work. Windows/Linux put the paths in `argv` (first launch) or route them through `tauri-plugin-single-instance` (already-running app); **macOS never puts them in `argv`** — Finder sends an Apple Event, surfaced as `RunEvent::Opened { urls }`, which is why `run()` is `.build(...)` + `.run(callback)` and not `.run(context)`. Both paths funnel into `deliver_files()`. **The event is a signal, not a transport**: the paths always go into a buffer first and the frontend fetches them with `take_pending_files` (argv is consumed once, via `argv_taken`). This matters because a single missed emit used to mean a silently lost file — the Apple Event lands long before `onMount`, mpv init takes hundreds of ms, and the webview may be inactive. There are therefore *two* independent triggers for draining: the event, and **window focus** — opening a file from Finder always activates the app, which makes focus a guaranteed backstop and is what fixed "opening a second file in an already-running player does nothing". `drainPendingFiles()` guards against re-entry so the two triggers cannot split one list between them.
- **Anything mpv keeps across a file change is a leak waiting to be noticed.** `video-rotate`, `video-aspect-override`, `panscan`, the A–B loop points and — measured — **`sub-delay` and `audio-delay`** all survive a `loadfile`, so a correction dialled in for one episode silently applies to the next. Every one of them is therefore given an explicit value on `file-loaded`: its own, or the default. The delays are stored per source in the track entry (the same store, because they answer the same question — how this file needs to be played — and outlive the position), and **never per folder**: a mux error belongs to one file, and applying one episode's correction to the next would be inventing a fault. The value written is read back from mpv rather than computed, since `nudgeDelay` uses `add` and mpv owns the result, and it is debounced because a delay is dialled in by repeated presses and only where it settles is worth keeping. Zero deletes the record instead of storing a zero, or resetting a delay would leave an entry behind for ever.
- **What a source *is* is not how the player reaches it.** Everything remembered about a video — position, chosen tracks, title — is filed under `sourceId()` (source.ts), not under the path. A path is a fine key for a file and a poor one for anything else: the same YouTube video arrives as `youtu.be/ID?si=<tracking>` from a share button and as `youtube.com/watch?v=ID` from the address bar, and a torrent stream (ROADMAP 21) is served from `http://127.0.0.1:<port>/…` where **the port changes every run**, so a key taken from the transport forgets the file every session. Local paths are their own identity, which is what makes this free: `sourceId('/a/b.mkv')` is `/a/b.mkv`, so every record ever written still reads and there is nothing to migrate. Records now carry `src` beside the key — the id answers "which video is this", `src` answers "how do I open it", and the two are only the same thing for local files. The resume snapshot deliberately keeps a path for that reason: it is not a lookup key. URL canonicalisation drops the fragment, lower-cases scheme and host but **not** the path (which is case-sensitive), removes tracking parameters and sorts the rest, and leaves `t`/`start`/`list` alone — dropping those would be a guess about what the viewer meant rather than a fact about the video. One consequence worth knowing: a network source gets **no folder scope** for remembered tracks, because a URL has no folder — taking one would put every video on a site into a single `youtube.com/watch` bucket deciding the dub for all of them.
- **A video's name is asked for only when it is not already free, and only from the site serving it.** mpv supplies `media-title` for anything that plays (yt-dlp resolves the page), so that is recorded into one cache keyed by `sourceId` and costs nothing. What it cannot cover is a link in the recents list that never played, or one whose title never arrived — there `oembed_title` asks **the provider's own oEmbed endpoint** (YouTube, Vimeo), never a third-party aggregator like noembed. The distinction is not fussiness: YouTube already knows you are watching the video because you are streaming it from them, while an aggregator learns it for the first time — the same objection that keeps subtitle search talking straight to OpenSubtitles. The cost is coverage, and it is the right trade because everything actually watched gets its name for free anyway. The lookup is skipped for private paths, runs one request at a time, and for the title bar waits a moment first to see whether mpv produces a title on its own.
- **The start screen shows the title the player showed, not the file name.** A path is written for sorting, not for reading, and for a link it is a video id with a tracking query attached — so `frameplayer.positions` carries the `media-title` mpv reported (the container's own metadata, or the name yt-dlp resolved) alongside the position. It is only ever overwritten by a real one: mpv reports `media-title` a beat after the file opens, and the null in between must not erase what an earlier viewing recorded. `displayName()` is the fallback for anything never watched long enough to be recorded — extension off, query and fragment off, dots to spaces *between non-space characters only*, so a name that already reads properly is left alone. It is also what the title bar falls back to, since mpv's `filename` for a shared YouTube link is `TfUP5fQcbCM?si=…`.
- **Start screen recents**: `RECENT_LIMIT` cards, candidates drawn from a pool 3× that size — a dead file (renamed, deleted, unplugged drive) is replaced by the next candidate rather than leaving a gap, and is *not* purged from the history, since an unplugged drive comes back and the record could not be rebuilt. **It is a rail, not a wrapping grid**, and that is a structural fix rather than a tuned number: a grid was the only part of the start screen that grew with its content, so once network entries stopped being dropped it went three rows deep and pushed the torrents section 220px below the fold at 1280x800 — measured, and a section nobody scrolls to may as well not exist. One row keeps the page a fixed height whatever the history holds. It needs **`justify-content: safe center`, never a bare `center`** — the same trap the start overlay already carries a note about: a centred flex container that overflows does so in *both* directions, and rendered with a bare `center` twelve cards began at the fifth with the first four unreachable off the left edge. The trackpad scrolls it with no work at all, because `.overlay` is in `WHEEL_SURFACES` and `onWheel` returns early there, handing wheel events straight to the browser. **The list is verified before it is published, and a missing poster is not evidence of a missing file.** It used to go on screen in full and then shed entries one at a time as `poster_frame` failed on them, which reads as the player briefly showing files that then vanish — a grid of black cards collapsing, including things renamed months ago. Worse, `poster_frame` opens a *path*, so it fails for every network source: a YouTube link or a torrent episode was dropped on that basis and could never stay in this list at all, which silently disabled resuming a torrent from a card. So existence is now settled up front by `paths_exist` (one batched `stat`, microseconds against a poster decode) for local files only — a URL does not rot the way a renamed file does — and the poster loop only decides whether there is a picture. A network entry keeps its place and shows the link mark, the same answer the end-of-file cards already give. The overlay scrolls, which needs two non-obvious things: `justify-content: safe center` (a centered flex container overflows in *both* directions, so the top of the content becomes unreachable — the scrollbar will not go there), and a wheel that scrolls rather than changing the volume, which is now one rule in `onWheel` (`WHEEL_SURFACES`) rather than a `stopPropagation` on each surface. The `::-webkit-scrollbar` rules in app.css are **universal, not opt-in** — Windows otherwise draws its native light-grey bar, which is wide and alien in a dark UI; declaring them also switches macOS off overlay scrollbars, so the two platforms stop diverging. They were a `.scrollable` class first, itself a replacement for a list of surface selectors, and both failed the same way: a surface that starts scrolling without anyone telling it to. The context-menu submenus inherited `overflow-y: auto` from the class they share with the menu and drew native bars on Windows — invisible on macOS, where the overlay bar is dark and nearly transparent. There is no page content here that should keep the platform's own bars, so the safe default is all of them. A horizontal bar also needs `height` — `width` alone styles the vertical one, which is why the horizontal bar came out two to three times thicker — and `::-webkit-scrollbar-corner` needs a colour of its own, or the square where the two bars meet stays the platform's white. Related and easy to miss: **setting one overflow axis computes the other from `visible` to `auto`**, so a menu that only ever scrolls vertically still raised a horizontal bar (and lost a row's height to it) whenever a row was a fraction of a pixel too wide — `overflow-x: hidden` is part of making something scroll vertically, not an extra. The start overlay starts at `top: 48px` (title-bar content height) so the bar does not run into the window buttons, and uses `scrollbar-gutter: stable both-edges` because its content is centred — a one-sided gutter shifts it off-centre relative to the title bar.
- **Start-screen layout must not depend on its own content.** `.overlay` is a `grid` with `place-items: center`, which sizes the column from content — so the recents grid was measured from the cards, and the cards changed as posters arrived, moving the whole page. `.overlay.start` overrides it to `flex` + `align-items: center` so widths flow container → children, plus `scrollbar-gutter: stable both-edges` (the scrollbar takes layout space on Windows). Its padding lives on the inner `.start-inner`, never on the scroll container itself: a scroll container's `padding-bottom` is not part of its scrollable area, so the bottom gap vanished exactly at the height where the content was flush but no scrollbar had appeared yet. Separately, `restoreGeometry()` must `settleLayout()` before `show()`: the resize reaches the webview asynchronously, so the window was being shown with the layout of its previous size — the giveaway is the title-bar logo sitting too far from the right edge, since that is outside the overlay entirely.
- **A remembered track is a description, not an id, and its scope is the folder.** Track ids are positions inside one file — the Russian dub that is #2 in episode 1 is routinely #3 in episode 2 — so a choice is stored as `{lang, title, codec, forced, index}` and resolved against whatever the next file turns out to have. Resolution is **scored, not compared for equality**, because not one of those fields is guaranteed: releases exist with languages and no titles, with titles and no languages ("Rus"/"Jap" as names), and with two same-language tracks separated only by codec. Language +100, title +60, codec +12, a forced/full mismatch −50 (a forced track carries alien dialogue, not the script — never a silent substitute), position +5 as a tiebreak only; below a floor of 60 nothing is applied at all and mpv's own `alang`/`slang` stands, which is the right answer for an episode that simply has no Russian dub. Language codes are normalised through a 639-2→639-1 table rather than compared by prefix, because `jpn` and `ja` share one letter. The choice is written to **two** scopes: the file (what was playing here) and its **folder** (what to look for next door) — a folder is what a season is and what the play queue is already built from, where a global memory would carry an anime's Japanese track onto an unrelated film. A better match may still arrive after the first one is applied (external subtitles land a beat after `file-loaded`), so the pending restore keeps the score it acted on and re-applies only on a strictly better candidate, until its deadline or a manual pick clears it. Entries written before this carried plain ids; they are still read, exact in the one file they came from.
- **Restoring on resume has two traps.** The chosen tracks live in `frameplayer.tracks`, separate from `frameplayer.positions` because those entries are *deleted* past 97 % and a dub choice should outlive finishing an episode; only explicit picks are recorded, since mirroring mpv's own auto-selection would freeze it against later `alang`/`slang` changes. Applying the choice cannot be a one-shot on `file-loaded`: external subtitles found by `sub-auto` appear a beat later and setting `sid` to an id that does not exist yet silently selects nothing — hence the `$effect` that waits for the track to show up, with a deadline so it cannot hijack a manual pick made in the meantime. Separately, a resume seek must carry the knob with it, and that takes **both** halves of the fraction. `seekOnResume` sets `seekValue` optimistically and holds it with `seekSettling` (exactly as a drag release does), because otherwise it stays at zero until mpv reports the new position — a second on a 4K file — and then jumps across the bar in full view. But the knob is drawn as `seekValue / duration`, and `duration` only arrives once mpv has opened the file, which is *after* the OSC is on screen — so fixing only the numerator still leaves a visible frame at the far left. `primeResume` therefore fills both from the history record (the same numbers the "resuming" popup prints) at `beforeLoad` time, and `barDuration` hands over to mpv's own the moment it has one. Display only: seek maths must keep using `player.duration`, since you cannot seek in a file whose length is still a guess.
- **Watch history & privacy**: a file enters the history only once playback passes `min(15 s, 5 % of duration)` and leaves it again past 97 % — the relative half of that floor is not optional, a flat 15 s made anything shorter than ~15.5 s permanently unrecordable (a 17 s clip had a two-second window between "not started" and "already finished"). Writes happen on pause, on file change, on unload, and every ~5 s from `resyncState`. The start screen lists unfinished videos from `frameplayer.positions` with posters from `poster_frame` (reads a ready frame out of the storyboard cache when there is one, decodes a single keyframe otherwise; deliberately a throwaway session so it does not reset the live `ThumbState`, and loaded one at a time rather than eight decoders at once). Privacy has to be enforced in **four** places or it leaks: `persistPosition`, `saveResumeSnapshot` (a plain-text snapshot that auto-restores after an update), the on-disk thumbnail cache, and `subs_search` — the last two live in Rust, hence `set_private_paths` and `thumb_service::is_private`. Four is today's count, not a property of the design: **every new path by which something about a file leaves this machine is another enforcement point**, and the check is easy to forget precisely because such a path is usually being added for an unrelated reason. Subtitle search was predicted as the fourth and duly became it — a file hash sent to OpenSubtitles names what is being watched as surely as a stored position does. Path matching is on a component boundary (`/Movies` must not swallow `/Movies2`) and case-insensitive, and it is mirrored in JS (`pathUnder`) and Rust (`path_under`) — change one, change the other. **Excluding a folder also erases what is already recorded for it**, and that is a correction rather than a refinement: filtering on read (which is all it used to do) left the entries in localStorage and the frames in the thumbnail cache, so the start screen was clean while the disk was not — and removing the folder from the list brought everything back, which is how the gap was found. `purgeFolder` clears every store keyed by a path (positions, both track scopes, titles, downloaded subtitles, the resume snapshot; `frameplayer.links` is exempt because a URL has no folder) and hands the thumbnails to Rust. The folder is added to the list **before** the purge runs, so a write racing it — the position timer fires every ~5 s — is already refused rather than landing behind the deletion. Purging thumbnails is what forced `CACHE_MAGIC` to v4: the cache file name is a hash of path + size + mtime, so without the source path *inside* the file an entry cannot be attributed to a folder at all. Entries in an older format are deleted too, since they cannot be attributed either and are unreadable to the current build anyway. Because this deletes data irreversibly, the settings hint says so before the folder picker opens. "History off" is a separate `all` flag, **not** a synthetic `/` root: roots get their trailing separators trimmed, so `/` collapses to an empty string and would match nothing.
- **The mini player is a window mode, and every other size mode has to know about it.** With `wid` embedding there is no true picture-in-picture to reach for — the video is a child view of our own window — so it is a small always-on-top window with the chrome out of the way, which is 80 % of the value out of parts that already existed. What it cost was the interactions, and each one is a trap someone would otherwise find later: **the minimum window size has to be lifted first** (`minWidth`/`minHeight` are 480×320 in tauri.conf and a smaller request is silently clamped — the window simply would not shrink, with nothing to say why), and put back on the way out; **geometry must not be captured while mini**, exactly as it is not while fullscreen or maximized, or the next launch opens a thumbnail in the corner; **fit-to-video stands down**, or the next file's aspect undoes a size the viewer chose; **always-on-top is owned by the mode** and the pref restored on exit; **fullscreen and mini each leave the other** on the way in; on macOS the mode also **floats over other applications' fullscreen spaces** (see below); on macOS the **traffic lights are hidden outright**, since in a 420 px window they sit on the picture; and going back to the start screen leaves mini, because the button that leaves it is drawn over the video. Dragging still works without the title bar: dragging the video area moves the window, which it already did — and the window is **magnetic** there (`snapMini`, on by default, in the window submenu): dragged within `SNAP_DIST` of a resting place it goes the rest of the way, to the same padded corner it opened in. Snapping and clamping answer different questions and both are needed — snapping owns the band near an edge, clamping owns everything outside the work area, since a mini window hanging off the screen has no title bar to grab it back by. The constraint that shapes it: **a native drag runs its own event loop and never says when it ends**, so "stopped moving for `SNAP_SETTLE_MS`" is the only signal there is, and the number is a compromise — long enough that a pause mid-drag rarely reaches it, short enough to read as the window settling rather than moving on its own later. The move itself is **animated from the frontend** — one `setPosition` per frame over `GLIDE_MS`, eased out, driven by elapsed time rather than a frame count so a slow round trip stretches the steps and not the animation. There is no animated `setPosition` to call instead, and a window that teleports reads as a glitch: the eye has nothing to attribute the new position to. Its exit button is **round**, and that is not a style choice — a rounded rectangle inset from the window's own rounded corner has to obey the concentric rule (inner radius = outer minus the gap), and the outer radius is not ours to know: macOS picks one, Windows 11 another, and either can change with the OS. A circle has no corner to disagree with, which is why the system's own corner controls are circles. Two things this cost that are worth stating on their own, because neither announces itself: **a window API the frontend has never called before needs its capability added** — `setMinSize` was not in `capabilities/default.json`, so the call *rejected*, and with the geometry work sitting behind a bare `catch {}` the feature entered mini chrome on a window that had not moved or resized at all. Hence the mode flag now flips **after** the geometry lands, and failures are logged: "P does nothing" is a far better bug than a mode that half-applied. And **hiding a grid item does not re-centre the rest** — `.controls` is `1fr auto 1fr`, so dropping the two side clusters left the remaining one auto-placed in the first column, i.e. the mini controls sat against the left edge; `justify-content` on a grid whose columns are `1fr` changes nothing.
- **Floating over another app's fullscreen is decided by the window's class, not by its level — and every plausible guess about it is wrong.** "Always on top" only lifts a window above the others *on its own space*, and a fullscreen app is a space of its own, so the mini player vanished exactly when a small player on top is wanted; it is the one thing a system PiP panel does that an always-on-top window does not. Everything below was measured with a probe app that put labelled windows in each configuration and screenshotted them over a fullscreen TextEdit, because three rounds of reasoning got it wrong first. **The level is irrelevant**: a plain `NSWindow` does not reach the space at floating (3), modal (8), main-menu (24), status (25), pop-up (101) *or* `CGShieldingWindowLevel`, which is above everything the system itself draws. **`CanJoinAllSpaces | FullScreenAuxiliary` is necessary but not sufficient** — every probe window had it. What decides it is **an `NSPanel` whose style mask carries `NonactivatingPanel`**, and it then works at level 3; either half alone fails (a plain window with the bit does not float, a panel without it does not float). Since the window is tao's `TaoWindow` and we never get to ask for a panel, it is **promoted in place with `object_setClass`** and put back on exit — verified in both directions over a fullscreen app. That is only sound because **`NSPanel` adds nothing to `NSWindow`** (measured: `class_getInstanceSize` 520 for both, zero own ivars), so only the method table changes; the size is re-checked at runtime anyway, and a future macOS that grew NSPanel would get a no-op rather than a corrupted window. Three consequences. `TaoWindow`'s overrides are gone while promoted — `canBecomeKeyWindow`/`canBecomeMainWindow` fall back to NSPanel's defaults (**key yes, main no**) and `sendEvent:` (tao's `movableByWindowBackground` drag) is not in use here anyway. **Nothing may call `set_focusable` while mini is on**: tao looks its `focusable` ivar up by name and NSPanel does not have it, so that panics inside tao rather than failing quietly. And `hidesOnDeactivate` must be forced off, because panels hide themselves when the app deactivates and switching to the fullscreen app *is* a deactivation. The restore has its own trap: **`FullScreenPrimary`, the flag that makes a window fullscreen-capable at all, shares an exclusivity group with `FullScreenAuxiliary`** (AppKit takes at most one from each group), so it comes off while mini is on and forgetting to put it back leaves `setFullscreen` silently doing nothing — hence the whole previous state is saved and written back verbatim rather than recomputed, and restored **first** on the way out, where the awaited window calls after it travel the same main-thread queue and act as a barrier for `toggleFullscreen`, which leaves mini on its way in. What this does *not* buy is corner tucking and pinch resize; those need the private `PIPViewController` route IINA takes, which would additionally mean reparenting mpv's `wid` view into a system panel — leaving gotcha 10's hole in our own window — and giving up the HTML overlay with it.
- **Placing a floating box is three rules, and they belong in one place.** Flip to the other side of the anchor when the preferred one has no room, shift along the other axis to stay inside, cap the size when the box is simply bigger than the space. `floating.ts` is those rules as two functions (`flipAxis`, `shiftAxis`) with unit-tested arithmetic; tooltips, the context menu and its submenu all placed themselves before, which is exactly why each of them was wrong in a different way. Floating UI would be this plus scroll containers, virtual anchors and auto-update — none of which exists here (one non-scrolling viewport, every anchor a real element), so the dependency buys nothing the 40 lines do not. Three findings are baked into the call sites. **A box laid out at `left: x` may only use the width to its right**, so a tooltip near the right edge wrapped to one word per line — and the measure-then-clamp pass that followed read the *wrapped* width and called it a fit, which is why it never recovered. The tip is therefore laid out at the window origin and moved with a `transform`, which happens after layout instead of deciding it. **A cap is not a clamp**: in the mini player the context menu is taller than the whole window, so no position shows all of it and it has to scroll — hence `max-height` from the placement's `room`. And **a panel must not be rendered inside a scroll container it is meant to escape.** The moment the context menu got a `max-height`, its submenus were cut off at its edge — only the sliver overlapping the menu's own box was left. `position: fixed` in viewport coordinates is supposed to be the escape, and it measures as one: a fixed box inside an `overflow: auto` parent lays out *and hit-tests* at full size in both engines (checked in headless Chrome and in a WKWebView harness built for this, since macOS is WebKit and Windows is Blink). It was still cut off on screen. Rather than argue with the screen, the submenus are now rendered as **siblings of the menu** instead of children of the item that opens them — nothing about the placement changed, since it was already in viewport coordinates, and the hover bridge is geometric so it did not care either. The parent still closes them on scroll: fixed panels do not travel with the content underneath. The general rule that came out of it: when a floating panel has to leave its parent's box, take it out of the parent, and keep `overflow` for things that are genuinely inside. Two more traps live in the same code. **There is no global `box-sizing` reset here**, so a `max-height` handed to a bordered, padded box applies to its *content* and the thing renders 14px taller than it was told — the menu ate the 8px margin it was meant to keep and ended up past the window edge, which reads as "the placement has no padding". And **a submenu needs a plan for having no room at all**: in the mini player the window is narrower than two menus side by side, and flipping to "the roomier side" then half-overlaps the parent, which reads as a menu growing out of its own middle and being clipped by it. When the chosen side cannot fit the box (`room < size`), it is placed *over* the parent and aligned to it instead — the drill-down every small-screen menu uses. **That changes how submenus open, not only where they land**, which is the half that is easy to miss: a submenu covering its parent must not open on *hover*, or the parent stops being usable — every pointer move across it lands on another submenu head, and it cannot even be scrolled, so reaching an item means aiming at the corners of the ones that are not submenus. Below `SIDE_BY_SIDE_MIN` (the two menus' widths plus their margins) hover is therefore inert, the parent is hidden behind the panel (`visibility`, so the placement can still measure it — which works only because the panel is no longer its descendant), and the panel carries a back row, since otherwise the only way out is closing the menu and opening it again.
- **The player's wheel gestures stop at the edge of any floating surface.** Vertical is volume and horizontal is a scrub, which is right over the video and wrong over a list — scrolling the queue was changing the volume. The rule lives once in `onWheel` (`WHEEL_SURFACES`, matched with `closest`), not as a `stopPropagation` per surface: that list is invisible until the one surface missing from it is found by hand, which is how the queue, the chapter list and the context menu all ended up missing. Ctrl+wheel still calls `preventDefault` everywhere, surface or not — without it the webview zooms the whole UI and there is no way back.
- **The HTML resize edges are Windows-only, and on macOS they were actively harmful.** `startResizeDragging` reaches `drag_resize_window`, which on macOS is a stub returning `NotSupported` — and Tauri discards the error (`let _ = ...`), so nothing anywhere reports that the call did nothing. The eight `.rz` strips are 5px wide, sit *inside* the window at `z-index: 50` and set their own `n-resize`/`e-resize` cursors, so on macOS they took the band AppKit uses for edge resizing and turned it into a dead zone that still looked live: the arrows appeared, the press was swallowed, and the window only resized when the pointer happened to land in the system's band **outside** the frame — which reads as "resizing works sometimes". They are needed on Windows, where the window is `decorations: false` and there are no system edges at all; on macOS the window is `Titled | Resizable` and AppKit handles edges and corners, including the outside band no DOM element can reach. General shape of the trap: a platform-stubbed API plus a discarded error means a control that is present, styled and inert.
- **Window prefs & the macOS menu bar**: settings live in `localStorage` (`frameplayer.window`: remember geometry / fit to video / always-on-top), restored **before** `show()` — restoring a visible window reads as a jump. `window_guard::clamp_to_visible_area` was written for this and was inert until now (the window was always `center: true`). Geometry is never captured while fullscreen or maximized, or it would restore as a monitor-sized window with no maximized flag. `fitWindowToVideo` must fix the **position** too, not just the size: a window grows from its top-left corner, so one near the right/bottom edge grows off-screen. Bounds come from `Monitor.workArea` (already excludes Dock and taskbar — the old `size * 0.95` guesswork was wrong in both directions), inset by `SCREEN_PADDING`. If the requested size fit, the window keeps its place and is only pulled back inside; if it had to shrink, the old position is meaningless and it is centred. The macOS menu (`macos_menu.rs`) owns no state: items emit their id to the frontend, which runs the *same* functions as the context menu, and `sync_window_menu` pushes checkmarks back. **Accelerator rule**: only Cmd-combinations may be used. A menu accelerator makes the OS swallow the key before the webview sees it, so any single-key accelerator would silently replace the `e.code` hotkey rather than complement it. **The menu bar is also load-bearing for text editing**: replacing Tauri's default menu removed its Edit submenu, and without those items AppKit never delivers ⌘V, ⌘X or ⌘A to a focused field — the link dialog simply could not be pasted into. The Edit menu is back, deliberately **without Copy**, because ⌘C is this player's "copy the current frame" and a menu item would swallow it; copying text works through the right-click menu instead, which is why `onContextMenu` and the dialog backdrops leave editable elements to the system rather than calling `preventDefault` on everything.
- **A link promises navigation; an action gets a button.** `.settings-link` is for "show mpv.conf in Finder" and nothing else. Destructive actions are `.btn-danger`, and secondary actions next to a `.primary` — "open a link", "install yt-dlp" — are `.btn-outline`: they open a dialog or download a binary, which is not navigating anywhere.
- **Hiding the cursor must trail the native button hide, never race it.** `set_buttons_visible` hides the traffic lights with `setHidden`, which asks AppKit for a title-bar relayout — and a relayout resets the window's cursor rectangles, putting the arrow back. With `cursor: none` applied at the same moment as `idle`, it was undone ~40 ms later, and with the pointer standing still nothing re-applied it (WebKit updates the cursor from mouse events), so it blinked once and stayed. The tell is that it looks like a windowed-only bug while nothing in the cursor code mentions fullscreen: in fullscreen `set_buttons_visible` returns early, so there is no relayout to undo it. Hence `CURSOR_HIDE_MS`, a margin covering the button timer, the command round-trip, the main-thread hop and the relayout. Only the hiding is delayed — showing the cursor again answers the pointer moving, where any lag is felt at once.
- **Hiding the cursor on idle has exactly one exception, and it is a corner, not a band.** `.player.nocursor` applies in windowed mode too — there is no fullscreen condition. The exception is the macOS traffic lights: hovering them stops the webview from receiving mousemove, so the cursor sticks there, the idle timer fires anyway, and hiding it would be wrong because the user is working with the native popup on the green button and we cannot see it. That exception was originally the whole 48 px band across the full width on both platforms, which reads in use as "the cursor never hides in a window" — the pointer lands in that band constantly after dragging the window or using the buttons, while in fullscreen it rarely does, so the behaviour looked like a windowed-vs-fullscreen difference that does not exist in the code. It is now `IS_MAC && y <= 48 && x <= 110`; Windows needs none of it, because the window buttons there are our own HTML and stop being hit-testable once the bar fades. Worth knowing when this comes up again: `cursor: none` cannot leak outside the window — it is a property of our document and only applies while the pointer is over our content, and re-entering the window fires mousemove, which restores it.
- **A `$derived` re-evaluates the moment it is read again, not at the end of the tick.** So an event handler must read the derived object it is acting on *once*, before it touches anything that derived depends on. The skip button got this wrong — `skipUsed = skipHint.from; seekChapter(skipHint.next.index)` — and the second read returned `null`, threw, and left a control that visibly disappeared (its block had already unmounted) while doing nothing at all. Verified against the real compiler and runtime rather than guessed: compile a runes module with `compileModule`, read a derived, mutate its dependency, read it again — it is already the new value. Destructure first (`const { from, next } = skipHint`) and the whole class of bug goes away. Worth knowing that the symptom is silent: the exception dies in the handler, so what the user sees is a button that vanishes on click.
- **State lives in `.svelte.ts` modules, not in a store library.** Runes work outside components, so a module exporting a class instance with `$state` fields *is* the store — with per-field reactivity a subscription-based store cannot match. Two rules: never export a `let` that gets reassigned (the importer gets a snapshot — use a class field or a getter function, as `osd()`/`locale()` do), and keep the dependency direction one-way (`history`/`window-prefs`/`zoom` → `player` → nothing). The page is where they meet: `initPlayer` takes hooks rather than the module reaching back into the page, because that observer callback used to be where every concern in the app collided. **A `$effect` is not a substitute** for the `property` hook: the seekbar guard (`!dragging && !seekSettling && …`) has to run *only* on a time-pos report, whereas an effect would also re-run when the guards themselves flip — which is precisely the "knob jumps back on release" bug the guard exists to prevent.
- **Splitting further**: the file is markup-light (~680 lines) and CSS-heavy. Extracting components means moving their CSS with them, and the one selector that crosses a would-be boundary is `.player.no-video .topbar::before`. The seekbar/scrub logic is the riskiest thing to move — its invariants are in architecture.md and no test covers them.
- **A hotkey is a row in a table, and three things move with it.** `ACTIONS` in [keys.svelte.ts](src/lib/keys.svelte.ts) is the only place a default binding is written; `onKeydown` normalises the event to a chord (`ctrl+alt+shift+meta+<code>`, modifiers in that fixed order so the string is comparable) and dispatches. Overrides go to `frameplayer.keys` **sparsely — only what the user changed**, so a default corrected in a later version still reaches anyone who has opened the editor. Three consequences that are not obvious until something breaks. **Modifier overloads had to become separate actions**: `KeyS` was `saveScreenshot(e.shiftKey)` and the arrows were three things each, which an editor cannot express — "rebind screenshot" would mean rebinding a key *and* a modifier convention. **`noRepeat` and `quiet` are fields of the action**, since "holding this must not re-fire it" and "this already raises a popup" are facts about what happens, not about which button was pressed; as key-code lists they silently followed the old key after a rebind. And **a bound chord now gets `preventDefault` unconditionally** — per-case was fine while `Ctrl+=` was always the audio delay, and wrong the moment a viewer can put anything there while it stays the webview's zoom. What the editor refuses is as load-bearing as what it accepts: bare 0–9 (one parameterised action across ten keys), Escape and Enter (contextual — they unwind dialogs and take whatever is being offered), and on macOS **every accelerator the menu bar owns**, because the system swallows those before the webview sees a keydown and the binding would look accepted and never fire (`MAC_MENU_ACCELERATORS`, kept in sync with `macos_menu.rs` by a note at each end). Recording runs a **capture-phase** listener on the window — the player's own handler is a bubble listener on that same window, so stopping propagation on the way down is what keeps recording a binding for "полный экран" from going fullscreen while recording it. Labels are **US-QWERTY on both platforms**: `navigator.keyboard.getLayoutMap()` would give the active layout's label (Я for `KeyZ`) but it is Blink-only with no WebKit implementation, so using it would make one build print different badges on Windows and macOS; mpv, IINA and VLC all print the US name. Twenty-two places used to spell a key out — twelve in markup and eight inside a translated sentence (`'Играть/пауза (пробел)'`, `'Звук (M)'`) — and all of them now read `hint()`. A translation carrying a key in its text is the regression to watch for, and the sweep that finds them is a grep for a parenthesised key name in [i18n.svelte.ts](src/lib/i18n.svelte.ts); the two remaining `(Esc)` are deliberate, since Esc is reserved and cannot move.
- **Localisation**: user-facing strings live only in `src/lib/i18n.svelte.ts` and reach the UI through `t('key')` / `t('key', { param })`. `t()` reads reactive state, so switching the language re-renders everything — including the `SETTINGS` array, which is `$derived` for exactly that reason. Two things do not follow that path and are easy to miss. **The macOS menu is built natively in Rust** (`macos_menu.rs`) and cannot reach the dictionary: it carries its own `EN`/`RU` tables, is built in English at startup, and the frontend corrects it from `onMount` via `set_menu_locale` — a new menu item means editing both tables. Rebuilding the menu also replaces the check-mark items, hence `MenuChecksState` behind a mutex (`manage` keeps the *first* value it is given) and a `Once` around `on_menu_event` (handlers stack, so re-registering would fire every action twice). **Platform wording gets separate keys** (`ctx.reveal_win`/`ctx.reveal_mac`, `set.hdr_off_win`/`set.hdr_off_mac`), never a branch inside one string — the two sentences differ by more than a word in at least one language. Note `t` is now a module-scope binding: don't shadow it with a loop variable.
- **The language of the interface and the language of the film are different questions, and conflating them was a bug with a name.** Every language choice in the player used to offer exactly two — `alang`/`slang` in the settings, and the subtitle-search filter — which was never a decision about languages: it was the *translation set* leaking into content preferences. There are two translations because there are two; what is being watched has nothing to do with that, and anyone with Japanese audio and Polish subtitles was simply not served. `languages.ts` is the fix and is **one table**: 639-1 code, the language named in itself, and the 639-2 spellings. Everything else is derived from it — `LANG_ALIASES` (which the remembered-track scoring uses to know `jpn` and `ja` are one language), `mpvLangValue`, `parseLangList`, `searchLanguages` — rather than kept as a second copy that drifts, which is exactly what the old alias map beside it had become. Four rules the code depends on. **Each language is named in itself**: someone hunting for Polish subtitles is looking for "Polski", and that also keeps 60-odd languages out of the `t()` dictionary, where they would be 120 strings saying the same thing and where the one entry a viewer needs is the one nobody translated. **A chosen language expands to all of its spellings, adjacent** — `--alang` is an ordered priority list, so `ja,jpn,en,eng` means "Japanese however it is tagged, else English", while grouping by spelling would let an `eng` track beat a `jpn` one. **The list is derived from the mpv.conf line, never stored beside it**, which is what makes a value someone typed by hand show up correctly and why nothing needed migrating: the two values this dialog used to write, `rus,ru` and `eng,en`, parse back to exactly `[ru]` and `[en]` (tested, along with the round trip, the B/T collapse `ger,deu,fre` → `[de, fr]`, and unknown tags being *kept* — the line is theirs and silently dropping an entry would change what mpv selects). And **search is ranked, not filtered in table order**: prefix-matching codes puts near-misses first — measured, typing `ru` matched Romanian ahead of Russian through its own `rum`. The control is a new `SettingDef` kind (`langs`) rather than a pill row, because `.segmented` picks one of a few *named* values and this is an ordered list drawn from sixty; chips carry the order, clicking one promotes it to preferred (order is priority, and without that the only way to change it is to remove everything above and re-add, which appends and therefore does not even work). The subtitle-search filter is those same preferences plus "любые", and it reads them from **mpv**, not from `settingsValues` — that map is filled when the settings dialog opens and is empty until then, so the filter would have depended on whether the viewer had been into settings this session.
- **"No subtitles in a language I am already hearing" is mpv's option, not ours, and its rule is not the obvious one.** `subs-with-matching-audio` — choices `no`/`forced`/`yes`, default **`yes`** on mpv 0.41 (read out of `options.c`, not assumed, which is why `null` is the "показывать" pill). Building this ourselves would mean reimplementing `select_default_track` and then fighting it *and* the remembered-track restore. Two things about the semantics, both from the source and both different from what one would design by hand. It gates on `mp_match_lang(langs, audio_lang)` — **the whole `slang` list against the selected audio track**, not the candidate subtitle's language — so with Russian audio and `slang=[ru,en]` the answer is *no subtitles at all*, not "skip Russian and fall through to English". That is the better rule: someone watching a Russian dub does not want English subtitles, they want none. And the consequence that follows from the same line, which the hint has to say out loud: because it tests the whole list, having `en` in your **subtitle** languages means an English-audio film gets no automatic subtitles either. That is what makes `forced` the sane middle rather than a curiosity — a forced track is alien dialogue and signage, exactly what you still want in a film you understand, and it matches what the track scoring already believes (`-50` for a forced/full mismatch). One more consequence worth knowing before it is reported as a bug: an external subtitle found by `sub-auto` is gated too, so with `no` a `.srt` sitting beside the video is not auto-selected when the audio matches. A subtitle downloaded through the OpenSubtitles panel is unaffected *that* session — `attachTrack` uses `sub-add … select`, which is an explicit pick — and only meets this rule on the next playthrough.
- **Focusing an input scrolls it into view, and that silently undoes whatever scrolling you just arranged.** The subtitle panel's sign-in form unfolds at the bottom of a box that already scrolls (`.settings` is `max-height: 100%; overflow-y: auto`), so opening it has to bring the form into view or the button reads as doing nothing. Scrolling there and *then* focusing the first field looks correct and is not: the browser's own scroll-on-focus runs afterwards, is instant where ours is smooth, and lands the field near the top — leaving the form's buttons under the fold, which is the half that mattered. `focus({ preventScroll: true })` is half the fix, and the scroll is aimed at the form with `scrollIntoView({ block: 'end' })` rather than at the container's `scrollHeight`, so it stays correct whatever else the panel is showing. The other half came from a WKWebView harness built against this exact structure, because two plausible causes had to be ruled out rather than argued about: **a nested scroll container is not the problem** (every API — `scrollIntoView`, `scrollTo`, `scrollTop`, smooth or instant — reaches the bottom of a `max-height` box), and **neither is the form being inserted on click** (it works with no waiting at all, `tick` or `requestAnimationFrame` notwithstanding). What does fail is the combination: with a `focus()` call nearby, a **smooth** scroll stops 710 px short of 717 — *and `preventScroll: true` does not save it*. So the scroll is instant, which lands exactly, and runs a second time on the next frame to cover the box still settling as the form unfolds. General rule: when a scroll "does nothing", suspect a focus call before suspecting the scroller.
- **A flex item does not shrink below its content unless told to.** `min-width: auto` is the default, so `overflow: hidden; text-overflow: ellipsis` on a label inside a flex row never gets the chance to fire: the row grows instead, and the panel around it grows a horizontal scrollbar. Every ellipsizing label in a flex row needs `min-width: 0` on itself *and* on each flex ancestor between it and the fixed-width box — in the queue that is the name, the row button and the row. **And all of that is worth nothing if the row is not actually a flex container**, which is how the queue spent a while with names running past the button and under the × with no way to read them. The button carries two classes, `.menu-item` (`display: block`) and `.chapter-item` (`display: flex`); they weigh exactly the same, so the winner was whichever came later in the file — and it was `block`. Measured in the compiled bundle rather than argued about: `display:flex` at byte 27352, `display:block` at 27753. With the parent not a flex container the `flex`/`min-width` pair is inert and the name stays an **inline** span, where `overflow: hidden` does not apply at all. Hence `.menu-item.chapter-item`: a rule that has to beat another is written to win rather than left to source order. Two traps around it worth naming. Reconstructing a panel's CSS by hand to test it is how this was missed twice — the harness had the two rules in the opposite order and "proved" the layout was fine; building the real bundle and feeding *that* into the harness is the only version of this test worth trusting. And the panel is positioned by its right edge with `left: auto`, so it grows leftwards without bound: a long name made it 972px wide inside a 700px window at `offsetLeft: -297`, clipped and unreachable. Menus therefore carry a `max-width` with a viewport term (`min(520px, calc(100vw - 48px))`), which is also what keeps them inside the mini player.
- **Reusing a class means beating it, and equal weight is decided by source order — this has now cost two bugs.** The queue rows lost `display: flex` to `.menu-item`'s `display: block` that way; the torrent list's delete button then lost `position: static` to `.card-forget`'s `position: absolute` the same way, and with no positioned ancestor in the row it flew to `top: 4px; right: 4px` of the overlay and sat under the title-bar logo — invisible as well, since `.card-forget` also carries `opacity: 0` until a `.card` is hovered. Both times the override was written as a bare second class of equal specificity, and both times the borrowed rule happened to sit later in the file. So: **write the winning selector** (`.menu-item.torrent-file`, `.card-forget.torrow-forget`), never a lone modifier class. Measure it in the **built bundle**, not a hand-written copy: `npm run build`, then read the rule offsets out of `build/_app/immutable/assets/*.css` — the compiled order is the thing that decides. The bug reproduces exactly by `sed`-ing the winning selector back down to one class in that same file and re-measuring in a browser, which is the cheapest possible proof that the diagnosis is right rather than plausible. **The same arithmetic decides a control's own hover against its container's**, and there source order does not save you: Svelte scopes a descendant selector as `.a.svelte-x .b:where(.svelte-x)` — the `:where()` is free, so `.row:hover .cross` weighs (0,4,0) against a bare `.cross:hover`'s (0,3,0) and the container wins. A three-strength control (resting / row hovered / itself hovered) therefore needs its top state written as `.row:hover .cross:hover`, or the glyph never reaches full strength under the pointer.
- **Animating `opacity` on a small glyph makes it twitch, and no amount of measuring geometry will find it.** The torrent list's delete cross was reported "jumping and coming back" on hover. Geometry was identical across rest / row-hover / cross-hover — same row height, same offset inside the row, to the hundredth of a pixel, measured both standalone and in the real page nesting with transitions disabled. Nothing in the box model moves. The cause is that taking a layer off full opacity makes the engine re-rasterise it and switch how it antialiases, which on a **1.4px stroke** is visible as a wobble; Chrome does not reproduce it, WKWebView does. So the three strengths (resting / row hovered / hovered) are **colour**, and `opacity` is pinned at 1 and never transitioned. Worth knowing generally: opacity is the wrong lever for a control that is always on screen — it is for things that appear and disappear, where the rasterisation switch is hidden by the fade itself.
- **The hover preview keeps the video's own aspect, not 16:9.** mpv reports `dwidth`/`dheight` — the size with the aspect already applied — the moment a file opens, so the box can be shaped correctly before any frame exists. It used to be a hardcoded `aspect-ratio: 16 / 9` on the placeholder, which meant the first real frame resized the whole popup: invisible on a 16:9 film and a jump on every hover for a 4:3 one, a phone clip, or a 2.39:1 scope transfer. Torrents merely made it obvious, since there the placeholder is on screen for much longer. The **crossfade layer** was the other half of that blink and a separate bug: `.thumb.fading` inherits `.thumb`'s `width` and 16:9 `aspect-ratio`, while the inline aspect that corrects them sits only on the in-flow frame — so on anything wider than 16:9 (a 1920x816 rip is ordinary) it computed 105px over an 80px box and overflowed onto the timestamp for the length of the fade. The tell was that arriving from an un-downloaded position never blinked: there is no outgoing frame there, so the element is never created. An overlay must take its size from the box it covers — `width/height: 100%` and **not** `auto`, because an `<img>` is a replaced element whose `auto` means its intrinsic size rather than the insets (measured: 484px), plus `box-sizing: border-box` or its own 2px border lands on top of the 100%. **And the shape must only ever move to a real value.** `dwidth`/`dheight` are observed with `none`, so mpv reports them *unavailable* whenever the VO reconfigures — which on a torrent is every stall for pieces. Read directly, the box fell back to 16:9 for those frames and snapped back, a visible blink while hovering; the swap of one frame for another was measured stable at 139px throughout, so the flicker was never the image. Same rule as `media-title`: a transient null must not erase what is already known. Related: a position of a torrent that has not downloaded gets a **distinct** state, not an empty box — the arrow the download readout already uses — because an empty outlined rectangle reads as a preview that broke rather than one that was never coming, which is the same mistake the end-of-file cards were fixed for.
- **Tooltips**: put `data-tip="..."` (+ matching `aria-label`) on any element — a delegated handler renders the custom tooltip. Don't use `title`. **A raw source string is not a tooltip** (`readableLink` in format.ts): a URL is percent-encoded, so a Cyrillic path arrives as a run of `%D0%B1` and the one thing meant to answer "which link is this" became the least readable text in the dialog; and a magnet is long not because it says a lot but because it carries a *tracker list*, which is how a client finds peers and not how a person tells two magnets apart. So trackers are dropped and what is left is the name and the hash — and deliberately **not** the row's own label, which is the name alone: a tooltip that repeats what it is pointing at is noise.
- **OSD**: `showOsd(text, icon)` with icons `info|volume|mute|speed|loop|zoom` — icon + value only, no progress bars.
- **Validation before finishing any task**: `npm run check` (0 errors) and, if Rust/config changed, `cargo check` (isolated target dir if dev is running). Run sidecar smoke tests when touching step_engine/thumb_service.
- **Releases**: `npm run set-version 0.21.0` (or `patch`/`minor`/`major`), then push to main. **Five files carry the version** — package.json, package-lock.json, tauri.conf.json, Cargo.toml, Cargo.lock — and they cannot be collapsed into one: `tauri.conf.json`'s `version` accepts a path to a package.json instead of a literal, but the release workflow reads that literal with `jq` to decide whether a push *is* a release, so making it indirect would leave the gate with nothing to compare; and Cargo cannot read a version out of JSON at all. So `scripts/set-version.mjs` writes them, with one anchored line per file rather than a JSON round-trip (which reformats tauri.conf.json's hand-written inline arrays — measured on the `endpoints` array) and with **every anchor required to match exactly once**, since a bump that silently skipped a file is the whole failure being prevented. Run with **no argument** it reports instead of writing and exits non-zero on disagreement: worth doing before a release, because this drift is invisible — `package-lock.json` had been sitting at **0.1.0** since the first commit, which is exactly what the script found on its first run. `src-tauri/tauri.conf.json` remains the authority: a `patch`/`minor`/`major` bump is measured from what *it* says, whatever the others have drifted to. CI needs repo secrets `TAURI_SIGNING_PRIVATE_KEY` (passwordless), `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_PUBLIC_URL` (= https://frameplayer-updates.risen.dev), and `FP_OPENSUBTITLES_KEY` — the OpenSubtitles *application* key, baked in with `option_env!` at build time. Two things about that one. It is not really a secret (it identifies the app, not the user, and cannot be hidden inside a desktop binary); what a leak costs is **availability**, since abuse gets it revoked and subtitle search then breaks for everyone at once — which is why `opensubtitles.rs` looks in `<app_data>/opensubtitles.key` *before* the compiled-in value, so a revoked key can be replaced without a release. **Nothing delivers that file yet**: today it is a manual escape hatch, and wiring it to the signed R2 channel next to `latest.json` is the piece still missing. And `option_env!` is read at compile time **without** registering a dependency on the variable, so `build.rs` carries `rerun-if-env-changed=FP_OPENSUBTITLES_KEY` — without it a warm target directory keeps baking in the previous key. An absent secret is not a build failure: the feature simply reports that this build has no key. Updater pubkey lives in tauri.conf.json.
- **Icon**: master is `src-tauri/icons/icon-master.svg` (viewfinder glyph, indigo #6366f1, ~3% inner margin, no tile); regenerate via resvg + `npm run tauri icon`. Keep the title-bar inline SVG in +page.svelte visually in sync (same glyph, rounded triangle).
- **Accent colors**: indigo `#6366f1` (fills) / `#818cf8` (hover/active/focus); white text on accent surfaces. Indigo means **one** thing — selected / on / primary / focused (`.segopt.sel`, `.tab.sel`, `.switch.on`, `.updbtn`, focus rings). Passive readouts stay white, like `.seekfill`: the OSD bar used to be indigo, which inverted the logic — the control you drag was white while the thing that merely reports a value wore the accent. The exception is `.card-progress`, indigo on purpose because it sits over arbitrary video frames where white would disappear. Floating surfaces come from one scale (`rgba(16,16,22,~0.96)`), not per-component values — **and that fill is half of the recipe**: it is also the start screen's own colour, so a surface without the hairline border beside it is invisible there, and one without the shadow is lost over a bright video frame. Taking the fill and leaving the rest is the mistake to watch for.
